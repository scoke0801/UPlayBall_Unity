# 구단주 경기 스프라이트 연결 검증

## 변경 내용

구단주 관전의 `MatchPlayVisualizer`와 선수 커리어의 `PlayResolutionPresenter`는 이미
`Resources/UI/SpriteMatch/AnimationCatalog`를 읽고 있었다. 실제 카탈로그가 비어 있어
`CanPresent`가 실패하고 상공 구장의 원형 표식으로 돌아가는 것이 원인이었다.

원본·알파 합성·Unity 합성을 검수한 9클립 70프레임을 경기용으로 등록한다.
확률 모델·경기 결과·공개 시점·세이브 구조는 변경하지 않는다.

## 리소스 검수와 보완

- 이전 내야 수비는 다음 행의 모자가 이전 셀에 끼어들고 일부 모자가 잘렸다. 동일 캐릭터를
  8프레임으로 재제작해 각 셀 내부에 포구·송구 자세가 모두 들어가도록 했다.
- 이전 포수는 오른손에 글러브를 끼고 있었다. 후면 구도에서 왼손 글러브·오른손 보호 자세로 재제작했다.
- 이전 주루는 같은 쪽 다리와 팔을 반복했다. 발 지지와 다리 교대가 구분되는 4프레임 시트를 재제작했다.
  실패한 8프레임 후보와 보정 전 시안은 경기 매니페스트에 넣지 않는다.
- 투구 시트의 분리 공 및 다음 행 잔여 조각, 외야수 첫 셀 하단의 다음 행 공 조각은
  기존 `objectMasks`로 제거한다. 원본 파일은 보존한다.
- 새 원본은 내장 Imagegen으로 생성했다. 프롬프트는 `generated-v5/*-prompt.txt`,
  실제 RGBA 프레임은 `Assets/04.Images/SpriteMatch/<Clip ID>/frame_*.png`에 보존한다.
  Source→Processed 정본은 `Tools/SpriteSheetPipeline/sprite_sheet_sources.json`이다.

## 런타임 보완

- 주루 클립 참조를 `Batter.HitToRun`에서 `Runner.Run`으로 수정하고 진행 구간에 맞춰 좌우 방향을 바꾼다.
  손잡이가 있는 투구·타격·수비 그림은 반전하지 않는다.
- 타자 주자가 홈을 떠나면 타석 그림을 숨기고 다음 투구에서 복원한다.
- 포수 대기 모션을 투구 시간에 맞춰 재생한다. 초기 연결 화면은 포수를 지나치게 줄여 사용자 검수에서 반려됐다.
  포수 배율을 0.82로 다시 맞추고 타자와 가까운 체격, 홈 뒤 위치를 확인했다.
- `FieldLayout.asset`에 마운드·외야·중앙 내야의 실제 구장 좌표를 저작한다.
  기존 초기 좌표에서는 외야수가 담장·관중석 쪽으로 올라가 있었다.
- 홈에서 외야로 이어지는 깊이 곡선에 따라 선수와 공을 함께 줄인다. 외야 최소 배율 0.06,
  곡선 지수 1.6, 공 기준 지름 8을 구장 에셋에 둔다.
- 볼·스트라이크·파울 및 송구 완료, 타석·이닝·경기 종료 뒤 외부 공을 숨긴다.
- `Contact` 자체에는 완성된 수비 데이터가 없으므로 세션이 같은 타석에서 찾은 확정 타구를
  재생 시간에도 사용한다. 뜬공을 기본 판정 시간으로 압축하던 연결을 수정했다.
- 타자 주자는 타석 위치에서 출발한다. 한 베이스당 0.9초 기준으로 다리 모션을 반복하고,
  베이스 도착 및 대기에는 별도 `Runner.Idle` 시트를 사용한다. 주자 배율은 0.86이다.
- 페어 타구의 팔로스루 뒤 타자 주자가 먼저 출발한다. 결과 공개 전에는 1루 도착 전까지만
  이동하며, HUD 갱신으로 이 위치를 초기화하지 않는다. 후속 진루·아웃은 같은 위치에서 이어진다.
  출발 시점과 선행 이동량은 `batterRunStartProgress`, `batterRunLeadProgress`로 저작한다.
- 최초 송구의 수신 야수가 확정 목적 베이스를 커버하고 글러브 접점으로 공을 받는다.
  수비 야수 자신이 목적 베이스를 커버하는 경우 자기 자신에게 송구하지 않는다.
  주자와 몸이 겹치지 않도록 수신 야수는 `baseReceiverOffset`만큼 베이스 안쪽에 선다.
- 병살 중계는 직전 포구 야수의 실제 위치에서 포구→손 이탈→송구를 재생한다.
  다음 수신 야수도 직전 위치에서 커버를 시작한다. 베이스 사이에서 공이 바로 생성되는 경로를 제거했다.
- `OwnerMatchRunnerRoute.Collect`가 같은 타구에 속한 기존 주자의 최초 진루·주자 아웃 경로를
  중복 없이 준비한다. 관전 세션은 이 조회에서 이벤트 공개 수나 HUD를 변경하지 않는다.
  주자들은 타구 비행과 다른 주자의 플레이 동안 함께 이동하고, 자기 사건 전에 베이스에 도착하지 않는다.
  태그업은 포구 뒤에 출발한다. 이동 중 HUD가 갱신돼도 원래 베이스로 돌아가지 않는다.

## 검증 범위

검증 로그와 원본 캡처는 `output/sprite-sheet-validation/`에 보존한다.
격리 Unity 프로젝트는 실제 프로젝트의 에셋과 GUID를 복사한 뒤 처리 결과를 두 번 가져온다.
현재 단계의 검증 결과:

- 재개 후 기본 필터 Unity EditMode 50/50 통과: 실제 카탈로그의 네 투타 조합, 투구 판정 뒤 공 종료,
  완성된 타구의 재생 시간, 송구 도착 뒤 공 종료, 달리기에서 대기 자세 전환 포함.
  기존 주자 3명의 동시 출발, HUD 갱신 뒤 위치 유지, 각 사건으로의 연결과 포구 전 태그업 금지도 포함한다.
- Import 두 번의 316파일 내용·GUID 동일, 검수 카탈로그 14클립 / 경기용 9클립.
- 동일 Seed 20260911의 실제 상세 시뮬레이션 954이벤트 일치. 이벤트 전체를
  `MatchPlayVisualizer`로 1·2·4배속 재생하고 타석·이닝·경기 종료의 공 비노출을 검사했다.
- `replay-GroundBall`, `replay-LineDrive`, `replay-FlyBall`, `replay-HomeRun`에 실제 사건의
  연속 PNG를 저장한다. 대응 GIF는 `build_motion_previews.py`로 생성한다.
- `replay-DoublePlay`는 같은 Seed의 실제 병살 사건을 별도로 저장한다. 재생 검증기는
  관전 세션과 동일한 `OwnerMatchPlaybackGroup`으로 Out·RunnerThrownOut을 묶는다.
- 신규 대기 시트의 크로마키 배경 알파 평균 0, 경계 녹색 우세 최댓값 8.

실제 이벤트 재생 검증기는 확정 사건과 표현기를 연결한다. 캡처 샘플에서 홈런을 포함해 각 타구 종류가 확인됐다.

### 중단 작업 재개 후 관전 세션 검증

`CaptureOwnerSession`으로 실제 `OwnerMatchSpectatorSession`과 관전 화면의 `UpdateGameCast`를
연결해 전체 사건을 재생했다. 이닝 점수표 정리의 `Destroy`가 EditMode에서 실패해 오류와
자식 객체가 누적되는 문제를 수정했다. Play Mode에서는 기존 지연 삭제를 유지하고,
EditMode에서만 `DestroyImmediate`를 사용한다. 수정 후 Visual 실행은 종료 코드 0이며
삭제 오류·C# 컴파일 오류·재생 예외가 없다. Unity 라이선스 초기 연결 오류 뒤 재연결과
기존 partial 클래스 가져오기 경고는 별도로 남아 있다.

| 관전 모드 | 배속 | 공개 사건 | 최종 점수 | 일시정지 |
| --- | --- | --- | --- | --- |
| 모든 순간 | 1 / 2 / 4 | 각각 954 | 각각 10:11 | 사건 수·재생 시간 정지 확인 |
| 중요 순간 | 1 / 2 / 4 | 각각 954 | 각각 10:11 | 사건 수·재생 시간 정지 확인 |
| 경기 결과 | 1 / 2 / 4 | 각각 954 | 각각 10:11 | 즉시 종료하므로 해당 없음 |

매 프레임 HUD 점수가 마지막 공개 사건과 같고, 선행 경로 조회가 HUD를 변경하지 않음을 검사한다.
종료 후 공식 BoxScore 점수 일치, 결과 패널·홈 복귀 버튼 표시를 검사한다.
결과는 `owner-session-replay.csv`, 실제 타격·종료 화면은 `owner-session-*.png`에 보존한다.
카메라의 투구→타격 확대→일반 타구/홈런 추적→다음 투구 복귀 경계와 동일 진행률 재호출의
위치 유지도 회귀 테스트로 검사한다.

이 검증은 격리 Unity **EditMode에서 관전 갱신 함수를 직접 호출**한다. 메인 프로젝트의 새 게임,
Unity `Update` 타이밍, 마우스·키보드·게임패드 입력 전체를 실행한 Play Mode 검증은 아니다.
확장 EditMode 실행 83건 중 82건이 통과했고, 실제 Identity 카탈로그가 필요한
`즉시결과는경기오디오상태를변경하지않는다` 1건은 격리 프로젝트에 해당 데이터가 없어 실패했다.
이 실패를 스프라이트 검증 통과에 포함하지 않는다.
기본 스프라이트 필터의 최종 재실행은 카메라 회귀 2건을 포함해 50/50 통과했다.
Python 파이프라인은 이번 재개에서 재검증하지 못했다. 현재 기본 Python 3.13과
기존 `python-deps`의 Pillow 3.11 바이너리가 맞지 않는다. 이전 Python 통과 기록과 구분한다.

기존 `UI_Scene_OwnerMatchSpectator`의 배치·스타일과 `AnimationCatalog`·`FieldLayout`을 재사용한다.
1280×720, 1920×1080, 2560×1440, 3440×1440의 투구·타격 캡처에서 경기장 비율과
구장/우측 정보 영역의 분리를 확인했다. 새로운 Skin·입력·포커스 흐름은 추가하지 않았다.
공용 셸을 포함한 전체 Safe Bounds 자동 검사나 키보드·게임패드 검증을 대체하지 않는다.
별도 발견 사항: 기존 결과 화면의 감독 판단 요약에 원시 판단·기준 수치가 노출된다.
스프라이트 적용 범위 밖이므로 변경하지 않았으며 프로젝트의 디버그 정보 비노출 지침에 맞춘 후속 정리가 필요하다.

관전 화면 캡처는 실제 `UI_Scene_OwnerMatchSpectator`가 만든 무대에 고정 투타 입력을 재생한
정적 합성이다. 네 해상도 배치 확인과 실제 경기용 카탈로그 로딩을 검증하지만,
메인 프로젝트의 새 게임 시작부터 경기 종료까지 전체 Play Mode를 검증했다는 의미는 아니다.
선수 커리어는 공통 카탈로그를 소비하지만 전체 커리어 흐름은 이번 작업의 실행 검증 대상이 아니다.

## 검수 보류 리소스

`Pitcher.FollowReady.R/L`, `Pitcher.Idle.Unreviewed`, `Batter.HitToRun`,
`Batter.HighlightReaction`의 5클립은 검수용에만 남긴다. 기본 투구는 완결된 Pitch 시트로 재생하며,
주루에는 새 전용 시트를 사용하므로 이 후보들은 경기 활성화에 필요하지 않다.
외야 시트는 포구·송구 준비까지만 포함한다. 손 이탈 사건이 없는 외야 송구 애니메이션은 생성하지 않는다.

## 다음 연출 검수

기본 체격·원근 보완을 전체 관전 품질의 최종 완료로 보지 않는다. 타자 주자의 선행 출발과
최초 송구의 수신 야수 연결은 반영했고 위치 연속성·베이스 커버 회귀를 통과했다.
병살 중계의 수신·송구 연결과 기존 루상 주자의 공식 경로 준비·동시 이동을 반영했다.
타격 카메라 전환과 관전 세션 전체 재생의 EditMode 검증을 마쳤다.
메인 프로젝트 Play Mode의 실제 입력·공용 셸 통합과 최종 아트 검수는 남아 있다.
사용자의 하이라이트 정의에 맞춰 모션 시트와 별개인 삽입 이미지 6종을 제작·연결했다.
최신 검증은 기본 필터 EditMode 74/74, 실제 경기에서 6종 발생, 4개 해상도 24개 합성이다.
제작·사건 매핑·검증 범위는 [하이라이트 적용 기록](highlight-insets-v1/README.md)을 따른다.

이 기록이 이전 `ImplementationReport.md` 및 `generated-v4/README.md`의
경기용 0클립·전체 미승인 설명보다 현재 연결 상태에 대해 우선한다.
