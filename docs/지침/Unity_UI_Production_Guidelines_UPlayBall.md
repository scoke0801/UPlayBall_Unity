# Unity UI 제작 지침 — UPlayBall

> 문서 버전: 1.1  
> 기준일: 2026-08-30  
> 대상: UI 기획자, UI 디자이너, Unity 클라이언트 개발자, AI 코딩 에이전트  
> 엔진 기준: Unity 6

---

## 0. 문서 목적

이 문서는 UPlayBall의 모든 화면을 **하나의 게임에서 제작된 일관된 UI**로 유지하기 위한 공통 제작 기준이다.

새 화면을 추가하거나 기존 화면을 수정할 때는 개별 화면의 완성도보다 다음 항목을 우선한다.

1. 전체 메뉴 구조와의 일관성
2. 정보 우선순위와 조작 흐름의 명확성
3. 마우스·키보드·게임패드에서 동일하게 사용할 수 있는 조작성
4. 해상도와 화면비가 달라져도 유지되는 가독성
5. 공통 컴포넌트 재사용과 유지보수성

본 문서에서 **필수**로 표시한 규칙은 임의로 변경하지 않는다. 변경이 필요하면 한 화면에서만 예외 처리하지 말고 공통 기준 자체를 먼저 개정한다.

## 1. 최우선 원칙

### 1.1 공통 셸을 화면마다 다시 설계하지 않는다

일반 메뉴 화면은 아래의 공통 구조를 유지한다.

```text
┌──────────────────────────────────────────────────────────────┐
│ 공통 상단 헤더                                               │
│ 로고 / 현재 시즌·날짜 / 보유 자원 / 알림 / 설정·도움말       │
├──────────────────────────────────────────────────────────────┤
│ 화면별 제목·상단 탭 또는 필터                                │
├───────────────┬──────────────────────────────────────────────┤
│ 선택형        │                                              │
│ 좌측 서브메뉴 │               메인 콘텐츠                    │
│ 또는 목록     │                                              │
├───────────────┴──────────────────────────────────────────────┤
│ 공통 하단 내비게이션                                         │
│ 홈 / 선수 / 성장 / 일정 / 리그 / 구단 / 기록 / 계약          │
└──────────────────────────────────────────────────────────────┘
```

- **상단 헤더, 하단 내비게이션, 콘텐츠 시작 위치를 화면마다 바꾸지 않는다.**
- 화면에 필요한 기능이 많아도 새로운 전역 메뉴를 임의로 추가하지 않는다.
- 화면별 기능은 상단 탭, 좌측 서브메뉴, 필터, 상세 패널 중 하나로 해결한다.
- 같은 수준의 메뉴를 어떤 화면에서는 탭, 다른 화면에서는 하단 버튼으로 표현하지 않는다.

### 1.2 메인 내비게이션 순서는 고정한다

아래 순서를 전 화면에서 동일하게 사용한다.

```text
홈 → 선수 → 성장 → 일정 → 리그 → 구단 → 기록 → 계약
```

필수 규칙:

- 메뉴 이름, 순서, 아이콘 의미를 화면마다 변경하지 않는다.
- 현재 화면은 파란색 선택 상태와 명확한 인디케이터로 표시한다.
- 선택 상태는 동시에 하나만 존재해야 한다.
- 비활성 메뉴는 숨기기보다 비활성 상태와 잠금 사유를 보여주는 방식을 우선한다.
- 계약 화면을 포함한 후속 추가 화면도 동일한 하단 내비게이션을 사용한다.

### 1.3 정보 구조를 시각 장식보다 우선한다

- 가장 중요한 정보와 주요 행동은 첫 화면에서 바로 식별되어야 한다.
- 동일한 의미의 정보는 동일한 위치와 표현을 사용한다.
- 데이터가 많다는 이유로 모든 수치를 같은 강조도로 표시하지 않는다.
- 한 화면의 대표 행동은 원칙적으로 하나만 강한 색으로 강조한다.
- 장식용 패널, 과도한 테두리, 의미 없는 그래프를 추가하지 않는다.

## 2. 적용 범위와 예외

### 2.1 본 지침을 그대로 적용하는 화면

- 홈
- 선수
- 성장
- 일정
- 리그
- 구단
- 기록
- 계약
- 설정
- 도움말
- 우편함·알림
- 시즌 결과 및 보상 확인
- 오프시즌 활동 선택

### 2.2 별도 레이아웃을 허용하는 화면

아래 화면은 플레이 집중을 위해 공통 셸 일부를 숨길 수 있다.

- 경기 진행 화면
- 경기 시작 연출
- 경기 결과 요약
- 튜토리얼 오버레이
- 전체 화면 팝업 또는 시네마틱 연출

단, 별도 레이아웃에서도 다음은 유지한다.

- 동일한 색상·폰트·아이콘 체계
- 동일한 버튼 상태 표현
- 동일한 확인·취소 입력 규칙
- 동일한 팝업과 툴팁 스타일
- 메뉴 복귀 시 이전 선택 위치 복원

## 3. Unity 구현 기술 원칙

### 3.1 기존 UI 기술을 우선한다

- 프로젝트에 이미 사용 중인 UI 프레임워크를 유지한다.
- 한 화면을 구현하기 위해 uGUI와 UI Toolkit을 임의로 혼합하지 않는다.
- 신규 기술 도입은 화면 단위 편의가 아니라 프로젝트 전체 유지보수성을 기준으로 판단한다.

### 3.2 런타임 UI 기본 기준

런타임 게임 UI가 uGUI 기반이라면 다음을 적용한다.

- 텍스트는 TextMeshPro를 사용한다.
- 화면 전체를 하나의 거대한 프리팹으로 만들지 않는다.
- 공통 셸, 화면, 팝업, 반복 컴포넌트를 분리한다.
- Canvas 수를 무분별하게 늘리지 않는다.
- 자주 변하는 영역과 정적인 영역은 Canvas 또는 갱신 범위를 분리한다.
- `LayoutGroup + ContentSizeFitter`의 순환 의존 구조를 만들지 않는다.
- 긴 목록은 오브젝트 풀링 또는 가상화 구조를 사용한다.

UI Toolkit 기반이라면 다음을 적용한다.

- 스타일 값은 USS 변수와 공통 클래스에 모은다.
- 화면별 USS에 동일 색상과 여백 값을 복제하지 않는다.
- 반복 목록은 `ListView` 등 가상화 가능한 컨트롤을 우선한다.
- 화면 로직과 VisualElement 생성 코드를 분리한다.

### 3.3 화면 로직과 게임 로직을 분리한다

UI는 다음 역할만 담당한다.

- 현재 상태를 표현한다.
- 사용자의 의도를 입력 이벤트로 전달한다.
- 로딩, 성공, 실패, 비활성 사유를 표시한다.

UI가 직접 수행하지 않아야 하는 역할:

- 계약 결과 계산
- 성장 확률 계산
- 리그 순위 계산
- 세이브 데이터 직접 수정
- 보상 지급
- 경기 시뮬레이션 실행 규칙 결정

계산과 상태 변경은 서비스·도메인 계층에서 수행하고, UI는 결과만 반영한다.

## 4. 해상도와 레이아웃 기준

### 4.1 기준 화면비

- 기본 화면비: **16:9**
- 디자인 마스터 권장: **2560 × 1440**
- 구현 검증 필수 해상도:
  - 1280 × 720
  - 1920 × 1080
  - 2560 × 1440
  - 3440 × 1440

프로젝트에 기존 CanvasScaler 기준값이 있으면 해당 값을 유지한다. 기준값이 없다면 1920 × 1080을 사용하고 2560 × 1440 시안과 동일한 비율로 스케일한다.

uGUI 권장값:

```text
UI Scale Mode: Scale With Screen Size
Screen Match Mode: Match Width Or Height
Match: 0.5
Reference Pixels Per Unit: 프로젝트 공통값 유지
```

### 4.2 앵커 규칙

- 상단 헤더는 상단 좌우에 고정한다.
- 하단 내비게이션은 하단 좌우에 고정한다.
- 메인 콘텐츠는 헤더와 하단 내비게이션 사이에서 확장한다.
- 우측 상세 패널은 우측 고정 너비 또는 전체 너비 대비 비율로 정의한다.
- 중앙 고정 좌표에만 의존하지 않는다.
- 해상도가 변해도 버튼과 텍스트가 화면 밖으로 밀려나지 않아야 한다.

### 4.3 울트라와이드 대응

- 16:9 콘텐츠를 단순 가로 확대하지 않는다.
- 헤더와 배경은 전체 너비까지 확장할 수 있다.
- 핵심 정보 영역은 최대 너비를 두고 중앙 정렬한다.
- 데이터 테이블은 추가 열을 노출할 수 있으나, 기본 정보 우선순위는 유지한다.
- 좌우 여백이 늘어났다는 이유로 패널 사이 간격을 과도하게 벌리지 않는다.

### 4.4 간격 체계

모든 간격은 4px 배수 체계를 사용한다.

| 토큰 | 값 | 용도 |
|---|---:|---|
| `Space-1` | 4 | 아이콘 내부 미세 간격 |
| `Space-2` | 8 | 텍스트와 아이콘 간격 |
| `Space-3` | 12 | 작은 컨트롤 내부 여백 |
| `Space-4` | 16 | 기본 패널 내부 여백 |
| `Space-6` | 24 | 카드·섹션 간격 |
| `Space-8` | 32 | 주요 영역 간격 |
| `Space-12` | 48 | 화면 단위 분리 |

임의의 13px, 19px, 27px 같은 값은 특별한 시각 보정 사유가 없으면 사용하지 않는다.

### 4.5 Layout Bounds / Content Safe Area — 필수

"화면 밖으로 밀려나지 않는다"만으로는 패널끼리의 침범, 콘텐츠가 장식 프레임 위로 올라가는 문제를 잡지 못한다. 모든 주요 Panel은 다음 두 영역을 분리한다.

```text
PanelRoot
│
├─ Skin                     ← Visual Bounds
│  ├─ Background
│  ├─ Frame
│  └─ Decoration
│
└─ ContentSafeRect          ← Content Safe Bounds
   ├─ HeaderSlot
   ├─ BodySlot
   └─ FooterSlot
```

- **Visual Bounds**: 프레임, 배경, 장식을 포함하는 전체 시각 영역. Skin은 PanelRoot 밖으로 조금 튀어나올 수 있다.
- **Content Safe Bounds**: 실제 텍스트, 버튼, 표, 카드가 배치되는 영역. 일반 UI 콘텐츠는 반드시 `ContentSafeRect`의 자식으로 배치하며, 이 영역을 절대 벗어나지 않는다.

금지:

- Panel 내부 콘텐츠가 ScreenRoot를 기준으로 Anchor를 잡는 것
- 형제 Panel을 기준으로 위치를 계산하는 것
- 음수 Margin을 사용해 다른 Panel 영역으로 콘텐츠를 밀어내는 것
- 버튼이나 텍스트를 장식 프레임 위에 배치하는 것
- Footer 버튼을 Panel 외곽선에 겹쳐 배치하는 것
- Scroll Content가 Viewport 외부로 렌더링되는 것
- 한 Panel의 Raycast 영역이 인접 Panel까지 침범하는 것

허용되는 Overflow는 다음으로 제한한다: Skin Decoration, Tooltip, Dropdown, Popup, Drag Preview, 명시적으로 정의된 Overlay. 일반 Text, Button, Table Row, Card, Progress Bar에는 Overflow를 허용하지 않는다.

동일 Layout Container에 속한 형제 Panel끼리 Visual Bounds 중첩은 원칙적으로 0px이어야 한다. 장식 프레임끼리 의도적으로 겹치는 디자인은 공통 Prefab에서만 정의하며, 화면 구현 코드에서 임의로 겹치게 만들지 않는다.

### 4.6 Screen 영역 소유권 (Slot 구조) — 필수

화면 전체에도 영역 소유권을 명시한다.

```text
Screen
├─ HeaderSlot             ← Header만 사용
│
├─ PageContentSlot
│  ├─ PageTitleSlot
│  └─ MainContentSlot
│
├─ BottomNavigationSlot   ← Bottom Nav만 사용
│
└─ OverlayRoot            ← Popup / Tooltip / Dropdown
```

- 화면별 UI는 `MainContentSlot` 밖에 직접 생성하지 않는다.
- 일반 화면 코드가 `HeaderSlot` 또는 `BottomNavigationSlot`의 RectTransform을 직접 변경하지 않는다.
- Popup, Tooltip, Dropdown 이외의 일반 콘텐츠를 `OverlayRoot`에 생성하지 않는다.
- Panel 내부 코드가 자신의 `PanelRoot`보다 상위 RectTransform을 기준으로 좌표를 계산하지 않는다.

### 4.7 Responsive Layout 우선순위 — 필수

공간이 부족할 때 해결 순서는 다음과 같다.

1. 불필요한 여백 축소
2. 보조 정보 접기 또는 상세 영역으로 이동
3. Layout Column 재배치
4. Scroll 적용
5. 표시 열 축소
6. 마지막 수단으로 컴포넌트 크기 조정

금지:

- 텍스트를 최소 가독성 이하로 축소하여 문제를 해결하는 것
- Panel끼리 겹치게 하여 문제를 해결하는 것
- Content Safe Bounds를 줄여 Skin 위에 콘텐츠를 배치하는 것

패널·셸의 최소/여백 수치는 프로젝트에서 승인된 프리팹을 기준으로 다음과 같은 공통 Metric으로 관리한다. 화면마다 `23`, `37`, `51` 같은 임의 값을 직접 정하지 않는다.

```text
Panel.MinWidth
Panel.MinHeight
Panel.ContentInsetLeft / Right / Top / Bottom
Shell.HeaderHeight
Shell.BottomNavHeight
Shell.PagePadding
Shell.PanelGap
```

## 5. 시각 디자인 시스템

### 5.1 기본 방향

UPlayBall의 공통 시각 방향은 다음과 같다.

- 짙은 네이비·블랙 기반 배경
- 블루 계열의 주요 선택·행동 강조
- 흰색 계열의 본문 텍스트
- 금색 계열의 희귀 보상·특수 계약·핵심 성과 강조
- 패널, 카드, 표, 차트 중심의 스포츠 대시보드형 레이아웃
- 장식보다 정보 구분과 빠른 비교를 우선

### 5.2 색상 토큰

아래 값은 공통 스타일 자산에서 관리하며, 개별 화면 코드에 직접 입력하지 않는다.

| 역할 | 토큰 | 기본 제안값 |
|---|---|---|
| 최하단 배경 | `Color.BgBase` | `#09111C` |
| 상위 배경 | `Color.BgRaised` | `#0F1A2A` |
| 패널 | `Color.Panel` | `#162438` |
| 선택 패널 | `Color.PanelSelected` | `#1B3453` |
| 경계선 | `Color.Border` | `#2A3B52` |
| 주요 블루 | `Color.Primary` | `#438FF5` |
| 주요 블루 Hover | `Color.PrimaryHover` | `#67A8FF` |
| 금색 강조 | `Color.AccentGold` | `#D6AA52` |
| 기본 텍스트 | `Color.TextPrimary` | `#F3F7FC` |
| 보조 텍스트 | `Color.TextSecondary` | `#AAB6C6` |
| 비활성 텍스트 | `Color.TextDisabled` | `#647186` |
| 성공 | `Color.Success` | `#52BD7A` |
| 경고 | `Color.Warning` | `#E2B657` |
| 위험·실패 | `Color.Danger` | `#E0646B` |
| 포커스 링 | `Color.Focus` | `#8CC2FF` |

필수 규칙:

- 색상만으로 상태를 구분하지 않는다.
- 성공·실패·경고에는 아이콘 또는 텍스트를 함께 제공한다.
- 금색은 일반 선택 상태에 사용하지 않는다.
- 주요 블루는 선택과 대표 행동에 사용한다.
- 한 화면에 강한 강조색을 과도하게 사용하지 않는다.

### 5.3 타이포그래피

- 한글 가독성이 검증된 프로젝트 공통 폰트를 사용한다.
- TMP Font Asset과 Fallback 체계를 공통 관리한다.
- 숫자 비교가 많은 화면은 숫자 폭이 안정적인 폰트 또는 Tabular Figure를 우선한다.
- 본문 전체를 굵게 처리하지 않는다.

2560 × 1440 디자인 기준 권장 크기:

| 역할 | 크기 | 굵기 |
|---|---:|---|
| 화면 제목 | 32–40 | Bold |
| 섹션 제목 | 26–32 | SemiBold |
| 핵심 수치 | 28–40 | Bold |
| 기본 본문 | 20–24 | Regular |
| 버튼·탭 | 20–24 | SemiBold |
| 표 본문 | 18–22 | Regular |
| 보조 설명 | 17–20 | Regular |

- 1080p 환산 시 보조 텍스트가 지나치게 작아지지 않도록 확인한다.
- 중요한 HUD·핵심 수치는 32px 수준의 체감 가독성을 우선한다.
- 줄 간격은 글자 크기의 1.25–1.4배를 권장한다.
- 말줄임표를 사용할 때는 툴팁 또는 상세 확인 경로를 제공한다.

### 5.4 패널과 카드

아래 수치는 **Skin 자산이 없는 순수 색상 패널**(단색 Image 기반, 5.5의 예외 항목)에만 적용한다. 승인된 UPlayBall Skin(금속 프레임, 모서리 절삭, 스티치 장식 등)이 있는 패널은 원본 Skin의 형태를 그대로 유지하며 아래 수치로 대체하지 않는다.

- 기본 패널 모서리 반경: 8–12px
- 작은 버튼·태그: 6–8px
- 팝업·대형 카드: 12–16px
- 테두리는 1px을 기본으로 한다.
- 모든 패널에 그림자를 넣지 않는다.
- 패널 계층은 배경 명도, 테두리, 간격으로 구분한다.
- 같은 단계의 카드에는 같은 패딩과 제목 위치를 사용한다.

### 5.5 UPlayBall UI Skin 적용 규칙 — 필수

UPlayBall의 공통 UI Skin은 선택적인 장식 요소가 아니다. 공통 Skin은 게임의 시각적 아이덴티티를 구성하는 필수 UI 자산으로 취급한다.

**Skin과 Theme의 구분**

Theme: 색상, 폰트, 텍스트 크기, 간격, 상태 색상 — 5.2, 5.3에서 정의한 토큰.

Skin: 패널 외곽 프레임, 패널 배경 Sprite, 버튼 프레임, 탭 프레임, Header/Footer 장식, 코너 장식, 선택 상태 Sprite, 야구 스티치 등 UPlayBall 고유 장식.

Theme 토큰을 사용했다는 이유만으로 Skin 사용을 생략할 수 없다. 색상·간격이 토큰과 일치해도 패널을 `Image + Color`만으로 구성했다면 규칙 위반이다.

**필수 규칙**

- 기존 프로젝트에 동일 역할의 Skin Prefab 또는 Sprite가 존재하는 경우 반드시 해당 자산을 재사용한다.
- Panel, Card, Button, Tab, Popup 등 시각적으로 Skin이 정의된 컴포넌트를 단순 `Image + Color` 조합으로 대체하지 않는다.
- 화면별 필요에 따라 크기가 달라지는 경우 다음 중 하나만 사용한다.
  1. 기존 Prefab의 RectTransform을 확장
  2. 승인된 Prefab Variant 제작
  3. 9-Slice가 허용된 Skin 사용
- 기존 Skin과 비슷한 형태를 코드에서 다시 그리거나 새로운 단색 사각형으로 대체하지 않는다.

**예외**

다음 요소는 단색 Image를 사용할 수 있다.

- 데이터 그래프
- Progress Bar 내부 Fill
- 구분선
- 투명 Hit Area
- Mask
- 전체 화면 배경
- Skin 내부의 기능성 강조 영역

예외 요소가 Panel/Card/Button의 외관을 대신해서는 안 된다.

**UPlayBall Skin 보호 규칙**

"장식을 최소화한다"(1.3, 5.1)는 규칙은 승인된 UPlayBall Skin을 제거하라는 의미가 아니다. 기존 프레임, 코너 형태, 스티치, 금속 장식은 Brand Shell에 해당하며 임의로 제거하거나 단순화하지 않는다. 이 규칙이 금지하는 것은 **새로운 장식을 임의로 추가하는 것**이지, 기존 승인된 Skin을 사용하는 것이 아니다.

## 6. 공통 화면 구성요소

### 6.1 상단 헤더

상단 헤더는 다음 정보를 공통 위치에 배치한다.

- 좌측: UPlayBall 로고 또는 현재 게임 모드
- 중앙 또는 우측: 시즌, 연도, 현재 일정 정보
- 우측: 보유금, 주요 자원, 알림, 설정, 도움말

규칙:

- 현재 화면 제목을 로고 위치에 덮어쓰지 않는다.
- 보유금과 시즌 정보의 위치를 화면마다 이동하지 않는다.
- 자원 수치는 단위와 자릿수 표기를 통일한다.
- 설정과 도움말 아이콘은 동일한 위치와 크기를 유지한다.

### 6.2 하단 내비게이션

각 메뉴 항목은 다음 상태를 가져야 한다.

- Normal
- Hover
- Pressed
- Selected
- Focused
- Disabled
- Locked

선택 표현은 최소 두 가지를 함께 사용한다.

- 배경 또는 아이콘 색상 변화
- 하단 바, 외곽선, 점, 라벨 굵기 중 하나

Hover와 Selected가 같은 표현이 되지 않도록 한다.

### 6.3 상단 탭

- 같은 화면 안에서 동등한 데이터 집합을 전환할 때 사용한다.
- 탭 개수는 가급적 2–6개로 제한한다.
- 7개 이상이면 좌측 서브메뉴, 드롭다운 또는 그룹화 구조를 검토한다.
- 현재 탭은 명확하게 표시하며, 탭 전환 후 선택한 필터 상태를 가능한 범위에서 유지한다.

### 6.4 좌측 서브메뉴 또는 마스터 목록

다음 상황에서 사용한다.

- 선수 목록 → 선수 상세
- 팀 목록 → 팀 상세
- 성장 카테고리 → 세부 성장 항목
- 계약 대상 목록 → 계약 상세

규칙:

- 좌측 항목을 선택하면 우측 상세가 갱신된다.
- 상세 화면으로 진입하면서 공통 하단 내비게이션을 숨기지 않는다.
- 선택 항목은 스크롤 후에도 유지되어야 한다.
- 목록으로 돌아왔을 때 이전 스크롤 위치와 포커스를 복원한다.

### 6.5 버튼

버튼 계층은 세 종류로 제한한다.

1. **Primary**: 화면의 대표 행동
2. **Secondary**: 보조 행동
3. **Tertiary/Ghost**: 취소, 닫기, 세부 기능

규칙:

- Primary 버튼을 한 화면에 여러 개 남발하지 않는다.
- 위험 행동은 Danger 스타일과 확인 팝업을 사용한다.
- 비활성 버튼에는 비활성 사유를 툴팁이나 설명으로 제공한다.
- 아이콘만 있는 버튼은 접근 가능한 라벨과 툴팁을 제공한다.
- 클릭 영역은 시각적 아이콘보다 충분히 크게 설정한다.

권장 최소 크기:

```text
마우스 중심 버튼: 높이 44px 이상
게임패드 주요 버튼: 높이 52px 이상
아이콘 버튼 클릭 영역: 44 × 44px 이상
```

### 6.6 표와 데이터 목록

기록, 리그, 구단, 성장 화면은 표 사용 빈도가 높으므로 다음을 지킨다.

- 열 제목과 데이터 정렬 기준을 통일한다.
- 문자열은 좌측, 수치는 우측, 짧은 상태값은 중앙 정렬을 기본으로 한다.
- 정렬 가능한 열에는 정렬 방향을 표시한다.
- 선택 행은 파란색 계열로 강조한다.
- Hover와 Selected를 구분한다.
- 홀수·짝수 행 배경 차이는 매우 약하게 적용한다.
- 중요한 수치 변화는 색상뿐 아니라 `+`, `-`, 화살표를 함께 사용한다.
- 너무 많은 열을 한 화면에 강제로 표시하지 않는다.
- 상세 수치는 우측 상세 패널이나 툴팁으로 분리한다.

### 6.7 필터·검색·드롭다운

- 시즌 선택, 포지션, 리그, 팀, 기록 종류는 화면 상단의 동일한 필터 바 패턴을 사용한다.
- 필터 적용 여부를 한눈에 알 수 있어야 한다.
- 전체 초기화 기능은 필터가 실제로 적용된 경우에만 강조한다.
- 검색 결과가 없으면 빈 화면이 아니라 검색어와 초기화 행동을 보여준다.
- 드롭다운은 화면 끝에서 잘리지 않도록 위·아래 열림 방향을 자동 판단한다.

### 6.8 팝업

팝업 종류:

- 정보 확인
- 선택 확인
- 위험 행동 확인
- 보상 획득
- 오류·실패

규칙:

- 팝업 위에 팝업을 연속으로 쌓지 않는다.
- 확인과 취소 버튼의 위치를 프로젝트 전체에서 통일한다.
- 기본 포커스는 안전한 행동에 둔다.
- 위험 행동은 길게 누르기 또는 2차 확인이 필요한지 검토한다.
- 팝업을 닫으면 팝업을 연 버튼으로 포커스를 복원한다.

### 6.9 로딩·빈 상태·오류 상태

모든 데이터 화면은 아래 상태를 반드시 정의한다.

```text
Loading
Loaded
Empty
Error
Locked
Offline 또는 데이터 없음
```

- 로딩 중 빈 패널만 노출하지 않는다.
- 0건과 로딩 중을 같은 화면으로 처리하지 않는다.
- 오류 메시지는 원인, 영향, 재시도 행동을 포함한다.
- 잠금 상태는 해제 조건을 표시한다.

## 7. 화면별 고정 구조

| 화면 | 핵심 목적 | 권장 구조 | 구조상 금지 사항 |
|---|---|---|---|
| 홈 | 현재 시즌 상태와 다음 행동 확인 | 요약 카드 + 다음 경기/일정 + 주요 알림 | 홈에서만 별도 전역 메뉴 사용 |
| 선수 | 보유 선수 탐색과 상세 확인 | 좌측 선수 목록 + 중앙/우측 상세 + 상단 필터 | 선수 상세 진입 시 하단 메뉴 제거 |
| 성장 | 성장 계획과 장착·구매 관리 | 성장 카테고리 + 현재 상태 + 선택 결과 미리보기 | 성장 자원과 비용을 화면마다 다른 위치에 표시 |
| 일정 | 시즌 진행과 경기 진입 | 달력 또는 일정 목록 + 선택 경기 상세 | 홈과 다른 경기 시작 버튼 규칙 사용 |
| 리그 | 순위, 대진, 리그 현황 | 상단 시즌 필터 + 순위표 + 팀 상세 | 표마다 다른 선택색 사용 |
| 구단 | 구단 정보와 운영 현황 | 구단 요약 + 재정/시설/구성 세부 탭 | 구단 화면만 별도 헤더 사용 |
| 기록 | 선수·팀·시즌 기록 비교 | 기록 종류 탭 + 필터 + 정렬 표 + 상세 | 핵심 열을 아이콘만으로 표현 |
| 계약 | 계약 대상, 조건, 협상 결과 확인 | 대상 목록 + 계약 상세 + 조건 비교 + 대표 행동 | 계약 화면만 전역 메뉴 순서·구성 변경 |

### 7.1 계약 화면 추가 규칙

계약 화면은 다른 시스템과 분리된 별도 앱처럼 보이지 않아야 한다.

필수 구성:

- 공통 상단 헤더
- 공통 하단 내비게이션
- 계약 대상 목록 또는 현재 계약 상태
- 연봉·계약금·기간·옵션·보너스의 비교 영역
- 변경 전·후 조건 비교
- 계약 가능 여부와 불가 사유
- 대표 행동 버튼 하나
- 결과 확인 팝업 또는 결과 화면

금지:

- 계약 화면에만 새로운 색상 테마 적용
- 공통 메뉴를 좌측 세로 메뉴로 임의 변경
- 계약금과 보유금을 서로 다른 단위로 표시
- 계약 확정 전에 총비용을 숨김
- 실패 사유 없이 버튼만 비활성화

## 8. 경기 화면 UI 원칙

초기 경기 화면은 2D 야구장, 선수 아이콘, 공 이동, 타구 궤적, 주자 이동, 간단한 이펙트를 중심으로 한다.

### 8.1 기본 정보 우선순위

1. 현재 이닝과 공수 상태
2. 점수
3. 볼·스트라이크·아웃
4. 주자 상태
5. 현재 투수와 타자
6. 경기 로그 또는 주요 사건
7. 진행 속도와 일시정지

### 8.2 경기 중 조작

- 경기 진행 속도는 현재 상태가 명확히 보여야 한다.
- 자동 진행과 수동 선택의 경계를 분명히 한다.
- 중요한 선택이 발생하면 진행을 일시 정지하거나 충분한 입력 시간을 제공한다.
- 경기 로그는 최신 사건이 쉽게 식별되어야 한다.
- 득점, 홈런, 교체, 부상 등 주요 사건은 동일한 연출 규칙을 사용한다.
- 경기 종료 후에는 즉시 결과 화면으로 전환하지 말고 종료 상태를 짧게 확인시킨다.

### 8.3 경기 화면에서 금지할 것

- 실제 경기 정보보다 큰 장식용 캐릭터 일러스트
- 공·주자 위치를 가리는 과도한 이펙트
- 결과에 영향을 주지 않는 선택지 남발
- 진행 속도 변경 상태를 숨기는 표현
- 메뉴마다 다른 확인·취소 입력

## 9. 입력과 포커스 내비게이션

### 9.1 지원 입력

- 마우스
- 키보드
- 게임패드

세 입력 방식 중 하나에서만 가능한 기능을 만들지 않는다.

### 9.2 포커스 규칙

- 화면이 열리면 의미 있는 첫 항목에 포커스를 둔다.
- 팝업이 열리면 포커스가 팝업 밖으로 빠져나가지 않아야 한다.
- 팝업을 닫으면 이전 포커스로 복원한다.
- 탭 전환 후 첫 항목 또는 이전 선택 항목으로 포커스를 이동한다.
- 스크롤 목록의 포커스 이동 시 선택 항목이 화면 안에 보이도록 자동 스크롤한다.
- 비활성 요소는 포커스 대상에서 제외한다.
- 방향키 이동은 화면의 실제 시각 방향과 일치해야 한다.

### 9.3 게임패드 버튼 규칙

프로젝트의 Input Action을 기준으로 아래 의미를 통일한다.

```text
Submit  : 선택·확인
Cancel  : 뒤로·닫기
TabLeft : 이전 탭
TabRight: 다음 탭
Menu    : 메뉴 또는 설정
```

- 화면 하단 또는 버튼 내부에 현재 입력 장치에 맞는 프롬프트를 표시한다.
- 키보드와 게임패드 프롬프트를 동시에 무분별하게 표시하지 않는다.
- 마지막 입력 장치를 감지해 프롬프트를 전환한다.
- 버튼 프롬프트와 실제 Input Action을 코드에 중복 하드코딩하지 않는다.

### 9.4 뒤로 가기 규칙

뒤로 입력은 다음 우선순위를 따른다.

1. 열린 툴팁·드롭다운 닫기
2. 팝업 닫기
3. 상세 패널에서 목록으로 복귀
4. 하위 화면에서 이전 화면으로 복귀
5. 최상위 메뉴에서 종료 또는 메인 메뉴 확인 팝업

한 번의 뒤로 입력으로 여러 단계를 동시에 닫지 않는다.

## 10. 애니메이션과 피드백

### 10.1 기본 전환 시간

| 용도 | 권장 시간 |
|---|---:|
| Hover·Pressed | 80–120ms |
| 탭·패널 전환 | 140–200ms |
| 팝업 등장·퇴장 | 160–220ms |
| 숫자 카운트·보상 강조 | 300–600ms |

- 일반 메뉴 전환에 긴 페이드나 과도한 확대 연출을 사용하지 않는다.
- 입력 가능한 시점과 애니메이션 종료 시점이 불필요하게 묶이지 않도록 한다.
- 반복적으로 사용하는 화면은 애니메이션이 피로를 주지 않아야 한다.

uGUI에서 트윈이 필요하면 프로젝트 공통 방식에 맞춰 DOTween 기반 `RectTransform + CanvasGroup + Sequence` 조합을 우선한다.

### 10.2 권장 애니메이션

- 패널: 8–20px 이동 + 짧은 페이드
- 팝업: 0.96 → 1.0 스케일 + 페이드
- 탭: 선택 바 이동 또는 배경 전환
- 수치 변경: 짧은 숫자 보간과 변화 방향 표시
- 오류: 과도하지 않은 짧은 흔들림과 오류 문구

금지:

- 모든 버튼의 강한 바운스
- 화면 전체의 반복 펄스
- 목적 없는 파티클
- 정보 확인을 방해하는 긴 전환
- 애니메이션 중 입력을 무조건 차단하는 구현

### 10.3 UI 사운드

UPlayBall의 UI 효과음은 별도 정책이 추가되기 전까지 SFX 하위로 관리한다.

AudioMixer 노출 파라미터:

```text
MasterVolume
BGMVolume
SFXVolume
VoiceVolume
```

UI 사운드 종류:

- Hover 또는 포커스 이동
- Confirm
- Cancel
- Tab 전환
- Error
- Reward
- Important Notification

같은 행동에는 같은 사운드를 사용하며, 포커스 이동 소리는 빠른 연속 입력에서 과도하게 겹치지 않도록 제한한다.

기존 프로젝트 구조가 있으면 위 구조로 강제 이동하지 말고, 역할 분리 원칙만 적용한다.

### 11.2 명명 규칙

예시:

```text
Screen_Home
Screen_PlayerList
Screen_Contract
Panel_PlayerSummary
Panel_ContractTerms
Popup_ContractConfirm

```

코드 예시:

```text

```

규칙:

- `UI`, `Manager`, `Controller` 같은 포괄적 단어만으로 이름을 만들지 않는다.
- 역할과 대상이 이름에서 드러나야 한다.
- 동일 개념에 Player, Athlete, Character를 혼용하지 않는다.
- Prefab 이름과 컴포넌트 이름의 대상 용어를 일치시킨다.

### 11.3 화면 생명주기

화면은 최소한 아래 단계를 명시적으로 관리한다.

```text
Initialize  : 참조 연결과 1회 설정
Bind        : 데이터 및 이벤트 연결
Show        : 화면 표시와 포커스 설정
Refresh     : 상태 갱신
Hide        : 화면 숨김
Unbind      : 이벤트 해제
Dispose     : 필요 시 자원 정리
```

- `OnEnable`에서 이벤트를 중복 구독하지 않는다.
- 화면을 다시 열 때 이전 이벤트가 남지 않아야 한다.
- 전체 화면을 재생성하지 않고 필요한 데이터만 갱신한다.
- 표시 중인 화면이 아닌데도 매 프레임 갱신하지 않는다.

### 11.4 공통 컴포넌트 우선

새 화면을 만들기 전에 다음 공통 컴포넌트가 존재하는지 확인한다.

- Primary/Secondary/Ghost 버튼
- 아이콘 버튼
- 탭
- 드롭다운
- 필터 칩
- 검색창
- 데이터 행
- 정보 카드
- 선수 카드
- 상태 배지
- 툴팁
- 확인 팝업
- 토스트
- 로딩 인디케이터
- 빈 상태 패널

기존 컴포넌트가 요구사항의 80% 이상을 충족하면 새로 복제하지 말고 확장한다. **Skin이 존재하는 컴포넌트는 새로운 시각 컴포넌트를 제작하지 않는다** — 5.5 Skin 적용 규칙을 따른다.

### 11.5 금지 구현

- 화면마다 색상값 직접 입력
- 화면마다 동일 버튼 프리팹 복제
- `GameObject.Find` 또는 문자열 경로 기반 탐색 남용
- `Resources.Load`에 의존한 임의 UI 로딩
- UI 코드에서 세이브 데이터 직접 변경
- 모든 화면을 하나의 거대한 Manager에서 관리
- 이벤트 구독 해제 누락
- 매 프레임 문자열 생성과 레이아웃 재계산
- 리스트 갱신 시 전체 오브젝트 파괴 후 재생성
- 테스트를 어렵게 만드는 정적 전역 상태 남용

## 12. 성능 기준

### 12.1 uGUI

- 변화가 잦은 UI와 정적인 배경을 동일 Canvas에 무조건 묶지 않는다.
- 투명 이미지가 화면 전체를 덮는 구조를 줄인다.
- 중첩 Mask와 RectMask2D를 최소화한다.
- ScrollRect 내부 반복 요소는 풀링한다.
- LayoutRebuilder 강제 호출을 남용하지 않는다.
- `ContentSizeFitter`와 LayoutGroup 중첩을 점검한다.
- Raycast가 필요 없는 Graphic의 `Raycast Target`을 끈다.
- 비활성 화면의 애니메이션·Update를 중지한다.

### 12.2 데이터 갱신

- 값이 바뀐 항목만 갱신한다.
- 동일 데이터 포맷을 매 프레임 반복하지 않는다.
- 정렬과 필터는 UI 요소가 아니라 데이터 컬렉션 단계에서 처리한다.
- 대규모 기록 목록은 페이지, 가상화, 지연 로딩 중 하나를 적용한다.
- 서버가 없는 로컬 게임이어도 로딩 상태와 비동기 흐름을 고려한다.

## 13. 텍스트와 로컬라이징

- 화면에 출력되는 문자열을 코드에 직접 작성하지 않는다.
- 동일 의미의 용어를 화면마다 다르게 번역하거나 축약하지 않는다.
- 버튼 라벨은 행동형 문장으로 작성한다.
- 오류 문구는 사용자 행동으로 해결할 수 있는 정보를 포함한다.
- 숫자, 날짜, 금액, 백분율 표기 형식을 공통 유틸리티로 관리한다.

예시:

```text
나쁜 예: 확인
좋은 예: 계약 확정

나쁜 예: 실패했습니다.
좋은 예: 보유금이 부족해 계약을 확정할 수 없습니다.
```

권장 공통 표기:

```text
금액: 1,250,000
백분율: 72%
증감: +12 / -8
날짜: 2027년 3월 2일
시즌: 2027 시즌
```

- 좁은 화면에서 임의 축약어를 만들지 않는다.
- 툴팁 없이 의미를 알기 어려운 약어는 사용하지 않는다.

## 14. 접근성과 가독성

- 색상만으로 선택, 성공, 실패를 구분하지 않는다.
- 텍스트와 배경의 대비를 충분히 확보한다.
- 작은 회색 글자를 장시간 읽게 하지 않는다.
- 포커스 위치는 색상과 외곽선으로 동시에 식별 가능해야 한다.
- 중요한 정보는 애니메이션이 끝난 후에도 남아 있어야 한다.
- 깜빡임, 과도한 플래시, 반복 흔들림을 피한다.
- 아이콘에는 텍스트 또는 툴팁을 제공한다.
- 입력 프롬프트는 현재 장치와 일치해야 한다.

## 15. 제작 절차

### 15.1 화면 제작 전

1. 화면의 핵심 목적을 한 문장으로 정의한다.
2. 사용자가 화면에서 수행할 대표 행동 하나를 정한다.
3. 공통 셸에서 어느 영역을 사용할지 결정한다.
4. 기존 화면과 공통 컴포넌트를 조사한다.
5. Loading, Empty, Error, Locked 상태를 정의한다.
6. 마우스·키보드·게임패드 포커스 흐름을 작성한다.

### 15.2 와이어프레임 단계

- 색상과 장식 전에 정보 구조를 검증한다.
- 최초 진입 시 보이는 정보만으로 다음 행동을 이해할 수 있어야 한다.
- 목록 → 상세 → 행동 → 결과의 흐름을 확인한다.
- 공통 메뉴와 화면별 메뉴의 위계를 혼동하지 않는지 점검한다.

### 15.3 구현 단계

- 공통 프리팹과 토큰을 먼저 사용한다.
- 임시 하드코딩 값은 작업 완료 전에 제거한다.
- 데이터가 없는 상태에서도 화면이 깨지지 않도록 한다.
- 실제 최대 길이 텍스트와 최대 자릿수로 확인한다.
- 입력 장치 전환과 포커스 복원을 확인한다.

### 15.4 리뷰 단계

리뷰는 아래 순서로 진행한다.

1. 메뉴 구조 일관성
2. 정보 우선순위
3. 조작 흐름
4. 가독성
5. 상태 누락
6. 성능
7. 세부 시각 완성도

세부 장식이 좋아도 1–3번에 문제가 있으면 완료 처리하지 않는다.

## 16. AI 코딩 에이전트 작업 지침

AI가 UI를 생성하거나 수정할 때 반드시 다음을 따른다.

### 16.1 작업 전 확인

- 현재 프로젝트의 UI 프레임워크와 폴더 구조를 먼저 확인한다.
- 공통 상단 헤더와 하단 내비게이션 구현을 찾는다.
- 동일한 역할의 기존 Prefab과 컴포넌트를 찾는다.
- 기존 색상·폰트·간격 토큰을 확인한다.
- 기존 화면의 포커스·뒤로 가기 처리 방식을 확인한다.

작업 시작 전에 반드시 아래를 확인하고 결과에 기록한다.

```text
Skin Reference   : 사용할 기존 Panel/Button/Tab/Card/Popup Prefab 또는 Skin 자산
Layout Reference : 가장 구조가 유사한 기존 화면
Metrics          : Header / Bottom Navigation / Panel Gap / Content Inset 기준(4.7)
```

재사용할 Prefab을 찾지 못한 경우 즉시 새로운 스타일을 만들지 않는다. "적합한 기존 Skin을 찾지 못함"을 작업 결과에 명시하고 Placeholder 상태로 남긴다.

### 16.2 구현 원칙

- 기존 구조를 확인하지 않은 상태에서 독립된 새 UI 시스템을 만들지 않는다.
- 요구사항에 없는 메뉴, 재화, 탭, 버튼을 임의로 추가하지 않는다.
- 한 화면의 문제를 해결하기 위해 공통 메뉴 구조를 변경하지 않는다.
- 화면마다 새로운 스타일 클래스를 복제하지 않는다.
- 공통 컴포넌트 수정 시 다른 화면에 미치는 영향을 확인한다.
- 임시 Placeholder는 명확한 이름과 교체 지점을 남긴다.
- 컴파일 성공만으로 완료 처리하지 않는다. **Skin 재사용 여부와 Prefab을 실제로 사용했는지를 확인하지 않고 완료 처리하지 않는다** — Prefab을 "찾았다"는 것과 "적용했다"는 것은 다르다.

구현 금지:

- Raw Image를 일반 Panel의 최종 외관으로 사용하는 것
- 기존 Skin이 있는데 새로운 Panel 디자인을 만드는 것
- 화면 코드에서 Skin Sprite를 직접 교체하는 것
- `ContentSafeRect`(4.5) 밖에 기능 UI를 배치하는 것
- 음수 offset으로 Panel 간격 문제를 해결하는 것
- 다른 Panel 위에 버튼/텍스트를 덮어서 배치하는 것
- 해상도 문제를 fontSize 축소만으로 해결하는 것(4.7 우선순위를 따른다)

### 16.3 결과 보고 항목

작업 결과에는 최소한 다음을 정리한다.

```text
- 생성·수정한 화면과 컴포넌트
- 재사용한 공통 요소
- 재사용한 Skin Prefab/Sprite와 미발견 시 대체 방식
- 추가한 상태 처리
- 입력·포커스 흐름
- 해상도 대응 방식
- Content Safe Bounds / 형제 Panel 침범 여부 확인 결과
- 남은 Placeholder
- 검증한 항목과 미검증 항목
```

### 16.4 AI가 하지 말아야 할 것

- 공통 내비게이션 순서 변경
- 화면별로 로고·보유금·시즌 위치 변경
- 계약 화면만 다른 메뉴 체계로 제작
- 색상과 폰트의 화면별 하드코딩
- 버튼 비활성 사유 생략
- 목록 선택 상태와 포커스 상태 혼용
- 데이터가 없을 때 NullReference가 발생하는 구현
- 장식 목적의 불필요한 애니메이션 추가
- 기존 코드 스타일과 무관한 대규모 리팩터링 동시 수행
- Skin이 존재하는 컴포넌트를 `Image + Color`만으로 대체하는 것
- 승인된 UPlayBall Skin(프레임·코너·스티치 등)을 임의로 제거·단순화하는 것
- Content를 `ContentSafeRect` 밖에 배치하거나 형제 Panel과 겹치게 만드는 것

## 17. 완료 조건 — Definition of Done

아래 항목을 모두 충족해야 UI 작업을 완료로 본다.

### 구조

- [ ] 공통 상단 헤더와 하단 내비게이션이 기존 화면과 동일하다.
- [ ] 메인 메뉴 순서가 `홈·선수·성장·일정·리그·구단·기록·계약`으로 유지된다.
- [ ] 화면별 탭·서브메뉴의 위계가 명확하다.
- [ ] 대표 행동이 한눈에 식별된다.

### 상태

- [ ] Normal, Hover, Pressed, Selected, Focused, Disabled 상태가 정의되어 있다.
- [ ] Loading, Empty, Error, Locked 상태가 정의되어 있다.
- [ ] 비활성 사유와 오류 해결 행동이 표시된다.
- [ ] 팝업 종료 후 이전 포커스가 복원된다.

### 입력

- [ ] 마우스로 모든 기능을 사용할 수 있다.
- [ ] 키보드로 모든 기능을 사용할 수 있다.
- [ ] 게임패드로 모든 기능을 사용할 수 있다.
- [ ] 뒤로 가기 우선순위가 일관된다.
- [ ] 현재 입력 장치에 맞는 프롬프트가 표시된다.

### 해상도

아래 각 해상도의 실제 실행 화면(스크린샷 또는 자동 검증)을 확인한다. 확인 없이 완료 처리하지 않는다.

- [ ] 1280 × 720에서 잘림이 없다.
- [ ] 1920 × 1080에서 가독성이 유지된다.
- [ ] 2560 × 1440에서 과도한 빈 공간이 없다.
- [ ] 3440 × 1440에서 핵심 정보가 지나치게 벌어지지 않는다.
- [ ] 긴 한글과 최대 자릿수 데이터로 검증했다.
- [ ] 각 해상도에서 Text Overflow, Panel 중첩, 버튼 중첩, Frame/Content 중첩, 화면 밖 Raycast 영역이 0건이다.

### Skin 검증

- [ ] 모든 주요 Panel이 승인된 Skin 또는 Prefab을 사용한다.
- [ ] 모든 Button/Tab이 공통 Skin State를 사용한다.
- [ ] Raw Image 기반 임시 Panel이 남아 있지 않다.
- [ ] 승인되지 않은 신규 UI Sprite가 없다.
- [ ] Skin의 비율과 Border가 비정상적으로 늘어나지 않았다(9-Slice 확인).

### Layout Bounds 검증

- [ ] Content가 `ContentSafeRect`를 벗어난 곳이 0건이다.
- [ ] 형제 Panel끼리 침범한 곳이 0건이다.
- [ ] `HeaderSlot` 영역 침범이 0건이다.
- [ ] `BottomNavigationSlot` 영역 침범이 0건이다.
- [ ] 일반 UI가 `OverlayRoot`에 배치된 곳이 0건이다.
- [ ] ScrollView 콘텐츠가 Viewport 밖으로 노출되지 않는다.
- [ ] Decoration 이외의 음수 Margin 사용이 없다.

### 구현 품질

- [ ] 공통 컴포넌트를 우선 재사용했다.
- [ ] 색상·폰트·간격을 직접 하드코딩하지 않았다.
- [ ] 이벤트 중복 구독과 해제 누락이 없다.
- [ ] 비활성 화면이 불필요하게 갱신되지 않는다.
- [ ] 반복 목록이 전체 파괴·재생성 방식에 의존하지 않는다.
- [ ] Console 오류와 경고를 확인했다.

### 시각 일관성

- [ ] 배경, 패널, 선택색, 텍스트색이 공통 토큰을 사용한다.
- [ ] 같은 역할의 버튼이 같은 스타일을 사용한다.
- [ ] Hover, Selected, Focused 상태가 서로 구분된다.
- [ ] 금색과 파란색의 역할이 혼용되지 않는다.
- [ ] 다른 화면과 나란히 보았을 때 동일한 게임 UI로 인식된다.

## 18. 최종 금지사항 요약

다음 항목은 별도 승인 없이 허용하지 않는다.

- 화면별 메인 메뉴 재설계
- 하단 내비게이션 항목의 누락·순서 변경
- 계약 화면만 다른 레이아웃 체계 사용
- 화면별 색상·폰트·간격 하드코딩
- 작은 텍스트로 정보량만 늘리는 설계
- 색상만으로 상태 구분
- 비활성 사유 없는 버튼
- 포커스가 보이지 않는 게임패드 UI
- 팝업 종료 후 포커스 유실
- 데이터 없음과 로딩 중의 동일 처리
- 전체 목록의 반복 파괴·생성
- 의미 없는 장식, 그래프, 애니메이션 추가
- 기존 공통 컴포넌트 확인 없이 유사 Prefab 복제
- Skin이 있는 Panel/Button/Tab/Card/Popup을 `Image + Color`로 대체
- 승인된 UPlayBall Skin(프레임·코너·스티치·금속 장식)의 임의 제거·단순화
- Content가 `ContentSafeRect`를 벗어나거나 형제 Panel/Header/BottomNav를 침범하는 배치
- 컴파일 성공만으로, 또는 Skin Compliance·Layout Bounds 검증 없이 UI 작업을 완료 처리하는 것

## 19. 한 문장 기준

> **새 화면은 새 디자인을 만드는 작업이 아니라, UPlayBall의 기존 공통 UI 문법 안에 새로운 정보를 배치하는 작업이다.**
>
> **새 화면의 시각 외관은 승인된 UPlayBall Skin을 조합하고, 기능 콘텐츠는 각 Skin이 정의한 Content Safe Bounds 안에서만 배치한다. Skin 미사용 또는 Bounds 침범이 하나라도 있으면 UI 작업은 미완료다.**
