# 15. 리그 시즌 기록 집계와 선수 기록 화면

> 상태: 현재 시즌 기록 집계와 화면 연결 구현 완료. UI 화면 실행 검증은 사용자 검증 범위이며,
> 지난 시즌 보관과 구단 통산 기록실은 별도 후속 작업이다.

구단주 모드에는 **현재 시즌 개인 기록 집계가 존재하지 않았다.** `LeagueSeasonStatisticsState`와
`LeagueStatisticsService`는 선수 커리어 모드에서만 호출됐고, 구단주 순위표는 완료 대진의 점수만
역산해 승패·득실을 보여줬다. 즉 "누가 잘하고 있는가"를 볼 수 있는 경로가 없었다.

이 문서는 `00_작업명세_지침_한시.md` §2의 7개 항목을 채운 작업 명세다.

## 대상 모드

**구단주.** 선수 커리어 모드는 이미 같은 집계를 갖고 있으며 동작이 바뀌지 않는다. 다만 규정
타석·이닝, 지표 계산, 순위 규칙을 두 모드가 공유하도록 공용 서비스로 추출한다(§3-3 이중 트랙 금지).

## 소비자 경로 (필수)

### 집계

```text
UI_Scene_OwnerHome.PlayNextGameButton
  → OwnerModeShellCoordinator.HandlePlayNextGameRequested
  → OwnerModeManager.PlayNextGame
  → ManagerModeMatchService.PlayNextGame           (플레이어 구단 경기)
  → ManagerModeMatchService.SimulateAiGame         (AI 구단 경기)
  → LeagueStatisticsService.RecordMatch(match, RegularSeason, round, false, false)
  → ManagerLiveSeasonState.Statistics : LeagueSeasonStatisticsState
```

### 표시

```text
셸 좌측 [리그 > 선수 기록]
  → OwnerModeShellCoordinator.HandleRouteChanged
  → OwnerSharedInformationWorkspaceCoordinator.TryShowRoute(SeasonRecordsRouteId)
  → UI_Scene_OwnerSeasonRecords.ShowCategory
  ← OwnerSharedInformationWorkspaceCoordinator.BindSeasonRecords(OwnerSeasonRecordsPresentationModel)
  ← OwnerSharedInformationSnapshotFactory.CreateSeasonRecords(OwnerModeManager)
  ← OwnerSeasonRecordsService.Build(ManagerHistoricalRuntimeState, ...)   [Game]
  ← LeagueLeaderboardService.BuildLeaderboard(...)                        [Game, 공용]
  ← LeagueLeaderboardSnapshotAdapter.CreateLeaderboardTable(...)          [Presentation, 공용]
```

### 저장

```text
OwnerModeManager.Save → ManagerHistoricalSaveAdapter.CreateSaveData
  → LeagueSeasonStatisticsSaveMapper.CreateSaveData   (saveVersion 6)
Restore ← LeagueSeasonStatisticsSaveMapper.Restore
```

## 콘텐츠 수량

**저작 데이터 없음.** 집계와 표시만 다루며 SO/JSON에 새로 저작할 항목이 없다. 기록 부문은 기존
`CareerRecordCategory` 4종(타격·투구·수비·주루)을 그대로 쓰고 새 enum을 만들지 않는다.

## 선행 설계 결정

| 질문 | 결정 | 근거 |
|---|---|---|
| 집계 상태를 어디에 두는가 | `ManagerLiveSeasonState.Statistics` | 시즌 단위 상태다. `CreateNextSeason`에서 자연히 새로 만들어져 시즌 경계가 코드로 강제된다. |
| 커리어와 같은 타입을 쓰는가 | 쓴다. `LeagueSeasonStatisticsState` / `LeagueStatisticsService` 재사용 | `RecordMatch`는 `MatchResult`만 요구해 모드 비의존이다. 구단주 전용 통계 타입을 새로 만들면 한 개념이 두 벌이 된다(§3-3). |
| 세이브에 무엇을 넣는가 | 타격·투구·수비 시즌 누적만. `GameContributions`·`TeamSplits`는 저장하지 않는다 | 두 필드는 커리어 모드의 감독 평가 가중치·수상 가중치·시즌 중 트레이드 분할 전용이고 구단주 모드에 소비자가 0건이다. 경기별 기여도는 시즌당 2만 건 규모라 저장 비용도 정당화되지 않는다. **Source of Truth는 저장된 시즌 누적이고, 기여도·구단 분할은 커리어 모드 런타임에서만 존재하는 파생 상태다.** |
| AI 구단 경기도 집계하는가 | 집계한다 | 집계하지 않으면 기록표가 다시 플레이어 구단 선수만으로 채워진다. |
| 규정 타석·이닝 | 커리어와 동일 (`팀 경기수 × 3.1 타석`, `팀 경기수 × 3 아웃`) | 두 모드가 다른 규정을 쓸 이유가 없다. 공용 추출로 상수를 한 벌만 남긴다. |

## 제거/정리 대상

**대체가 아니라 추가다.** 다만 아래는 이동이며 중복 생성이 아니다.

- `CareerRecordsService`의 범용 statics(지표 값 계산, 규정 판정, 순위, 기본 열, `FieldingTotals`)를
  `LeagueLeaderboardService`로 옮기고 `CareerRecordsService`는 위임한다.
- `CareerRecordsSnapshotAdapter.CreateLeaderboard`의 표 생성부를
  `LeagueLeaderboardSnapshotAdapter`로 옮기고 기존 메서드는 위임한다.

부수적으로, 이미 구현돼 있으나 내비게이션에 없어 도달할 수 없던 `Shared.League.Schedule`(구단 일정)과
`Shared.League.Records`(역사 기록) 두 화면을 리그 탭에 노출한다 — §1-1의 미배선 2건 해소다.

## 남은 항목

- **지난 시즌 개인 기록 보관이 없다.** `ManagerModeRuntimeFactory.CreateNextSeason`은 새 시즌마다
  빈 `LeagueSeasonStatisticsState`를 만들므로 시즌이 넘어가면 직전 시즌 개인 기록이 사라진다.
  커리어 모드의 `CareerSeasonHistoryRecord`에 해당하는 보관처가 구단주 모드에는 없다. 여러 시즌
  누적을 전제로 하는 설계 원칙상 별도 작업으로 남긴다.
- **구단 통산 기록실이 없다.** §3-6에서 흡수 불가로 판정한 `NEWS_CLUB_RECORD_BROKEN` 등 세 Cue의
  전제 조건이며, 위 시즌 보관이 먼저 필요하다.
