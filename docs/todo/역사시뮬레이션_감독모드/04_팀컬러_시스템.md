# 04. 팀컬러 시스템

## 0. 목적

1군 25인의 구성(구단·연도·Edition 일치도)에 따라 발동하는 팀 전체 능력치 보너스를 정의한다.
팀컬러는 **BaseStat을 수정하지 않고**, 경기 판정 직전에 계산되는 EffectiveStat 레이어에서만
적용된다.

## 0.1 수치 출처 표기 규칙

이 문서의 모든 팀컬러 수치는 다음 두 태그 중 하나를 명시한다.

```text
[Reference]        실제 프야매 공개 자료(인벤 팀컬러 공지, mlbpark 패치 안내 등)로 확인된 수치
[ProjectOriginal]  프야매에 없거나 확인되지 않아 이 프로젝트가 새로 설계한 수치
```

`[ProjectOriginal]`은 그대로 구현해도 되지만, "프야매 동일 규칙"이라고 검증 문서에 적지
않는다 — 이후 밸런스 근거를 댈 때 출처를 혼동하면 안 되기 때문이다.

## 1. 능력치 레이어

감독모드 카드와 선수 커리어 모드 선수는 서로 다른 레이어 구성을 쓴다(§1.1, §1.2). 공통
전제: **BaseStat은 기존 프로젝트의 `AbilityRatings` 하드캡(1~99)을 그대로 따른다.** 이
문서가 처음 초안에서 썼던 "BaseStat 0~100"은 기존 코드 구조와 어긋나므로 폐기한다.

### 1.1 감독모드 카드 (본 문서, 03·05절 대상)

```text
BaseStat                 // 1~99, PlayerSeasonDefinition 원본, 불변, 나이/노화 없음
+ CardTrainingBonus       // DP 훈련 고정 성장분, 05절 §5. NaturalGrowth/노화 Resolver 사용 금지
+ CardEnhancement         // 중복 강화, 0~+5 (05절)
+ TeamColorBonus          // 본 문서
+ ConditionBonus          // 기존 컨디션 시스템 재사용
+ TacticCardBonus         // 06절, 경기 중 임시
= EffectiveRating         // 별도 타입, §1.3 상한 규칙
```

### 1.2 선수 커리어 모드 선수 (기존 시스템 + 07절 Wildcard만 추가)

```text
BaseStat
+ NaturalGrowth           // 기존 성장 시스템, 나이·경험 기반
+ TrainingBonus           // 기존 유학/Skill Board 등
+ TeamColorBonus          // 07절 Wildcard 판정으로만 발생, 본 문서 수치를 그대로 사용
+ ConditionBonus
= EffectiveRating
```

두 레이어를 하나의 공식으로 합치지 않는다 — 감독모드 카드는 "나이를 먹지 않는 스냅샷"이고
선수 커리어 모드 선수는 "나이를 먹는 인물"이라는 전제가 다르기 때문이다(03절 §"카드는
나이를 먹지 않는다" 참고).

### 1.3 EffectiveRating 상한 — SoftCap + HardCap

BaseStat은 1~99로 유한하다. EffectiveRating은 이를 넘을 수 있지만 무제한은 아니다.

**단일 Cap 120은 엔드게임에서 너무 쉽게 포화될 가능성이 크다.** 예를 들어
`BaseStat 95 + CardEnhancement 5 + Mvp Edition 3~5 + YearFranchise TeamColor 17`만으로도
이미 120을 넘는다 — 여기에 DP(`CardTrainingBonus`), Condition, 전술카드 보너스가 아직
더 남아있다. 고급 카드들이 전부 상한에 붙어버리면 강화·MVP·DP 사이의 실질적 차이가 사라질
위험이 있다. 따라서 단일 `EffectiveRatingCap` 대신 이중 구조를 기본으로 채택한다.

```text
EffectiveRatingCapTable
{
    SoftCap    // 초기값 120 — 이 지점부터 Rating Curve의 확률 증가율이 급격히 완만해진다
    HardCap    // 초기값 140 — 물리적으로 넘을 수 없는 절대 상한
}
```

`SoftCap`은 Rating Curve의 변곡점으로만 쓰고(그 지점부터 곡선 기울기를 낮춘다), 실제 값
자체를 자르지 않는다. `HardCap`만 EffectiveRating의 물리적 상한이다. Simulation의 확률
판정은 `EffectiveRating / 99`처럼 선형으로 쓰지 않고 이 SoftCap/HardCap을 반영한 Rating
Curve 함수를 거쳐 확률로 변환한다. 정확한 SoftCap/HardCap 값과 곡선 형태는 Phase 5 전
반드시 대량 시뮬레이션(엔드게임 카드 조합 기준 EffectiveRating 분포 실측)으로 재검증하고,
필요하면 SoftCap/HardCap 수치 자체도 조정한다(프야매도 능력치 상한을 120에서 140으로
단계적으로 확장한 선례가 있다 — `[Reference]`, 다만 정확한 SoftCap 개념은 프야매 확인
자료에 없으므로 `[ProjectOriginal]`).

## 2. 팀컬러 슬롯 — 자유 2슬롯 조합

1군 25인 기준으로 판정한다(2군·미등록·컬렉션 보관 카드는 계산에서 제외). 슬롯은 **2개**이며,
**활성화된 팀컬러 후보 중 어떤 조합이든 2개까지 자유롭게 장착할 수 있다.** 초안에 있던
"같은 Family끼리만 조합 가능" 제한은 폐기한다 — 프야매에서도 서로 다른 종류의 팀컬러(예:
단일연도 구단 20인 컬러 + 동일구단 25인 컬러)를 함께 쓰는 것이 정상적인 덱 구성이었다
(`[Reference]`).

```text
TeamColorSlot[0], TeamColorSlot[1]   // 어떤 TeamColorDefinition이든 장착 가능, 단 §2.2 StackPolicy 적용
```

### 2.2 StackPolicy — 같은 카드 집합을 겨냥한 상위/하위 단계 조건의 중첩 제한

"자유 2슬롯 조합"은 **서로 다른 카드 집합을 겨냥하는 팀컬러끼리** 자유롭게 섞을 수 있다는
뜻이다. 그런데 같은 팀컬러 계열 안에서 인원 조건만 다른 두 단계(예: GoldenGlove 8명과
GoldenGlove 10명(전원)처럼 **거의 같은 카드 집합**을 대상으로 한 상위/하위 조건)까지 둘 다
슬롯에 얹으면, 사실상 하나의 카드 집합에서 두 번 보너스를 받는 부당 중첩이 생긴다. 따라서
`TeamColorDefinition`에 다음 필드를 추가한다.

```text
TeamColorDefinition
{
    ...
    UpgradeGroupId?    // 값이 있으면 같은 그룹 내에서는 StackPolicy = HighestOnly
    StackPolicy         // Stackable(기본값) | HighestOnly
}
```

- **Stackable(기본값)**: YearFranchise의 10/20/25단계처럼, 인원 조건이 다르면 자연히
  카드 집합도 달라지는(20명 조건을 채운 로스터가 25명 조건도 채우는 포함 관계) 경우에도
  "정석 조합"으로 두 단계를 함께 장착하는 것을 허용한다(예: `YearFranchise 25 + 20`).
  YearFranchise/Franchise 계열은 이 프로젝트가 프야매 레퍼런스에서 이미 "하위 단계 +
  상위 단계 동시 장착"을 정석 조합으로 확인했으므로 그대로 `Stackable`을 유지한다.
- **HighestOnly**: 같은 `UpgradeGroupId`를 가진 팀컬러들 중에서는 **조건을 만족하는 것 중
  가장 강한 단계 하나만** 장착 후보 목록(`TeamColorResolver.Resolve`의 결과)에 노출한다.
  하위 단계는 자동으로 후보에서 제거되므로 애초에 슬롯에 꽂을 수 없다.

`GoldenGlove` 동일 연도 8명/10명(전원) 두 단계는 `UpgradeGroupId = "GoldenGlove_SameYear"`,
`StackPolicy = HighestOnly`로 지정한다 — 10명(전원)을 만족하면 8명 조건은 후보에서 사라지고
10명(전원) 하나만 남는다("8명 조건과 10명 조건을 동시에 장착해 Contact/Mental +9를 만드는"
부당 중첩을 원천 차단한다). §8을 참고한다.

### 2.1 카드별 적용 대상은 팀컬러마다 다르다

두 슬롯에 서로 다른 팀컬러를 꽂아도, **각 팀컬러의 효과는 그 팀컬러 조건을 만족하는 카드
에게만 적용된다.** 팀컬러를 장착했다고 로스터 25인 전원이 모든 슬롯의 효과를 받는 것이
아니다.

예: `2011 Comets YearFranchise 20` + `Comets Franchise 25`를 장착한 경우

```text
2011 Comets 소속 선수 20명  → YearFranchise 보너스 + Franchise 보너스 모두 적용
다른 연도 Comets 선수 5명   → Franchise 보너스만 적용 (YearFranchise 조건 불충족)
```

`TeamColorResolver`는 슬롯마다 독립적으로 조건을 평가하고, 한 카드가 두 슬롯 조건을 모두
만족하면 두 보너스를 합산해서 적용한다.

## 3. TeamColorFamily — 분류 목적으로만 유지

Family 구분은 "동시 장착 제한"이 아니라 **카드 발생 조건과 UI 분류**를 위한 개념으로만
남긴다.

```text
TeamColorFamily
  YearFranchise   // 구단별 연도덱 (동일 구단+연도)
  Franchise       // 구단덱 (연도 무관, 동일 구단)
  Year            // 연도덱 (구단 무관, 동일 연도)
  AllStar
  GoldenGlove
  Mvp
```

## 4. 구단별 연도덱 (YearFranchise) — `[Reference]`

가장 좁은 선수풀, 가장 강한 보너스. 조건은 `OriginFranchiseId` + `OriginYear`가 모두 동일한
1군 인원 수.

| 인원 | 야수 | 투수 |
| ---: | --- | --- |
| 10 | ALL +5 | ALL +3 |
| 20 | ALL +7 | ALL +5 |
| 25 | ALL +10 | ALL +7 |

25인 달성 시 10/20/25 세 조건이 모두 Unlock. 정석 조합은 `25 + 20`:

```text
야수 ALL +17
투수 ALL +12
```

## 5. 구단덱 (Franchise) — `[Reference]`

연도 무관, `OriginFranchiseId`만 동일.

| 인원 | 야수 | 투수 |
| ---: | --- | --- |
| 10 | ALL +3 | ALL +2 |
| 20 | ALL +4 | ALL +2 |
| 25 | ALL +6 | ALL +3 |

25 + 20 조합: 야수 ALL +10 / 투수 ALL +5.

## 6. 연도덱 (Year) — `[Reference]`

구단 무관, `OriginYear`만 동일. 25인 고정 조건 하나만 사용(10/20 단계 없음).

```text
25인: 야수 ALL +4 / 투수 ALL +2
```

## 7. All-Star 덱

`Edition == AllStar`인 카드 수 기준.

| 조건 | 야수 | 투수 | 출처 |
| --- | --- | --- | --- |
| 동일 연도 20명 | Power +5 / Mental +5 | Velocity +2 / Breaking +5 / Mental +3 | `[Reference]` |
| 연도 무관 10명 | Power +2 / Mental +2 | Velocity +1 / Breaking +2 / Mental +1 | `[ProjectOriginal]` |
| 연도 무관 20명 | Power +3 / Mental +3 | Velocity +1 / Breaking +3 / Mental +1 | `[ProjectOriginal]` |

`동일 연도 20명`만 실제 확인된 프야매 수치다. `연도 무관 10/20명` 단계는 카드 수가 적은
초반에도 All-Star 수집에 목표를 주기 위한 프로젝트 확장 규칙이며, 밸런스 확정 전까지
`ProjectBalanceValue`로 표시해 별도 조정 여지를 남긴다.

**StackPolicy(§2.2):** "동일 연도 20명"을 만족하는 로스터는 그 20장이 전부 AllStar
Edition이므로 "연도 무관 20명" 조건도 자동으로 함께 만족한다 — 즉 정확히 같은 20장의
카드로 두 조건이 동시에 성립할 수 있다. 이 셋(연도 무관 10명/20명, 동일 연도 20명)은
YearFranchise의 10/20/25(의도된 정석 스택)나 MVP의 10/20(의도된 정석 스택)과 달리
**"같은 카드 집합에 대한 서로 다른 명칭"에 가깝고, 이 문서 어디에도 이 셋을 동시에 쌓는
것을 의도된 정석 조합으로 명시한 적이 없다.** 따라서 `UpgradeGroupId = "AllStar_SamePool"`,
`StackPolicy = HighestOnly`로 묶어, 조건을 만족하는 것 중 가장 강한 하나만
(우선순위: 동일 연도 20명 > 연도 무관 20명 > 연도 무관 10명) 장착 후보로 노출한다.

## 8. Golden Glove 덱 — 수치 정정

**주의:** 초안은 03절의 GoldenGlove Edition 카드 자체 보너스(야수 Power+2/Defense+2, 투수
Stuff+2/Breaking+2, `[Reference]`, Cost 무관 고정)와 이 절의 TeamColor 보너스를 사실상
동일한 수치로 섞어 놓았다 — **오류였다.** 카드 자체 효과와 덱(TeamColor) 효과는 서로 다른
레이어이며 이 절은 덱 효과만 다룬다.

확인된 실제 자료는 **동일 연도 골든글러브 8명** 조건 하나뿐이다(`[Reference]`, 2014년 패치
공지 기준):

```text
동일 연도 Golden Glove 8명
  야수: Contact +4 / Mental +4
  투수: Stuff +2 / Breaking +2 / Mental +4
```

**이전 초안의 오류를 다시 정정한다:** 원 레퍼런스가 요구하는 인원은 8명이지, 10명이
아니다. 연도당 Golden Glove Edition 카드가 10장 존재한다고 해서 팀컬러 발동 조건까지
10명으로 늘릴 이유는 없다 — "8명을 모으면 발동"이 원 레퍼런스와 동일한 조건이다. 따라서
기본 조건은 8명으로 되돌리고, 10명(전원) 조건은 **레퍼런스의 변형**임을 명시해 별도로만
둔다. 연도 무관 조건은 원 레퍼런스에 없으므로 순수 프로젝트 확장이다.

| 조건 | 야수 | 투수 | 출처 |
| --- | --- | --- | --- |
| 동일 연도 8명 | Contact +4 / Mental +4 | Stuff +2 / Breaking +2 / Mental +4 | `[Reference]` |
| 동일 연도 10명 (전원) | Contact +5 / Mental +5 | Stuff +3 / Breaking +3 / Mental +5 | `[ProjectOriginal — 8인 Reference를 10인 전원 조건으로 변형, 소폭 상향]` |
| 연도 무관 10명 | Contact +2 / Mental +2 | Stuff +1 / Breaking +1 / Mental +2 | `[ProjectOriginal]` |
| 연도 무관 20명 | Contact +3 / Mental +3 | Stuff +2 / Breaking +2 / Mental +3 | `[ProjectOriginal]` |

**StackPolicy(§2.2):** 위 네 조건은 전부 같은 "그 연도 GoldenGlove Edition 카드 집합"을
겨냥한다 — 동일 연도 10명(전원)을 만족하면 동일 연도 8명도, 연도 무관 10명도 자동으로
함께 만족된다. 이걸 자유 2슬롯 조합으로 그대로 두면 "8명 + 10명(전원)"처럼 같은 카드
집합에서 이중으로 보너스를 받는 부당 중첩(예: Contact/Mental +9)이 생긴다. 따라서 네
조건을 전부 `UpgradeGroupId = "GoldenGlove_SamePool"`, `StackPolicy = HighestOnly`로 묶는다
— `TeamColorResolver`는 이 그룹 안에서 조건을 만족하는 것들 중 **1인당 보너스 총합이 가장
큰 하나만** 장착 후보로 노출하고 나머지는 자동으로 후보에서 제외한다. 결과적으로 "8명
확보 전까지는 미발동, 8명 확보 후 10명(전원)까지 채우면 더 강한 조건으로 자동 대체된다"는
단계적 목표로 기능한다(중첩이 아니라 대체).

효과는 GoldenGlove Edition 카드에만 적용된다. 03절 Edition 자체 보너스(Power/Defense,
Stuff/Breaking)와 이 절의 TeamColor 보너스(Contact/Mental 위주)는 서로 다른 능력치 축을
건드리므로 합산해도 한쪽 능력치만 과도하게 몰리지 않는다.

## 9. MVP 덱 — `[ProjectOriginal]`

**주의:** MVP 카드 자체의 Cost별 보너스(03절, ALL +3~+5)는 `[Reference]`로 확인되지만,
"MVP 10명/20명 팀컬러"라는 별도 덱 규칙은 프야매 공개 자료로 확인되지 않았다. 이 절 전체는
**MVP 카드 효과를 참고해 이 프로젝트가 새로 설계한 TeamColor**임을 명시한다.

`Edition == Mvp`인 카드 수 기준.

| 인원 | 보너스(해당 카드에만) |
| ---: | --- |
| 10 | ALL +2 |
| 20 | ALL +3 |

10+20 조합 시 MVP 카드에 ALL +5. MVP 카드 자체 보너스(Cost별 +3~+5)와 합산되므로 후반
콘텐츠로 의도한다.

## 10. TeamColorResolver 판정 입력

Resolver는 카드의 서사(이름, 스토리)를 몰라야 한다. **자격 판정**(어떤 카드가 어떤
팀컬러 조건을 만족하는가)의 입력은 정확히 다음 4개 필드(`TeamColorEligibilityKey`)뿐이다.

```text
TeamColorEligibilityKey
{
    OriginYear
    OriginFranchiseId
    OriginTeamSeasonKey
    Edition
}
```

다만 자격 판정만으로는 보너스를 계산할 수 없다 — 예를 들어 구단별 연도덱은 "야수 ALL +10 /
투수 ALL +7"처럼 **보너스 자체가 타자/투수에 따라 다르다.** 따라서 실제 보너스 계산
(`ApplyEquipped`)의 입력에는 `TeamColorEligibilityKey`와 별개로 `PlayerRole`
(Hitter/Pitcher 구분, `PlayerSeasonDefinition.Position`/`PitcherRole`에서 파생)을 추가로
전달한다.

```text
TeamColorResolver.Resolve(ActiveRoster25) → List<TeamColorCandidate>   // 발동 가능한 모든 후보, 단계별
TeamColorResolver.ApplyEquipped(
    roster: IReadOnlyList<(TeamColorEligibilityKey Key, PlayerRole Role, CardId CardId)>,
    slot0, slot1)
  → PerCardBonusMap
```

`ApplyEquipped`는 슬롯별로 조건을 만족하는 카드 집합을 각각 구하고, 카드별로 보너스를
합산한 결과(`PerCardBonusMap`)를 반환한다. Presentation은 결과를 표시만 하고 판정하지
않는다(`Simulation_Architecture_Guidelines`의 시뮬레이션/표현 분리 원칙과 동일).

## 11. 팀컬러 요약표

| 덱 | 완성 조건 | 최종 보너스 | 출처 |
| --- | --- | ---: | --- |
| 구단별 연도 | 25+20 | 야수 +17 / 투수 +12 | `[Reference]` |
| 구단 | 25+20 | 야수 +10 / 투수 +5 | `[Reference]` |
| 연도 | 25 | 야수 +4 / 투수 +2 | `[Reference]` |
| All-Star | 동일연도20 | 야수 Power/Mental +5, 투수 Velocity+2/Breaking+5/Mental+3 | `[Reference]` |

수치는 전부 `TeamColorBalanceTable`로 데이터화하고 실제 대량 시뮬레이션 결과(승률 영향)를
근거로 재조정한다. 자유 2슬롯 조합이 가능해졌으므로, 조합 상한 검증(예: YearFranchise 25+20
과 유사한 총 보너스를 가진 다른 조합이 우연히 더 세지 않는지)이 이전보다 더 중요해졌다.

## 12. 검증 기준

- 10/20/25 각 단계 경계에서 보너스가 정확히 표에 일치하는지 EditMode 테스트.
- 2슬롯에 서로 다른 Family 팀컬러를 장착했을 때, 각 카드가 자신이 조건을 만족하는 슬롯의
  보너스만 받는지(§2.1 예시) 테스트.
- 동일 팀컬러를 두 슬롯에 중복 장착할 수 없는지 테스트.
- 1군 25인 밖의 카드(2군, 컬렉션)는 판정에 전혀 영향을 주지 않는지 테스트.
- EffectiveRating이 `EffectiveRatingCapTable.HardCap`(초기 140)을 절대 넘지 않는지, 그리고
  `SoftCap`(초기 120) 부근부터 Rating Curve 기울기가 완만해지는지 테스트.
- 엔드게임 조합(고Cost BaseStat + 강화 +5 + MVP Edition + YearFranchise 완성 팀컬러)을
  대량 시뮬레이션으로 실측해 EffectiveRating 분포가 SoftCap 근처에 지나치게 몰리지 않는지
  (강화/MVP/DP 간 차별성이 유지되는지) Phase 5 전에 확인한다.
- `[ProjectOriginal]` 태그가 붙은 수치는 별도로 "출처 없음"이 검증 리포트에 표시되는지
  확인(밸런스 근거 문서화 누락 방지).
- `ApplyEquipped`가 `PlayerRole` 없이 호출되면 실패하는지, 그리고 같은 `TeamColorEligibilityKey`
  라도 Hitter/Pitcher에 따라 다른 보너스가 정확히 갈리는지 테스트.
- Golden Glove 8명 조건이 정확히 8명에서 발동하는지(9절 초안의 10명 요구가 남아있지 않은지)
  테스트.
- `GoldenGlove_SamePool`/`AllStar_SamePool` UpgradeGroupId 내에서 여러 조건을 동시에
  만족해도 `TeamColorResolver.Resolve` 후보에 그룹당 하나만 노출되는지, 그리고 두 슬롯에
  같은 그룹의 서로 다른 단계를 억지로 꽂을 수 없는지 테스트.
- YearFranchise(10/20/25)와 MVP(10/20)처럼 의도적으로 Stackable인 조합은 여전히 두 단계를
  함께 장착할 수 있는지(§2.2에서 StackPolicy 도입이 기존 정석 조합을 깨지 않는지) 회귀
  테스트.
