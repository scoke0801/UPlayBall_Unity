# 01. 시대 보정과 가상 선수 생성

## 0. 목적

`docs/KBO_REFERENCE_DATA_PIPELINE.md`가 만드는 정규화 JSON(연도별 선수·팀·수상 기록)을
게임에서 사용할 수 있는 **가상 선수·가상 구단용 Runtime-safe 콘텐츠**로 변환한다.

가장 중요한 경계는 다음과 같다.

- 가상 선수의 인물 정보, 연도별 능력치, 연도별 원소속 구단, Cost, TrainingCeiling은 **Offline/Editor에서 생성하여 Bake**한다.
- Runtime에서 새로운 가상 선수를 생성하거나 원소속 구단을 다시 추첨하지 않는다.
- 실제 시즌 성적과 수상 기록은 별개의 축이다. 새 게임에서 `WorldRecordMode`에 따라 과거 기록을 시뮬레이션하거나 Bake된 고유 기록을 로드한다.
- 실제 KBO 실명·실제 구단명·Raw 식별자는 Runtime 경계를 넘지 않는다.

```text
KBO Normalized JSON
  ↓
Era / Role Normalization
  ↓
Reliability Shrinkage
  ↓
Correlation Extraction
  ↓
Synthetic Person / Career / PlayerSeason Generation
  ↓
연도별 OriginFranchise / TeamSeason 배정
  ↓
BaseAttributes / Cost / TrainingCeiling 확정
  ↓
실존 선수 유사도 검사
  ↓
Synthetic Team/Core25 구성 (02절)
  ↓
Runtime-safe Original Season Record 변환
  ↓
Validation + Content Bake + Manifest/Hash
  ↓
──────────────── Runtime Boundary ────────────────
  ↓
Baked Definition Load
  ↓
New Game: SimulatedHistory 또는 OriginalHistory → 공통 WorldHistorySnapshot
```

## 1. 어셈블리 배치 — 생성은 Offline, Runtime은 소비만 한다

### 1.1 Offline / Editor

다음은 `Baseball.Editor`, Python/Tools 또는 동등한 Offline Data Pipeline의 책임이다.

```text
Era/Role Normalization
Reliability Shrinkage
Correlation Extraction
SyntheticCareerGenerator
SyntheticPlayerGenerator
SyntheticTeamGenerator
Similarity Validator
Cost / TrainingCeiling 계산
Runtime-safe Original Record 변환
Content Bake / Manifest 생성
```

순수 계산 코드의 테스트 재사용을 위해 Engine-independent 라이브러리로 분리할 수는 있으나,
**실제 Game Runtime Flow에서는 Synthetic 생성기를 호출하지 않는다.**

### 1.2 Runtime

Runtime은 다음과 같은 Bake 결과만 읽는다.

```text
PlayerPersonDefinition
PlayerSeasonDefinition
Normal Card Base / Edition Modifier Definition
TeamSeasonDefinition
OriginalSeasonRecordDefinition
OriginalAwardRecordDefinition      // OriginalHistory용, 실제 식별자는 제거된 가상 콘텐츠 기록
SyntheticContentManifest
```

`Baseball.Core`/`Baseball.Simulation`이 KBO Raw JSON이나 실제 선수/구단 식별자를 직접 읽는 경로는 금지한다.

## 2. 시대·역할 정규화

같은 절대 기록도 시대에 따라 가치가 다르므로 모든 Raw 기록은 다음 집단 내부에서 비교한다.

```text
GroupKey = OriginYear + PositionGroup + RoleTier
```

- `PositionGroup`: 타자는 수비 포지션, 투수는 선발/불펜 Reference 역할.
- `RoleTier`: 규정 타석/이닝 충족 여부(주전/서브). 규정 미달 선수를 주전 분포에 그대로 섞지 않는다.

각 지표(AVG, OBP, SLG, HR/PA, BB%, K%, SB rate, ERA, WHIP, K/9, BB/9 등)는 그룹 평균 `μ`,
표준편차 `σ`를 이용해 Z-Score로 변환한다.

```text
Z = (Stat - μ_group) / σ_group
```

이 Z-Score가 능력치 생성의 입력이다. 절대 기록 수치를 능력치 산식에 직접 넣지 않는다.

## 3. 표본 크기 보정 (Reliability Shrinkage)

표본이 작은 선수의 극단값을 평균 방향으로 회귀시킨다.

```text
Reliability(PA)  = PA  / (PA  + PA_ReliabilityConstant)
Reliability(TBF) = TBF / (TBF + TBF_ReliabilityConstant)

AdjustedZ = RawZ × Reliability
```

`PA_ReliabilityConstant`(초기값 250), `TBF_ReliabilityConstant`(초기값 200)는 하드코딩하지 않고
`EraNormalizationConfig`에 둔다. 실제 데이터 분포로 검증 후 조정한다.

## 4. 상관관계 추출 (Covariance)

완전 독립 랜덤 생성은 비현실적인 조합을 만든다. 능력치/기록 간 공분산을 Reference에서 추출해
Synthetic 생성에 사용한다.

최소 보존 대상:

```text
Power ↔ HR Rate
Contact ↔ K% (역상관)
Speed ↔ SB Rate
Control ↔ BB/9 (역상관)
Stuff ↔ K/9
Stamina ↔ (선발) IP/G
```

구현은 다변량 정규분포 + Cholesky 분해 등을 사용할 수 있다. RNG는 데이터 생성용 Seed를
주입받아 같은 입력/버전/Seed에서 같은 Bake 결과가 나와야 한다.

## 5. Offline Synthetic Career / Player Generator — 다년도 커리어 연결

한 인물의 여러 시즌을 사후에 임의로 묶지 않는다. Person 단위로 먼저 생성한 뒤 연도별
PlayerSeason을 파생한다.

```text
1. Person 생성
   PlayerPersonId, 가상 이름, 생년월일, 좌우타/투, 체격, 성격,
   PersonPotentialTrait, 등록 유형(Domestic/Foreign 등 기존 필드 우선)

2. CareerSpan 결정
   데뷔 연도, 종료 연도, 커리어 길이

3. 연도별 PlayerSeason 생성
   §2~§4의 통계 분포를 이용해 각 시즌 능력치 Profile 생성

4. 연도별 원소속 배정
   OriginFranchiseId / OriginTeamSeasonKey 확정
   이 값은 Bake 후 모든 World에서 고정

5. 시즌 스냅샷 확정
   Z-Score → Rating → Cost → TrainingCeiling

6. TeamSeason 배치
   02절의 공통 25인/외국인/투수 역할 규칙을 만족하도록 Core25 및 전체 Pool 구성

7. Original Record 연결
   `OriginalHistory`에서 사용할 Runtime-safe 시즌 기록/수상 기록을 PlayerSeasonId에 연결

8. Validation / Bake
```

`TrainingCeiling`은 Person 생성 시점에 만들지 않는다. 그 시즌의 `BaseStat`과 `Cost`가 확정된
후 03절 규칙에 따라 파생한다.

```text
SyntheticCareerGenerator.GenerateCareer(...)
  → SyntheticCareerBlueprint { PlayerPersonId, IReadOnlyList<PlayerSeasonBlueprint> }
```

이 API/도구가 실제로 존재하더라도 **Offline Pipeline 전용**이다.

한 인물의 여러 시즌은 이전 시즌 Z-Score를 다음 시즌 생성의 prior로 약하게 반영해 극단적인
연도 간 단절을 줄인다. 다만 생성이 끝난 뒤에는 이 능력치 궤적이 Baked Content로 고정된다.

### 5.1 개별 시즌 Rating 생성

```text
SyntheticPlayerGenerator.GenerateSeason(
    referencePool,
    priorZ,
    generationRng)
  → PlayerSeasonBlueprint
```

혼합 규칙:

- 시즌마다 3~7개의 Reference를 혼합하고 특정 실제 선수 한 명을 그대로 복사하지 않는다.
- 능력치별 Reference를 달리할 수 있으나 §4의 상관을 심각하게 깨는 조합은 Reject한다.
- 이름/생년월일/좌우타/체격/PersonPotentialTrait은 Person 단위로 유지한다.
- `Rating = 50 + 14 × Z`, 클램프 `[25, 95]`를 초기 기준으로 사용한다.
- 최종 Runtime BaseStat 하드캡은 기존 `AbilityRatings` 규칙(1~99)에 맞춘다.

### 5.2 선수의 원소속은 Bake 고정

`OriginYear`, `OriginFranchiseId`, `OriginTeamSeasonKey`는 PlayerSeason의 정적 정체성이다.
`WorldHistorySeed`가 달라져도 이 값을 다시 뽑지 않는다.

예:

```text
2011 김도윤 / COMETS_2011 / Cost 8
```

은 `SimulatedHistory`와 `OriginalHistory` 모두 같은 Origin을 갖는다. 게임 진행 이후의
트레이드/FA/영입으로 `CurrentRosterState`가 바뀌는 것은 별개이며 Origin은 변하지 않는다.

## 6. 실존 선수 유사도 검사

유사도 검사는 Rating 변환 이전의 `SyntheticFeatureVector` 공간에서 수행한다.

```text
SyntheticFeatureVector = { AvgZ, HrRateZ, BbPercentZ, KPercentZ, SbRateZ, ... }
```

생성 선수의 특징 벡터를 실제 Reference 벡터와 비교해 임계값보다 지나치게 가까운 경우
Offline 생성 단계에서 재생성한다. Position과 생성 시점 나이도 비교 입력에 포함한다.

이 검사는 Runtime에서 수행하지 않는다. 최종 Bake에 들어온 선수는 이미 검사를 통과한 상태여야 한다.

## 7. Original Record와 Runtime Award의 분리

### 7.1 OriginalHistory용 고유 기록

`OriginalHistory`는 과거 기록 Simulation을 생략하고 미리 준비된 Runtime-safe 기록을 사용한다.
따라서 Offline Pipeline은 가상 PlayerSeason/TeamSeason과 연결되는 원기록 Snapshot을 제공해야 한다.

개념 예:

```text
OriginalSeasonRecordDefinition
{
    PlayerSeasonId
    SeasonStatistics
}

OriginalAwardRecordDefinition
{
    SeasonYear
    AwardType
    PlayerSeasonId
    TeamSeasonKey
}
```

프로젝트에 이미 동등한 Record 타입이 있으면 새 타입을 만들지 않고 재사용한다.
실제 KBO 선수 ID/실명/실제 구단명은 이 기록에도 포함하지 않는다.

### 7.2 SimulatedHistory용 수상 기록

**Offline `SyntheticAwardResolver`로 All-Star/GoldenGlove/MVP를 능력치 순위에서 확정하지 않는다.**
`SimulatedHistory`에서는 Baked 선수/구단으로 경기와 시즌을 시뮬레이션한 뒤 실제 Statistics를
기반으로 수상자를 선정한다.

```text
Baked Ability
  ↓
Match / Historical Season Simulation
  ↓
Season Statistics
  ↓
AllStarSelectionResolver
GoldenGloveAwardResolver
RegularSeasonMvpResolver
  ↓
All-Star Game Simulation → AllStarGameMvpResolver
Postseason Simulation    → PostseasonMvpResolver
  ↓
WorldAwardRecord
```

All-Star/GG/MVP Consumer는 수상 기록이 Original에서 왔는지 Simulated에서 왔는지 알 필요가 없다.
두 경로는 모두 `WorldHistorySnapshot`/`WorldAwardRecord`로 변환된다.

## 8. WorldRecordMode — 새 게임 과거 기록 초기화 방식

```text
WorldRecordMode
  SimulatedHistory
  OriginalHistory
```

### SimulatedHistory

- Baked PlayerSeason/TeamSeason을 그대로 사용한다.
- Origin, BaseAttributes, Cost, TrainingCeiling은 변경하지 않는다.
- 과거 Match/Season을 Fast Simulation 경로로 실행해 성적과 수상을 새로 만든다.
- 이 최초 Historical Simulation에는 02절의 원래 정규 Franchise 구단만 참가하며 `AllStarComposite`/`GoldenGloveComposite`/`YearSelectComposite`는 절대 포함하지 않는다.
- Statistics/Award와 `WorldHistorySnapshot`이 먼저 확정된 뒤 02절 `SpecialCompositeTeamBuilder`가 특수 합성팀을 만든다.
- 같은 WorldHistorySeed면 같은 결과, 다른 Seed면 성적/수상 결과가 달라질 수 있다.

### OriginalHistory

- Historical Simulation을 실행하지 않는다.
- §7.1의 Runtime-safe 고유 기록을 공통 `WorldHistorySnapshot`으로 로드한다.
- WorldAwardRecord가 확정된 뒤 02절과 동일한 `SpecialCompositeTeamBuilder` 경로로 AllStar/GoldenGlove/YearSelect 특수 합성팀을 구성한다.

두 모드 모두 게임 시작 이후 새 시즌은 실제 게임 Simulation으로 진행한다.
`WorldRecordMode`는 미래 시즌을 미리 고정하는 옵션이 아니다.

## 9. Bake 산출물과 Manifest

최종 Bake에는 개별 가상 선수까지 포함한다.

```text
EraNormalizationConfig
PositionGroupReferenceData         // Editor 검증/재생성용. Runtime 배포 여부는 최소화
PlayerPersonDefinition[]
PlayerSeasonDefinition[]
Normal Card Base Definition[]
TeamSeasonDefinition[]
OriginalSeasonRecordDefinition[]
OriginalAwardRecordDefinition[]
SyntheticContentManifest
```

Manifest 예:

```text
SyntheticContentManifest
{
    ReferenceDataVersion
    GeneratorVersion
    BalanceVersion
    GenerationSeed
    ContentHash
}
```

같은 Reference/Generator/Balance/Seed 조합은 동일한 Stable ID와 ContentHash를 생성해야 한다.
Card/Player/Season ID를 Bake 때마다 무작위 GUID로 새로 바꾸지 않는다.

## 10. 검증 기준

- Synthetic 선수 분포(평균/표준편차/포지션 비율)가 Reference 분포와 통계적으로 유사한지 검증.
- 동일 Offline Generation Seed와 동일 버전으로 Bake했을 때 Stable ID와 ContentHash가 동일한지 검증.
- Runtime Assembly/Game Flow에서 `SyntheticCareerGenerator`/`SyntheticPlayerGenerator`/
  `SyntheticTeamGenerator`가 호출되지 않는지 검증.
- 실존 선수 유사도 Reject를 통과하지 못한 조합이 최종 Bake에 남지 않는지 검증.
- 한 `PlayerPersonId`의 연속 시즌 능력치가 비정상적으로 단절되지 않는지 검증.
- `PersonPotentialTrait`은 Person당 1회, `TrainingCeiling`은 시즌별 BaseStat+Cost 이후 파생되는지 검증.
- 다른 WorldHistorySeed에서도 `PlayerSeasonId`, BaseAttributes, Cost, TrainingCeiling,
  OriginYear/OriginFranchiseId/OriginTeamSeasonKey가 동일한지 검증.
- `SimulatedHistory`에서 Award Resolver가 `SeasonStatistics` 없이 BaseAttributes만으로 수상자를
  확정할 수 없는 API인지 검증.
- 같은 Baked Content + 같은 WorldHistorySeed에서 Historical Statistics/Award가 동일한지 검증.
- 다른 Seed에서는 성적/All-Star/GG/MVP가 달라질 수 있는지 통계적으로 확인.
- `OriginalHistory` 선택 시 Historical Simulation이 호출되지 않고 고유 기록이 공통
  `WorldHistorySnapshot`으로 변환되는지 검증.
- `SimulatedHistory` 최초 기록 생성에 특수 합성팀이 참가하지 않고 원래 정규 구단만 사용되는지 검증.
- 두 WorldRecordMode 모두 Award/History 확정 이후에만 특수 합성팀 Builder가 실행되는지 검증.

두 단일 검증본은 바이트 단위 SHA-256까지 같았고, 분할 Editor Archive를 다시 읽어 원본과 같은

Cost/TrainingCeiling 산출 순서, 25인 구성, 외국인/중복, 실명 금지, 유사도 하한을 Offline에서
검증한다.

### 11.2 Editor Asset 경계

이번 단계에서 생성하는 Bake 파일의 유일한 보관 위치는 다음과 같다.

```text
Assets/Editor Default Resources/HistoricalSimulation/1982-2025/
  manifest.json
  player_persons.json
  Years/
    1982.json
    ...
    2025.json
```

실제 생성물은 JSON 46개, 총 12,908,847 bytes다. Manifest의 파일별 SHA-256과 Archive Hash,
재조립한 내용, 동일 Seed 재생성 전후 46개 파일의 바이트 일치를 검증했고 Unity Import/Compile도
종료 코드 0으로 통과했다.

이 경로는 Unity Editor의 `EditorGUIUtility.Load`/`LoadRequired`용이며 Runtime
`Resources.Load` 경로가 아니다. 일반 `Assets/**/Resources`에 복사하지 않는다. 현재 파일은
Editor 재생성·검증 Source이고, Player Build에 넣을 Runtime 배포 포맷/Provider가 확정됐다는
뜻이 아니다.

### 11.3 아직 Phase Gate를 닫지 못한 항목

- 실제 `ICareerBakedContentProvider` 구현과 배포 데이터 로더가 없다.
- `NewGameConfiguration` 기본은 `LegacyRuntimeSynthetic`이며 `CareerWorldFactory`에
  `TeamGenerator` 경로가 남아 있어 "Runtime Synthetic 호출 0" 조건은 아직 충족하지 못했다.
- `IHistoricalDetailedSeasonSource`의 실제 Schedule/Lineup 공급 구현이 없어
  `SimulatedHistory` 전체 과거 시즌을 아직 실행하지 않았다.
- 다중 World Seed 통계와 전체 Career 장기 회귀는 시뮬레이션 코드 개선 후 수행한다.

따라서 Phase 1은 **Editor Bake 산출물과 결정론 검증은 완료, Runtime 소비 경계는 부분 완료**로
기록한다.
