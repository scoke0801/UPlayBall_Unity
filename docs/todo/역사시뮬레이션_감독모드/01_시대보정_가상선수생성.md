# 01. 시대 보정과 가상 선수 생성

## 0. 목적

`docs/KBO_REFERENCE_DATA_PIPELINE.md`가 만드는 정규화 JSON(연도별 선수·팀·수상 기록)을
게임에 넣을 수 있는 **가상 선수·가상 구단 능력치 분포**로 변환한다. 실제 선수·구단 데이터는
이 단계를 넘어 런타임에 도달하지 않는다.

```text
KBO Normalized JSON (기존 구현)
  ↓
Era/Role Normalization          (본 문서 §2, Editor)
  ↓
Reliability Shrinkage           (본 문서 §3, Editor)
  ↓
Correlation Extraction          (본 문서 §4, Editor)
  ↓
Editor 전용 익명 Reference SO 굽기 (본 문서 §7, Editor — 여기까지 Editor 경계)
  ↓
──────────────── 어셈블리 경계 ────────────────
  ↓
Synthetic Career/Player Generator (본 문서 §5, Baseball.Simulation, 새 게임/월드 생성 시점 실행)
  ↓
Synthetic Team Fingerprint         (02절, Baseball.Simulation)
```

## 1. 어셈블리 배치 — Editor 경계와 Simulation 경계를 명확히 분리

이전 초안은 "생성 파이프라인 전체를 Editor/오프라인 도구에 둔다"고 썼는데, 이는 README가
`SyntheticPlayerGenerator`를 `Baseball.Simulation` 순수 C#으로 규정한 것과 모순됐다. 이
문서에서 최종적으로 확정하는 배치는 다음과 같다.

```text
Baseball.Editor / 오프라인 도구 (Python/Tools)
  §2 Era/Role Normalization
  §3 Reliability Shrinkage
  §4 Correlation Extraction
  §7 PositionGroupReferenceSO 굽기 (μ, σ, 상관행렬, Reliability 상수 — 실명 없는 분포 데이터만)

Baseball.Simulation (순수 C#, Unity 비참조, 결정론적 RNG 주입)
  §5 SyntheticCareerGenerator / SyntheticPlayerGenerator
    — Game 레이어가 PositionGroupReferenceSO를 순수 C# 구조체로 변환해 주입한 뒤,
      새 게임/월드 생성 시점에 이 Resolver가 실제 가상 선수·커리어를 생성한다.
    — 즉 "가상 선수 데이터"는 Editor에서 미리 구워두는 것이 아니라, 월드마다 결정론적으로
      새로 생성된다(같은 Seed → 같은 가상 선수 집단).
```

**Runtime(`Baseball.Core`, `Baseball.Simulation`)은 KBO Raw JSON이나 실명 데이터를 절대 직접
읽지 않는다.** Simulation이 참조하는 것은 §7에서 만드는 "익명 분포 SO"를 Game 레이어가
변환한 순수 C# 구조체뿐이다. 이는 `docs/KBO_REFERENCE_DATA_PIPELINE.md` 마지막 절("후속 SO
단계")의 계약과 동일하다 — "Runtime Synthetic Generator가 Raw JSON이나 KBO Season SO를
직접 참조해서는 안 된다."

## 2. 시대·역할 정규화

같은 절대 기록도 시대에 따라 가치가 다르다. 모든 raw 기록은 다음 집단 내부에서만 비교한다.

```text
GroupKey = OriginYear + PositionGroup + RoleTier
```

- `PositionGroup`: 타자는 포지션, 투수는 선발/불펜.
- `RoleTier`: 규정 타석/이닝 충족 여부(주전/서브) — 규정 미달 선수를 주전 분포에 섞지 않는다.

각 지표(AVG, OBP, SLG, HR/PA, BB%, K%, SB rate, ERA, WHIP, K/9, BB/9 등)에 대해 그룹 평균 `μ`,
표준편차 `σ`를 구하고 Z-Score로 변환한다.

```text
Z = (Stat - μ_group) / σ_group
```

이 Z-Score가 이후 모든 능력치 산출의 입력이다. 절대 기록 수치를 능력치 산식에 직접 넣지 않는다.

## 3. 표본 크기 보정 (Reliability Shrinkage)

표본이 작은 선수의 극단값을 평균 방향으로 회귀시킨다.

```text
Reliability(PA)  = PA  / (PA  + PA_ReliabilityConstant)
Reliability(TBF) = TBF / (TBF + TBF_ReliabilityConstant)

AdjustedZ = RawZ × Reliability
```

`PA_ReliabilityConstant`(초기값 250), `TBF_ReliabilityConstant`(초기값 200)는 하드코딩하지 않고
변환 설정 파일(§7의 `EraNormalizationConfig`)에 둔다. 실제 KBO 분포로 검증 후 조정한다 —
"20타석 4할"과 "500타석 4할"이 같은 값으로 취급되면 안 된다는 것이 검증 기준이다.

## 4. 상관관계 추출 (Covariance)

완전 독립 랜덤 생성은 비현실적인 선수(장타력은 최상급인데 번트만 특출난 선수 등)를 만든다.
따라서 능력치 그룹 간 공분산 행렬을 실제 데이터에서 추출해 생성 단계에서 사용한다.

최소 보존 대상 상관:

```text
Power ↔ HR Rate
Contact ↔ K% (역상관)
Speed ↔ SB Rate
Control ↔ BB/9 (역상관)
Stuff ↔ K/9
Stamina ↔ (선발) IP/G
```

구현은 다변량 정규분포에서 Cholesky 분해로 상관을 유지한 채 표본을 뽑는 방식을 권장한다.
Core에 새 수학 유틸을 만들지 말고, 이미 프로젝트에 결정론적 RNG 유틸이 있으면 그 위에 얹는다.

## 5. Synthetic Career/Player Generator — 다년도 커리어 연결

**이전 초안의 가장 큰 누락:** 01~02절이 "연도별 가상 선수를 각각 생성"하는 것까지만
다루고, `2010 김도윤`과 `2011 김도윤`을 **같은 인물**로 연결하는 단계가 없었다. 이대로면
03절의 `PlayerPersonDefinition → 여러 PlayerSeasonDefinition` 구조(한 인물이 여러 연도
카드를 가진다는 전제)가 성립하지 않는다. 따라서 생성 순서를 다음으로 고정한다.

```text
1. Person 생성           — PlayerPersonId, 이름, 생년월일, 좌우타, 체격, 성격, 성장곡선,
                           PersonPotentialTrait(03절 §1.1, 능력치별 성장 성향, Person당 1회만 생성)
2. CareerSpan 결정        — 데뷔 연도, 은퇴(또는 현재) 연도, 커리어 길이
3. 연도별 PlayerSeason 생성 — CareerSpan의 각 연도마다 §2~§4 정규화를 거친 Z-Score 표본을 배정
4. 연도별 소속/이적 배정    — 각 연도의 FranchiseId (트레이드/이적으로 연도마다 바뀔 수 있음)
5. 시즌 능력 스냅샷 확정    — 연도별 Z-Score → §5.1 Rating 변환 → Cost 확정(03절 §2) →
                           TrainingCeiling 파생(03절 §1.1, BaseStat+Cost 기반, 시즌마다 새로 계산)
6. TeamSeason 배치        — 확정된 PlayerSeason을 해당 연도 TeamSeason의 Core25/AllNormalCardIds에 배치
```

**주의:** `TrainingCeiling`은 1단계에서 정하지 않는다. `PersonPotentialTrait`(1단계, 성향만)과
`TrainingCeiling`(5단계, 그 시즌의 실제 BaseStat+Cost로부터 파생된 절대 상한)을 혼동하지
않는다 — 03절 §1.1이 이 둘을 분리한 이유(저코스트 시즌이 고코스트 시즌의 절대 수준을
따라잡지 못하게 하는 것)를 그대로 따른다.

```text
SyntheticCareerGenerator.GenerateCareer(
    referencePools: IReadOnlyDictionary<GroupKey, IReadOnlyList<PlayerSeasonReference>>,
    rng: IDeterministicRandom)
  → SyntheticCareerBlueprint { PlayerPersonId, IReadOnlyList<PlayerSeasonBlueprint> }
```

한 인물의 여러 시즌은 **연도가 바뀌어도 능력치 궤적이 급격히 튀지 않도록** 이전 시즌의
Z-Score를 다음 시즌 추첨의 사전 분포(prior)로 약하게 반영한다(완전 독립 재추첨 금지 —
그렇지 않으면 "2010 백업급 선수가 2011 갑자기 리그 최정상급"처럼 부자연스러운 궤적이
나온다). 이 단계에서 비로소 03절의 "`2009 Normal → 2010 AllStar → 2011 MVP`" 같은 자연스러운
커리어 성장 궤적이 생긴다.

### 5.1 개별 시즌 Rating 생성

`SyntheticPlayerGenerator`는 `SyntheticCareerGenerator`가 각 연도마다 호출하는 하위 단계다.
한 명의 실제 선수를 이름만 바꿔 복사하지 않는다 — 각 시즌마다 반드시 3~7개의 Reference
Pool을 혼합한다.

```text
SyntheticPlayerGenerator.GenerateSeason(
    referencePool: IReadOnlyList<PlayerSeasonReference>,   // 동일 GroupKey 후보들
    priorZ: PlayerAbilityZVector?,                          // 직전 시즌 Z-Score (커리어 연속성)
    rng: IDeterministicRandom)
  → PlayerSeasonBlueprint
```

혼합 규칙:

- Contact/Power/Speed/Bunt/Defense/Mental(투수는 대응 6항목) 각각을 **서로 다른 Reference**에서
  가져올 수 있게 하되, §4의 상관관계를 깨지 않는 조합만 허용한다(상관 위반 조합은 재추첨).
- 이름, 생년월일, 출신, 좌우타, 체격, 성격, 성장곡선, 잠재력은 §5의 Person 생성 단계에서
  이미 정해져 있으므로 시즌마다 다시 생성하지 않는다.
- 능력치 스케일: `Rating = 50 + 14 × Z`, 클램프 `[25, 95]`. 100은 이후 팀컬러/카드강화용으로
  남겨두고 원본 생성 단계에서는 쓰지 않는다(04절 §1.1의 BaseStat 1~99 하드캡과 정합).
- `PersonPotentialTrait`(03절 §1.1, 능력치별 성장 성향)은 §5 1단계에서 Person당 한 번
  생성하고 시즌마다 재생성하지 않는다 — 한 인물이 "어느 능력치가 상대적으로 더/덜 자라는
  유형인가"는 커리어 내내 일관돼야 한다. 다만 이 값 자체는 절대 상한이 아니며, 시즌별
  `TrainingCeiling`은 §5 5단계에서 그 시즌의 BaseStat과 Cost로부터 매번 새로 파생한다
  (03절 §1.1).

### 5.2 SyntheticAwardResolver — Edition 자격 부여

**이전 초안의 누락:** 03절은 "연도당 AllStar 24~30명, GoldenGlove 10명, MVP 최대 3명"이라고
인원만 정의했지, 그 인원을 그 해 어떤 가상 선수로 채우는지는 정의하지 않았다. 이 규칙이
없으면 Phase 5 구현자가 임의로 정하게 된다. 이 단계는 01절 §5의 5단계(시즌 능력 스냅샷
확정) 직후, 06절 TeamSeason 배치 이전에 실행하며, 그 연도(GroupKey)의 모든
`PlayerSeasonBlueprint`가 확정된 뒤에만 돌 수 있다(같은 해 선수들끼리 비교해야 하므로).

```text
SyntheticAwardResolver.ResolveYear(
    yearSeasons: IReadOnlyList<PlayerSeasonBlueprint>,   // 그 OriginYear에 속한 모든 시즌 카드
    rng: IDeterministicRandom)
  → SyntheticAwardResult { AllStarPersonIds[], GoldenGlovePersonIds[], MvpAwards[] }
```

세 개의 하위 Resolver로 나눈다.

**AllStarResolver** — 포지션 그룹별(P/C/1B/2B/3B/SS/OF/DH)로 쿼터를 두고, 그룹 안에서 §2의
`RoleAdjustedOverall`(포지션 보정 종합 능력치) 상위 N명을 뽑아 연도당 합계 24~30명을
채운다. 포지션별 쿼터는 데이터화(`AllStarQuotaTable`)한다 — 코드에 포지션 이름을 하드코딩
하지 않는다.

**GoldenGloveResolver** — 정확히 10명: P/C/1B/2B/3B/SS 각 1명 + OF 3명 + DH 1명. 각
포지션에서 `RoleAdjustedOverall` 1위 한 명만 선정한다(동률 시 결정론적 RNG로 타이브레이크).
AllStarResolver와 별개로 독립 실행한다 — 같은 선수가 AllStar이면서 동시에 GoldenGlove일
수 있다(그러면 03절 §3처럼 두 Edition 카드가 모두 생성된다).

**MvpResolver** — 세 슬롯을 각각 결정론적으로 선정한다.

```text
RegularSeasonMvp   — 포지션 제한 없이 그 해 전체 선수 중 종합 가치 지표
                     (타자는 Power+Contact+Speed 가중합, 투수는 Stuff+Control+Stamina 가중합
                     등 CompositeValueScore로 통일해 비교) 1위.
AllStarGameMvp     — AllStarResolver가 뽑은 선수 집단 안에서, CompositeValueScore 상위 소수
                     (예: 상위 5명) 중 결정론적 RNG로 1명 추첨 — 실제 한 경기 활약처럼
                     상위권 안에서의 우연성을 반영한다(무조건 최상위 1명 고정은 지양).
PostseasonMvp      — 이 시점(월드 생성 이전의 과거 시즌 시드)에는 실제 포스트시즌 시뮬레이션이
                     없으므로, 해당 연도 `ReferenceStrength` 상위 2개 TeamSeason 소속 선수
                     중 CompositeValueScore 1위로 대체 선정한다. 이 대체 로직으로도 후보를
                     특정할 수 없는 해(TeamSeason 데이터 부족 등)에는 **그 해의
                     PostseasonMvp Edition을 생성하지 않는다** — 매 연도 정확히 3명을
                     강제하지 않는다.
```

한 인물이 여러 MVP 슬롯을 동시에 차지해도(예: 정규시즌 MVP와 올스타전 MVP를 같은 해에 모두
차지) Mvp Edition 카드는 03절 §3대로 1장만 생성하고, 수상 이력만 `MvpAwardRecords[]`에
누적한다.

**중요한 범위 제한:** `SyntheticAwardResolver`는 **월드 생성 시점에 KBO Reference 연도로부터
과거 시즌 카드를 시드할 때만** 사용한다. 월드가 시작된 뒤 실제로 플레이되는 미래 시즌
(예: 게임 내 2037시즌)의 AllStar/GoldenGlove/MVP 수상자는 이 Resolver가 아니라 **그 시즌의
실제 시뮬레이션 결과**로 결정해야 한다 — 이는 이 폴더의 범위가 아니라 기존(또는 별도 구현할)
시즌 진행/시상 시스템의 책임이며, `docs/구현_현황.md` 등 기존 시즌 루프 문서를 따른다. 다만
그 시즌 결과를 03절의 `PlayerCardDefinition.Edition`으로 변환하는 마지막 단계(수상자 →
AllStar/GoldenGlove/Mvp Edition 카드 생성)는 이 문서의 03절 §3 규칙을 그대로 재사용한다.

## 6. 실존 선수 유사도 검사

**비교 공간을 명확히 한다.** 생성된 선수의 게임 Rating(Contact/Power 등)은 실제 KBO 지표
(AVG/HR Rate 등)와 스케일이 다르므로 직접 비교할 수 없다. 유사도 검사는 **Rating 변환 이전,
§2~§4의 Z-Score 특징 벡터(`SyntheticFeatureVector`) 공간**에서 수행한다.

```text
SyntheticFeatureVector = { AvgZ, HrRateZ, BbPercentZ, KPercentZ, SbRateZ, ... }  // Reference와 동일 축
```

생성된 선수의 `SyntheticFeatureVector`를 Reference Database의 각 실제 선수 시즌
`SyntheticFeatureVector`와 비교해 Distance가 임계값 미만이면 재생성한다. 비교 대상에는
Position, 그리고 생성 시점 기준 나이(§5의 CareerSpan에서 파생)도 함께 포함한다.

특히 "실제 유명 선수의 특정 시즌이 바로 연상되는 조합"은 명시적으로 Reject한다. 이 검사는
**§5 `SyntheticCareerGenerator`가 각 시즌을 생성할 때마다** 수행한다(Editor 사전 계산이
아니다 — §1에서 확정했듯 실제 생성은 Simulation에서 새 게임/월드 시점에 일어나므로, 검사도
그 시점에 함께 실행되고 재생성 루프를 돈다).

## 7. Editor 전용 Derived Reference SO

**여기서 굽는 SO에는 개별 가상 선수가 들어가지 않는다.** §1에서 확정했듯 개별 가상 선수는
Simulation이 새 게임/월드 생성 시점에 만든다 — Editor는 그 생성에 필요한 분포·설정만
굽는다.

```text
EraNormalizationConfig      // §2, §3의 상수 (그룹 정의, Reliability 상수)
PositionGroupReferenceSO    // 그룹(GroupKey)별 μ, σ, 상관행렬, 유사도 검사용 실제 선수
                             // SyntheticFeatureVector 목록(§6, 실명 없이 특징 벡터만)
```

이 SO들은 `Assets/10.Datas/`에 두되, KBO Raw JSON이나 실명 문자열을 필드로 갖지 않는다.
Game 레이어가 이 SO를 읽어 순수 C# 구조체로 변환해 Simulation에 주입하는 기존 밸런스 테이블
패턴(`BaseballManager_PROJECT.md`/`CLAUDE.md`의 "밸런스 테이블" 절)을 그대로 따른다.
`SyntheticCareerGenerator`/`SyntheticPlayerGenerator`는 이 구조체만 입력받고 SO를 직접 읽지
않는다(Simulation의 Unity 비의존 계약).

## 8. 검증 기준

- Synthetic 생성 선수 집단의 분포(평균/표준편차/포지션별 비율)가 Reference 분포와 통계적으로
  유사한지 EditMode 테스트로 확인한다(예: KS 검정 또는 평균 차이 허용 오차).
- 동일 Seed로 두 번 생성한 결과(커리어 전체, 연도별 시즌 포함)가 완전히 일치하는지 결정론
  테스트로 확인한다.
- §6 유사도 검사를 통과하지 못하는 조합이 재생성 없이 통과되는 회귀가 없는지 테스트한다.
- 한 `PlayerPersonId`의 연속된 시즌 Z-Score가 직전 시즌과 극단적으로 단절되지 않는지(§5
  prior 반영이 실제로 동작하는지) 테스트한다.
- `PersonPotentialTrait`이 Person 생성 시 한 번만 만들어지고 시즌마다 재생성되지 않는지
  테스트한다.
- 같은 Person의 서로 다른 시즌이 서로 다른 `TrainingCeiling`을 가지며, 저코스트 시즌의
  `TrainingCeiling`이 고코스트 시즌의 BaseStat 수준을 넘지 않는지 테스트한다(03절 §1.1의
  Headroom 스케일이 실제로 동작하는지).
- `SyntheticAwardResolver`가 연도별로 AllStar 24~30명, GoldenGlove 정확히 10명(포지션당
  쿼터 준수)을 선정하는지, MVP 세 슬롯이 후보 부족 시 강제로 채워지지 않고 비어있을 수
  있는지 테스트한다.
- 동일 Seed로 두 번 돌린 `SyntheticAwardResolver` 결과(AllStar/GoldenGlove/Mvp 선정자)가
  완전히 일치하는지 결정론 테스트로 확인한다.
