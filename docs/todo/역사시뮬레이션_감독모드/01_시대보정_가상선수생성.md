# 01. 시대 보정과 Source-backed 가상 선수 Bake

## 0. 목적

`docs/KBO_REFERENCE_DATA_PIPELINE.md`가 만드는 정규화 JSON(연도별 선수·팀·수상 기록)을
게임에서 사용할 수 있는 **Source-backed 가상 선수·가상 구단용 Runtime-safe 콘텐츠**로 변환한다.

가상화는 실제 인물·구단 식별자를 제거하는 콘텐츠 경계다. 선수의 실력 정본을 여러 실제 선수로
합성하는 과정이 아니다. 한 Source Player는 한 가상 `PlayerPersonDefinition`에, 한 Source
PlayerSeason은 한 가상 `PlayerSeasonDefinition`에만 대응한다.

가장 중요한 경계는 다음과 같다.

- Source PlayerSeason의 연도별 BaseAttributes와 Cost는 **Offline/Editor에서 확정하여 Bake**한다.
- Runtime에서 새로운 가상 선수를 생성하거나 원소속 구단을 다시 추첨하지 않는다.
- 같은 Source Player의 여러 시즌은 같은 가상 Person ID와 가명을 사용한다.
- 한 Runtime PlayerSeason에 여러 Source PlayerSeason을 혼합하거나, 하나의 Source PlayerSeason을
  여러 일반 Runtime PlayerSeason으로 복제하거나, 다른 연도 기록으로 위장하는 것을 금지한다.
- 10개 정규 Franchise의 Core25 Hitter140/Pitcher110 quota를 Source-backed 선수만으로 채울 수 없을 때만
  `ReplacementGenerated`를 생성한다. Replacement에는 `SourcePlayerId`가 없다.
- 실제 시즌 성적과 수상 기록은 별개의 축이다. 새 게임에서 `WorldRecordMode`에 따라 과거 기록을 시뮬레이션하거나 Bake된 고유 기록을 로드한다.
- 실제 KBO 실명·실제 구단명·Raw 식별자는 Runtime 경계를 넘지 않는다.

```text
KBO Normalized JSON
  ↓
Source Player / Source PlayerSeason 1:1 Join
  ↓
Season Position / NaturalPitcherRole 파생
  ↓
OriginYear + Position/Role 공통 Baseline
  ↓
Reliability Shrinkage → BaseAttributes
  ↓
Role-adjusted Composite → Source population Cost threshold
  ↓
10개 가상 Franchise에 Source-backed 시즌 배정
  ↓
부족 슬롯만 ReplacementGenerated 생성
  ↓
가변 Team Pool / Core25 구성 (02절)
  ↓
Runtime-safe Original Season Record 변환
  ↓
Validation + Content Bake + Manifest/Hash
  ↓
──────────────── Runtime Boundary ────────────────
  ↓
Baked Definition Load
  ↓
New Game: SimulatedHistory 또는 OriginalHistory → 공통 WorldHistorySnapshot
```

## 1. 어셈블리 배치 — 생성은 Offline, Runtime은 소비만 한다

### 1.1 Offline / Editor

다음은 `Baseball.Editor`, Python/Tools 또는 동등한 Offline Data Pipeline의 책임이다.

```text
Source Person/Season Join
Era/Position/Role Normalization
Reliability Shrinkage
SourceBackedPlayerSeasonDeriver
FictionalIdentityMapper
SourceBackedTeamAllocator
ReplacementPlayerGenerator
Cost / TrainingCeiling 계산
Runtime-safe Original Record 변환
Content Bake / Manifest 생성
```

`ReplacementPlayerGenerator`는 Source-backed 후보가 부족한 슬롯을 채우는 Offline 전용 도구다.
순수 계산 코드의 테스트 재사용을 위해 Engine-independent 라이브러리로 분리할 수는 있으나,
**실제 Game Runtime Flow에서는 Source-backed 파생기·배치기·Replacement 생성기를 호출하지 않는다.**

### 1.2 Runtime

Runtime은 다음과 같은 Bake 결과만 읽는다.

```text
PlayerPersonDefinition
PlayerSeasonDefinition
Normal Card Base / Edition Modifier Definition
TeamSeasonDefinition
OriginalSeasonRecordDefinition
OriginalAwardRecordDefinition      // OriginalHistory용, 실제 식별자는 제거된 가상 콘텐츠 기록
HistoricalContentManifest
```

`Baseball.Core`/`Baseball.Simulation`이 KBO Raw JSON이나 실제 선수/구단 식별자를 직접 읽는 경로는 금지한다.

## 2. 시대·역할 정규화

같은 절대 기록도 시대에 따라 가치가 다르므로 Source-backed 시즌 기록은 다음 공통 집단 내부에서
비교한다.

```text
HitterGroupKey  = OriginYear + PositionGroup
PitcherGroupKey = OriginYear + NaturalPitcherRoleGroup
```

- `PositionGroup`: 타자의 해당 시즌 Natural Position.
- `NaturalPitcherRoleGroup`: 투수의 해당 시즌 자연 역할.
- `RoleTier(Qualified/Limited)`: 표본 신뢰도와 진단을 위한 metadata일 뿐 Z-score baseline을 나누지 않는다.

각 지표(AVG, OBP, SLG, HR/PA, BB%, K%, SB rate, ERA, WHIP, K/9, BB/9 등)는 그룹 평균 `μ`,
표준편차 `σ`를 이용해 Z-Score로 변환한다.

```text
Z = (Stat - μ_group) / σ_group
```

이 Z-Score가 능력치 생성의 입력이다. 한 선수의 분자·분모는 해당 Source PlayerSeason에서만 온다.
같은 그룹 선수들은 평균과 표준편차를 제공할 뿐, 개별 선수의 metric이나 Ability를 혼합하지 않는다.

## 3. 표본 크기 보정 (Reliability Shrinkage)

표본이 작은 선수의 극단값을 평균 방향으로 회귀시킨다.

```text
Reliability(PA)  = PA  / (PA  + PA_ReliabilityConstant)
Reliability(TBF) = TBF / (TBF + TBF_ReliabilityConstant)

AdjustedZ = RawZ × Reliability
```

`PA_ReliabilityConstant`(초기값 250), `TBF_ReliabilityConstant`(초기값 200)는 하드코딩하지 않고
`EraNormalizationConfig`에 둔다. 실제 데이터 분포로 검증 후 조정한다.

## 4. Replacement 전용 분포와 상관관계

Source-backed PlayerSeason의 BaseAttributes에는 난수 생성이나 covariance sampling을 사용하지 않는다.
다만 Source-backed 후보가 부족해 02절의 10개 정규 TeamSeason 계약을 채울 수 없는 슬롯에는 같은
`OriginYear + Position/Role` Source 집단의 aggregate와 covariance로 `ReplacementGenerated`를
생성할 수 있다.

최소 보존 대상:

```text
Power ↔ HR Rate
Contact ↔ K% (역상관)
Speed ↔ SB Rate
Control ↔ BB/9 (역상관)
Stuff ↔ K/9
Stamina ↔ (선발) IP/G
```

Replacement 생성은 다변량 정규분포 + Cholesky 분해 등 데이터 기반 분포를 사용할 수 있다. 다음
제약을 모두 지킨다.

- Source-backed 후보를 모두 사용해도 채울 수 없는 정확한 부족 슬롯 수만 생성한다.
- Hitter 수는 `Max(0, 140 - SourceBackedHitterCount)`, Pitcher 수는
  `Max(0, 110 - SourceBackedPitcherCount)`만 생성한다.
- 예를 들어 1982 Source-backed Hitter102/Pitcher39이면 Replacement는 Hitter38/Pitcher71, 총
  109명이다. Pool 크기를 임의의 고정값으로 맞추기 위한 추가 Replacement는 만들지 않는다.
- `SourcePlayerId`/SourceSeason provenance를 부여하지 않는다.
- 특정 Source vector를 그대로 복사하거나 가장 가까운 실제 선수를 골라 복제하지 않는다.
- 다른 연도 SourceSeason을 현재 `OriginYear` 선수로 위장하지 않는다.
- RNG는 Offline Generation Seed를 주입받고 Stable ID tie-break를 사용한다.
- Source-backed 시즌만 baseline, BaseAttributes formula 검증, composite 분포와 Cost percentile
  threshold의 모집단을 구성한다. Replacement는 확정된 composite threshold에 대입하며 모집단에서
  제외한다.

## 5. Source-backed Person / PlayerSeason — 다년도 커리어 연결

한 인물의 여러 시즌을 slot이나 능력치 유사도로 묶지 않는다. 정규화 Archive의 `SourcePlayerId`가
동일 인물을 연결하는 유일한 정본이다.

```text
1. Source Person 연결
   `SourcePlayerId → Stable PlayerPersonId`를 Offline에서 만들고 가명을 Person당 한 번 확정한다.

2. Source PlayerSeason 연결
   `SourcePlayerId + SeasonYear → Stable PlayerSeasonId`로 실제 해당 시즌 기록을 1:1 연결한다.

3. 연도별 PlayerSeason 파생
   해당 시즌 기록만으로 Natural Position/PitcherRole, Z-score, Reliability, BaseAttributes를 확정한다.

4. Cost 확정
   OriginYear 전체 Source-backed 모집단에서 role-adjusted composite 순위와 percentile threshold를
   계산한다. Runtime Team에 뽑히지 않은 SourceSeason도 모집단에 포함한다.

5. 연도별 가상 원소속 배정
   OriginFranchiseId / OriginTeamSeasonKey 확정
   이 값은 Bake 후 모든 World에서 고정

6. TeamSeason 배치
   해당 OriginYear의 모든 고유 SourceSeason을 10개 팀의 가변 Pool에 중복 없이 배치한다. 10개
   Core25의 Hitter140/Pitcher110 quota 부족분만 ReplacementGenerated로 보충한다.

7. Original Record 연결
   Source-backed는 해당 SourceSeason 기록을 연결한다. Replacement record는 Source record로 가장하지
   않고 별도 provenance를 기록한다.

8. Validation / Bake
```

`TrainingCeiling`은 Source 사실이 아니라 03절의 별도 gameplay rule이다. 유지할 경우 해당 시즌의
BaseAttributes와 Cost가 확정된 뒤 결정론적으로 파생하며, Source에 없는 생년·투타·등록 유형·
Potential을 실제 정보처럼 임의 생성하지 않는다.

### 5.1 Source-backed 시즌 Rating

- Rating의 metric 분자·분모는 정확히 한 Source PlayerSeason에서만 온다.
- 이전 시즌 Ability를 현재 시즌 metric에 섞지 않는다.
- 표본 부족은 같은 Position/Role 공통 prior로 더 강하게 shrink하는 원인이다.
- `Qualified/Limited` 경계는 Rating 불연속을 만들지 않는다.
- Rating clamp와 metric weight는 `DerivationBalance`에 둔다.

### 5.2 선수의 원소속은 Bake 고정

`OriginYear`, `OriginFranchiseId`, `OriginTeamSeasonKey`는 PlayerSeason의 정적 정체성이다.
`WorldHistorySeed`가 달라져도 이 값을 다시 뽑지 않는다.

예:

```text
2011 김도윤 / COMETS_2011 / Cost 8
```

은 `SimulatedHistory`와 `OriginalHistory` 모두 같은 Origin을 갖는다. 게임 진행 이후의
트레이드/FA/영입으로 `CurrentRosterState`가 바뀌는 것은 별개이며 Origin은 변하지 않는다.

## 6. Provenance와 Runtime 익명화

Source-backed 선수는 실제 시즌 기록을 정본으로 사용하므로 Source vector와 가까운 것을 오류로 보는
Similarity Reject를 적용하지 않는다. 대신 다음을 검증한다.

- Editor Source Audit에는 SourcePlayerId/SeasonYear와 파생 Trace를 보존한다.
- Runtime에는 실제 이름, 실제 Source ID, 실제 구단 식별자와 Editor Trace를 포함하지 않는다.
- 같은 SourcePlayerId의 모든 Runtime 시즌은 같은 가상 Person ID와 가명을 사용한다.
- 서로 다른 SourcePlayerId 또는 Replacement Person이 같은 가명을 공유하지 않는다.
- Replacement에는 `dataProvenance=ReplacementGenerated`를 기록하고 Source provenance를 만들지 않는다.
- Runtime 로스터·경기·수상·카드 시스템은 provenance에 따라 선수를 차별하지 않는다.

## 7. Original Record와 Runtime Award의 분리

### 7.1 OriginalHistory용 고유 기록

`OriginalHistory`는 과거 기록 Simulation을 생략하고 미리 준비된 Runtime-safe 기록을 사용한다.
따라서 Offline Pipeline은 가상 PlayerSeason/TeamSeason과 연결되는 원기록 Snapshot을 제공해야 한다.

개념 예:

```text
OriginalSeasonRecordDefinition
{
    PlayerSeasonId
    SeasonStatistics
}

OriginalAwardRecordDefinition
{
    SeasonYear
    AwardType
    PlayerSeasonId
    TeamSeasonKey
}
```

프로젝트에 이미 동등한 Record 타입이 있으면 새 타입을 만들지 않고 재사용한다.
실제 KBO 선수 ID/실명/실제 구단명은 이 기록에도 포함하지 않는다.

Source-backed Original Record는 대응하는 단일 SourceSeason 기록에서 오며 여러 선수 기록을 평균하지
않는다. Replacement의 준비 기록은 같은 연도 생성 모델의 결과임을 Editor provenance에 명시하고
Source 기록으로 가장하지 않는다. Runtime Award Resolver는 두 provenance를 구분하지 않고 같은
Statistics와 Position quota로 평가한다.

### 7.2 SimulatedHistory용 수상 기록

**Offline `SyntheticAwardResolver`로 All-Star/GoldenGlove/MVP를 능력치 순위에서 확정하지 않는다.**
`SimulatedHistory`에서는 Baked 선수/구단으로 경기와 시즌을 시뮬레이션한 뒤 실제 Statistics를
기반으로 수상자를 선정한다.

```text
Baked Ability
  ↓
Match / Historical Season Simulation
  ↓
Season Statistics
  ↓
AllStarSelectionResolver
GoldenGloveAwardResolver
RegularSeasonMvpResolver
  ↓
All-Star Game Simulation → AllStarGameMvpResolver
Postseason Simulation    → PostseasonMvpResolver
  ↓
WorldAwardRecord
```

All-Star/GG/MVP Consumer는 수상 기록이 Original에서 왔는지 Simulated에서 왔는지 알 필요가 없다.
두 경로는 모두 `WorldHistorySnapshot`/`WorldAwardRecord`로 변환된다.

## 8. WorldRecordMode — 새 게임 과거 기록 초기화 방식

```text
WorldRecordMode
  SimulatedHistory
  OriginalHistory
```

### SimulatedHistory

- Baked PlayerSeason/TeamSeason을 그대로 사용한다.
- Origin, BaseAttributes, Cost, TrainingCeiling은 변경하지 않는다.
- 과거 Match/Season을 Fast Simulation 경로로 실행해 성적과 수상을 새로 만든다.
- 이 최초 Historical Simulation에는 02절의 원래 정규 Franchise 구단만 참가하며 `AllStarComposite`/`GoldenGloveComposite`/`YearSelectComposite`는 절대 포함하지 않는다.
- Statistics/Award와 `WorldHistorySnapshot`이 먼저 확정된 뒤 02절 `SpecialCompositeTeamBuilder`가 특수 합성팀을 만든다.
- 같은 WorldHistorySeed면 같은 결과, 다른 Seed면 성적/수상 결과가 달라질 수 있다.

### OriginalHistory

- Historical Simulation을 실행하지 않는다.
- §7.1의 Runtime-safe 고유 기록을 공통 `WorldHistorySnapshot`으로 로드한다.
- WorldAwardRecord가 확정된 뒤 02절과 동일한 `SpecialCompositeTeamBuilder` 경로로 AllStar/GoldenGlove/YearSelect 특수 합성팀을 구성한다.

두 모드 모두 게임 시작 이후 새 시즌은 실제 게임 Simulation으로 진행한다.
`WorldRecordMode`는 미래 시즌을 미리 고정하는 옵션이 아니다.

## 9. Bake 산출물과 Manifest

최종 Bake에는 개별 가상 선수와 provenance 집계를 포함한다.

```text
EraNormalizationConfig
PositionGroupReferenceData         // Editor 검증/재생성용. Runtime 배포 여부는 최소화
PlayerPersonDefinition[]
PlayerSeasonDefinition[]
Normal Card Base Definition[]
TeamSeasonDefinition[]
OriginalSeasonRecordDefinition[]
OriginalAwardRecordDefinition[]
HistoricalContentManifest
SourceBacked/Replacement Count Report
```

Manifest 예:

```text
HistoricalContentManifest
{
    ReferenceDataVersion
    GeneratorVersion
    BalanceVersion
    GenerationSeed
    SourceIdentityPolicyVersion
    SourceSeasonSelectionVersion
    ReplacementGeneratorVersion
    SourceBackedPlayerPersonCount
    SourceBackedPlayerSeasonCount
    ReplacementPlayerPersonCount
    ReplacementPlayerSeasonCount
    ContentHash
}
```

같은 Reference/Generator/Balance/Seed 조합은 동일한 Stable ID와 ContentHash를 생성해야 한다.
Card/Player/Season ID를 Bake 때마다 무작위 GUID로 새로 바꾸지 않는다.

## 10. 검증 기준

- 모든 Source-backed PlayerPerson/PlayerSeason이 Source Player/Source PlayerSeason과 각각 1:1인지 검증.
- 한 Runtime PlayerSeason이 여러 SourceSeason을 참조하거나 하나의 SourceSeason이 일반 Runtime
  PlayerSeason으로 복제되지 않는지 검증.
- Source SeasonYear와 Runtime OriginYear가 일치하며 타연도 기록 위장이 없는지 검증.
- 같은 SourcePlayerId의 모든 시즌이 같은 가상 Person ID와 가명을 사용하는지 검증.
- Source-backed만 baseline/composite/Cost threshold 모집단에 포함되는지 검증.
- Replacement 수가 제약 충족에 필요한 최소 부족분이며 `SourcePlayerId`를 갖지 않는지 검증.
- Replacement의 Position/Role별 분포와 covariance가 해당 OriginYear Source aggregate에서 벗어나지
  않고 특정 Source vector를 복제하지 않는지 검증.
- 동일 Offline Generation Seed와 동일 버전으로 Bake했을 때 Stable ID와 ContentHash가 동일한지 검증.
- Runtime Assembly/Game Flow에서 Source-backed 파생/배치/Replacement Generator가 호출되지 않는지 검증.
- 같은 rate에서 표본이 줄면 공통 prior로 수축하고 Qualified/Limited 경계에서 점프하지 않는지 검증.
- Source에 없는 Person metadata를 실제 정보처럼 임의 생성하지 않는지 검증.
- `TrainingCeiling`을 유지한다면 Source 파생과 분리된 gameplay rule로 BaseStat+Cost 이후 계산하는지 검증.
- 다른 WorldHistorySeed에서도 `PlayerSeasonId`, BaseAttributes, Cost, TrainingCeiling,
  OriginYear/OriginFranchiseId/OriginTeamSeasonKey가 동일한지 검증.
- `SimulatedHistory`에서 Award Resolver가 `SeasonStatistics` 없이 BaseAttributes만으로 수상자를
  확정할 수 없는 API인지 검증.
- 같은 Baked Content + 같은 WorldHistorySeed에서 Historical Statistics/Award가 동일한지 검증.
- 다른 Seed에서는 성적/All-Star/GG/MVP가 달라질 수 있는지 통계적으로 확인.
- `OriginalHistory` 선택 시 Historical Simulation이 호출되지 않고 고유 기록이 공통
  `WorldHistorySnapshot`으로 변환되는지 검증.
- `SimulatedHistory` 최초 기록 생성에 특수 합성팀이 참가하지 않고 원래 정규 구단만 사용되는지 검증.
- 두 WorldRecordMode 모두 Award/History 확정 이후에만 특수 합성팀 Builder가 실행되는지 검증.
- Source-backed와 Replacement가 Runtime Roster/Match/Award/Card eligibility에서 동일하게 취급되는지 검증.

## 11. 구현 및 Bake Gate

기존 3~7 Reference 혼합 Runtime Bake와 그 Hash/Count/Simulation 결과는 이 계약 확정 이전의
**폐기 대상 검증값**이다. 2026-09-03에 Source-backed/Replacement 분리 구현과 재 Bake를 완료했으며,
아래 자동 생성 스냅샷만 현재 Archive 검증값으로 사용한다. Historical World 경기 수와 결정론 Hash는
새 Bake 기준 대량 Simulation을 실행하기 전까지 비어 있어야 한다.

Bake 파일의 공식 보관 위치는 다음과 같다.

```text
Assets/Editor Default Resources/HistoricalSimulation/1982-2025/
  manifest.json
  player_persons.json
  Years/
    1982.json
    ...
    2025.json
  Runtime/                 // Source-backed + 최소 Replacement, 실명 제거 Player Build 입력
    manifest.json
    player_persons.json
    Years/...
```

이 경로는 Unity Editor의 `EditorGUIUtility.Load`/`LoadRequired`용이며 Runtime
`Resources.Load` 경로가 아니다. 일반 `Assets/**/Resources`에 복사하지 않는다. 실제 이름은 이
Editor 경계를 넘지 않는다. Player Build Exporter는 같은 Bake가 `Runtime/`에 생성한 정제 분할본만
읽으며, 원본명 Archive를 직접 복사하지 않는다.

최종 Bake 보고는 Manifest/ValidationReport 한 곳에서 다음을 생성해 문서에 동기화한다.

```text
Source-backed Person/Season 수
Replacement Person/Season 수와 연도·포지션·역할별 생성 사유
Editor/Runtime ContentHash와 ArchiveHash
파일 수/크기
경기 수/결정론 Hash
테스트 수
```
