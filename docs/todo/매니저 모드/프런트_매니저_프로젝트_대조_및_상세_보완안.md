# 프런트 매니저 — 프로젝트 대조 및 상세 보완안

작성일: 2026-09-11. 상태: **소스 대조를 마친 기획 제안, 구현 미착수**.

대상은 구단주 모드의 안내 캐릭터다. 감독 AI·코칭 스태프 능력 개선과 구분한다. 기존 Markdown 통합기획과 HTML 디자인 시안을 검토하되, 아래 구현 근거와 프로젝트 기준에 어긋나는 부분은 이 보완안을 우선 검토한다. 외부 게임의 동작을 추가로 검증한 문서는 아니다.

> 후속 구현: 아래 본문은 구현 전 대조 기록이다. 현재 세 흐름의 코드 연결·저장 버전·검증 및 잔여 범위는 [단계별 구현 결과](프런트_매니저_단계별_구현_결과.md)를 따른다.

## 1. 디렉터 판단

원안의 ‘상황 파악 → 실제 조작 대상 안내 → 결과 확인’ 방향은 유지한다. 다만 60개 조언, 다섯 탭 Drawer, 범용 Flow 엔진을 먼저 만들면 기존 메뉴를 설명하는 별도 메뉴가 생길 가능성이 높다. 첫 목표는 **다음 경기에 필요한 판단을 짧게 정리하고, 사용자가 선택한 구성을 존중하며, 실제 달라진 점을 확인하는 것**이다.

최소 범위는 선수단 검증, 경기 준비, 경기 후 점검 세 흐름이다. 추천을 따르는 횟수나 과제 완수율을 게임의 성과로 취급하지 않는다. 허용되는 약점을 감수하고 타선을 유지하는 것도 정상적인 구단 운영이다. 모든 경기에서 변경을 요구하거나 패배 뒤 반드시 교체를 제안하지 않는다.

## 3. 원안에서 먼저 정정할 사항

1. **내부 코드명:** 화면 명칭은 ‘프런트 매니저’를 유지한다. `FrontOfficeGuide` 전면 개명은 필요하지 않다. 신규 모델명은 구현 때 기존 Guide 명명에 맞춘다.
2. **레이어:** 경제·운영 상태는 실제 소유 서비스에서 조회한다. 원안의 ‘Core/Simulation이 경기·경제·등록 전체 원본’ 표는 Game의 진행·상태 소유까지 옮기라는 뜻으로 사용하지 않는다. Game에서 Presentation ViewModel을 참조해서도 안 된다.
3. **저장 버전:** `NewGameFlow`의 16과 Owner 저장의 19는 다른 경로다. 변경되는 저장 계약의 현재 버전만 올린다. 배포 전 포맷을 위한 신규 마이그레이션은 만들지 않는다. 문서 작업만으로 버전을 올리지 않는다.
4. **RNG:** WorldSeed/EventId를 이용하는 기존 문구 선택은 내부 결정론 장치로 유지할 수 있다. Seed를 사용자 Evidence로 노출하지 않으며 경기 RNG를 소비하지 않는다.
5. **배치:** 96px Dock·440px Drawer는 시안값이다. 실제 안전 영역·130% 글자·고밀도 화면 검증 전 확정 수치로 취급하지 않는다. 본문을 줄이려고 자동 글자 축소를 사용하는 현재 표현과 원안 사이의 차이를 검수 항목으로 남긴다.
6. **착수 규모:** 60개 조언은 보류한다. 세 흐름에서 서로 다른 실제 문제가 확인된 뒤 규칙을 추가한다. 범용 조건식 DSL, 자유 대화, 새 보상·호감도 경제는 도입하지 않는다.

## 4. 최소 콘텐츠 상세

### A. 선수단 문제를 바로 찾기

| 항목 | 상세 |
|---|---|
| 시작 근거 | 현재 등록 검증의 문제 코드·대상, 또는 현재 프리셋 검증 결과 |
| 첫 문장 | ‘현재 선수단에 등록 조건을 충족하지 못한 항목이 있어요.’ 구체적인 수량·역할은 원본 결과로 치환 |
| CTA | 타선 문제는 `RosterLineup`, 투수 보직 문제는 `RosterPitching`으로 연결하고 실제 슬롯 선택 |
| 근거 펼치기 | 현재 상태, 요구 조건, 경기 시작 차단 여부. 합법적인 비주포지션 기용은 경고로 구분 |
| 선택 | 후보 검토, 다른 유효 구성 적용, 허용 경고라면 현재 구성 유지 |
| 후보 부족 | ‘현재 후보로는 해결하기 어려워요.’ 원본 후보 조회에 근거한 경우만 표시. 조건 설명과 수동 스카우트 진입 제공, 구매 강요 없음 |
| 완료 | 해당 문제의 원본 검증 해소와 적용 결과 확인. 전체 선수단에 다른 문제가 남으면 그 사실을 별도 표시 |
| 예외 | 슬롯을 눌렀거나 초안만 바꾼 상태는 미완료. 실패한 저장에는 성공 대사 없음 |

첫 구현은 이미 Adapter가 제공하는 등록 수량·보직 부족부터 시작한다. 포지션·선호 타순·궁합을 하나의 ‘잘못된 배치’로 합치지 않는다. 해당 영역의 공개 판정과 대상 연결이 준비된 항목만 후속 추가한다.

### B. 다음 경기 판단을 세 묶음으로 요약하기

원안의 일곱 단계를 화면에 체크리스트로 강제하지 않는다. 기존 준비 결과를 ‘진행 조건’, ‘검토할 선택’, ‘준비 완료’로 요약한다.

- **진행 조건:** `PresetValidation`과 `CanStartGame`의 실제 차단 항목만 우선 노출한다.
- **검토할 선택:** 예상 선발의 공개 신뢰도, 내 투수 가용성, 공개 궁합·팀컬러·전술 조건 중 근거가 있는 항목 최대 2개. 불확실한 상대 정보를 확인하려고 모든 메뉴를 방문할 필요는 없다.
- **준비 완료:** 차단이 없으면 ‘현재 구성으로 경기 준비를 진행할 수 있어요.’ 기존 경기 준비 화면의 확정 버튼으로 이어진다. Guide CTA가 직접 경기 시작이나 상태 확정을 실행하지 않는다.

목적지는 `MatchCenterAnalysis`와 `MatchCenterLineup`을 기존 Context 진입 절차에 연결한다. 이는 현재 Guide CTA에 모두 연결됐다는 뜻이 아니다. 일반 메뉴 이동으로 Context 복귀 이력을 깨뜨리지 않는다.

**비교 문법 제안:** ‘현재 구성의 장점 → 대안으로 달라지는 점 → 감수할 점’. 비교값은 기존 Preview가 제공할 때만 표시한다. 예를 들어 후보 적용으로 공개 궁합이 개선되더라도 ‘승리할 확률이 높아졌어요’라고 번역하지 않는다. 유효한 대안 비교가 없으면 단순 상태 확인으로 끝낸다.

### C. 경기 결과와 다음 행동 연결하기

공식 결과 공개와 보상 처리가 끝난 뒤 사실 1건, 다음 경기 점검 1건을 기본으로 제시한다. 사건 3개를 항상 채우지 않는다.

| 정보 수준 | 허용 문장 | 금지 해석 |
|---|---|---|
| 공식 기록 | 실제 기록에 따른 ‘이번 경기 볼넷은 …개였어요’ | 볼넷이 많았다는 사실만으로 패배 원인 확정 |
| 공개 상태 변화 | ‘다음 경기 투수진 상태를 확인해 볼까요?’ | 타자의 출전량이 컨디션을 소모한다고 새 규칙 가정 |
| 준비 선택 기록 | ‘경기 전 선택한 구성을 사용했어요’ — 실제 적용 대조가 있을 때 | ‘제 조언대로 해서 이겼어요’ |
| 설명 근거 부족 | 결과·상세 기록 열람만 제공 | 미공개 AI 판단이나 정확한 잔여 체력으로 사후 설명 생성 |

전후 상태가 덮어써지는 항목은 공개 시점의 최소 스냅샷 또는 불변 기록 참조가 먼저 필요하다. 기록 생산부·공개 시점 연결이 확인되지 않은 변화 대사는 출시 대상에서 제외한다. 연패만으로 자동 교체를 권고하거나 한 경기 결과를 전술의 효과 검증으로 취급하지 않는다.

## 5. 목표·이동·표시를 분리하는 계약

아래 모델·상태는 **신규 제안**이며 현재 구현된 API 이름이 아니다.

### 문제의 수명

`IssueKey = 모드 + 세이브 식별 + 시즌/경기 범위 + 규칙 + 대상 + 문제 회차`로 식별한다. 내용 전체 해시는 근거 변경 확인에만 쓰고 동일 문제의 재발 여부는 별도로 추적한다.

- 초안 변경은 새 회차를 만들지 않는다. 적용된 원본 상태가 문제 없음으로 바뀐 뒤 재발하면 새 회차다.
- 무관한 로스터 변경으로 같은 보직 부족이 다시 발화하지 않도록 기존 로스터 해시와 문제별 이력을 분리한다.
- 현재 구성 유지는 선택형 문제에만 허용하고 해당 경기 준비가 끝나면 만료한다. 등록 위반을 해결 처리하지 않는다.
- 보류 기한은 원본 게임 진행 기준으로 계산한다. UI 간격 타이머는 저장된 경기 상태나 시뮬레이션 판단에 참여하지 않는다.
- 화면 닫기는 표시 종료, 과제 종료는 해결·유지·만료·취소 중 하나다. 기존 `GuideMessage` 확인 처리와 같은 의미로 사용하지 않는다.

### 이동의 수명

`Requested → RouteReady → TargetReady`를 구분하고 `Cancelled / Unsupported / TargetMissing` 실패를 반환한다. 실제 구현은 기존 Coordinator를 통해 수행한다.

1. 최신 모드·Profile·시즌 상태에서 행동 지원 여부 확인.
2. 편집 중이면 해당 화면의 기존 저장·취소 정책 적용. 이동 취소 시 초안과 원래 포커스 유지.
3. 요청 식별자와 Route 인스턴스로 늦게 도착한 이전 요청 무효화.
4. 탭·필터·안정 ID를 적용한 뒤 가상 목록의 실제 항목 표시를 기다림.
5. 대상 준비를 확인하고 강조. 화면만 열렸다면 대상 도달 통계에 포함하지 않음.
6. 대상이 사라지면 원본 문제 재평가. 실제 해결이면 종료, 대상 의미 소멸이면 만료, UI 연결 누락이면 재시도 안내.

선수 인물 ID, 카드 ID, 슬롯 ID는 목적에 맞게 구분한다. 같은 선수의 다른 시즌 카드가 잘못 선택되는 것을 막는다. Game은 의미적 목적지·대상만 소유하고 RectTransform·포커스·스크롤은 Presentation이 소유한다.

### 표시의 수명

처음에는 Dock과 현재 과제 카드, 수동 상세만 제공한다. 다섯 탭 Drawer는 콘텐츠가 충분해진 뒤 검토한다. 자동 안내는 한 건만, 경기·모달·드래그·스카우트 연출 중에는 표시하지 않는다. 억제 해제 뒤 오래된 큐를 그대로 보여주지 않고 근거를 재검증한다.

‘안내할 항목 없음’은 정상 빈 상태다. 로딩 중, 근거 조회 실패, 모든 조언 보류 상태와 다른 문구를 쓴다. 수동으로 연 안내를 닫으면 원래 포커스로 돌아간다. 우하단 Dock과 실제 확정 버튼이 겹치면 공용 레이아웃에서 예약 공간을 조정하며 좌표만 임의 이동시키지 않는다.

## 6. 저장·콘텐츠 저작

Owner의 기존 `guideRepeatState`와 새 목표 이력의 역할을 구분한다. 반복 대사 이력을 과제 완료 이력으로 해석하지 않는다. 최소 저장은 문제 회차, 보류 기한, 현재 구성 유지 범위, 추적 목표와 정의 버전이다. 화면 좌표·대사 완성 문자열·Unity 참조는 저장하지 않는다.

세이브를 바꾸거나 모드를 전환하면 대기 이동 요청과 화면 Anchor를 폐기한다. 로드 후 현재 원본 상태로 재검증하며 과거 화면을 자동으로 열지 않는다. 시즌 종료 시 경기 단위 항목을 만료하고, 장기 기록은 요약·보존 정책을 두어 20시즌 동안 표시 이력이 무제한 커지지 않게 한다. 보존 한도는 실제 저장 크기를 측정해 결정한다.

조언 정의마다 다음 연결표를 저작한다: 기존 Fact/추가 Provider, 원본 조회 메서드, 공개 근거, 의미적 대상, 실제 Route 상수, Anchor Adapter, 완료 판정, 기한, 모드 권한, 검증 사례. 셋 중 하나라도 빠진 **근거·목적지·완료 판정**이 있으면 운영 추천 팩에 넣지 않는다. 문자열만 추가하는 방식으로 콘텐츠 수를 늘리지 않는다.

## 7. 구현 순서와 통과 기준

| 순서 | 구체 작업 | 다음 단계 진입 조건 |
|---|---|---|
| 1 | 기존 큐·Fact 유지, Owner 행동별 지원 확인과 이동 결과 반환 | 미지원 행동 홈 대체를 대상 도착으로 처리하지 않음. 빠른 전환·이동 취소 검증 |
| 2 | 등록 문제 한 종류의 대상 연결·상태 재평가·문제 이력 저장 | 안내 → 실제 슬롯 → 사용자 적용 → 해결 → 저장/로드까지 연결 |
| 3 | 같은 경로를 경기 준비 검증으로 확장 | 허용 경고 유지, 상대 정보 부족, 변경된 프리셋 재검증, 기존 준비 확정 통과 |
| 4 | 공용 안전 영역·Dock·문맥 카드, 기존 Presenter 중복 방지 | 실제 선수단·경기 준비 화면에서 버튼 가림·잔존·포커스 탈취 없음 |
| 5 | 공식 결과 이후 공개 기록을 이용한 점검 | 미공개 결과 선노출 없음, 원인 단정 없음, 다음 대상 연결 |
| 6 | 반복·저장 크기·사용성 평가 후 조언 확대 | 현재 흐름의 발견·도달·해결 실패가 정리된 뒤 신규 영역 선정 |

P1 후보는 실제 공개 조회가 있는 팀컬러·전술 비교, 재정 지출 내역, 계약 기한이다. P2는 시즌 회고와 Career 전용 안내다. 시설·스태프 계약·수집 팩의 세부 명령 연결은 이번 감사에서 전수 검증하지 않았으므로 위 세 흐름의 확정 범위에 넣지 않는다.

필수 회귀 사례:

- Guide 켜짐/꺼짐에서 **같은 실제 명령열**을 실행했을 때 경기 이벤트·기록·RNG 결과 동일. 서로 다른 선수 선택의 결과까지 같아야 한다는 뜻은 아니다.
- 등록 부족 → CTA → 잘못된 대상/미지원 행동/다른 카드 선택 방지 → 유효 적용 → 해결. 저장 실패는 미해결 유지.
- 다른 화면에서 해결, 같은 문제가 재발, 무관한 편집, 보류 후 로드, 시즌 변경을 각각 구분.
- Owner → Career 전환 후 구단 편성 행동이 남지 않음. 초기 온보딩 건너뛰기와 신규 과제 해결 분리.
- 정보 부족, 후보 없음, 로딩, 조회 실패에서 서로 다른 상태·다음 행동 제공.
- 원안 해상도와 130% 글자에서 본문·확정 버튼·복귀 동선 확인. 최종 Unity 화면 검증 필수.

정량 평가는 잘못된 목적지와 허위 해결 0건을 기능 통과 기준으로 삼고, 준비까지 이동 수·반복 닫기·자발적 유지 선택을 변경 전후 비교한다. ‘왜 추천했는지, 유지하면 무엇을 감수하는지’를 사용자가 설명할 수 있는지도 확인한다. 현재 측정값은 없으므로 개선율 목표를 실적으로 쓰지 않는다.

## 8. 이번 검토 범위와 잔여 확인

코드·밸런스·저장 포맷은 변경하지 않았다. 컴파일, EditMode, 대량 시뮬레이션, Unity 화면 검증은 실행하지 않았다. 기존 테스트 파일 확인을 통과 실적으로 보고하지 않는다. 구현 시 기존 Headless EditMode와 의미 있는 회귀를 실행하고, 경기 계수까지 바뀌는 별도 작업은 대량 통계 근거를 요구한다.

중요 확인 사항은 현재 Owner CTA의 미지원 행동 홈 대체와 첫 진입 `SkipOnboarding()` 경로다. 이는 확인된 코드 동작이며 모든 사용자에게 문제가 재현됐다는 주장은 아니다. 이번 요청은 기획 보완이므로 임의 수정하지 않았다. Anchor별 실제 선택·스크롤 API, 미저장 편집 보호의 화면별 연결, 경기 후 공개 변화의 생산부는 구현 착수 때 메서드 단위 연결표와 실행 증거를 추가해야 한다.
