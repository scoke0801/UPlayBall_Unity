## 1. 기획 목표와 적용 기준

프런트 매니저는 **현재 플레이 상태를 근거로 필요한 일을 정리하고, 해당 화면의 실제 조작 지점까지 안내하며, 행동 결과를 확인하는 구단 운영 동료**다.

완성할 경험은 다음과 같다.

> “현재 프리셋에 포지션 경고가 있어요.” → [경고 슬롯 보기] → 해당 프리셋·선수·슬롯으로 이동 → 유저가 수정하고 적용 → “포지션 경고가 해결됐어요. 전술카드도 확인해 볼까요?”

통합 기준은 프로젝트 제공 문서 `14_프런트_매니저_가이드_내비게이션_고도화.md`의 시스템·콘텐츠·권한·레이어 구조다. 기존 `front-manager-design.md`에서 화면 수명, 방해 억제, 이동 예외, 실제 완료 판정, UI 크롭·접근성 규칙을 보강했다. 두 초안이 충돌하는 경우 본 문서의 결정이 우선한다.

**문서의 확정 범위:** 제품 동작과 구현 계약의 통합본이다. 이번 작업에서는 저장소를 직접 감사하거나 구현을 실행하지 않았다. SharedGameShellView, ViewModel, Command 등은 프로젝트 에이전트가 제공한 명칭이며 실제 시그니처·파일 위치·구현 완료 여부는 착수 감사에서 확인한다. 수치와 임계값은 원본 시스템을 사용하고, UI 크기·노출 빈도는 명시된 초기 튜닝값을 적용한다.

## 2. 문제와 해결 방향

| 현재 보고된 문제 | 해결 구조 | 완료를 확인할 증거 |
|---|---|---|
| 이미지·도움말이 엉뚱한 곳에 등장 | 공통 Presenter와 Route별 슬롯·보호 영역 계약 | 임의 좌표 출력과 이전 화면 잔존 0건 |
| 무엇을 설명하는지 불분명 | Stable Anchor, 대상 테두리, 짧은 문맥 설명 | 조언 대상과 강조 대상 일치 |
| 메뉴를 다시 찾아야 함 | 대상까지 연결되는 내비게이션 | CTA 이후 실제 탭·대상 도달 |
| 내 상황을 이해하지 못하는 느낌 | Evidence·Confidence·이력 기반 대사 | 근거 펼치기, 행동 전후 변화 확인 |

| 알림·오류·서사가 혼재 | Local Validation, Context Card, Guided Flow, Decision 분리 | 오류마다 큰 캐릭터가 등장하지 않음 |

## 3. 역할과 레퍼런스

프런트 매니저의 역할은 브리핑, 문맥형 조언, 행동 안내, 결과 확인이다. 기존 감독 AI, ManagerTacticalProfile, 코칭 스태프 효과와 분리한다. 조언 수락 여부로 능력치·호감도 보너스·경기 판정이 변하지 않는다. 자유 대화형 생성 AI와 자동 영입·자동 편성은 이번 범위에 포함하지 않는다.

| 참고 대상 | 적용할 원칙 | 적용 위치 |
|---|---|---|
| 엔트리브 프로야구매니저 | 캐릭터가 운영을 돕는 친근한 역할 | 표정·말투·주요 결과 반응 |
| Football Manager | 선수단 상태와 평가에 근거한 운영 판단 | Evidence 기반 조언, 상세 검토 연결 |
| EVE AIR Career Program / Aura | 목표 강조·추적·다른 경로의 진행 인정 | Guided Flow와 완료 판정 |
| OOTP의 메시지 허브 구상 | 제공 프로젝트 문서에서 제안한 뉴스·과제 통합 방식 | Drawer의 할 일·기록·필터 |
| FFXIV 도움말 구상 | 제공 프로젝트 문서에서 제안한 문맥 도움·다시 보기 방식 | 가이드 센터·수동 재열람 |

앞선 조사에서 확인한 자료: [프야매 부매니저 역할 보도](https://www.news1.kr/it-science/general-it/1322107), [Football Manager 공식 가이드](https://www.footballmanager.com/the-dugout/first-10-things-do-fm26), [EVE 공식 AIR Career Program 안내](https://support.eveonline.com/hc/en-us/articles/5194673685148-AIR-Career-Program). 프야매 자료는 검색 결과의 역할 설명 범위만 확인됐다. OOTP·FFXIV의 세부 기능은 이번 통합에서 별도로 검증하지 않았으므로 프로젝트 제공 참고 구상으로 취급한다. 아래 UI 좌표·정책은 본 프로젝트의 설계값이며 레퍼런스의 실제 구현 수치를 뜻하지 않는다.

## 4. 사용자 경험과 공통 UI

### 4.1 Manager Dock — 항상 같은 진입점

모든 관리 화면의 ContentRect 우하단 예약 영역에 둔다. 기본 96×96, 표현 크기 상한 112×112. 기본 상태는 Idle / NewAdvice / Urgent / Muted다. 캐릭터 얼굴, 미확인 과제 Badge, 명확한 도움 라벨을 제공한다.

- 클릭·패드 확인: Advice Drawer 열기.
- 보조 입력 또는 명시적 더보기 버튼: 조언 숨김·설정·가이드 센터. 우클릭만으로 기능을 숨기지 않는다.
- 새 이슈 알림 모션은 1회. 주기적인 점멸·흔들림 없음.
- 실경기·미니게임·전체화면 연출에서는 숨김 또는 해당 화면이 허용한 축소 상태. 조작 중 도움을 자동으로 열지 않는다.
- Dock 위치는 카드마다 바꾸지 않는다. 우하단에 핵심 행동 버튼이 있으면 Shell에서 두 영역을 분리한다.

### 4.2 Context Advice Card — 지금 하는 행동 설명

현재 화면과 직접 관련된 조언 1건만 노출한다. 본문 최대 3줄, 주 행동 1개·보조 행동 1개. 대상 옆 카드는 초상을 생략하는 것이 기본이며 필요 시 48~64px 얼굴만 쓴다.

캐릭터 Stage와 같은 대사를 중복 출력하지 않는다. Stage가 켜져 있으면 대상 옆에는 “경고 슬롯을 선택해 주세요” 수준의 조작 설명만 남긴다. 단순 입력 실패는 기존 Local Validation이 처리한다.

### 4.3 Advice Drawer — 브리핑·다시 보기·근거

오른쪽 ContentRect 안에 폭 440의 Drawer를 연다. 탭은 오늘 / 할 일 / 조언 / 기록 / 가이드이며 설정은 별도 버튼으로 제공한다.

| 영역 | 표시 내용 |
|---|---|
| 오늘 | 현재 유효한 최우선 과제 최대 3개, 각 1개 주 행동 |
| 할 일 | 사용자의 행동이 필요한 항목, 진행·보류 상태 |
| 조언 | 경기 준비·성장·운영·수집 등 카테고리 필터 |
| 기록 | 해결·선택 유지·만료·중요 리포트의 결과 |
| 가이드 | 기능 설명 검색, 읽은 도움말 다시 보기 |
| 왜 이런 조언을 했나요? | 공개 가능한 Evidence, 기준 시점, Confidence |

Drawer는 기본 수동으로 연다. 홈 진입마다 전체 Drawer를 자동으로 열지 않는다. 홈 브리핑은 홈의 예약 Stage 안에서 갱신하고, 공간이 없으면 Dock Badge로 제공한다. 유저가 직접 연 Drawer는 필요 시 본문 일부 위에 표시할 수 있으나, 대상 조작을 시작하면 접어 대상과 핵심 버튼을 드러낸다.

### 4.4 Guided Flow — 선택한 과제 1개 추적

유저가 수락한 흐름은 한 번에 1개 추적한다. 단계 번호, 현재 행동, 나중에, 흐름 종료, 처음부터를 제공한다. 처음부터는 설명 진행만 재평가하며 이미 실행한 게임 명령을 되돌리지 않는다.

다른 메뉴로 나가면 UI만 접고 목표는 유지한다. 다른 경로에서 완료해도 인정한다. 새로운 일반 조언이 추적 중인 목표를 덮지 않는다. 다른 흐름을 선택하면 기존 흐름을 보류하고 진행 이력을 보존한다.

### 4.5 Decision Dialogue와 Bottom Debrief

큰 캐릭터 대화는 새 게임 인사, 시즌 개막·종료, 승강 확정, 우승·주요 수상, 중요한 선택 설명, 핵심 해금의 자연스러운 정지 구간에서만 사용한다.

경기 후 Debrief는 스코어·보상 공개가 끝난 뒤 결과 화면의 예약 영역에 표시한다. 결과 요약, 실제 변화, 다음 행동을 전달한다. 별도 결과 연출과 동시에 겹치지 않는다. 기존 확인 화면이 있는 선택은 매니저가 두 번째 확인 모달을 만들지 않고 설명 영역으로 참여한다.

## 5. 배치·크기 최종 규격

### 5.1 기준과 슬롯

1920×1080, uGUI CanvasScaler 기준 단위. Safe Margin은 좌우 32, 상하 24. ContentRect는 상단 Navigation과 하단 Footer를 제외한 실제 영역이다. 기존안의 화면 절대 좌표와 고정 400px 우측 열은 폐기하고 ContentRect 상대 슬롯을 사용한다.

| 슬롯 | 기본 크기 | 배치·사용 조건 |
|---|---|---|
| DockRightBottom | 96×96, 상한 112×112 | ContentRect 우하단, Primary Action과 별도 예약 |
| StageRight / StageLeft | 캐릭터 220×360 + 말풍선 420×170 | 좌우 배치 시 합성 경계 약 656×360, 간격 16 포함. 전체 영역 확보 필수 |
| HomeBriefing | Stage 말풍선 420×220까지 | 홈의 과제 요약 전용, 넘치면 Drawer 상세 |
| DrawerRight | 폭 440 × ContentRect 높이 | 수동 확장, 내부 스크롤 |
| ContextCard | 폭 340~440, 높이 120~200 | 대상 인접, 내용 넘치면 상세 분리 |
| InlineCard | 기본 320×110 | 해당 탭의 문서 흐름 안에서 높이 자동 확장 |
| BottomDebrief | ContentRect 폭 70%, 높이 240 | 허용 폭 68~76%, 높이 220~280 |
| CenterDecision | 860×500, 상한 960×580 | Safe Area 안에서만 사용, 긴 내용 스크롤 |

Stage는 캐릭터 220px만 확보했다고 표시할 수 없다. 말풍선 포함 전체 경계가 보호 영역과 겹치지 않아야 한다. 선수단 같은 고밀도 화면은 기본 Context Card를 쓰고, Stage는 명시적으로 슬롯이 확보된 경우에만 허용한다.

### 5.2 대상 배치와 충돌 정책

각 Route는 reservedRects, primaryActionRect, scrollViewportRect, modalRect, managerAnchors를 등록한다. 추가로 RouteInstanceId와 AllowedPresentationKinds를 제공한다.

1. Anchor의 Route 인스턴스·활성 상태·대상 Stable ID를 검사한다.
2. 탭·필터를 맞추고 필요하면 ScrollProvider로 노출한다. 드래그·수동 스크롤 중에는 보류한다.
3. 오른쪽 → 왼쪽 → 아래 → 위 순으로 12~20px 간격 후보를 계산한다. 화면별 우선순위 재정의 가능.
4. 화면 밖, 선택 카드·목록 조작 영역, 주요 수치·경고·확정 버튼, 모달과 겹치는 후보를 제외한다.
5. 유효 위치가 없으면 대상 강조만 남기고 설명을 Drawer에 보관한다. 자동 fallback은 Drawer를 강제로 열지 않고 Badge로 알린다. 유저가 도움을 요청한 경우 Drawer를 열 수 있다.
6. Anchor가 없으면 가짜 좌표를 만들지 않는다. 조언의 데이터상 유효성과 UI 구현 오류를 별도로 기록한다.

Stage 좌우 선호는 안전성보다 우선하지 않는다. Dock의 기본 위치는 유지하며 ‘좌측/우측 고정’ 설정은 허용된 Stage 위치를 선택하는 설정으로 정의한다. 대상 카드가 어느 쪽에도 놓일 수 없으면 Drawer로 보낸다.

### 5.3 글자·해상도·입력

- 본문 18~20, 제목 22, 보조 16 기준. 버튼 높이 최소 44, 패딩 16, 간격 8~12.
- 긴 대사를 작은 카드에 맞추려고 글자를 축소하지 않는다. 요약 + 자세히로 분리하고 CTA는 유지한다.
- 1600×900·1366×768: 주요 콘텐츠 최소 너비를 먼저 보장하고 Stage가 안 맞으면 얼굴·카드 또는 Dock으로 축소한다.
- 1280×720 이하: 반신 Stage 사용하지 않음, Dock 얼굴 80~96, Drawer 폭 340~380, Context 폭 300~360, 2줄 요약, Debrief 높이 최대 220.
- 21:9는 ContentRect 기준으로 배치한다. 2560×1440은 같은 논리 구조와 글자 설정을 검증한다.
- Text Scale 130%, 한국어 대비 30% 긴 번역에서도 버튼 유실·잘림이 없어야 한다. 단순 비례 축소만으로 통과 처리하지 않는다.
- 자동 안내는 입력 포커스를 가져가지 않는다. 수동 안내 이동에만 대상 포커스를 적용한다.
- Esc/뒤로는 가장 위의 도움 UI를 한 단계 닫고 원래 유효한 입력 대상으로 복귀한다. 게임 모달이 열려 있으면 모달의 우선순위를 따른다.
- 그림·투명 여백은 Raycast를 차단하지 않는다. 색상 외에 제목·아이콘·테두리로 중요도를 표시한다.

## 7. 조언 생성·우선순위·노출 정책

### 7.1 읽기 전용 입력

기존 immutable ViewModel 또는 동일 Application Service에서 Signal을 만든다. 재정·시설, OpponentScoutingReport/IntelState, LineupPreset 검증, Staff 계약·효과, Condition/Chemistry Breakdown, WorldCardCatalog/Scout, TeamColor/Tactic 결과를 중복 계산하지 않는다.

운영 추천에는 공개 가능한 Evidence 최소 1개와 유효한 다음 행동 최소 1개가 필요하다. 단순 축하·확인에는 행동 버튼이 없어도 된다. 기능 설명의 근거는 해당 기능의 공개 RuleEvidence다.

### 7.2 심각도와 선택 순서

카테고리: Onboarding / Decision / Risk / Opportunity / MatchPrep / Development / Collection / Operation / Narrative / Confirmation.

심각도: Blocker / Urgent / Normal / Info. Blocker는 기존 진행 검증이 실패했을 때 Local Warning으로 전달하며 어느 화면에서나 캐릭터가 튀어나오는 권한을 주지 않는다.

선택 절차는 다음 순서를 고정한다.

1. 모드·Capability·Route·Evidence·기한·억제 정책을 통과한 후보만 유지.
2. 현재 유저 행동의 Blocker 대응을 우선. 이후 사용자가 선택한 추적 흐름을 우선.
3. 일반 후보는 Severity, 현재 화면 관련성, 실제 기한, 예상 영향, 신규성 순으로 비교.
4. 동점은 Stable AdviceId, SubjectStableId 순으로 정렬.

초기 버전은 위 우선순위 비교를 사용한다. 기존 초안의 가중치 합산 점수는 튜닝 확장안으로 남긴다. Normal의 여러 가산점이 Blocker보다 높아지는 구조는 허용하지 않는다. Urgent도 드래그나 경기 연출을 끊지 않는다.

### 7.3 표시 시점과 빈도

RouteReady와 데이터·레이아웃 준비가 모두 끝나고 0.5초 동안 안정된 시점에 평가한다. 입력·드래그·뽑기·경기·결과 공개·모달·로딩 중에는 지연하고, 해제 후 후보를 새로 평가한다.

| 정책 | 기본값과 의미 |
|---|---|
| 동시 자동 노출 | 확장 안내 1건. 현재 Route 방문당 최대 1건 |
| 자동 안내 간격 | 실시간 60초. 게임 규칙이 아닌 UI 방해 억제 타이머 |
| 일반 자동 표시 예산 | 세션당 최대 6건. 발견 팁은 그 안에서 최대 1건 |
| 세션 | 세이브 로드부터 타이틀 복귀·앱 종료까지 |
| 홈 브리핑 | 구단의 기준 진행 단위마다 1회. 일간/주간 중 원본 진행 단위 하나로 BriefingKey 생성 |
| 버튼 있는 안내 | 유저가 접거나 Route를 벗어날 때까지 유지. 타이머로 CTA 제거하지 않음 |
| 짧은 Confirmation | 기본 6초, 자동 접기 해제 가능 |
| 수동 재열람·수락한 Flow | 자동 예산 제외. 유효성·권한 검사는 유지 |
| Blocker 반복 시도 | 기존 경고 갱신. 새 팝업 중첩 없음 |

설정 ‘최소’는 일반 자동 확장을 끄고 Dock·수동 안내·기존 Local Warning을 유지한다. ‘보통’은 위 기본값. ‘적극’의 초기값은 간격 30초, 세션 10건이며 발견 팁 1건 제한과 집중 상태 억제는 유지한다.

### 7.4 중복·닫기·보류를 구분

- IssueKey = AdviceId + 대상 Stable IDs + 문제 발생 회차. 해결됐다 재발했을 때만 새 회차로 본다.
- EvidenceHash는 의미 있는 공개 증거를 정규화해 생성한다. 현재 시간·매 프레임 값처럼 추천 의미를 바꾸지 않는 데이터는 제외한다.
- 동일 IssueKey와 EvidenceHash는 자동 재노출하지 않는다. 수치가 조금 바뀌면 기존 카드 내용만 갱신한다.
- 중요도 상승·기한 임박·새로운 유효 행동 발생 등 정책에 정의된 의미 있는 변경만 재알림 자격을 가진다. 명시적 보류와 종류 끄기는 일반 추천보다 우선한다.
- 닫기: UI를 접고 읽은 상태 기록. 해당 Route 방문에서는 다시 열지 않으며 같은 증거를 자동 재노출하지 않는다.
- 나중에: 다음 기준 진행 단위까지 보류. WorldDate/ProgressKey로 저장한다. 다음 주간 진행이 기준이면 일자 대신 해당 경계를 사용한다.
- 오늘 조언 숨김: 현재 기준 진행 단위에서 일반 자동 안내를 숨긴다. 앱 재시작으로 해제되지 않는다.
- 발견 팁 닫기: 최소 게임 7일 동안 자동 재노출 금지. 기간이 지나도 이미 익힌 동일 팁은 반복하지 않는다. 주요 기능 변경 이후의 새 GuideVersion에서만 다시 후보가 될 수 있다.
- 이 종류 끄기: Save 설정으로 유지, 수동 가이드 열람 가능. 기존 게임의 필수 검증 경고는 유지한다.

기존안의 현실 24시간 제한은 제거한다. **게임상 보류·기한은 WorldDate, 화면상 방해 간격은 실시간**으로 구분한다.

## 8. 내비게이션·행동·완료 계약

### 8.1 이동 데이터

`FrontOfficeGuideAction`은 ActionId, RouteId, TabId?, ContextStableId?, SlotId?, FilterPresetId?, AnchorId?, FocusMode, ReturnToken, RequiredCapability[], SafetyLevel을 가진다. ID는 Registry에 등록된 값만 사용한다.

ReturnToken은 원래 Route, 탭, 선택 Stable ID, 필터, 스크롤 상태를 담는다. RectTransform이나 오래된 UI 객체를 저장하지 않는다.

### 8.2 실행 순서

1. CTA 연타를 막고 현재 데이터·Capability·목표·대상 존재를 재검사한다.
2. 미저장 변경이 있으면 기존 저장·버리기·취소 절차를 따른다. 취소는 원래 편집·안내 유지.
3. ReturnToken을 기록하고 Route로 이동한다.
4. 데이터 준비 → 탭 → 필터 → 선택 → 스크롤 → Anchor 노출 순으로 진행한다.
5. 도착 Anchor가 실제 대상으로 등록됐을 때만 Highlight와 다음 단계 표시.
6. 유저의 기존 명령 실행을 기다리고 성공 결과와 최신 상태로 완료를 평가한다.
7. 완료 사실을 짧게 보여 준다. 관련 후속 행동은 버튼으로 제안하고 자동 실행·자동 다음 화면 이동은 하지 않는다.

준비 제한 시간 초기값은 10초. 실패 시 대기를 풀고 재시도·닫기를 제공한다. 비동기 응답에는 RouteInstanceId와 요청 세대를 검사해 이전 화면 콜백을 폐기한다.

### 8.3 대상이 사라졌을 때의 판정

| 상황 | 처리 |
|---|---|
| 원래 문제 자체가 실제 해소됨 | Resolved. 비추적 조언이면 목록만 갱신 |
| 선수 삭제·시즌 변경으로 과제 의미가 사라짐 | Expired. 성공·칭찬 출력하지 않음 |
| 문제는 남았고 원래 후보만 없어짐 | 재평가해 유효 후보 또는 목록으로 연결 |
| 데이터는 유효하지만 UI Anchor 누락 | 이동/표시 실패 기록, Drawer 설명·재시도. 완료 아님 |
| 기능 잠금·권한 부족 | 실행 CTA 제거, 필요한 경우 공개 해금 조건·모드 설명 제공 |

‘대상 없음’을 일괄 성공으로 처리하지 않는다. 기능을 설명할 필요가 있는 경우 [감독 결정 안내] 같은 열람 행동을 제공할 수 있지만 실행 불가능한 편성 CTA는 만들지 않는다.

### 8.4 명령 안전 등급

NavigateOnly / Preview / ReversibleCommand / ConfirmRequired / Forbidden으로 분류한다. 초기 출시의 매니저 직접 행동은 NavigateOnly와 Preview다. 판매·계약·스카우트 소비·경기 시작은 기존 화면의 명시적 실행·확정 절차를 사용한다. 새로운 Command를 만들어 원본 판정을 우회하지 않는다.

### 8.5 완료 의미

수정형 목표는 저장·적용 성공과 검증 해소를 모두 요구한다. 열람형 목표는 지정 상세를 열면 완료할 수 있다. 슬롯이 비어 있어도 선택 사항이면 유저의 [현재 구성 유지]를 AcceptedAsIs로 기록한다. 이를 ‘슬롯을 채워 해결’한 Resolved와 혼동하지 않는다.

추천과 다른 유효 선수를 선택해도 인정한다. 저장 실패는 완료하지 않는다. 이미 다른 메뉴에서 해결한 문제도 동일 기준으로 인정하며, 안내를 따랐는지에 따라 게임 보상을 달리하지 않는다.

## 9. 핵심 Guided Flow

### 9.1 최소 출시 흐름 A — 선수단 경고 해결

홈에서 현재 실제 검증 경고를 요약 → [경고 슬롯 보기] → 선수단 Route·관련 탭·슬롯 → 유효 후보 선택 → 기존 적용 명령 → 원본 검증 재평가 → 해결 또는 남은 경고.

후보가 없으면 원인과 실제 가능한 확보·규칙 설명 경로를 제공한다. 자동 구매로 연결하지 않는다. 비주포지션이 허용되는 게임 규칙이면 Blocker로 잘못 분류하지 않는다.

### 9.2 최소 출시 흐름 B — 경기 준비

| 단계 | 안내와 대상 | 통과 기준 |
|---|---|---|
| 1 상대 분석 | OpponentScoutingReport와 IntelState | 공개 리포트 열람, 정보 부족도 정상 상태로 인정 |
| 2 예상 선발 | 확정/유력/추정/정보 부족 표시 | 신뢰도 확인. 숨은 실제 선발로 보정 금지 |
| 3 프리셋 검증 | stale 또는 invalid 경고 Anchor | 원본 validation 통과 또는 허용 경고를 유저가 수용 |
| 4 컨디션·궁합 | 공개 Breakdown | 필요한 변경 적용 또는 현재 구성 유지 |
| 5 팀컬러 | 현재 슬롯·활성 후보 | 장착 성공 또는 선택 사항 유지 |
| 6 전술카드 | 조건·슬롯 검증 | 원본 필수 조건 통과, 선택 사항 유지 가능 |
| 7 경기 확정 | 기존 경기 시작 화면 | 유저 확정과 기존 Freeze Snapshot 성공 |

처음부터 7단계를 강제로 실행시키지 않는다. 완료된 단계는 건너뛰고 현재 남은 항목만 보여 준다. 실제로 시작을 막는 조건만 필수다. UI에는 Freeze Snapshot 대신 ‘경기 준비 확정’처럼 플레이어가 이해하는 표현을 사용한다.

### 9.3 최소 출시 흐름 C — 경기 후 점검

경기·보상 연출 종료 → 결과 화면의 BottomDebrief → 실제 컨디션·재정·기록 변화 중 핵심 최대 3개 → [투수진 상태] 또는 [상세 기록] → 대상 확인 → 다음 준비 연결. 원인으로 확인되지 않은 패배 요인을 단정하지 않는다.

### 9.4 확장 흐름 — 첫 구단주 주간

홈 3개 과제로 시작한다. 선수단 검증, 빈 스태프·재정 점검, 다음 경기 준비로 묶는다. 세부 흐름은 선수단 → 스태프 → 재정/시설 → 상대 분석 → 프리셋/전술 → 경기 → 결과다. 원래 유효한 단계는 생략하며 선택 사항을 억지로 완료시키지 않는다.

### 9.5 확장 흐름 — 시즌 종료

시즌 성과 → 팬·재정 변화 → 급여·계약 만료 → 확정된 승강 결과 → 다음 시즌 준비. 승강 전망과 확정 결과를 구분한다. 실제 시즌 규칙의 확정 이벤트가 있어야 ‘승격했어요’라고 말한다.

### 9.6 선수 커리어

성장·컨디션·일정·본인 계약·경기만 허용한다. 전체 라인업·TeamColor·Tactic 직접 변경 권한을 제공하지 않는다. 감독의 벤치 기용 이유는 공개된 설명용 결과가 있는 경우에만 인용한다. 피로가 보인다는 이유로 “피로 때문에 벤치입니다”라고 추론해 확정하지 않는다.

## 10. 대사·근거·개인화

대사는 **관찰 → 의미 → 행동**으로 작성한다. 기본은 밝고 신뢰감 있는 존댓말. ‘구단주님’은 첫 인사와 주요 사건에 사용한다. Concise는 1~2문장, Standard는 관찰·의미·행동, Detailed는 Drawer에서 근거·규칙까지 제공한다. 개인화는 표현 밀도만 바꾸며 추천 판정과 공개 정보 범위는 동일하다.

| 상황 | 표시 예시 | 필요한 근거 |
|---|---|---|
| 프리셋 경고 | “현재 프리셋에 포지션 경고가 {count}건 있어요. 해당 슬롯부터 확인해 볼까요?” | 실제 validation 결과 |
| 상대 분석 | “상대 선발은 우완으로 추정돼요. 아직 확정 정보는 아니에요.” | 공개 Report와 Confidence |
| 스카우트 | “집중 스카우트를 이용할 수 있어요. 선택 가능한 조건을 확인해 볼까요?” | 실행 가능 상태, 공개 조건 |
| 후보 없음 | “현재 필터에 맞는 후보가 없어요. 조건을 조정해 볼까요?” | 공개 검색 결과 |
| 팀컬러 | “지금 선수단으로 활성화할 수 있는 팀컬러가 있어요.” | 실제 후보와 효과 검증 |
| 전술카드 | “선택한 카드의 적용 조건을 충족하지 못했어요. 조건을 확인해 볼까요?” | 원본 조건 결과 |
| 재정 | “예정 지출 반영 후 자금은 {amount}로 예상돼요. 항목별 내역을 확인해 볼까요?” | 원본 Forecast·기준 시점 |
| 스태프 | “{role} 계약이 {deadline}에 만료돼요. 계약 조건을 비교해 볼까요?” | 실제 계약 기한 |
| 경기 후 | “{player} 선수의 경기 후 상태가 {state}예요. 다음 경기 가용성을 확인해 볼까요?” | 공개 컨디션 변화 |
| 커리어 정보 부족 | “현재 확인 가능한 정보만으로는 기용 이유를 알기 어려워요. 내 상태부터 확인해 볼까요?” | 설명 결과 없음·공개 본인 상태 |
| 적용 성공 | “프리셋이 적용됐고 포지션 경고가 해결됐어요.” | Command 성공 + 재검증 |
| 유지 선택 | “현재 구성을 유지할게요. 이 경기 준비에서는 같은 조언을 반복하지 않을게요.” | AcceptedAsIs와 경기 ID |

숫자·선수명·역할·시점은 Presentation에서 바인딩하고 대상 판단은 Stable ID를 쓴다. 손실 전망의 기준·비율 분모가 없으면 ‘자금 18%’ 같은 모호한 문구를 쓰지 않는다. 로스터 패널티는 원본 Breakdown에 존재하는 효과만 설명한다.

Evidence 유형은 Metric / Event / Rule / Trend / Deadline. Trend는 표본과 비교 기간을 포함한다. Confidence는 확정/유력/추정/정보 부족을 그대로 표시한다. 상대 미공개 라인업·Tactic, 숨은 정확한 Stamina, RNG, AI Utility는 근거와 로그·대사 모두에서 배제한다.

### 11.3 Anchor Registry

RouteId + RouteInstanceId + AnchorId + ContextStableId?로 대상 등록을 식별한다. RectTransform, PreferredBubbleEdges, ScrollProvider, SelectionProvider를 현재 화면에 한해 연결한다.

프로젝트 문서의 후보 키: `owner.pregame.probable_starter`, `owner.pregame.preset_warning`, `owner.roster.shortstop_slot`, `owner.staff.conditioning_slot`, `owner.operation.money_forecast`, `owner.scout.pity_gauge`.

이는 연결할 키의 제안이지 등록 완료 목록이 아니다. 반복 카드의 Anchor는 선수 Stable ID로 인스턴스를 구분한다. Route 종료 시 해제하고 세이브에 Unity 객체를 저장하지 않는다.

### 11.4 정의 예시

```json
{
  "adviceId": "owner.pregame.preset_warning",
  "category": "MatchPrep",
  "severity": "Normal",
  "allowedModes": ["Owner"],
  "eligibilityRuleId": "PresetHasPublicValidationIssue",
  "evidenceBindingIds": ["PresetValidationSummary"],
  "presentationKind": "ContextCard",
  "anchorId": "owner.pregame.preset_warning",
  "cooldownPolicyId": "IssueEvidenceOnce",
  "completionRuleId": "PresetAppliedAndTargetIssueCleared",

    "actionId": "inspect_preset_issue",

```

예시 Route·Rule 키는 스키마 설명용이다. 실행용 팩은 실제 Registry와 연결한 뒤 배포한다. 심각도는 원본 validation에 따라 Resolver에서 Blocker 등으로 결정하며 모든 포지션 경고를 차단으로 취급하지 않는다.

## 12. 저장·복원·기록

저장: IssueKey별 노출·닫기·보류·유지 선택, 의미 있는 EvidenceHash, 완료 Flow와 버전, 추적 Flow·단계, 고정 조언, BriefingKey, 빈도·설명·위치·접근성 설정. Source SaveId와 TeamSeasonKey로 다른 세이브·시즌과 혼동하지 않는다.

저장하지 않음: UI 좌표, RectTransform, 애니메이션 진행도, 다시 계산 가능한 현재 대사 문자열. 중요한 과거 리포트는 불변 기록의 Stable Reference를 저장한다. 원본 기록이 덮어써지는 구조라면 공개 값만 가진 버전별 최소 스냅샷을 저장해 과거 사실이 현재 값으로 바뀌지 않게 한다.

로드 후 현재 상태 재평가 → 이미 해결·만료된 항목 정리 → WorldDate 보류 검사 → 현재 Route 앵커 재등록. 자동으로 과거 화면을 열지 않는다. 완료 Flow는 다시 시작하지 않되 같은 종류의 새로운 문제 회차는 별도 이슈로 처리한다.

기존 세이브 마이그레이션에서는 현재 진행 이력을 이용해 이미 배운 기능의 팁을 억제한다. 새로운 설정 기본값 때문에 모든 온보딩이 한꺼번에 재생되지 않도록 한다.

## 13. 아트·연출·설정

기본 인상은 밝고 친근하며 신뢰할 수 있는 야구 구단 안내 캐릭터다. 이번 통합은 외형 재설계를 확정하는 작업이 아니므로 기존 승인 이미지의 정체성·화풍을 우선 보존한다. 현 이미지의 배치·크롭 문제가 해결되는지 먼저 확인하고 필요한 자산만 보완한다.

- 최소 자산: 기존 반신 1종, 얼굴 크롭, Neutral / Explain / Concern / Pleased 4개 표현.
- 확장: Serious / Celebrate 추가, 설명·우려·축하 포즈, 원형 얼굴 6종, 말풍선 꼬리 4방향, Dock 상태.
- 얼굴 중심·눈높이·인물 가시 영역을 통일해 표정 교체 때 몸이 움직이지 않게 한다. 반신을 작은 얼굴 칸에 통째로 축소하지 않는다.
- 실제 텍스트·버튼·숫자를 이미지에 넣지 않는다. UI는 별도 렌더링한다.
- Dock→Stage는 위치 이동 경로를 크게 보여 주지 않고 180~240ms 짧은 slide/fade. Context 120~180ms, 표정 100~160ms, 강조 pulse 최대 2회 후 정지.
- Reduced Motion은 위치·scale 변화 없이 Fade만 사용. 반복 바운스·무한 점멸 없음.

설정: 빈도 적극/보통/최소, 설명 간결/기본/상세, Stage 자동/우측/좌측, 발견 팁, 서사 대화, 중요한 조언 자동 확장, Reduced Motion, 효과음. 자동 확장 허용도 집중 상태 억제를 우회하지 않는다. 화면 읽기 라벨에는 제목·중요도·대상·행동을 포함한다.

저장·보류·억제는 마지막 장식 단계가 아니라 최소 출시부터 포함한다. 공통 계약 확정 전 기존 팝업을 일괄 삭제하지 않는다. Flow별 전환 후 기존 진입 경로를 제거하거나 Adapter로 단일화해 이중 발화를 막는다.

### 14.2 확장 팩 60개

| 팩 | 목표 정의 수 |
|---|---:|
| 공통 Onboarding | 12 |
| 홈·일정 | 6 |
| 선수단·라인업 | 10 |
| 경기 준비·TeamColor·Tactic | 10 |
| 경영·시설 | 8 |
| 스태프 | 5 |
| 스카우트·컬렉션 | 5 |
| 경기 후·시즌 | 4 |
| 합계 | 60 |

60개는 전체 확장 목표이며 본 문서가 60개 실행 데이터를 제공했다는 뜻은 아니다. 각 정의의 E2E 연결을 먼저 완성하고 이후 의미가 같은 문장 2~4개를 추가한다. Variation 선택은 같은 이슈 표시 중에 바뀌지 않도록 고정한다. 선수 커리어 팩은 공용 규칙을 Capability로 재사용하고 모드 전용 규칙은 별도 확장한다.

구현 분담은 감사/공통 계약, Resolver·Save, Route·Anchor, uGUI, 콘텐츠 팩, 대사·아트, 테스트·독립 검토로 나눈다. 감사와 공통 계약 이후에만 독립 모듈 작업을 병렬화한다. 본 문서 작성은 구현 에이전트 실행을 포함하지 않는다.

| 보류 | WorldDate 경계·주간 진행·로드 | 정의된 시점에만 해제 |
| 이동 | CTA 연타·빠른 Route 전환 | 전환 1회, 이전 요청 취소 |
| 편집 보호 | 미저장 상태에서 이동 취소 | 편집·선택·안내 유지 |
| 대상 | 삭제·비활성·스크롤 밖·Anchor 누락 | 허공 강조 0건, 해결/만료/실패 구분 |
| 완료 | 저장 실패·다른 유효 선택·다른 메뉴에서 해결 | 정확한 실제 상태 판정 |
| 모드 | 선수 커리어에서 구단 운영 CTA | 무권한 이동·명령 0건 |
| 정보 경계 | Report 부족·숨은 AI 정보 | 미공개 정보 접근·노출 0건 |
| Simulation | 조언 수락/거절의 영향 | 조언 자체의 판정·RNG 변경 0건 |
| 화면 | 모달·드래그·뽑기·실경기 | 자동 침범·포커스 탈취 0건 |
| 접근성 | 패드·키보드·130% 글자·긴 번역 | 원래 포커스 복귀, CTA·본문 잘림 0건 |
| 저장 | 신규·기존 세이브·FlowVersion 변경 | 상태 보존, 완료 흐름 부당 재시작 0건 |

해상도: 1920×1080, 1600×900, 1366×768, 1280×720, 2560×1080, 2560×1440. 실제 지원 범위에 맞춰 목록을 확정하되 고밀도 선수단과 경기 준비 화면을 반드시 포함한다.

최종 E2E: 홈 브리핑 → 선수단 문제 CTA → 실제 슬롯 이동 → 유저 수정·적용 → 해결 확인 → 경기 준비 흐름 → 기존 경기 시작·확정 → 경기 종료·Debrief → Save/Load → 완료·보류 상태 유지.

Definition과 이미지의 존재만으로 완료 처리하지 않는다. Production에서 실제 상태에 의해 조언이 생성되고, 정확한 대상 이동과 실제 해결·재노출 억제까지 모두 연결돼야 한다.

## 16. 계측과 평가

이벤트: advice_impression, advice_open_detail, advice_action_click, advice_route_arrived, advice_target_interacted, advice_resolved, advice_accepted_as_is, advice_expired, advice_dismiss, advice_snooze, advice_reopen, flow_step_complete, flow_abandon.

최소 필드: AdviceId, IssueKey, RouteId, 대상 종류, PresentationKind, FlowId·StepId, 시각·WorldDate, 성공/실패 사유. 숨은 상태를 분석 로그에 붙이지 않는다.

| 지표 | 정의·활용 |
|---|---|
| 실제 대상 도달률 | 대상 Anchor 준비 성공 / CTA 시도. Route만 열리면 성공으로 세지 않음 |
| 해결률 | 상태 수정형 이슈의 실제 해결 / 노출된 고유 수정형 이슈 |
| 첫 경기 준비 이동 수 | 준비 시작부터 실제 확정까지의 Route 이동 수 |
| 반복 닫기 | 같은 IssueKey의 반복 노출·닫기, 정책 결함 확인 |
| Invalid 시작 시도 | 원본 검증 실패 상태에서 경기 시작 시도 수 |
| 다시 보기 | 가이드 재열람과 이후 목표 진행. 높다는 이유만으로 성공 단정하지 않음 |
| 동행감 | ‘현재 상황에 맞았다’, ‘다음 행동 위치를 알았다’ 문항의 전후 비교 |

기준 수치는 아직 측정되지 않았다. 변경 전후 동일 조건에서 비교하며 클릭률을 높이려고 노출을 늘리지 않는다. 원래 메뉴로 직접 해결한 사용자도 비교에 포함한다.

## 17. 초안 충돌 해소 기록

| 쟁점 | 최종 처리 이유 |
|---|---|
| 상단 56px 버튼 vs 우하단 Dock | 프로젝트 Shell의 우하단 Dock으로 통일 |
| 절대 좌표·상시 우측 열 vs ContentRect 슬롯 | 기존 콘텐츠를 덜 침범하는 Route별 예약 슬롯 채택 |
| 라인업에 항상 큰 캐릭터 | 고밀도 화면은 Context 기본, Stage는 전체 공간 확보 시만 |
| 홈 Drawer 자동 오픈 | 예약 Stage에서 브리핑, 없으면 Badge. 전체 Drawer는 수동 기본 |
| 대상 사라짐 = 해결 | 실제 해결·만료·UI 실패를 구분 |
| 현실 24시간 vs WorldDate | 게임 보류는 WorldDate, UI 간격만 실시간 |
| EvidenceHash 변경마다 신규 안내 | IssueKey로 문제를 유지하고 의미 있는 변화만 재알림 |
| 모든 안내에 CTA 필수 | 운영 추천에는 필수, 단순 축하·확인에는 선택 |
| 숨길지 비활성 버튼을 남길지 | 실행 불가 CTA는 제거, 필요한 권한·모드 설명은 열람 제공 |
| 가중치 합산 우선순위 | 초기에는 심각도·추적을 보장하는 결정적 비교 |
| 60개를 먼저 제작 | 핵심 3개 흐름 E2E 후 확장 팩 60개 |
| 완료 확인이 모두 화면 열기 | 열람·수정·현재 구성 유지의 종료 의미를 구분 |
| 커리어 기용 이유 단정 | 공개된 설명 결과가 있을 때만 이유 인용 |
| Save·억제를 후반 구현 | 최소 출시부터 필수 계약으로 포함 |

최종 적용의 중심은 **고정된 매니저 진입점, 문맥에 맞는 대상 안내, 공개 근거, 실제 행동까지 이어지는 이동, 결과와 이력의 연결**이다.
