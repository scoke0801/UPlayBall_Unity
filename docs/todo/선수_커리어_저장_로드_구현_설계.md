# 선수 커리어 저장 / 불러오기 구현 설계

> 상태: **코드 구현 완료 · 테스트/실행 검증 미실행(요청 기준)**
> 대상: 선수 커리어 저장 구현 + 구단주 모드 설정 UI 연결
> 기준일: 2026-09-06
> 기준 문서: `BaseballManager_PROJECT.md` 34절, 38절, 41.11~41.12절

구현 확인 기록:

- `Baseball.Game` 컴파일: 성공, 경고 0 / 오류 0
- `Baseball.Game.Unity` 보조 컴파일: 프로젝트의 `Unity.InputSystem`·UI 참조 누락으로 선행 중단
- `Baseball.Presentation` 및 Unity 실행 검증: 미실행
- 자동화 테스트·Play Mode 테스트: 사용자 요청에 따라 미실행

## 0. 결론

선수 커리어의 첫 실제 디스크 세이브를 `SaveVersion = 1`로 구현한다. 저장 대상은 내 선수만이 아니라
현재 `CareerState`가 소유하는 10개 영속 리그의 런타임 상태 전체다. 그래야 저장 전과 불러온 뒤의
일정·상대·구단 이동·계약·통계·뉴스가 이어지고, 같은 Seed의 이후 결과도 달라지지 않는다.

UI의 주 진입점은 기존 `UI_Popup_CareerSettings`에 추가하는 **저장 / 불러오기** 탭이다. 타이틀의
`설정` 버튼도 같은 Popup을 타이틀 문맥으로 열어, 실행 직후에도 `설정 → 저장 / 불러오기 → 불러오기`로
접근할 수 있게 한다. 선수 모드 카드에 별도 불러오기 버튼을 추가하지 않는다.

초기 범위는 **수동 저장 슬롯 1개 + 자동 백업 1개**다. 자동 저장, 다중 슬롯, 클라우드 동기화,
경기 도중 체크포인트 저장은 v1 범위에서 제외한다. 저장 파일 교체는 원자적으로 수행하고, 불러오기는
새 상태의 복원·검증이 모두 끝난 뒤에만 현재 `CareerState`를 교체한다.

사용자가 허용한 "선수 Bake 시점과 달라진 데이터 유실"은 다음처럼 해석하고 계약으로 고정한다.

- 저장 파일의 `ContentHash` 또는 Balance hash가 현재 Bake와 다르면 그 세이브는 **호환 불가**다.
- 이전 Bake용 마이그레이션이나 ID 추측 복원은 만들지 않는다. 사용자가 확인한 경우에만 파일을
  삭제하고 새 커리어를 시작한다.
- 같은 `ContentHash` 안에서 발생한 성장, 능력치, 계약, 통계, 리그 이동, 기록 유실은 허용하지 않는다.
  이것은 Bake 차이가 아니라 저장 결함이다.

## 1. 현재 상태와 문제

### 1.1 확인된 구현

- `CareerState`와 하위 `WorldState`, `PlayerState`, `LeagueState`, `SeasonState`에는 `SaveVersion`과
  런타임 상태가 이미 있다.
- `CareerManager.BeginCareer(CareerState, BalanceTable)`는 새 게임 또는 복원된 커리어를 현재 시즌
  단계 그대로 인수할 수 있는 진입점이다.
- `CareerStateChecksum.Calculate`는 공개 상태와 참조 구조를 고정 순서 SHA-256으로 계산한다.
  저장 전후 완전 일치 검증에 재사용할 수 있다.
- 구단주 모드에는 `ManagerHistoricalSaveAdapter`와 `ManagerHistoricalSaveJsonStore`가 있으나,
  선수 커리어와 다른 Aggregate다. 파일 I/O의 참고 구현일 뿐 커리어 DTO로 합치지 않는다.
- `UI_Popup_CareerSettings`는 경기·화면·사운드·조작·게임 종료 탭을 런타임 생성하며, 현재는
  "저장을 지원하지 않는다"고 표시한다.
- 타이틀의 `설정` 버튼은 Popup을 열지 않고 후속 구현 안내만 표시한다.

### 1.2 구현 전 부재했던 경계

- `CareerState` 전용 Save DTO와 Capture/Restore Adapter
- 디스크 저장소와 원자적 교체·백업
- 현재 Bake/Balance와 저장 파일의 호환성 판정
- 저장 가능 시점 판정과 실패를 사용자 문구로 바꾸는 Command 결과
- 설정 Popup의 저장·불러오기·덮어쓰기·삭제·백업 복구 배선
- 저장 후 재로드 checksum 및 이후 시뮬레이션 결정론 회귀 테스트

따라서 현재 상태는 "백엔드는 있는데 UI만 없다"가 아니라, **저장 가능한 런타임 모델은 있으나 실제
Persistence 경계 전체가 없는 상태**다.

## 대상 모드

- 신규 Save Schema와 디스크 저장 구현은 선수 커리어 모드 전용이다.
- 구단주 모드의 `ManagerHistoricalSaveData` 및 `manager_historical.json`과 파일·버전·서비스를 공유하지
  않는다.
- 공통 설정 Popup은 두 모드에서 열릴 수 있으므로, 저장 탭은 현재 선택된 `UiGameMode`에 맞는 저장
  Command를 표시한다.
- 구단주 모드에서는 기존 `OwnerModeManager.Save/Load`와 단일 슬롯을 그대로 사용한다. 설정 Popup에
  저장·덮어쓰기·불러오기 UI를 추가하되, 기존 저장소에 없는 자동 백업과 삭제 기능은 노출하지 않는다.

### 구단주 모드 설정 UI

```text

→ UI_Popup_CareerSettings.ShowRuntime
```

선수와 구단주 저장 파일은 합치지 않는다. 공용인 것은 설정 Popup의 진입점과 확인 UI뿐이며, 실제
Aggregate·SaveVersion·파일 경로는 모드별 경계를 유지한다.

### 백업 복구와 삭제

```text
UI_Popup_CareerSettings.OnRecoverBackupClicked
→ CareerManager.LoadCareer(CareerSaveSource.Backup)
→ 검증된 백업을 Runtime에 먼저 적용
→ CareerSaveJsonStore.PromoteBackupToPrimaryAtomic

UI_Popup_CareerSettings.OnDeleteClicked
→ 2단계 사용자 확인
→ CareerSaveJsonStore.DeletePrimaryAndBackup
→ 슬롯 상태 Empty 갱신
```

UI는 파일을 직접 읽거나 호환성을 계산하지 않는다. `CareerSaveSlotView`와
`CareerSaveCommandResult`만 표시한다.

게임 콘텐츠 추가는 없다. 구현 산출물의 최소 수량은 다음과 같다.

| 항목 | 최소 수량 | 위치 |

## 선행 설계 결정

### 결정 1. 디스크 SaveVersion은 1부터 시작하고 런타임 상태 버전과 분리한다

`NewGameFlow.CurrentSaveVersion = 16`은 `CareerState` 하위 기능의 생성·마이그레이션 이력이고,
`CareerSaveAdapter.CurrentSaveVersion = 1`은 첫 실제 디스크 포맷이다. 둘을 1로 통합하면 현재 신규
커리어가 v15 이전 상태로 오인될 수 있으므로 의미를 분리한다.

- 신규 커리어의 내부 상태 버전은 16을 유지한다.
- 디스크 DTO는 `saveVersion = 1`을 정본으로 사용한다.
- v7~v16 마이그레이션 코드를 복원하지 않는다.
- 향후 v2가 실제 배포될 때만 `ICareerSaveMigration`의 `v1 → v2` 한 단계를 추가한다.
- 현재보다 높은 버전은 "더 최신 버전에서 만든 저장 데이터"로 거절한다.

### 결정 2. Bake 호환은 hash 완전 일치만 허용한다

`CareerContentReference`를 커리어 생성 시점에 고정하고 Save Header와 Payload에 보관한다.

```text
ContentSchemaVersion
ContentHash
NormalizedSchemaVersion
NormalizedContentHash
BalanceVersion
BalanceContentHash
WorldRecordMode
WorldHistorySeed
```

현재 `HistoricalSourceContentManifest`와 `BalanceTable` 값이 전부 같을 때만 불러온다. 불일치 시
선수·구단 ID를 이름이나 배열 위치로 추측해 붙이지 않는다. 파일은 자동 삭제하지 않고 설정 화면에서
호환 불가 이유와 "저장 데이터 삭제"만 제공한다.

Build 번호는 진단 정보로 기록하되 호환 판정에는 사용하지 않는다. 같은 포맷과 콘텐츠라면 코드 빌드
번호가 달라도 v1 저장을 읽을 수 있어야 한다.

### 결정 3. 정적 Bake가 아니라 런타임 World 전체를 저장한다

Save Payload는 다음 Aggregate를 포함한다.

| Aggregate | 반드시 보존할 상태 |
|---|---|
| Career Root | MyPlayerId, 현재 계약, Economy, Trade, Role, GrowthMilestones, Reputation, CreationProfile, GameSettings, CurrentOffseason |
| Career History | ContractHistory, SeasonHistory, resolved extension IDs, MemoryLog, News, Narrative, Retirement 및 Recap |
| World | WorldSeed, Calendar, HistoryStartYear, 10개 League, Team/Player/Contract Registry |
| World History | Player/Team 이동 Ledger, DomainEventJournal, WorldRecordState |
| Team | 영구 ID, LeagueId, 표시 정체성, Archetype, EmblemId, roster player IDs와 경쟁 상태 |
| Player | 영구 ID, 소속·계약·상태, 현재 능력치, 성장·학습·SkillBoard, Condition, 감독 평가, 최근 투구 부하, 커리어 누계 |
| League/Season | LeagueId/Level, Seed, Team, Schedule, 완료 점수, 순위, 정규·포스트시즌 통계, 수상, 정산, Review, Match Narrative, Tiebreak |
| 진행 중 선택 | Pending Reaction, 진행 중 Offseason 선택, 시즌 리뷰 공개 단계, 계약 전환 Checkpoint |

다음은 저장하지 않고 불러온 뒤 재구성한다.

- `BalanceTable`, ScriptableObject, Baked Person/Card/Team Definition, Sprite와 기타 Unity Object
- `CareerSeasonService`, `CareerPostseasonService`, View Model, 화면 탭·스크롤 위치
- `_lastGame`, `_lastSeasonAutoCompletion`, 각종 캐시와 진단용 성능 Snapshot
- Coroutine, Tween, `Time.timeScale`, 선택된 UI GameObject

`Overall`, 순위 표시 문구처럼 현재 상태에서 계산 가능한 값은 중복 저장하지 않는다. 반면 과거 시즌의
확정 사실과 공개 단계는 다시 계산하면 결과가 달라질 수 있으므로 저장한다.

### 결정 4. Runtime 객체를 JsonUtility에 직접 넘기지 않고 제한된 그래프 DTO를 사용한다

`JsonUtility.ToJson(CurrentCareer)`는 property·private 상태와 공유 참조를 보존하지 못하므로 사용하지
않는다. `CareerSaveAdapter`가 `CareerSaveGraphData`라는 명시적 public-field DTO를 만들고, JSON 경계는
이 DTO만 소비한다.

- DTO 값은 null/scalar/reference ID, object field, 배열/List/Dictionary/HashSet entry로 제한한다.
- `DateTime`·부동소수·decimal은 문자열 기반 exact representation으로 저장한다.
- 공유 객체는 reference ID로 복원해 World Registry와 `MyPlayer`의 동일 인스턴스 계약을 유지한다.
- field capture는 `Baseball.*` 순수 C# 타입과 기본 컬렉션만 허용하고, 타입·선언 타입·필드 이름을 함께
  기록한다. 코드 구조가 달라진 파일은 조용히 유실시키지 않고 호환 실패로 거절한다.
- `BalanceTable`과 `SkillBoardService`는 `[CareerSaveIgnore]`로 제외하고 현재 Bake에서 재주입한다.
- 복원 뒤 `WorldState.ValidateInvariants`와 `CareerStateChecksum`이 모두 통과해야 Runtime에 적용한다.

### 결정 5. 시즌 전환의 임시 상태를 영속 Checkpoint로 승격한다

현재 `CareerSeasonTransitionService`의 오퍼·선택·진행 단계는 `CareerManager`의 임시 객체에만 있어
그 화면에서 저장하면 유실된다. v1에서는 Save Root가 이 순수 C# 서비스의 진행 필드와 공유 참조를
그래프 Checkpoint로 함께 보존한다.

```text
Step
NextYear / NextSeasonId
CurrentTeamOffer와 RenewalOffers의 값 Snapshot
IsCurrentTeamOfferHeld
SelectedOfferTeamId
RookieTryoutAttemptCount
IsUnsignedRetirementRequired
계획을 재생성하는 Seed/Revision
```

`BalanceTable`과 파생 `SkillBoardService`는 포함하지 않고 복원 시 다시 연결한다. 콘텐츠 Hash가 달라진
세이브를 거절하므로 Checkpoint 안의 `TeamState` 공유 참조를 현재 Bake에 추측 연결하지 않는다. 이렇게
해야 계약 선택 화면에서 종료해도 같은 제안과 선택 상태로 돌아온다.

### 결정 6. 경기 중 Save는 v1에서 막고 Load는 명시 확인 뒤 허용한다

`CareerMatchSession`의 투구/타격 선택 재생과 이닝 체크포인트는 별도 기능이다. 프로젝트 문서에서도
경기 중 저장은 후속 범위로 남아 있으므로 v1에 억지로 포함하지 않는다.

- `_activeMatch != null`이면 저장 버튼을 비활성화하고 "경기를 마친 뒤 저장할 수 있습니다"를 표시한다.
- 시즌 Fast Forward batch가 실행 중이면 저장과 불러오기를 모두 비활성화한다.
- 불러오기는 활성 경기에서 선택할 수 있으나 "현재 경기의 저장되지 않은 진행이 사라집니다"를
  확인한 뒤 세션과 연출을 종료하고 저장 시점으로 돌아간다.
- Save Command는 UI 상태와 무관하게 같은 가드를 다시 검사한다.

경기 중 체크포인트가 필요해지면 `CareerMatchSession` 선택 로그와 저장된 `RandomSeed`를 재생하는 별도
SaveVersion에서 추가한다. v1 Save Payload에 반쪽짜리 경기 상태를 넣지 않는다.

### 결정 7. 한 파일 교체는 원자적이어야 한다

`CareerSaveJsonStore.SaveAtomic`은 같은 디렉터리에 임시 파일을 완전히 쓰고 flush한 뒤 기존 Primary를
Backup으로 보존하면서 교체한다.

```text
player_career_01.json.tmp 쓰기 + Flush
→ 기존 Primary가 있으면 File.Replace(tmp, primary, backup)
→ Primary가 없으면 tmp를 primary로 Move
```

파일에는 다음을 둔다.

```text
CareerSaveHeader
  saveVersion, savedAtUtcTicks, payloadSha256
  contentReference
  player/team/league/year/phase 요약
CareerSaveData payload
  stateChecksum
  CareerState DTO 전체
```

`payloadSha256`는 파일 손상을, `stateChecksum`은 Capture/Restore 손실을 잡는다. Primary 손상 시 Backup을
자동으로 덮어쓰지 않고 UI에 "백업 복구 가능" 상태를 표시한다. 복원 검증이 끝난 백업만 Primary로
승격한다.

### 결정 8. Load는 상태 교체 Transaction이다

불러오기 실패가 현재 플레이를 파괴하면 안 된다.

1. 파일 읽기와 payload hash 검증
2. SaveVersion과 ContentReference 검증
3. 별도 객체 그래프로 `CareerState` 복원
4. World 불변식과 저장된 `stateChecksum` 검증
5. 복원 상태에서 다음 경기/다음 선택을 만들 수 있는지 사전 점검
6. 성공한 경우에만 기존 Match/전환/화면 세션 정리
7. `CareerManager.BeginCareer(restored, balance)`로 한 번에 교체

1~5 중 실패하면 현재 `CurrentCareer`와 화면은 그대로 유지한다. 예외 원문을 UI에 그대로 노출하지 않고
`NotFound`, `Corrupt`, `IncompatibleVersion`, `IncompatibleContent`, `InvariantViolation`, `IoFailure`로
분류한 한국어 메시지를 반환한다.

### 결정 9. 불러온 뒤의 화면은 저장하지 않고 상태에서 결정한다

`CareerResumeRouteResolver`는 다음 우선순위로 진입 화면을 고른다.

1. 은퇴 확정 및 Recap 존재 → 은퇴 회고
2. 미응답 `PendingReaction` → 해당 질문 Popup
3. 계약 전환 Checkpoint가 선택 대기 → 계약 비교
4. `SeasonReview` 진행 중 → 저장된 공개 단계
5. 미완료 `CurrentOffseason` → 성장/오프시즌
6. 그 외 → Career Home

이는 UI 탭 자체를 세이브 데이터로 만들지 않으면서 플레이어가 하던 결정을 잃지 않는 기준이다.

## 2. 설정 UI 상세

### 2.1 탭 구성

기존 탭을 다음 순서로 바꾼다.

```text
경기 / 저장·불러오기 / 화면 / 사운드 / 조작 / 게임 종료
```

인게임에서는 기존처럼 `경기`를 기본 탭으로 연다. 타이틀 `설정` 버튼에서 열 때는

### 2.2 슬롯 카드

Ready 상태에서는 다음만 표시한다.

- 선수명, 포지션
- 현재 구단과 리그 단계
- 시즌 연도와 `정규시즌 / 포스트시즌 / 시즌 결산 / 오프시즌 / 은퇴`
- 저장 시각
- `저장` / `불러오기` 버튼

파일 경로, hash, SaveVersion은 일반 화면에 노출하지 않고 오류 상세 접기 영역에만 둔다.

### 2.3 확인과 결과

- 첫 저장: 즉시 실행한다.
- 덮어쓰기: 선수명·시즌·저장 시각을 보여 주고 1회 확인한다.
- 불러오기: 현재 세션에 저장 이후 변경이 있으면 유실 경고 후 1회 확인한다.
- 삭제: `삭제` 입력 같은 과도한 절차는 쓰지 않되, 위험 색상과 2단계 버튼으로 분리한다.
- 성공: `저장했습니다`, `불러왔습니다`를 Popup 안에 표시한다.
- 실패: 기존 플레이를 유지하고 원인과 가능한 행동(백업 복구/삭제/취소)을 표시한다.

저장·직렬화 중에는 중복 입력을 막고 짧은 진행 Overlay를 표시한다. UI는 `CareerSaveCommandResult`를
받기 전 성공 문구를 선반영하지 않는다.

## 4. 구현 순서

### P1. 영속 계약과 상태 소유 정리

- 디스크 `SaveVersion = 1`과 내부 상태 버전 16을 분리한다. **구현됨**
- Bake/Balance ContentReference를 Save Header에 고정한다. **구현됨**
- 시즌 전환 상태를 Save Root Checkpoint에 포함한다. **구현됨**
- 저장 가능 여부를 `CareerManager.SaveCareer`에서 재검증한다. **구현됨**

완료 조건: 새 게임, 정규시즌, 포스트시즌, 리뷰, 오프시즌, 계약 선택, 은퇴 상태가 모두 명시적인
Save Root 또는 명시적 비저장 Runtime으로 분류된다.

### P2. DTO Capture/Restore

- Root → World → League/Season → Team/Player/Contract → 기록/뉴스/은퇴 순으로 DTO를 작성한다.
- 모든 컬렉션의 저장 순서를 ID 기준으로 고정한다.
- Restore 전용 생성 경계를 추가하고 World 불변식을 재검사한다.
- 저장 전/후 `CareerStateChecksum` 완전 일치 검사를 구현한다. **테스트 미실행**

완료 조건: 디스크 I/O 없이 대표 상태 전부가 DTO round-trip 후 동일 checksum을 만든다.

### P3. 디스크 Store

- UTF-8 JSON 직렬화, payload SHA-256, 임시 파일, 원자 교체, Backup을 구현한다.
- 파일 I/O 실패를 `CareerSaveCommandResult`로 변환한다.
- Primary 손상·교체 중단·Backup 복구 fault injection은 요청에 따라 실행하지 않았다.

완료 조건: 저장 도중 실패해도 직전 Primary 또는 Backup 중 최소 하나가 검증 가능한 상태로 남는다.

### P4. CareerManager Production 배선

- `CareerManager.Persistence.cs`에서 Store/Adapter/현재 ContentReference를 구성한다.
- `SaveCareer`, `LoadCareer`, `InspectCareerSave`, `RecoverBackup`, `DeleteCareerSave` Command를 노출한다.
- Load 성공 시에만 현재 Runtime을 교체하고 모든 파생 Service를 `BeginCareer`에서 재생성한다.

완료 조건: 테스트 전용 호출이 아니라 실제 `CareerManager` Command에서 저장 파일 생성과 Runtime 교체가
발생한다.

### P5. 설정 Popup 배선

- 저장·불러오기 탭, Slot View, 확인 Modal, 오류/백업 복구 상태를 추가한다.
- 기존 "저장을 지원하지 않는다" 문구와 타이틀 복귀 경고를 실제 저장 여부 기반 문구로 바꾼다.
- 타이틀 설정 버튼을 같은 Popup에 연결한다.
- Load 성공 뒤 상태 기반 Resume Route로 이동한다.

완료 조건: 새 게임 → 경기 진행 → 설정 저장 → 타이틀 복귀 → 타이틀 설정에서 불러오기 → 같은 상태
표시가 실제 UI 조작만으로 가능하다.

### P6. 회귀와 성능 검증

이번 요청의 "테스트는 하지 않는다" 기준에 따라 실행하지 않은 후속 검증 단계다.

- 대표 단계 round-trip, 이후 결정론, 10개 리그 불변식, 파일 손상 복구를 실행한다.
- 10시즌 누적 Save의 파일 크기·저장 시간·불러오기 시간·할당량을 Editor와 Standalone에서 기록한다.
- 기준을 넘으면 데이터 유실로 줄이지 않고 DTO 중복 제거 또는 payload 압축을 별도 판단한다.

## 검증 근거

### A. DTO 완전성

다음 상태 각각에서 `Capture → Serialize → Deserialize → Restore` 후
`CareerStateChecksum.Calculate`가 완전히 같아야 한다.

1. 계약 직후 첫 시즌
2. 정규시즌 40경기 진행
3. 미응답 경기 후 Reaction 존재
4. 포스트시즌 진행 중
5. 시즌 리뷰 일부 공개
6. 오프시즌 활동 일부 완료
7. 기존 구단 협상 / 공개 시장 / 오퍼 선택 대기 각각
8. 리그 이동 계약 완료 직후
9. 은퇴 선언 상태와 은퇴 Recap 확정 상태
10. 10시즌 누적 후 생성 신인·은퇴 선수·이동 원장이 존재하는 World

### B. 결정론

- 원본과 round-trip 복원본을 같은 입력으로 다음 1시즌 진행해 Match 결과, Schedule, Standings,
  통계, 계약, 성장, 은퇴, 승강, News, DomainEventJournal checksum이 같아야 한다.
- 최소 10개 독립 World Seed에서 5시즌 동안 매 시즌 경계 Save/Load를 반복하고, Save/Load를 하지 않은
  대조군과 최종 checksum이 같아야 한다.
- Dictionary/HashSet 삽입 순서를 바꾼 fixture도 같은 JSON 배열 순서와 checksum을 만들어야 한다.

### C. 파일 안전성

- 파일 없음, 빈 파일, 잘린 JSON, 잘못된 payload hash, 미래 SaveVersion, 다른 ContentHash,
  다른 Balance hash를 각각 구분한다.
- 임시 파일 쓰기 전/중/후, replace 직전/직후 실패를 주입해 직전 정상 Save를 잃지 않는지 검사한다.
- Primary 손상 + 정상 Backup에서 복구한 뒤 Primary 재로드가 성공해야 한다.
- Load 실패 시 기존 `CareerManager.CurrentCareer` 참조와 checksum이 바뀌지 않아야 한다.

### D. UI/흐름

- 커리어 Home과 Match의 설정 버튼에서 저장 탭을 열 수 있다.
- 경기 중 저장 비활성 사유, 덮어쓰기, 불러오기 유실 경고, 호환 불가 삭제, Backup 복구 Modal을
  Play Mode에서 확인한다.
- 타이틀 설정에서 불러온 뒤 New Game 화면이 숨고, 저장된 Phase에 맞는 화면이 열린다.
- 16:9와 16:10에서 슬롯 카드와 Modal이 잘리지 않고 키보드/게임패드 기본 포커스가 안전 버튼에 간다.

### E. 성능 기록

- 첫 시즌, 5시즌, 10시즌 Save의 byte 크기와 Save/Load elapsed time, managed allocation을 기록한다.
- 개발 기준 PC Standalone에서 10시즌 Save 목표는 Save 2초 이하, Load 3초 이하다.
- 목표를 넘으면 완료로 판정하지 않고 Profile 근거와 함께 JSON 압축 또는 History 분할을 결정한다.

이번 작업은 확률·성장·경기 Balance를 바꾸지 않으므로 리그 타율/ERA 대량 밸런스 재측정은 필수
게이트가 아니다. 대신 Save/Load 유무에 따른 장기 결정론 비교가 필수다.
