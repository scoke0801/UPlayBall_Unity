# 14. 선수 도감과 위시리스트 시스템

> 상태: 신규 정본 기획안 / Codex 구현 기준  
> 적용 범위: 구단주 모드의 선수 카드 수집·탐색 UX, 선수 커리어 모드의 읽기 전용 도감  
> UI 기준: 기존 `SharedGameShellView` 계열 programmatic uGUI와 프로젝트 공통 UI 문법 재사용  
> 핵심 Source of Truth: `PlayerPersonDefinition`, `PlayerSeasonDefinition`, `TeamSeasonDefinition`, `WorldIdentityRegistry`, `WorldCardCatalog`, `OwnedPlayerCardState`

---

## 0. 목적

현재 프로젝트에는 다음 데이터와 시스템이 이미 존재한다.

```text
Canonical PlayerPerson / PlayerSeason
        ↓
Canonical TeamSeason / Franchise
        ↓
WorldIdentityRegistry
        ↓
WorldHistorySnapshot / WorldAwardRecord
        ↓
WorldCardCatalog
        ↓
구단주 OwnedPlayerCardState / Scout
```

그러나 플레이어가 다음 질문에 답할 수 있는 정식 Runtime UI가 없다.

```text
- 이 월드에 어떤 구단과 연도의 선수가 존재하는가?
- 특정 구단의 특정 연도에는 어떤 선수들이 존재하는가?
- 한 선수에게 어떤 연도 카드와 어떤 Edition 카드가 존재하는가?
- 내가 어떤 카드를 현재 보유하고 있는가?
- 과거에 한 번이라도 획득한 카드는 무엇인가?
- 아직 보유하지 못한 카드 중 앞으로 영입하고 싶은 카드는 무엇인가?
- 위시리스트에 등록한 카드만 별도로 모아서 확인하고 해제할 수 있는가?
- 그 카드를 노리려면 어떤 현재 스카우트 필터를 사용해야 하는가?
```

본 문서는 이를 해결하기 위해 **선수 도감(Player Encyclopedia)**, **카드 수집 이력(Collection History)**,
**위시리스트(Wishlist)**를 하나의 조회·수집 UX로 정의한다.

핵심 목표:

1. 모든 Canonical 구단의 모든 연도별 전체 선수 목록을 조회할 수 있다.
2. 각 `PlayerSeasonId`에 연결된 모든 현재 유효 카드 목록을 조회할 수 있다.
3. 현재 보유 여부와 과거 획득 여부를 분리해 표시한다.
4. 현재 미보유 카드를 `CardId` 단위로 위시리스트에 등록할 수 있다.
5. 위시리스트를 도감과 별도의 메뉴에서 조회·검색·해제할 수 있다.
6. 위시리스트는 Scout 확률·Pity·Bucket Weight를 절대 변경하지 않는다.
7. 기존 Stable ID, World Identity, WorldCardCatalog, Owned Economy 계약을 변경하지 않는다.
8. 엔트리브 프로야구매니저의 관리형 2D UI 문법을 참고하되 원본 UI를 픽셀 단위로 복제하지 않는다.

## 1. 절대 원칙

### 1.1 새 선수 DB를 만들지 않는다

도감은 별도의 Runtime 선수 원본을 소유하지 않는다.

```text
PlayerPersonDefinition
PlayerSeasonDefinition
TeamSeasonDefinition
WorldIdentityRegistry
WorldCardCatalog
```

를 조회해서 표시용 ViewModel을 만든다.

금지:

```text
EncyclopediaPlayerDefinition 복제
EncyclopediaCardDefinition 복제
도감 전용 Cost/Ability 복사본
도감 전용 Franchise/Year 문자열 정본
```

도감의 캐시와 Index는 파생 데이터일 뿐 Save 정본이 아니다.

### 1.2 Stable ID로 판정하고 DisplayName은 표시만 한다

선수:

```text
PlayerPersonId
PlayerSeasonId
```

구단:

```text
FranchiseId
TeamSeasonKey
```

카드:

```text
CardId
```

를 사용한다.

`WorldPlayerIdentity.DisplayName`, `WorldFranchiseIdentity.DisplayName`은 검색·정렬·UI 표시에만 사용한다.
카드 동일성, 위시리스트, 보유 여부, 수집률, Scout 후보 판정에 문자열 이름을 사용하지 않는다.

### 1.3 WorldCardCatalog가 카드 존재 여부의 정본이다

현재 정본 문서의 Card 구조는 다음이다.

```text
CardId = PlayerSeasonId + Edition
```

Normal은 Canonical PlayerSeason에 기반하고, World Award 계열 Edition은 해당 World의
`WorldAwardRecord` 결과를 통해 `WorldCardCatalog`에 활성화된다.

따라서 도감은 **현재 WorldCardCatalog에 존재하는 CardId를 현재 월드의 실제 카드**로 취급한다.

도감 UI가 임의로 다음을 생성해서는 안 된다.

```text
"이 선수라면 MVP 카드도 있을 것"
"이 연도라면 AllStar 카드를 미리 생성"
"Cost가 높으니 Legend/EX 슬롯을 가상 생성"
```

향후 Rare/EX/CareerHigh/Legend 등 별도 카드 기획이 Production Catalog에 추가되더라도
도감은 Edition을 switch 문으로 하드코딩하지 않고 Catalog/Presentation Metadata를 소비한다.

> 본 문서는 Edition의 발급 조건·Cost 조건·Bake 정책을 새로 정의하지 않는다.
> 현재 카드 정본과 향후 카드 정본이 만들어 낸 결과를 조회하는 Consumer다.

### 1.4 전체 선수는 Core25가 아니라 Canonical 선수풀이다

도감의 "특정 구단·특정 연도의 전체 선수"는 그 TeamSeason의 Core25만 의미하지 않는다.

```text
해당 OriginYear
+ 해당 OriginFranchiseId / OriginTeamSeasonKey
에 속하는 전체 PlayerSeasonDefinition
```

을 조회해야 한다.

Core25는 경기용 ActiveRoster 정본이고 도감의 전체 선수 목록을 제한하는 조건이 아니다.

### 1.5 특수 합성팀은 Origin Franchise가 아니다

`AllStarComposite`, `GoldenGloveComposite`, `YearSelectComposite`는 기존 PlayerSeason을 참조하는
게임용 로스터이며 카드의 Origin을 변경하지 않는다.

따라서:

- 구단×연도 도감의 행에 특수 합성팀을 일반 Franchise처럼 넣지 않는다.
- 합성팀에 들어갔다는 이유로 카드의 구단 필터가 바뀌지 않는다.
- 도감 구단 분류는 Canonical `OriginFranchiseId`를 사용한다.

특수 합성팀 로스터 조회가 필요하면 별도 "특수팀 보기" Consumer로 구현하며 본 도감의 구단 수집률과
섞지 않는다.

## 2. 용어

### 2.1 선수(Person)

한 Source Person에 대응하는 Canonical 인물.

```text
PlayerPersonId
```

같은 Person의 여러 연도 시즌은 한 World에서 같은 표시 이름을 사용한다.

### 2.2 선수 시즌(PlayerSeason)

한 선수의 한 시즌 Canonical 카드 원본.

```text
PlayerSeasonId
OriginYear
OriginFranchiseId
OriginTeamSeasonKey
Position / PitcherRole
Cost
BaseAttributes
```

도감의 "연도별 전체 선수" 기본 단위다.

### 2.3 카드(Card)

```text
CardId = PlayerSeasonId + Edition
```

한 PlayerSeason에 여러 Edition 카드가 존재할 수 있다.

### 2.4 현재 보유(Currently Owned)

현재 구단주 플레이어의 `OwnedPlayerCardState`에 해당 `CardId`가 존재하고 보유 수량이 1 이상인 상태.

### 2.5 획득 이력(Ever Acquired)

현재 보유 여부와 별개로 해당 Save에서 해당 `CardId`를 **한 번이라도 정상 획득한 적이 있는 상태**.

판매해서 현재 0장이 되어도 도감 수집 완료 기록은 유지한다.

### 2.6 위시리스트(Wishlist)

플레이어가 다시 영입하고 싶은 정확한 `CardId` 목록.

주 사용 대상은 미획득/미보유 카드지만, 이미 과거 획득했으나 현재 0장이 된 카드도 재영입 의도가
있다면 위시에 다시 등록할 수 있다.

## 3. 시스템 범위

### 3.1 포함

```text
전체 구단/전체 연도 선수 탐색
정확한 카드 목록
이름 검색
구단/연도/Position/Role/Cost/Edition 필터
현재 보유 상태
과거 획득 이력
수집률
구단×연도 수집 현황
선수의 다른 연도 탐색
같은 PlayerSeason의 다른 Edition 탐색
위시 등록/해제
위시 전용 화면
Scout 화면 연결
Save/Load
기존 Save Migration
```

### 3.2 초기 구현에서 제외

```text
도감 완성 보상
도감 전용 Money/SP/DP

위시 확률 보정

위시 전용 Scout

카드 거래소 자동 검색
실제 Source 선수명/구단명 표시
```

도감 완성 보상은 경제 밸런스에 영향을 주므로 별도 기획 전까지 추가하지 않는다.

## 4. 모드별 제공 범위

### 4.1 구단주 모드

전체 기능 제공.

```text
도감 조회
보유 상태
획득 이력
수집률
위시 등록/해제
위시 전용 화면
Scout 연결
```

### 4.2 선수 커리어 모드

두 모드는 Canonical World와 Identity를 공유하므로 **읽기 전용 선수/카드 도감**은 제공할 수 있다.

그러나 선수 커리어에는 구단주 `OwnedPlayerCardState`, SP Scout, Duplicate Enhancement가 없으므로:

```text
현재 보유 카드 판정
수집률
Wishlist
Scout 바로가기
```

는 기본적으로 비활성화한다.

선수 커리어에서도 별도 개인 북마크 기능을 원한다면 후속 기획으로 추가하며 구단주 Wishlist State를
공유하지 않는다.

### 4.3 AI

AI는 도감/위시리스트 State를 소유하지 않는다.

## 5. 메뉴 Depth와 Navigation

### 5.1 구단주 모드 권장 메뉴

```text
구단주 모드
└─ 선수
   ├─ 선수단              // 기존
   ├─ 선수 도감           // 신규
   └─ 위시리스트          // 신규
```

`위시리스트`는 도감 내부 필터만으로 숨기지 않고 같은 Depth의 독립 메뉴로 둔다.

이유:

- 도감의 목적 = 탐색/비교/수집 현황 확인
- 위시리스트의 목적 = 영입 목표 관리

사용자의 행동 목적이 다르다.

### 5.2 도감 내부 View Tab

추가 Route Depth를 만들지 않고 같은 Scene 안에서 탭만 전환한다.

```text
[선수] [카드] [수집 현황]
```

#### 선수
`PlayerSeasonId` 단위로 시즌 선수를 탐색.

#### 카드
정확한 `CardId` 단위로 탐색.

#### 수집 현황
Franchise × OriginYear 매트릭스와 Edition별 수집률을 확인.

### 5.3 Cross Navigation

```text
선수 도감 카드
  → 위시 등록/해제

카드 상세
  → 같은 선수의 다른 연도
  → 같은 시즌의 다른 Edition
  → 스카우트에서 찾기

위시리스트
  → 도감 상세
  → 스카우트에서 찾기
  → 위시 해제

Scout
  → 현재 Pool 안의 위시 카드 수 표시
  → 위시리스트 열기
```

Navigation은 View 전환만 수행하며 Scout Filter/RNG State를 몰래 변경하지 않는다.

`스카우트에서 찾기`를 누른 경우에만 명시적으로 가능한 Scout 화면과 필터 후보를 제안한다.

## 6. 도감 Scene 공통 레이아웃

프로야구매니저 레퍼런스의 다음 문법을 사용한다.

- 상단 짙은 남색/검정 제목 바.
- 은색/회백색 배경과 얇은 패널 경계.
- 상단 수평 탭.
- 정보 밀도가 높은 작은 선수 카드 배열.
- 카드 선택 시 우측 상세 정보.
- 드롭다운과 짧은 필터 버튼.
- 화면 전체를 특정 Franchise 색으로 칠하지 않음.
- 과도한 SF 네온/글래스모피즘/대형 모바일 카드 타일을 사용하지 않음.

권장 구조:

```text
┌──────────────────────────────────────────────────────────────┐
│ 선수 / 선수 도감                         Money / SP / DP     │
├──────────────────────────────────────────────────────────────┤
│ [선수] [카드] [수집 현황]                위시리스트  27     │
├──────────────────────────────────────────────────────────────┤
│ [검색____________] [구단▼] [연도▼] [포지션▼] [Cost▼]        │
│ [Edition▼] [수집상태▼] [세부필터]              [정렬▼]       │
├───────────────────────────────────────┬──────────────────────┤
│                                       │ 선택 상세             │
│       Virtualized List / Grid         │                      │
│                                       │ 큰 카드 / 선수 정보   │
│                                       │                      │
│                                       │ 수집/보유/위시 상태   │
│                                       │                      │
│                                       │ [위시] [상세]         │
│                                       │ [Scout에서 찾기]      │
├───────────────────────────────────────┴──────────────────────┤
│ 전체 8,423 | 조건 143 | 보유 57 | 획득 68 | 위시 11         │
└──────────────────────────────────────────────────────────────┘
```

## 7. 선수 View

### 7.1 단위

한 타일/행은 한 `PlayerSeasonId`.

표시:

```text
World DisplayName
OriginYear
Franchise DisplayName
Position / PitcherRole
Cost
현재 그 시즌에 활성화된 Card Edition 수
보유 Edition 수
획득 완료 Edition 수
```

예:

```text
2012 / Comets / SS / Cost 9
카드 4종  | 보유 1 | 획득 2
```

### 7.2 선수 Season 선택

우측 상세:

```text
[선수 Portrait]

이름
연도 / Franchise
Position / Role
Bats / Throws
Cost

현재 활성 카드
[Normal] [AllStar] [GoldenGlove] [Mvp] ...
```

Edition을 선택하면 같은 우측 패널에서 카드 상세로 전환한다.

### 7.3 같은 Person의 다른 연도

`PlayerPersonId` 기준으로 같은 인물의 다른 시즌을 찾아 하단 Timeline에 표시한다.

```text
다른 연도
[2009] [2010] [2011] [2012] [2013]
```

같은 World에서 표시 이름은 모두 동일해야 한다.

Franchise가 바뀐 시즌이 있으면 해당 시즌의 Origin Franchise를 그대로 표시한다.

## 8. 카드 View

### 8.1 단위

정확한 `CardId`.

미니카드에서 최소 표시:

```text
Portrait
DisplayName
OriginYear
Cost
Position/Role
Edition frame/icon
보유/획득/위시 상태 아이콘
```

### 8.2 카드 상태의 우선 시각 규칙

#### 현재 보유

```text
✓ 보유
```

원래 카드 디자인을 최대한 그대로 유지한다.

강화/훈련 정보가 있으면 소형 Badge로 표시한다.

#### 과거 획득, 현재 미보유

```text
✓ 획득
현재 미보유
```

카드의 시각 정보는 공개하되 현재 보유와 혼동되지 않도록 `획득 기록` 아이콘을 사용한다.

#### 미획득

```text
미획득
```

카드 전체를 검은 실루엣으로 숨기지 않는다.

위시리스트의 목적이 특정 카드를 찾아 노리는 것이므로 최소한 다음 정보는 확인 가능해야 한다.

```text
이름
연도
구단
Position
Cost
Edition
정상 카드 프레임/초상화
```

게임에 별도 Hidden 정보 공개 정책이 있다면 그 정책은 도감에서도 그대로 존중한다.
도감 때문에 미공개 Simulation 내부 수치를 노출하지 않는다.

#### 위시

```text
☆ / ★
```

색만 사용하지 않고 별 아이콘과 `위시` 텍스트/Tooltip을 함께 사용한다.

## 9. 카드 상세

기존 큰 선수 카드 앞/뒷면 컴포넌트를 재사용한다.

### 9.1 Front

기존 카드 Presentation.

### 9.2 Back

기존 프로젝트의 카드 뒷면 정보 계약을 재사용한다.

도감 전용 별도 능력치 계산을 만들지 않는다.

### 9.3 우측/하단 상세 Tab

```text

```

를 표시한다.

## 11. 선수 수집률과 카드 수집률

두 수치를 합치지 않는다.

### 11.1 PlayerSeason 수집률

한 `PlayerSeasonId`의 현재 Collectible Card 중 하나 이상을 EverAcquired 했다면 해당 시즌 선수를
"한 번 영입함"으로 계산한다.

```text
CollectedPlayerSeason =
    Exists(EverAcquiredCardId where Card.PlayerSeasonId == PlayerSeasonId)
```

### 11.2 Card 수집률

정확한 `CardId` 기준.

```text
EverAcquiredCardCount / CurrentCollectibleCardCount
```

### 11.3 현재 보유율

별도 수치.

```text
CurrentlyOwnedUniqueCardCount / CurrentCollectibleCardCount
```

카드를 판매했다고 과거 수집률이 내려가서는 안 된다.

### 11.4 WorldCardCatalog 변화

현재 또는 미래 시즌 진행으로 WorldCardCatalog에 새로운 CardId가 활성화될 수 있다면:

- 도감 총 카드 수가 증가한다.
- 신규 Card는 미획득으로 추가된다.
- 수집률은 자연스럽게 낮아질 수 있다.
- 과거 EverAcquired 기록은 그대로 유지한다.

Catalog Revision 변경 시 도감 Index와 Progress Cache만 무효화한다.

## 13. 위시리스트

### 13.1 등록 단위

정확한 `CardId`.

금지:

```text
DisplayName 문자열
PlayerPersonId만 저장
PlayerSeasonId만 저장
```

같은 선수의 같은 연도라도 Edition별로 따로 등록 가능해야 한다.

```text
2012 / Player A / Normal
2012 / Player A / AllStar
2012 / Player A / Mvp
```

는 서로 다른 Wishlist Entry다.

### 13.2 등록 조건

기본 허용:

```text
현재 WorldCardCatalog에 존재
AND 현재 보유 수량 == 0
```

과거에 획득한 적이 있지만 판매해서 현재 0장인 카드도 재영입 목적으로 위시 등록할 수 있다.

현재 보유 카드에는:

```text
[위시 등록]
```

버튼을 숨기거나 비활성화한다.

### 13.3 위시 수량 제한

게임 밸런스에 영향을 주지 않는 개인 목표 목록이므로 초기 구현에서는 하드 Cap을 두지 않는다.

다만 UI는 수백~수천 장에서도 Virtualization을 사용한다.

### 13.4 등록

도감 카드:

```text
☆ 위시 등록
→ WishlistState.Add(CardId)
→ ★ 위시
```

중복 Add는 no-op.

### 13.5 해제

```text
★ 위시 해제
→ WishlistState.Remove(CardId)
```

도감, 카드 상세, 위시리스트 전용 화면에서 모두 가능하다.

### 13.6 영입 성공 시 자동 해제

어떤 정상 카드 획득 경로이든 정확한 CardId가 현재 보유 상태로 커밋되면:

```text
OwnedPlayerCardState 갱신
→ CollectionHistory EverAcquired.Add(CardId)
→ Wishlist.Remove(CardId)
→ "위시 카드 영입" 표시 이벤트
```

순으로 처리한다.

동일 PlayerSeason의 다른 Edition Wishlist는 제거하지 않는다.

예:

```text
Wishlist = 2012 Player A Mvp
획득     = 2012 Player A Normal
```

이면 Mvp Wishlist는 유지한다.

### 13.7 판매 후

카드를 판매해 보유 수량이 0이 되어도:

- EverAcquired는 유지.
- Wishlist가 자동으로 다시 생기지 않는다.
- 필요하면 사용자가 다시 등록한다.

## 15. Scout 연동

### 15.1 절대 금지

Wishlist는 다음에 영향을 주지 않는다.

```text
CostWeights
EditionWeights
Joint Bucket
Bucket 내부 균등 추첨
Pity Gauge
Pity Cost 7+ 확정
RNG Seed
Scout PriceSP
```

### 15.2 Scout 후보 수 표시

현재 Scout Pool의 실제 후보 CardIds와 Wishlist를 교집합한다.

```text
현재 Scout 후보: 416
위시 카드 포함: 7
```

이는 정보 표시일 뿐 확률 보정이 아니다.

### 15.3 Scout에서 찾기

카드 상세에서 해당 카드가 들어갈 수 있는 Production Scout Pool을 계산한다.

예:

```text
[Franchise Scout]
[Year Scout]
[YearFranchise Scout]
[Award Scout]
```

버튼을 누르면 해당 Scout 화면으로 이동할 수 있다.

필터가 필요한 경우 명시적 Navigation Parameter로 전달한다.

```text
TargetFranchiseId
TargetYear
TargetEdition?
```

### 15.4 실제 확률

카드별 정확한 Scout 확률을 도감에서 별도 공식으로 계산하지 않는다.

정확한 확률이 필요하면 기존 Scout 후보 Bucket과 재정규화 결과를 사용하는 공통 Query API를 호출하거나
Scout 화면으로 이동한다.

### 15.5 Pity

Pity 100의 집중 스카우트에서 위시 카드가 포함된 구단/연도 선택지에는:

```text
위시 3장
```

Badge를 보여줄 수 있다.

그러나 위시 카드 자체를 보장하거나 자동 선택하지 않는다.

## 16. 카드 획득 이력 — 신규 정본 State

현재 `OwnedPlayerCardState`만으로는 도감 수집률을 정확히 표현할 수 없다.

이유:

```text
획득 → 도감 등록 → 판매
```

후 현재 보유 State만 보면 "한 번도 획득하지 않음"과 구분할 수 없기 때문이다.

따라서 구단주 Save에 다음 최소 상태를 추가한다.

```text
CardCollectionHistoryState
{
    CardId[] EverAcquiredCardIds
}
```

Set semantics를 사용한다.

### 16.1 저장하지 않는 것

```text
수집률 %
Franchise별 합계
Year별 합계
Edition별 합계
현재 보유 여부
DisplayName
카드 능력치
```

모두 Runtime에서 파생한다.

### 16.2 최초 획득 이벤트

카드 획득 commit 지점 한 곳에서만:

```text
EverAcquired.Add(CardId)
```

를 수행한다.

Scout 결과 Presentation이 직접 State를 수정하지 않는다.

### 16.3 중복 카드

동일 CardId 중복 획득:

```text
EverAcquired.Add(CardId) // 이미 있으면 no-op
```

수집률을 두 번 올리지 않는다.

## 19. Query / Index Architecture

  CardId Index

  Cost → CardId[]
  Edition → CardId[]

WorldCatalog Revision 또는 Content Version이 바뀌면 Index를 재구성한다.

### 19.1 Identity 변경

읽는다.

### 19.2 검색

이름 검색용 normalized lowercase/token cache는 Runtime 파생 Cache로 허용한다.

## 20. 전체 연도와 Franchise 조회 계약

### 20.1 Archive 전체 사용

현재 리그 배치 정책이 특정 연도만 실제 LeagueGrade에 배치하더라도 도감은 그 정책 목록을 선수풀
Source로 사용하지 않는다.

도감은 Production Runtime이 보유한 **전체 Canonical Archive / WorldCardCatalog**를 조회해야 한다.

따라서 다음은 금지한다.

```text
현재 LeagueInstance 참가 TeamSeason만 도감 노출
현재 플레이어 리그 연도만 노출
Core25만 노출
2016~2025 배치 목록만 도감 전체로 간주
```

### 20.2 World Identity 범위

도감에 노출되는 모든 `PlayerPersonId`와 `FranchiseId`는 해당 World의 Identity Registry에서 표시 이름을
조회할 수 있어야 한다.

누락 시 Production에서 임의 이름을 즉석 생성하지 않는다.

명시적 Content/Identity validation failure로 처리한다.

## 22. UIX 상세

### 22.1 Reference 문법

첨부된 엔트리브 프로야구매니저 레퍼런스에서 확인되는 특징을 본 시스템의 UI 문법에 적용한다.

#### 정보 화면

- 상단 검정/남색 제목 띠.
- 수평 탭 구조.
- 회백색 배경.
- 얇은 선으로 섹션 분리.
- 정보 밀도가 높고 빈 공간이 과도하지 않음.

#### 선수 오더 화면

- 작은 선수 카드가 한 화면에 다수 배치됨.
- 선택된 선수/그룹 오른쪽에 분석/상세 패널이 존재.
- 기능별 탭과 드롭다운이 짧고 명확함.
- 카드 자체 Edition/팀 시각 요소는 유지하지만 전체 화면은 중립색.

#### 카드 디자인

- 카드 앞/뒷면을 같은 카드 객체의 다른 정보 면으로 이해할 수 있음.
- 도감 상세는 기존 프로젝트의 큰 카드 앞/뒷면 전환 UI를 재사용.

### 22.2 화면 색

권장:

```text
Shell
  White / light gray / silver

Section header
  Deep navy / charcoal

Selection
  기존 Accent

Card Edition
  각 카드 프레임의 고유 표현
```

금지:

```text

강한 빨강/파랑을 공통 도감 Theme로 고정

투명 유리 패널 과다 사용
```

### 22.3 카드 Grid

1920×1080 기준 권장:

```text
본문 Grid 영역 68~72%
상세 패널      28~32%
```

카드 최소 가독성을 유지하면서 1행 7~9장을 목표로 한다.

1600×900은 6~8장, 1366×768은 5~7장 수준으로 자동 조정한다.

정확한 픽셀은 기존 공통 Shell과 MiniCard 크기를 감사한 뒤 확정한다.

### 22.4 Hover / Selection

Hover:

```text

이름/연도 Tooltip
```

Selection:

```text
명확한 Border/Focus
우측 상세 갱신
```

색만으로 Selected 상태를 표시하지 않는다.

### 22.5 위시 아이콘

카드 우상단 등 정보를 가리지 않는 위치.

```text

```

실제 버튼 Hit Area는 아이콘보다 크게 잡는다.

### 22.6 상태 표시

우선순위:

```text

Wishlist
Enhancement
```

`EverAcquired`는 상세/작은 체크 아이콘으로 보조한다.

## 25. Save / Persistence

### 25.1 신규 Save 데이터

구단주 플레이어 Save:

```text
CardCollectionHistoryState
WishlistState
```

### 25.2 저장 위치

`OwnedPlayerCardState`와 같은 플레이어 구단의 Owned Economy 경계와 연결하되, Wishlist는 특정
TeamSeason 소유 카드 자체가 아니라 **해당 World Save에서의 사용자 영입 목표**다.

따라서 플레이어가 같은 Save 안에서 TeamSeason을 이동하더라도 Wishlist와 EverAcquired History는
유지한다.

### 25.3 Save Schema

현재 문서군의 구단주 Save schema는 4다.

구현 시 기존 Serializer가 명시적 Version을 요구하면 schema를 다음 버전으로 올린다.

권장:

```text
v4 → v5
```

단 실제 Repository 감사 결과 이미 schema가 올라갔다면 그 최신 버전 +1을 사용한다.

### 25.4 Migration

기존 Save에는 EverAcquired History가 없다.

따라서 Migration:

```text
현재 보유 중인 모든 CardId
→ EverAcquiredCardIds에 등록

Wishlist
→ Empty
```

과거에 이미 획득했다가 판매한 카드는 기존 Save만으로 복원할 수 없다.

이를 추론하거나 가짜 이력을 생성하지 않는다.

### 25.5 Invalid CardId

Content Update 후 Save Wishlist/EverAcquired CardId가 현재 Catalog에 Resolve되지 않을 경우:

```text
Wishlist
  → Invalid entry를 Production UI에서 숨기고 migration/validation report 기록

EverAcquired
  → 기존 이력 자체는 보존 가능하나 현재 수집률 계산에서 제외
```

삭제 정책은 Save Compatibility Agent가 현행 Content Migration 규칙을 확인해 확정한다.
Load 중 임의로 다른 카드에 매핑하지 않는다.

## 26. Acquisition Transaction

카드를 획득하는 Production 단일 Commit 경계에 Collection/Wishlist를 연결한다.

개념 순서:

```text
1. Scout/Reward/etc 결과 CardId 확정
2. CardId가 WorldCardCatalog에 존재하는지 검증
3. OwnedPlayerCardState 갱신
4. CardCollectionHistoryState.EverAcquired.Add(CardId)
5. WishlistState.Remove(CardId)
6. AcquisitionResult 생성
7. Presentation에서 결과 연출
```

### 26.1 AcquisitionResult

```text
AcquisitionResult
{
    CardId
    WasFirstAcquisition
    WasWishlisted
    IsDuplicate
    EnhancementOrAutoSaleResult?
}
```

위시 성공 연출은 이 결과만 읽는다.

### 26.2 MAX Duplicate 자동 판매

현재 05절의 MAX 이후 자동 판매가 있더라도 카드 획득 자체는 발생했다.

따라서 정확한 CardId가 Wishlist에 있었다면 자동 판매 여부와 관계없이:

```text
EverAcquired = true
Wishlist remove
```

가 기본이다.

단 Product 코드의 획득/자동판매 Commit 순서를 Audit해서 이 정책이 사용자 기대와 맞는지 E2E로
확인한다.

## 30. 테스트

### 30.1 Catalog Coverage

- 전체 Production PlayerSeason 수와 선수 도감 Source 수 일치.
- Current WorldCardCatalog CardId와 카드 도감 Collectible CardId 집합 일치.
- Core25만 노출하는 회귀 0건.
- 현재 리그 참가 연도만 노출하는 회귀 0건.

### 30.2 Origin

- Franchise Filter는 `OriginFranchiseId`.
- Year Filter는 `OriginYear`.
- 특수 합성팀 이름으로 Origin이 바뀌지 않음.
- DisplayName만 바꿔도 Filter 결과 CardId 집합 불변.

### 30.3 Identity

- 동일 PlayerPerson의 여러 연도가 동일 DisplayName.
- 검색 문자열이 Stable ID 판정에 사용되지 않음.
- Source 실제 선수/구단명 Runtime 표시 없음.

### 30.4 Card

- 동일 `PlayerSeasonId + Edition` 중복 표시 0.
- Award 없는 특수 Edition을 도감이 임의 생성하지 않음.
- WorldCardCatalog에 새 Edition이 추가되면 도감이 자동으로 갱신.

### 30.5 Owned / EverAcquired

시나리오:

```text
미획득
→ 획득
→ 중복 획득
→ 판매해 0장
```

검증:

```text
현재 보유: false
EverAcquired: true
수집률 유지
```

### 30.6 Wishlist

- 미보유 Card 등록 가능.
- 중복 등록 no-op.
- 해제.
- 같은 PlayerSeason의 서로 다른 Edition 독립.
- 획득한 정확한 CardId만 자동 제거.
- 다른 Edition 획득으로 위시가 제거되지 않음.
- 판매 후 자동 재등록되지 않음.
- Save/Load 유지.

### 30.7 Scout Independence

Wishlist가 다른 두 State에서 같은:

```text
Scout Seed
SP
Pool
WorldCardCatalog
```

을 사용하면 Card Sequence가 완전히 같아야 한다.

Pity 결과도 같아야 한다.

### 30.8 Scout Navigation

- Card가 포함되는 Pool만 표시.
- 존재하지 않는 YearFranchise 조합을 추천하지 않음.
- Award Card가 현재 Award Pool 후보가 아니면 잘못된 경로 표시 금지.

### 30.9 Progress

- Card 판매로 EverAcquired 수집률 감소 0.
- WorldCardCatalog에 Card 추가 시 분모 증가.
- Matrix 빈 TeamSeason Cell은 0/0이 아니라 N/A.
- Franchise×Year Cell 선택 결과가 Card Filter 결과와 동일.

### 30.10 Persistence

- Save round-trip 후 EverAcquired/Wishlist 동일.
- Migration 시 현재 Owned 전부 EverAcquired.
- v4 기존 Save의 과거 판매 카드 이력을 임의 추론하지 않음.
- Load에서 WorldIdentity/WorldCardCatalog 재생성 호출 없음.

### 30.11 UI / Performance

- 5,000 / 10,000 / 20,000 Card fixture에서 화면 Object 수가 전체 Card 수에 비례해 폭증하지 않음.
- 빠른 Scroll 중 잘못된 Card binding/초상화 재사용 오류 없음.
- 빠른 Filter 변경 중 선택 Card가 다른 ID로 잘못 연결되지 않음.
- 16:9 주요 해상도에서 Filter/카드/상세가 겹치지 않음.

## 45. 최종 정의

선수 도감은 새로운 선수·카드 시스템이 아니다.

```text
Canonical 선수/구단
+ World Identity
+ WorldCardCatalog
+ Owned Card
+ Collection History
+ Wishlist
```

를 Stable ID로 합성해 보여주는 **Runtime 탐색·수집 Presentation 시스템**이다.

도감의 핵심 책임은:

```text
"무엇이 존재하는가"
"무엇을 현재 가지고 있는가"
"무엇을 과거에 획득했는가"
"무엇을 앞으로 영입하고 싶은가"
```

를 정확히 분리해 사용자에게 보여주는 것이다.

Wishlist는 목표 관리 도구이지 Scout 확률 조작 시스템이 아니다.

Card Acquisition의 게임 규칙은 기존 05절 Scout/Owned Economy가 유지하고,
도감은 그 결과를 정확히 기록·탐색·연결한다.

## 47. 구현 상태 (2026-09-07)

### Core / Query

**완료.** Canonical 전체 `PlayerSeasonDefinition`과 실제 `WorldCardCatalog.Cards`를 Stable ID Index로
조회한다. 이름 검색은 World DisplayName만 사용하고 구단·연도·연대·선수 유형·Position·Role·Cost·
Edition·수집 상태 Filter를 AND로 합성한다. Core25와 현재 참가 리그 제한은 없다. World History의
동일 PlayerSeason 다단계 기록은 정규시즌 전체 행만 상세에 사용한다.

### Acquisition / Scout Integration

**부분 완료.** 획득 Commit에서 Owned, EverAcquired, exact CardId Wishlist 해제를 함께 확정하고
`WasWishlisted`를 공개 결과로 전달한다. Production Scout Pool의 실제 후보 수·위시 포함 수와 가장
좁은 유효 Pool 바로가기를 제공하며 Wishlist는 Weight/Pity/RNG에 전달하지 않는다.

현행 경제의 판매는 `OwnedPlayerCardState.DuplicateCount`만 소비하므로 기본 보유 카드가 0장이 되는
Production 처분 경로는 없다. 로스터·계약·훈련·장착 Skill 상태를 함께 다룰 정책 없이 임의로 기본
카드를 삭제하지 않았으며 이 항목은 후속 Gate다.

### Persistence / Migration

**완료.** 구단주 SaveVersion 15가 EverAcquired ID Set과 `WishlistEntry(CardId, AddedSequence)`를
저장한다. v1~v14는 현재 Owned를 EverAcquired로 이행하며 과거 판매 이력은 추정하지 않는다.
Catalog에서 사라진 저장 ID는 보존하고 파생 집계에서는 제외한다.

### uGUI

**부분 완료.** Astra Medium UI 구현으로 기존 `SharedGameShellView`, Owner Skin,
`PlayerMiniCardView`, 카드 상세 Popup을 재사용했다. 구단주 `선수 도감`과 같은 Depth의 독립
`위시리스트`, 선수/카드/수집 현황 Tab, 상세와 다른 연도·Edition 탐색, Scout 연결을 제공한다.
목록은 가시 영역 Card만 생성하는 Virtualized Grid다.

읽기 전용 플래그는 Owner 기능을 숨기지만 선수 커리어 Production Route는 아직 없다. Career와
Historical World의 Seed가 분리될 수 있는데 현행 `CareerState`가 World History Seed를 저장하지 않으므로,
Save/Load 뒤 다른 월드를 조용히 재생성하는 임시 연결은 하지 않았다.

### Performance / E2E

- Unity 6 Editor Production Archive 단일 계측: Cards 19,044 / PlayerSeasons 17,387.
- Index build 420.80 ms, 전체 Card+PlayerSeason Query 432.38 ms, 구단·연도·Edition 복합 Filter 1.91 ms.
- 5,000 / 10,000 / 20,000 Card Virtualization과 Scroll 재바인딩 테스트 코드는 추가했다.
- 관련 Core/Simulation/Game/Presentation 및 Test asmdef는 변경 과정에서 컴파일을 확인했다.
- 전체 Unity Test Runner는 기존 `Unity.PerformanceTesting.Editor.TestRunBuilder` prebuild에서 실행 전
  중단되어 통과로 기록하지 않는다. 이후 사용자 요청에 따라 추가 Editor 실행과 테스트는 수행하지 않는다.
- 실제 16:9 조작·빠른 Scroll 초상 재사용·23단계 Production E2E는 미검증이다.

### Independent Review

**Critical 0 / Major 3 / Minor 3.** 첫 진입 Scout service와 시즌별 Wishlist 재색인 Major는 검토 중
수정됐다. 최종 Major는 Career 읽기 전용 Production Route, 기본 카드 0장 처분 경로, 필수 E2E 검증
공백이다. 따라서 본 기능 전체는 **부분 완료**다.
