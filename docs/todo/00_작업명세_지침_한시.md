## 1. 배경 — 이 지침이 필요한 이유

2026-09-05 `docs/todo` 전수 분석에서 세 가지 실패 패턴이 반복 확인됐다. 이 지침의 모든 규칙은
그 세 가지를 다시 만들지 않기 위한 것이다.

### 1.1 Definition/Resolver는 있는데 Production 소비자가 없다

순수 C# 계약과 EditMode 테스트까지 만들어 놓고, 실제 게임에서 그 코드에 도달하는 경로를 만들지
않은 채 "구현됨"으로 기록한 사례다.

| 대상 | 존재 | Production 호출 |
|---|---|---|
| `ScoutRoller` (`Simulation/Historical/CardEconomyResolvers.cs`) | 있음 | **없음 — 참조처가 EditMode 테스트뿐** |
| `CardEnhancementResolver.Enhance` | 있음 | **없음 — 동일** |
| `CareerPlayerWildcard` (`Core/Historical/`) | 있음 | **없음 — 동일** |
| 승강 규칙 (`RosterLeagueDefinitions`의 `PromotionWinningPercentage`, `MoveTo`) | 있음 | **없음 — Game 레이어 소비자 0건** |
| `FacilityType.TacticLab` 효과 Profile | 있음 | **없음 — 업그레이드해도 소비하는 시스템이 없음** |
| `OwnerRosterGuideEventAdapter` (프런트 매니저) | 있음 | **2026-09-05에 배선됨 — 그 전까지 호출처 0건** |
| `GuideManager.CaptureRepeatState` / `RestoreRepeatState` | 있음 | **없음 — 호출처 0건, `cooldownScope: Save`가 동작하지 않음** |

결과적으로 SP를 생산하는 시설은 있는데 **SP를 쓸 곳이 Production에 없다.** 시설 투자라는 의사결정
자체가 성립하지 않는다.

프런트 매니저 가이드도 같은 형태다. `factTypeIndex` 100개 중 실제 Fact 생산자가 있는 것은 11종뿐이고
나머지 Cue는 데이터·UI가 완비된 채 영원히 뜨지 않는다(`매니저_상황.md` §4.4). **한 시스템이 미배선이면
그 시스템만 죽는 게 아니라, 그것을 소비하려던 다른 완성 시스템까지 함께 죽는다.**

### 1.2 콘텐츠가 비어 있는데 시스템을 완료로 기록한다

전술카드 시스템은 Resolver·Trigger·Category·Tier가 전부 구현됐지만 실제 카드는
`NewGameDefinition.asset`에 **2장**뿐이다(문서 목표 16장). Counter 조합은 성립 자체가 불가능하다.
구조가 완성돼도 콘텐츠가 없으면 플레이어에게는 그 기능이 존재하지 않는다.

### 1.3 설계 결정을 미확정한 채 인접 시스템을 먼저 구현한다

`부상_제거_컨디션_시스템_TODO.md` §3의 설계 결정 3가지가 확정되지 않은 상태에서 12절
Condition·Chemistry가 먼저 들어갔다. 그 결과 부상과 컨디션이 **둘 다 살아 있는 이중 트랙**이 됐고,
컨디션 스케일도 `Core.Historical`의 10단계 표시 밴드와 `GrowthBalanceTable.ConditionBalance`의
2구간이 **두 벌** 공존한다. 의도된 설계가 아니라 미결정 상태가 굳은 것이다.

## 2. 작업 명세 필수 구조

이 폴더에 새 작업 명세를 쓰거나 기존 명세를 착수할 때, 아래 7개 항목을 **전부** 채운다. 하나라도
비어 있으면 착수하지 않는다. 특히 §2-2는 §1-1을 막는 핵심 항목이므로 생략할 수 없다.

```markdown
## 대상 모드
선수 커리어 / 구단주 / 공통 중 무엇인가. 두 모드에 다르게 동작하면 각각 적는다.

## 소비자 경로 (필수)
플레이어 입력 → Presentation → Game → Simulation → Core 까지 실제 호출 체인을 타입·메서드
이름으로 적는다. "Resolver를 만든다"로 끝나면 명세가 아니다.
예) UI_Scene_OwnerShop.OnScoutClicked → OwnerModeManager.ExecuteScout
    → ManagerModeCoordinator.Scout → ScoutRoller.Roll → OwnedPlayerCardState 갱신

## 콘텐츠 수량
데이터로 저작할 항목의 최소 수량과 저작 위치(SO/JSON 경로). 구조만 만들고 콘텐츠를 나중으로
미루려면 그 사실과 임시 수량을 명시한다.

## 선행 설계 결정
착수 전에 확정해야 할 질문과 그 답. 미확정 항목이 있으면 그 항목에 의존하는 작업은 착수하지
않는다. 답을 정했으면 근거와 함께 이 자리에 적는다.

## 완료 게이트
§3의 다섯 게이트 각각에 대해 이 작업에서 무엇을 통과 근거로 삼을지 적는다.

## 검증 근거
실행할 테스트와 대량 시뮬레이션의 종류·규모. 밸런스 계수를 건드리면 수치 보고 항목까지 적는다.

## 제거/정리 대상
이 작업으로 죽는 코드·문서·데이터. 대체가 아니라 추가라면 "없음"이라고 명시한다.
```

## 3. 완료 판정 규칙

### 3.1 Production 소비자 게이트 — 가장 우선한다

**Production 새 게임에서 도달할 수 없는 코드는 미구현이다.** 타입이 존재하고 EditMode 테스트가
통과해도 마찬가지다.

판정 방법 — 대상 타입을 리포지토리 전체에서 검색해 참조처를 분류한다.

```text
참조처가 Tests/ 와 자기 자신뿐        → 미구현
참조처에 Game 레이어가 있으나
  진입점이 UI/명령에 연결되지 않음    → 부분 완료 (§4 어휘 사용)
플레이어 조작 → 결과 반영까지 이어짐  → 완료 후보 (나머지 게이트로 판정)
```

작업 명세의 "소비자 경로"에 적은 체인이 실제 코드와 일치하는지 마지막에 다시 확인한다.

### 3.2 콘텐츠 게이트

시스템의 완료는 **그 시스템이 다루는 콘텐츠의 최소 수량**을 함께 만족해야 한다. 콘텐츠가 목표에
미달하면 "Resolver 완료, 콘텐츠 N/M"으로 나눠 기록하고 시스템 전체를 완료로 쓰지 않는다.

최소 수량의 기준은 "그 시스템의 핵심 상호작용이 성립하는가"다. 전술카드의 Counter 조합, 팀컬러의
Stack 판정, Scout의 Bucket 분포처럼 **여러 항목이 있어야만 발생하는 상호작용**이 있으면, 그
상호작용이 실제로 일어날 수 있는 수량이 최소치다.

### 3.3 선행 설계 결정 게이트

미확정 설계 결정에 의존하는 작업은 착수하지 않는다. 이미 인접 시스템이 먼저 들어가 개념이
이중화된 경우(§1-3), **새 코드를 얹기 전에 이중화를 먼저 해소**한다. 두 트랙을 유지한 채 세 번째
트랙을 추가하지 않는다.

한 개념에 스케일·상태·저장 위치가 두 벌 생기면 그 자체를 결함으로 본다. 통합하거나, 통합하지
않는다면 **어느 쪽이 Source of Truth이고 다른 쪽이 파생값인지**를 코드 주석과 명세에 남긴다.

### 3.4 검증 근거 게이트

- **과거 스냅샷 수치를 최신 완료 근거로 인용하지 않는다.** 코드가 병합된 뒤의 실행 결과만
  근거다. "이전 39/39 통과"는 그 이후 변경분의 근거가 될 수 없다.
- 실행하지 못한 검증은 **통과로 기록하지 않고 미실행으로 기록한다.** 환경 문제(Unity 라이선스 등)로
  못 돌렸으면 그 사유까지 적는다.
- 밸런스 계수를 바꿨으면 대량 시뮬레이션 수치를 근거로 제시한다
  ([[Balance_Testing_Guidelines_UPlayBall]] 절차).
- 결정론 확인: 같은 Seed·같은 입력을 두 번 돌려 결과가 일치하는지 본다.

### 3.5 표현 계층 게이트

Presentation은 Simulation/Game이 확정한 결과를 표시할 뿐이다. UI가 확률·판정·적합도를 다시
계산하면 그 작업은 완료가 아니다. 반대로 **결과를 만들 백엔드가 Production에 없는 상태에서 UI를
먼저 만들지 않는다** — 표시할 결과가 없는 화면은 게임을 진전시키지 않는다
([[Project_Principles_UPlayBall]] 3번).

### 3.6 가이드 Fact 게이트

프런트 매니저 Cue는 이미 100종이 저작돼 있고 대부분 생산자가 없다. **새 기능을 Production에 연결할
때, 그 기능에 대응하는 Cue가 데이터에 이미 있으면 Fact 생산자를 같은 작업 단위에서 붙인다.** 기능만
붙이고 안내를 다음 작업으로 미루지 않는다 — 미루면 §1-1의 미배선이 한 건 더 늘어날 뿐이다.

착수 시 `front_manager_guide_dataset_v1.json`의 `factTypeIndex`에서 해당 기능의 Fact 이름을 먼저
검색하고, 있으면 §2의 "소비자 경로"에 그 생산자 경로까지 포함해 적는다.

## 4. 상태 표기 어휘 고정

문서에 상태를 적을 때 아래 네 가지만 쓴다. 어휘를 섞으면 §1-1이 다시 발생한다.

| 표기 | 정의 |
|---|---|
| **완료** | §3의 다섯 게이트를 전부 통과했고, 그 근거가 최신 병합본 기준으로 존재한다. |
| **부분 완료** | 일부 게이트를 통과했다. **어느 게이트가 남았는지 반드시 함께 적는다.** |
| **코드 연결** | 코드 경로는 이어졌으나 실행 검증 근거가 아직 없다. **완료가 아니다.** |
| **미구현** | Production 소비자가 없다. Definition·테스트 존재 여부와 무관하다. |

## 5. 잔여 작업 순서

2026-09-05 분석 기준. 앞 항목이 뒤 항목의 전제이므로 순서를 바꾸지 않는다. 각 항목을 착수할 때
§2의 7개 항목을 채운 명세를 해당 기능 문서에 추가한다.

### S1. Scout·카드 강화를 Production에 연결

`ScoutRoller`/`CardEnhancementResolver`는 이미 검증돼 있다. 신규 시스템이 아니라 **배선 작업**이다.
`OwnerModeManager`에 Scout/강화/판매 커맨드를 노출해 SP 생산 시설이 처음으로 의미를 갖게 한다.
이것이 `프야매_UI_상점연출_통합_TODO.md`의 착수 조건(그 문서 §0)이기도 하다.

### S2. 전술카드 콘텐츠 16장과 `TacticLab` 소비자

콘텐츠를 2장 → 16장으로 채우고(§3-2), 연구/Inventory Runtime을 만들어 `TacticLab` 시설 효과에
소비자를 붙인다. 현재 `TacticLab`은 "돈을 넣으면 아무 일도 일어나지 않는 시설"이다.
Signature 해금과 AI 전술 선택도 이 단위에 포함한다.

### S3. 승강과 새 시즌 로스터 이월

`LeagueGrade` 승강 기준은 데이터로 이미 있고 소비자만 없다. 시즌 종료 transaction에 등급 판정과
로스터 이월을 붙인다. 승강이 붙는 순간 09~12절의 경제·Staff·Condition이 전부 "다음 등급으로
올라가기 위한 판단"으로 재해석되므로, 여러 시즌 연속 플레이 동기에 가장 크게 기여한다
([[Project_Principles_UPlayBall]] 4번).

### S4. 부상/컨디션 이중 트랙 정리

**코드보다 기획이 먼저다.** `부상_제거_컨디션_시스템_TODO.md` §3의 세 결정 —
① 결장 이벤트를 완전히 없앨 것인가, ② 컨디션 자연 변동 곡선, ③ 훈련용(0~100)과 경기용(10단계)
스케일을 통합할 것인가 — 를 먼저 확정해 그 문서에 반영한다. 결장 제거는 리스크의 무게감을 바꾸는
결정이라 임의로 진행하지 않는다. 확정 전까지 부상·컨디션 어느 쪽에도 새 코드를 얹지 않는다.

### S5. 상점/뽑기 UI

S1·S2가 끝난 뒤 착수한다(§3-5). 그 전에는 표시할 결과가 없다.

### S6. 프런트 매니저 미배선 정리

기능에 종속되지 않는 두 건만 독립 작업으로 남는다 — `TUTORIAL_OWNER_FIRST_ENTRY` Fact 생산자
("첫 진입"의 정의를 먼저 확정한다)와 `GuideRepeatState`의 세이브 연결(`cooldownScope: Save`가
동작하지 않는 원인). 나머지 Cue는 §3-6에 따라 S1~S3에 각각 흡수한다. 예를 들어
`TUTORIAL_OWNER_SCOUT_FIRST`는 S1의 작업 단위에 포함한다.

## 6. 착수 전 필수 확인

새 작업을 시작할 때 최소한 다음을 검색해 **이미 있는 것을 다시 만들지 않는지** 확인한다. 이
프로젝트는 Definition이 이미 있는데 소비자가 없는 경우가 많아, "없어서 못 쓴다"보다 "있는데 안
쓴다"가 더 흔하다.

```text
대상 기능의 Definition / State / Resolver 타입 이름
그 타입의 참조처 (Tests/ 만 나오면 §3-1의 미구현)
같은 개념의 다른 이름 (Condition vs Chemistry, Injury vs Availability 등)
데이터 저작 위치 (Assets/10.Datas/, OwnerExpansionBalance.json)
```
