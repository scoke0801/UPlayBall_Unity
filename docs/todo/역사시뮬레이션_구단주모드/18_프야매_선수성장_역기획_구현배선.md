# 18. 프로야구 매니저 선수 성장 — 역기획과 구현·배선 명세

> 상태: 구현 배선 완료 / 검증 보류 — 카드 훈련·유학·스킬 블록·강화의 Runtime/UI/Save/Match
> 경로를 연결했다. 사용자 요청에 따라 자동 테스트와 대량 Simulation은 실행하지 않았다.
>
> 조사 기준일: 2026-09-06
>
> 대상 모드: 역사 시뮬레이션 **구단주 모드 전용**

## 0. 결론

엔트리브 `프로야구 매니저`의 선수 성장은 한 장의 카드를 오래 쓰게 만드는 네 축으로 요약된다.

```text
훈련·유학으로 카드의 약점 보완
        +
16칸 스킬 블록으로 선수별 빌드 구성
        +
동일 카드로 단계 강화
        +
성장 전후를 비교하며 주전 선수를 선택
```

이 구조의 장점은 좋은 카드를 뽑는 순간이 끝이 아니라, **누구에게 제한 자원을 투자하고 어떤 역할로
완성할지**가 여러 시즌의 판단으로 이어진다는 점이다. 반면 원작 후기의 실패·랜덤 재분배·현금 재시도,
현실 시간 대기, 블록 회수 손실을 그대로 가져오면 결과의 납득 가능성보다 반복 노동과 매몰 비용이 커진다.

UPlayBall은 네 기능을 다음처럼 역할 분리한다.

| 기능 | 게임 내 역할 | 능력치 소유 계약 |
|---|---|---|
| 카드 훈련 | DP를 즉시 써서 원하는 약점을 정밀 보완 | 영구 성장. `TrainingCeiling` 안에서만 `CardTrainingState` 증가 |
| 유학 | 카드 사용 중단과 시간을 대가로 DP 효율이 좋은 복합 성장 | 영구 성장. 훈련과 **같은** `CardTrainingState`·`TrainingCeiling` 사용 |
| 스킬 블록 | 보유 블록을 4×4에 배치해 역할별 빌드 구성 | 교체 가능한 Loadout. Base/TrainingCeiling을 수정하지 않음 |
| 카드 강화 | 동일 `CardId` 중복의 가치 회수 | 실패 없는 별도 `EnhancementLevel`, 최대 +5 |

가장 중요한 구조 결정은 다음 두 가지다.

1. 훈련과 유학을 별도 성장 수치로 누적하지 않는다. 둘 다 기존 `CardTrainingState` 한 곳에 기록한다.
2. 경기, 프리게임, 보유 선수, 전력 비교 화면이 각자 능력치를 더하지 않는다. 하나의
   `OwnerCardAbilityResolver`가 단계별 Breakdown과 활성 Trait을 만들고 모든 Consumer가 이를 사용한다.

```text
BaseAttributes
→ EditionModifier
→ DevelopmentBonus (카드 훈련 + 유학, TrainingCeiling 제한)
→ EnhancementBonus
→ SkillBoardBonus / Trait
→ TeamColor
→ Condition / Tactic
→ MatchRatingCurve
```

`BaseRosterStrength`는 기존 계약대로 Base 능력치만 뜻한다. 성장 반영 전력에는
`OwnedCardEffectiveStrength`처럼 다른 이름을 사용해 기본 전력과 혼동하지 않는다.

## 1. 대상 모드

### 1.1 포함

- 역사 시뮬레이션 구단주 모드 플레이어 구단의 `OwnedPlayerCardState`.
- 선수 카드별 훈련·유학·강화 상태.
- 구단 공용 스킬 블록 Inventory와 카드별 4×4 배치.
- 구단주 Production UI, Save/Load, Match 적용, Front Manager 안내.

### 1.2 제외

- 선수 커리어 모드의 개인 훈련·오프시즌 유학·성장판 규칙 변경.
- AI 구단에 SP/DP, 중복 카드, 스킬 블록 Inventory를 부여하는 것.
- 나이 성장, 노화, 부상, 계약 재갱신 보너스.
- 직접 타격·투구 조작 또는 공 물리.

구단주 카드는 특정 시즌의 고정된 `PlayerSeasonDefinition`이므로 나이를 먹지 않는다. 선수 커리어의
`GrowthResolver`, `OffseasonState`, `PlayerStudyState`, `CareerEconomyState`를 구단주 상태에 억지로
공유하지 않는다. 공유 대상은 `PlayerAbility`, `SkillBlockDefinition`, 보드 기하 검증처럼 모드에
독립적인 계약뿐이다.

## 3. 역기획 — 원작 성장 루프가 작동한 이유

## 3.1 획득과 육성의 연결

```text
선수 카드 획득
→ 즉시 전력 비교
→ 약점 또는 팀 내 역할 발견
→ 훈련/유학/스킬 블록 투자
→ 동일 카드 획득 시 강화 또는 판매
→ 성장 결과로 라인업 경쟁 재평가
```

핵심은 각 기능의 버튼 수가 아니라, 하나의 카드가 다음 세 질문을 동시에 만든다는 점이다.

1. 지금 당장 DP를 써서 약점을 메울 것인가?
2. 주전에서 빼고 유학을 보내 더 효율적으로 성장시킬 것인가?
3. 희소한 블록과 중복 카드를 이 선수에게 귀속할 것인가?

## 3.2 좋은 긴장

- 훈련 자원은 모든 선수에게 충분하지 않다.
- 유학 중에는 해당 카드를 쓰지 못해 현재 전력이 낮아진다.
- 한 블록 Instance는 한 카드에만 장착할 수 있다.
- 동일 카드는 강화와 SP 판매 중 하나만 선택할 수 있다.
- 성장 상한 때문에 원래 강한 능력만 계속 올리는 것이 항상 최선은 아니다.

## 3.3 원작의 지배 전략

후대 기록상 긴 유학이 짧은 유학을 압도하거나, 집중 훈련이 일반 슬롯 개방을 대체하고, 실패 없는
확정 선택보다 랜덤 재시도 횟수가 성장을 결정하는 문제가 있었다. UPlayBall에서는 각 성장축에
서로 다른 대가를 부여하되 어느 축도 다른 축의 상위호환이 되지 않게 한다.

## 4. UPlayBall 정본 성장 구조

## 4.1 능력치 계층

`OwnerCardAbilityResolver`가 아래 값을 능력치별로 반환한다.

```text
OwnerCardAbilityBreakdown
{
    Base
    Edition
    Development       // 훈련 + 유학, 동일 CardTrainingState
    TrainingCeiling
    Enhancement
    SkillBoardRaw
    SkillBoardEffective
    TeamColor
    Condition
    Tactic
    PermanentRating
    MatchInputRating
}
```

계산 규칙:

```text
DevelopmentRating = min(Base + CardTrainingBonus, TrainingCeiling)
PermanentRaw       = DevelopmentRating + Edition + Enhancement + SkillBoardEffective
MatchRaw           = PermanentRaw + TeamColor + Condition + Tactic
MatchInputRating   = MatchRatingCurve.ResolveMatchInput(MatchRaw)
```

- `BaseAttributes`와 `TrainingCeiling`은 Offline Bake 이후 수정하지 않는다.
- 유학 완료도 `CardTrainingState.AddBonus`와 동등한 단일 영구 성장 Transaction으로 기록한다.
- Enhancement와 SkillBoard는 TrainingCeiling을 소비하지 않지만 최종 `MatchRatingCurve`의 HardCap을 따른다.
- UI는 위 식을 다시 구현하지 않고 Resolver 결과만 표시한다.
- 경기 핫패스에서는 매 타석 재계산하지 않는다. Lineup 확정 시 `MatchRosterSnapshot`에 값과 Trait을 동결한다.

## 4.2 자원과 대가

| 자원/제약 | 소비처 | 획득·회복 |
|---|---|---|
| DP | 카드 훈련, 유학 시작 | TrainingCenter 주간 생산, Staff 효율 |
| Money | 스킬 블록 상점, 시설·Staff | 기존 구단 경제 |
| 동일 카드 중복 | 강화 또는 SP 판매 | Scout |
| 시간 | 유학 4주 초기안 | `AdvanceWeek`로만 진행 |
| 유학 슬롯 | 동시 프로젝트 수 | TrainingCenter Level 1/2/3에서 1/2/3 |

Money로 DP를 직접 사거나, DP로 강화 재료를 대체하거나, 현실 시간을 단축하는 통로를 만들지 않는다.

## 5. 카드 훈련

## 5.1 역할

카드 훈련은 **즉시·정밀·비교적 비싼 DP 사용처**다. 한 번에 한 능력치를 선택하고 결과를 확정한다.

```text
카드 선택
→ 관련 6개 능력치의 Base / 현재 / Ceiling 확인
→ 훈련 프로그램 선택
→ DP 비용과 +1 후 경기 적용값 Preview
→ 확정
→ CardTrainingState 갱신
→ Pregame/Collection/Match Snapshot 무효화
```

### 초기 규칙

- 타자 6종, 투수 6종으로 총 12개 프로그램.
- 프로그램당 대상 `PlayerAbility` 1개.
- 1회 최대 +1을 기본값으로 시작한다.
- `DpCostPerPoint`는 `OwnerExpansionBalance.json`에서 저작한다.
- Hitting/Pitching/Development Coach는 현재처럼 DP 비용 효율만 바꾼다.
- 훈련 실패, 대성공, 랜덤 하락은 없다.
- 현재값이 Ceiling이면 실행하지 않고 다른 능력치를 추천한다.

`CardTrainingResolver`의 현재 계산 계약은 유지하되 `Preview`와 `Execute`가 같은 계산 함수를 사용하도록
Transaction을 분리한다. Preview 뒤 상태가 바뀌었으면 Revision 불일치로 실행을 거부하고 다시 계산한다.

## 5.2 플레이어가 보아야 할 정보

- 현재 DP / 소모 DP / 훈련 뒤 DP.
- Base, Edition, Development, Enhancement, SkillBoard를 분리한 현재값.
- 해당 능력치의 TrainingCeiling과 남은 성장 여지.
- Staff 때문에 절약되는 DP.
- 이 능력치가 실제로 영향을 주는 역할과 최근 기용 위치.
- 훈련 전후 `PermanentRating` 및 중립 조건의 `MatchInputRating`.

## 6. 유학

## 6.1 역할

유학은 **시간과 로스터 유연성을 대가로 DP 효율이 좋은 복합 훈련**이다. 카드가 나이를 먹지 않는
구단주 모드에서 잠재력·자연 성장 시스템을 흉내 내지 않는다.

```text
ActiveRoster 밖의 카드 선택
→ 유학 프로그램과 2~3개 목표 능력 확인
→ 완료 시 실제 상승량, 기간, DP, 슬롯 Preview
→ 시작 시 DP 소비 및 DevelopmentProjectState 생성
→ 4회 AdvanceWeek 동안 등록 불가
→ 완료 주에 같은 CardTrainingState에 확정 상승 반영
```

### 초기 규칙

- 유학 시작 대상은 현재 ActiveRoster에 등록되지 않은 카드만 허용한다.
- 유학 중인 카드는 ActiveRoster에 등록할 수 없다.
- 기본 기간은 4주, 카드별 시즌당 1회.
- 결과는 시작 시 확정되는 결정론적 수치이며 성공/실패가 없다.
- 목표 능력치가 Ceiling에 걸리면 Preview에서 실제 획득량을 줄여 표시한다.
- 실제 획득량이 0이면 시작할 수 없다.
- 시즌 종료까지 남은 주가 부족하면 시작할 수 없다.
- Save/Load 뒤에도 남은 주와 예정 결과가 동일해야 한다.

## 7. 스킬 블록

## 7.1 역할

스킬 블록은 영구 성장의 추가 이름이 아니라 **선수의 역할을 바꾸는 공유 장비**다. 예를 들어 같은
타자 카드라도 Contact 중심 리드오프, Power 중심 중심타선, Defense 중심 대수비 빌드가 달라진다.

### 보드 계약

- 카드마다 4×4 보드 1개와 Trait Socket 2개.
- 표준 Tetromino 7종, 회전·경계·겹침 검증.
- 한 `SkillBlockInstance`는 구단 안에서 한 카드에만 장착 가능.
- 모든 16칸은 처음부터 열려 있다. 슬롯 개방 훈련은 만들지 않는다.
- 블록 제거·재배치·카드 간 이동은 파괴나 Money 비용 없이 허용한다.
- 진행 중 경기에는 영향을 주지 않고 다음 `MatchRosterSnapshot`부터 적용한다.
- 대량 재배치 피로는 즐겨찾기·필터·전체 해제·카드별 배치 Preset으로 줄인다.

원작의 공간 퍼즐은 살리되 제거 손실은 폐기한다. 의사결정의 무게는 파괴 위험이 아니라
**희소한 한 Instance를 어느 카드에 배치할지**에서 나온다.

## 7.2 상태 분리

현재 `SkillBoardState`는 선수 커리어 한 명의 Inventory, Gacha Pity, 시즌 Lock, 배치를 모두 가진다.
이를 카드마다 복제하면 구단 공용 Inventory가 여러 벌 생기므로 그대로 사용하지 않는다.

```text
OwnerSkillBlockInventoryState       // 구단 공용
  NextInstanceId
  SkillBlockInstance[]
  GachaPityState

OwnedCardSkillBoardState            // OwnedPlayerCardState에 카드별 귀속
  BoardDefinitionId
  PlacedSkillBlock[]
  Revision
```

불변식:

1. 모든 InstanceId는 구단 안에서 유일하다.
2. 한 InstanceId는 0개 또는 1개의 카드 보드에만 나타난다.
3. 소유하지 않은 Definition/Instance는 배치할 수 없다.
4. 배치 Commit은 전체 요청을 먼저 검증한 뒤 원자적으로 적용한다.
5. 카드 보드 삭제·복원 시 장착 블록은 Inventory에서 유실되지 않는다.

`SkillBoardService`에서 회전·점유·Trait Socket·보너스 상한 계산을 모드 독립
`SkillBoardLayoutResolver`로 추출한다. Career 전용 Money/Offseason/Pity 처리는 기존 Service의
Adapter로 남겨 Career 세이브 의미를 바꾸지 않는다.

## 7.3 보너스와 Trait

초기에는 기존 계약을 재사용한다.

- 능력치별 유효 보너스 최대 +9.
- 카드 보드 전체 능력치 보너스 최대 +18.
- 같은 능력치의 1/2/3번째 블록 효율 100%/60%/30%, 이후 0%.
- Unique 이상 블록이 Trait Socket을 덮으면 기존 8종 Trait 중 하나 활성.
- Trait은 `DetailedMatchEngine`이 읽는 경기 Snapshot에 명시적으로 포함한다.

이 수치는 Career 밸런스의 현행값이지 구단주 모드 검증 완료값이 아니다. Owner 대량 Simulation을
통과하기 전까지 `초기 가설`로 표시하고, 필요하면 Owner 전용 상한을 `OwnerExpansionBalance.json`에
분리한다.

## 7.4 획득

기존 상점의 Skill Block 탭과 5개 등급 Offer를 구단주 모드에서도 사용한다.

```text
Skill Block 상품 선택
→ 실제 등급 확률·Pity·가격 Preview
→ Money 결제
→ 결정론적 Shop RNG
→ OwnerSkillBlockInventoryState에 Instance 추가
→ Reveal 및 장착 CTA
```

Career 전용 `SkillBlockPackFulfillment`은 `CareerEconomyState`와 `SkillBoardState`에 결합되어 있으므로
그대로 호출하지 않는다. 공통 추첨 계산을 추출하고 `OwnerSkillBlockPackFulfillment`가
`ManagerEconomyShopWallet`과 Owner Inventory Transaction을 사용한다.

블록 조합은 원작에 존재했지만 최초 범위에서는 제외한다. 420개 기본 조합과 Pity만으로 중복 블록의
가치가 충분한지 먼저 측정한다. Inventory 포화가 확인될 때에만 `같은 등급 3개 → 한 단계 위 후보
3개 중 1개 선택` 같은 결정론적 Recycling을 별도 기획한다.

## 8. 카드 강화

## 8.1 정본 규칙

05절과 현재 코드의 계약을 유지한다.

```text
+0 → +1 → +2 → +3 → +4 → +5 MAX
동일 CardId 중복 1장 소비
실패 없음
별도 Money/DP 없음
단계당 해당 선수 유형의 경기 사용 능력치 +1
```

실제 State는 현재처럼 단일 `EnhancementLevel`로 저장한다. 타자 화면은 타자 6개, 투수 화면은 투수
6개의 +1을 표시하며 사용하지 않는 반대 유형 능력치를 성장 보상처럼 과장하지 않는다.

## 8.2 UX 보완

현재 Collection의 강화 버튼은 즉시 실행까지 연결돼 있다. 중복 카드는 판매와 강화가 배타적이므로
다음 확인 단계를 둔다.

```text
강화 Preview
  현재 +N → +N+1
  소비 중복 1 / 보유 N
  관련 6개 능력치 전후
  중립 MatchInput 전후
  "실패 없음" 명시
→ 확정
```

최대 강화 뒤 추가 중복은 기존 기본 자동 판매 정책의 대상이지만, 자동 판매 설정과 예상 SP를
플레이어가 확인할 수 있어야 한다.

원작의 확률 강화, 실패 시 재료 소멸, 랜덤 상승 능력치, 최대 단계 재분배는 도입하지 않는다.

## 13. 구현 순서

앞 단계 Gate를 통과하기 전에 뒤 UI를 활성화하지 않는다.

## G0. 능력치 Source of Truth 통합

1. `OwnerCardAbilityResolver`와 Breakdown 정의.
2. Match, Pregame, Collection, Strength, 네 Preview를 같은 Resolver로 교체.
3. Pregame Enhancement 누락 회귀 테스트.
4. 기존 경기 결과 결정론 유지 확인.

## G1. 강화 마감과 카드 훈련 활성화

1. Enhancement Preview/확인 Transaction과 Guide Fact 생산자.

## 15. 검증 근거

## 15.1 Core/Simulation Unit

- Training과 Study 합계가 능력치별 `TrainingCeiling`을 넘지 않는다.
- DP 부족, Ceiling 도달, 역할 불일치 프로그램은 상태를 바꾸지 않는다.
- 같은 입력의 Preview와 Execute 결과가 같다.
- 유학 완료 주가 정확하고 중복 완료되지 않는다.
- 4×4 경계, 회전, 겹침, 중복 Instance, Trait Socket 규칙.
- 보드 능력치별 +9, 전체 +18, 중첩 체감 규칙.
- 강화 0→5, 중복 소비, MAX 이후 불변.
- 능력치 Breakdown 합계와 Match Input이 일치한다.

## 15.2 결정론

```text
같은 WorldSeed
+ 같은 ShopPurchaseHistory
+ 같은 성장 Command 순서
+ 같은 주차 진행
= 같은 Block 획득, 같은 성장 State, 같은 Match Event Stream
```

Save 직전/직후로 분기해 같은 Command를 실행한 결과도 byte-equivalent State 또는 필드별 완전 일치여야 한다.

## 15.3 Production E2E

최소 시나리오:

1. 새 게임 → DP 생산 → 훈련 Preview/실행 → Save/Load → 경기 반영.
2. Scout 중복 → 강화 Preview/확정 → +5 → 추가 중복 자동 판매.
3. Skill Block 구매 → Reveal → 카드 배치 → Trait 발동 → 경기 반영.
4. 카드 ActiveRoster 해제 → 유학 시작 → 4주 진행 → 완료 → 재등록 → 경기 반영.
5. 훈련/유학으로 Ceiling 도달 → 이후 실행 차단과 Front Manager 안내.

## 15.4 대량 Simulation

초기 밸런스 확정 전 최소 실행량:

- 10,000경기 × 성장 조합 대조군.
- 100시즌 × 20개 Seed의 1·3·5·10시즌 경제 추적.
- 동일 BaseRoster를 사용한 무성장 / Training / Study / Enhancement / SkillBoard / 전체 조합 비교.

보고 항목:

| 구분 | 지표 |
|---|---|
| 야구 통계 | AVG, OBP, SLG, HR/G, BB%, K%, ERA, WHIP, R/G |
| 전력 | 성장 Layer별 평균 Rating 변화, 승률 변화, 포지션별 기여 |
