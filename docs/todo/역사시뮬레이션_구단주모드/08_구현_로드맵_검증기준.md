# 08. Historical World 구현 로드맵과 검증 기준

## 0. 전제

이 로드맵의 완료 기준은 기능 존재가 아니라 Source→Canonical→World Identity→Simulation→History의
단일 Production 경로다. 문서와 구현 중 하나라도 과거 Synthetic Mixing 구조를 정식 경로로 유지하면
완료가 아니다.

```text
Source Data Normalize
        ↓
Source Person / Season 1:1 Mapping
        ↓
Deterministic Ability Conversion
        ↓
Cost / TrainingCeiling
        ↓
Source TeamSeason 1:1 Mapping
        ↓
Core25 Validation
        ↓
Canonical Content Bake
        ↓
World Identity Generation
        ↓
Historical Match / Season Simulation
        ↓
Statistics / Team Standings / Postseason
        ↓
Awards
        ↓
WorldCardCatalog
        ↓
Special Composite Teams
        ↓
TeamColor / Scout / AI / Career Consumer
```

## 1. 구현 Phase

### Phase 1 — Source Normalize와 1:1 Player Bake

- Source Snapshot/Normalized Schema/Version 확정
- Source Person Stable Key와 `PlayerPersonId` 1:1
- Source Person+Year와 `PlayerSeasonId` 1:1
- 동일 인물 다년도 연결과 CareerSpan
- Era/Position/Role Normalization과 Reliability Shrinkage
- 결정론적 BaseAttributes/Cost/TrainingCeiling/Origin Bake
- provenance, Manifest, Content Hash, Validation Report

완료 Gate:

- 다중 Source 개별 기록 Mixing 0건
- SourceSeason 복제·누락·타연도 위장 0건
- World Seed를 바꿔도 Canonical hash 동일
- HR Rate↔Power, K%↔Contact, SB↔Speed, K/9↔Stuff, BB/9↔Control,
  IP/G↔Stamina의 의도된 상관 확인

### Phase 2 — Source TeamSeason 1:1과 Core25

- Source TeamSeason Stable Key와 `TeamSeasonDefinition` 1:1
- 같은 Franchise 다년도 `FranchiseId` 연결
- 해당 Source TeamSeason 내부 PlayerSeason Pool 구성
- Core25 Hitter14/Pitcher11, SP5/Bullpen4/Setup1/Closer1, Foreign≤3
- 부족 데이터 조사와 명시적 Validation Failure/Fallback Report
- 실제 결손 슬롯만 `ReplacementGenerated`로 격리하고 연도·역할 20백분위 aggregate baseline 적용
- Canonical 선수 구성에서 ReferenceStrength/InitialClubDna 파생

완료 Gate:

- 타 Source Team 선수 Mixing 0건
- Source 연도별 TeamSeason 수와 Canonical 수 일치
- Core25 모든 선수의 `OriginTeamSeasonKey` 일치
- 동일 연도 전체 선수의 임의 10팀 Hash/round-robin 재배분 경로 0건
- 1982~2025 fallback 54명 외 `ReplacementGenerated` 0건, covariance/RNG 기반 생성 0건

### Phase 3 — Canonical Archive와 World Identity

- Canonical Player/Team Definition에서 Runtime DisplayName 제거
- 실제 Source 선수/구단명 Runtime Archive 제거와 blacklist 생성
- Domestic/Foreign Player Name 후보와 Franchise Name 후보 데이터화
- `WorldIdentityRegistry`, `WorldPlayerIdentity`, `WorldFranchiseIdentity`
- PlayerPersonId/FranchiseId 기준 결정론적 unique assignment
- Save DTO와 확정 이름 복원

완료 Gate:

- Source 실제 선수·구단명 exact match 0건
- World 내부 Player/Franchise 이름 중복 0건
- 같은 Person/Franchise의 모든 시즌·연도 DisplayName 일치
- null/empty, 숫자, 제어문자, 비정상 길이, 금칙어 0건
- 200~500개 이름 샘플 리포트 사람이 검수 가능
- Load에서 Name Generator 호출 0회

### Phase 4 — Historical Detailed Simulation

- Canonical TeamSeason에서 Schedule 생성
- `DetailedMatchEngine` 계열의 정식 Match 경로 사용
- 개인 Batting/Pitching/Fielding/Baserunning Statistics 누적
- 팀 Wins/Losses/Runs/RunsAllowed/AVG/ERA와 Standings
- Postseason 진출·대진·Champion
- Source 성적·순위·우승 복사 경로 제거

완료 Gate:

- 같은 Baked Content+World Seed의 Event/Statistics/Standings hash 일치
- 다른 Seed에서 Ability는 같고 개인·팀 결과는 달라질 수 있음
- Source Standings를 바꿔도 같은 Simulation 입력 결과는 불변
- 표시 Identity만 바꿔도 Match 결과 완전 일치
- 별도 Ability→예상 AVG/HR/ERA 근사기가 Production History를 만들지 않음

### Phase 5 — Awards와 World History

- Season Statistics 기반 All-Star/GG/Regular Season MVP
- All-Star Game과 Postseason Simulation
- All-Star Game MVP/Postseason MVP
- `WorldAwardRecord`와 `WorldHistorySnapshot`
- `OriginalHistory`를 Legacy/Debug/Validation 경계로 격리

완료 Gate:

- Award Resolver가 실제 World Statistics를 필수 입력으로 요구
- Source Award 복사와 BaseAttributes-only 수상 경로 0건
- Seed 변화에 따라 같은 PlayerSeason의 수상 여부가 달라질 수 있음
- Production New Game에서 `OriginalHistory` 사용자 선택/우회 호출 0건

### Phase 6 — Edition과 특수 합성팀

- Fixed `PlayerSeasonDefinition` + `WorldAwardRecord` → `WorldCardCatalog`
- Normal/AllStar/GoldenGlove/Mvp Edition 유지
- Award 확정 뒤 `SpecialCompositeTeamBuilder` 실행
- AllStar/GoldenGlove/YearSelect Composite Core25
- 세 특수팀 사이 `PlayerSeasonId` 중복 금지

완료 Gate:

- Award 없는 특수 Edition 활성화 0건
- Edition 간 Cost/BaseAttributes/Origin 변화 0건
- Historical Simulation/Award 입력에 특수 합성팀 참가 0건
- 원 Franchise Core25 변경·선수 이동 0건

### Phase 7 — Consumer와 Persistence

- TeamColor는 Canonical Origin+Edition 사용
- Scout/AI는 `WorldCardCatalog`와 Stable ID 사용
- Career/구단주 모드는 같은 `WorldIdentityRegistry`와 History 사용
- Career Player User Identity와 Historical Player Alias 분리
- Identity/Statistics/Standings/Awards/Composite State Save
- Load에 Simulation/Generator 의존성 제거

완료 Gate:

- DisplayName 변경으로 TeamColor/Scout/AI/Contract/Roster 결과 변화 0건
- Save/Load 전후 모든 World History/Identity hash 일치
- Load 중 Historical Simulation, Name Generator, Franchise Generator, Award Resolver 호출 0회
- Production Content 또는 명시적 2016~2025 LeagueGrade 배치 목록이 누락·중복·10구단 미달이면
  명시적 실패, 코드 추론식 최근 연도 선택과 Synthetic fallback 0건

## 2. 선후행 의존과 병렬화

핵심 Schema와 ID가 확정되기 전에 하위 Consumer를 임의로 맞추지 않는다.

```text
Canonical Schema
→ Player/Team Bake
→ World Identity
→ Historical Simulation
→ Statistics/Standings
→ Awards
→ WorldCardCatalog
→ Composite Team/Consumer
```

같은 Phase 안에서는 Source 검증, Name 후보 데이터, Save DTO, 독립 Test Fixture를 병렬화할 수 있다.
그러나 Award를 Statistics보다 먼저 만들거나 특수팀을 Award 입력에 넣는 순환 의존은 허용하지 않는다.

## 3. 필수 자동 테스트 매트릭스

### A. Source 1:1 Mapping

- 각 `PlayerSeasonDefinition` provenance가 정확히 한 Source PlayerSeason
- 한 Runtime Season에 서로 다른 Source Person의 개별 기록 혼입 0건

### B. Person 연결

- 같은 Source Person 다년도 `PlayerPersonId` 동일
- 다른 Source Person `PlayerPersonId` 불일치

### C. Ability 결정론

- 같은 Source 기록+Balance Version의 BaseAttributes 동일
- World Seed 변화에도 BaseAttributes 동일

### D. Cost 결정론

- World Seed/Award/Simulation Result 변화에도 Cost 동일

### E. Team 1:1 Mapping

- 일반 Canonical TeamSeason마다 Source TeamSeason 정확히 1건
- Core25 타 Source Team 선수 Mixing 0건

### F. Historical Statistics

- 고정 Ability라도 다른 World Seed의 실제 시즌 Statistics가 달라질 수 있음
- Source 시즌 기록을 Runtime 결과로 강제하지 않음

### G. Team Standings

- Source 승패/순위 대신 Match 결과에서 Standings 생성

### H. Award

- Source Award/BaseAttributes Ranking만으로 결정 불가
- 실제 World Statistics 입력 필수

### I. World Player Name

- 같은 World의 Person→DisplayName 고정
- 동일 Person 모든 시즌 동일 이름
- 다른 Person 이름 중복 0건

### J. Name Blacklist

- Reference DB 실제 선수명과 Generated DisplayName exact match 0건

### K. Name Quality

- null/empty, 숫자, 제어문자, 과도한 길이, 중복, 금칙어 0건
- 생성 이름 200~500개 샘플 출력

### L. Franchise Identity

- 같은 Franchise의 다른 OriginYear 이름 동일
- 다른 Franchise 이름 중복 0건
- Reference 실제 구단명 exact match 0건

### M. Identity가 Simulation에 영향 없음

- DisplayName만 바꾼 동일 입력의 Match Event/BoxScore/Season Statistics 동일

### N. Save / Load

- Player/Franchise DisplayName, Statistics, Standings, Awards 동일
- Historical/Identity/Award 재실행 0회

## 4. 통계 검증

Synthetic Player 분포 유사성이나 Synthetic Similarity Reject는 완료 기준이 아니다.

### Rating 변환

시대·역할·Reliability 보정 후 Source 통계와 Baked Rating 사이 의도된 순위 상관을 측정한다. 단일
정확 일치보다 방향, monotonicity, 포지션/역할별 왜곡과 극단치 수축을 본다.

### Historical Simulation

다수 World Seed에서 개인 기록 분포, 팀 승률 분포, AVG/OBP/SLG, HR, BB%, K%, ERA, WHIP,
득점·실점이 비정상적으로 붕괴하지 않는지 검증한다. 이는 다른 선수 기록을 섞는 근거가 아니라
Rating→Simulation 밸런스 검증이다.

밸런스 계수를 바꿨다면 실행 World/경기 수, Seed 범위, 평균·분산·분위수, 목표 범위, 실패 항목을
리포트한다. 몇 경기 육안 확인만으로 완료하지 않는다.

## 5. Legacy 제거 기준

대규모 회귀 때문에 타입을 즉시 삭제할 수 없으면 Migration Adapter를 둘 수 있다. 단 다음을
강제한다.

- Adapter는 Legacy/Debug/Validation namespace, 설정 또는 명시적 entry point로 격리
- Production New Game 호출 그래프에서 도달 불가
- Source 기록·Award·이름을 정식 World 결과로 되돌리지 않음
- 새 Save는 Canonical/Identity/Simulated History 구조만 기록

새 1:1 Pipeline과 기존 Synthetic Pipeline이 둘 다 실제 게임에서 사용되면 실패다.

## 8. 절대 완료 조건

아래 하나라도 참이면 완료로 선언하지 않는다.

- 일반 Player가 여러 실제 선수 기록의 혼합으로 생성됨
- 능력치별 Source Player가 다름
- 여러 실제 구단을 섞어 일반 Franchise를 만듦
- World Seed에 따라 BaseAttributes/Cost가 바뀜
- Source 성적·Standings·Award를 정식 World 결과로 복사함
- BaseAttributes만으로 All-Star/GG/MVP를 정함
- Player DisplayName이 Canonical Content에 World-independent하게 고정됨
- 프로젝트 보유 실제 선수·구단명을 Alias로 재사용함
- 같은 World의 이름 중복 또는 동일 Person/Franchise 다년도 이름 불일치
- Save/Load에서 이름 또는 History를 재생성함
- 코드와 문서 중 한쪽만 새 Source of Truth로 전환됨

## 9. 최종 정의

Canonical Player는 Source Player 데이터 1:1 기반의 고정 게임 데이터다. World Player Identity는 그
Canonical Person에 World별로 부여하고 Save한 가상 이름이다. Virtual Statistics/History는 고정된
Canonical 선수와 Source 1:1 구단을 실제 경기 Simulation에 투입해 얻은 결과다. 이 세 개념을 다시
하나의 Synthetic Player 데이터로 합치지 않는다.

## 10. 현재 구현·검증 상태

2026-09-05 기준 Canonical Bake, World Identity, Detailed Historical Simulation, Statistics/Standings,
Award, WorldCardCatalog, 특수 합성팀, Save DTO 연결과 README·01~08 개정은 구현됐다.

검증 Hash는 Seed 문자열 자체를 결과 변화의 근거로 삼지 않는다. `HistoricalWorldResultHasher`가
Player Statistics, Team Statistics, Standings/Postseason, Awards, Identity와 전체 History를 각각
Seed 제외 Fingerprint로 계산한다. 장기 검증은 Simulation Seed와 Identity Seed를 분리해 다음 네
실행을 비교한다.

```text
동일 Simulation Seed + 동일 Identity Seed
동일 Simulation Seed + 동일 Identity Seed 반복
다른 Simulation Seed + 다른 Identity Seed
동일 Simulation Seed + 다른 Identity Seed
```

동일 Seed 반복은 모든 Fingerprint가 같아야 한다. 다른 Simulation Seed에서는 Statistics, Standings,
Postseason, Awards가 실제로 달라져야 한다. Identity Seed만 바꾼 실행은 Identity만 달라지고 History,
Statistics, Standings, Awards는 같아야 한다. 모든 실행은 `WorldHistorySaveMapper` 왕복 뒤 History
Fingerprint가 유지돼야 한다.

현재 자동 검증 결과:

- Python Importer/Bake: 56 passed, 0 failed
- 순수 C# Headless Core/Simulation/Game: 538 passed, 0 failed, Explicit 장기 Fixture 1 skipped
- 전체 Headless 경과 시간: 277.5초
- Detailed 2024 Historical smoke: 3회, 실행당 409경기
- 동일 Seed Result Hash: `564e68ae44d943ff`
- Identity-only 변경 시 History 불변 및 Save DTO round-trip 통과

`HistoricalWorldFullValidationTests.FullRuntimePayload_1982To2025_CompletesAndReportsMetrics`는 실제
schema 5 Runtime Archive 44시즌을 위 네 조합으로 실행하고 TeamSeason 총수, 44개 Postseason,
결정론, Seed별 결과 변화, Identity 독립성, Save round-trip을 검사하도록 구현했다. 현재 환경에서는
Unity Licensing Client가 `com.unity.editor.headless` 권한을 획득하지 못해 Test Runner 진입 전
중단됐으므로 이 44시즌 4회 실행은 아직 통과로 기록하지 않는다.

동일한 이유로 `RuntimeHistoricalContentProviderTests`, `HistoricalDatabaseBrowserTests`의 Unity 실실행도
남아 있다. Historical Database Browser는 worker thread에서 `JsonUtility`를 호출하던 crash 경로를
main thread load로 교체했고 취소 시 UI 상태도 복구하지만, 라이선스가 정상인 Unity Editor에서 실제
Archive load를 다시 확인해야 한다.

원본 데이터에는 신뢰 가능한 Foreign 분류가 없어 현재 Runtime Person은 모두 Domestic이다. 또한
20개 TeamSeason의 투수 quota 부족 54석은 보고된 `ReplacementGenerated` deterministic aggregate
fallback으로 남는다. 이는 숨은 타 구단 Mixing이 아니며, 원본 데이터가 보강되기 전까지 별도 데이터
품질 제약으로 추적한다.
