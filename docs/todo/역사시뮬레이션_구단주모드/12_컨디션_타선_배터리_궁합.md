# 12. 컨디션과 타선·배터리 궁합

> 상태: 기존 Condition 계약의 정본 확장안 / Codex 구현 기준

## 0. 목적

현재 문서는 이미 `ConditionBonus`를 EffectiveRating에 포함하며, 비주포지션 야수/비본래 투수 역할에 Condition 하락을 적용하고, 감독 AI의 교체 판단도 Condition을 소비한다.

따라서 이 문서는 **새로운 평행 컨디션 시스템을 만드는 문서가 아니다.**

목표는:

1. 현재 코드의 Condition Source of Truth를 확인하고 하나로 고정한다.
2. 플레이어가 읽을 수 있는 단계형 Condition UI를 제공한다.
3. 타선/배터리 궁합을 Condition에 연결하되 별도 능력치 버프 레이어를 만들지 않는다.
4. AI와 Player Preview가 같은 Resolver를 사용하게 한다.
5. 경기/휴식/연투/비주포지션/회복 시설/스태프 효과를 하나의 Condition 흐름으로 정리한다.

## 1. 절대 원칙

### 1.1 기존 Condition 재사용

Codex Stage 0에서 반드시 조사한다.

- Condition 현재 타입/범위
- 저장 위치
- 경기 전/후 갱신 시점
- Condition → EffectiveRating 변환
- 투수 연투/피로와의 관계
- 부상과의 관계
- 비주포지션 Penalty가 Condition을 실제로 mutate하는지 Match Modifier인지

기존 타입이 있으면 새 `PlayerConditionState`를 중복 생성하지 않는다.

### 1.2 Chemistry는 Stat Bonus가 아니다

금지:

```text
LineupChemistry → Contact +3
BatteryChemistry → Control +4
```

허용:

```text
LineupChemistry → MatchConditionLevelDelta
BatteryChemistry → MatchConditionLevelDelta
```

그 결과 기존 `ConditionBonus` 경로가 능력치 판정에 반영한다.

### 1.3 Base Condition과 Match Effective Condition 분리

궁합 때문에 영구 Condition이 매 경기 누적 상승/하락하지 않도록 한다.

```text
StoredBaseCondition
 + AssignmentConditionModifier
 + LineupChemistryModifier
 + BatteryChemistryModifier
 + TemporaryMatchModifiers
 = EffectiveMatchCondition
```

현재 코드가 다른 구조를 사용한다면 이 의미를 기존 API에 맞게 표현한다.

## 2. Condition Presentation Level

현재 Condition Source가 연속 수치라면 UI에 10단계로 매핑한다.

```text
ConditionPresentationLevel = 1..10
```

- 실제 Source of Truth를 10단계 enum으로 강제 변환하지 않는다.
- UI Level 경계는 `ConditionPresentationTable`로 데이터화한다.
- 기존 수치 범위가 0~100이면 10개 구간이 자연스럽지만, Codex는 코드 감사 결과를 기준으로 정확한 매핑을 확정한다.

UI에서 각 단계에 짧은 상태명을 부여할 수 있다.

예:

```text
최악 / 매우 나쁨 / 나쁨 / 다소 나쁨 / 보통
다소 좋음 / 좋음 / 매우 좋음 / 최고 / 절정
```

표현명은 UX 작업에서 조정 가능하며 Simulation 계약이 아니다.

## 3. Condition 변화 원인

기존 프로젝트에서 이미 존재하는 원인을 우선한다.

정식 입력 카테고리:

```text
GameWorkload
Rest
RecentUsage
StartingOrReliefWorkload
PositionAssignmentPenalty
PitcherRoleAssignmentPenalty
InjuryOrRecoveryState (기존 시스템이 있을 때)
RecoveryFacilityModifier
ConditioningCoachModifier
OtherExistingConditionRules
```

새 문서가 부상 시스템 자체를 새로 설계하지 않는다.

## 4. 타선 궁합 — Lineup Chemistry

### 4.1 목표

타순을 단순 능력치 내림차순으로만 구성하지 않고, **선수 조합과 지속적인 함께 뛰기**에 작은 선택 가치를 준다.

단 능력치 격차를 뒤집는 핵심 버프가 되어서는 안 된다.

### 4.2 입력

```text
LineupChemistryResolver
input:
  TeamSeasonKey
  StartingLineup[9]
  BattingOrder[9]
  PlayerPersonId
  Bats
  PlayerRole/Position
  BaseAttributes (읽기 전용)
  TeamChemistryFamiliarityState
```

### 4.3 설명 가능한 조합 점수

초기 구현은 두 축으로 제한한다.

```text
A. Familiarity
   함께 선발 출장한 누적 경험

B. StyleComplement
   인접 타순 선수의 공격 스타일 보완
```

공격 스타일은 별도 신규 영구 능력치를 만들기보다 기존 BaseAttributes로 파생한다.

예:

```text
TableSetterLike  = Contact + Speed 중심
PowerLike        = Power 중심
Balanced         = 특정 축 편중 없음
```

정확한 파생 기준은 Balance Table.

### 4.4 Graph

타순 1~9의 인접 Edge를 계산한다.

```text
1 ↔ 2 ↔ 3 ↔ ... ↔ 9
```

필요하면 9↔1 연결은 하지 않는다. 실제 타순 순환을 반영하고 싶다면 별도 실험 후 결정한다.

각 선수의 MatchCondition Modifier는 자기 양옆 Edge를 기준으로 제한적으로 계산한다.

### 4.5 효과 범위

추천 기본 계약:

```text
매우 좋은 타선 궁합 → Condition Presentation +1단계 상당
중립               → 0
매우 나쁜 궁합      → -1단계 상당
```

정확한 내부 수치 Delta는 현재 Condition 범위에 맞춰 `ChemistryConditionDeltaTable`로 데이터화한다.

+2/-2 이상의 큰 단계 변화는 초기 구현에서 금지한다.

## 5. 배터리 궁합 — Battery Chemistry

### 5.1 대상

```text
현재 투수 ↔ 포수
```

선발뿐 아니라 구원 투수가 올라오면 해당 Pitcher-Catcher Pair를 다시 계산한다.

### 5.2 입력

```text
BatteryChemistryResolver
input:
  TeamSeasonKey
  PitcherPersonId
  CatcherPersonId
  PitcherAttributes
  CatcherAttributes
  SharedBatteryStartOrInningHistory
```

### 5.3 점수

초기 구현:

```text
BatteryScore
 = FamiliarityComponent
 + CatcherHandlingComponent
 + StabilityComponent
```

`CatcherHandlingComponent`는 기존 Defense/Mental 등 프로젝트에 이미 존재하는 능력치만 사용한다.

새 `CatcherHandling` Stat을 추가하지 않는다.

### 5.4 효과

배터리 궁합 역시 Condition만 조정한다.

추천 기본 계약:

```text
좋음  → 투수 Match Condition +1단계 상당
보통  → 0
나쁨  → 투수 Match Condition -1단계 상당
```

포수에게도 같은 효과를 줄지는 초기 구현에서 제외한다. 효과 폭증을 막기 위해 우선 **투수만** 적용하고 장기 시뮬레이션 후 확대 여부를 판단한다.

## 6. Familiarity State

같이 출전할수록 궁합이 무조건 최고가 되는 구조를 피하기 위해 Familiarity는 전체 점수의 일부로만 사용한다.

```text
TeamChemistryFamiliarityState
{
    TeamSeasonKey
    LineupPairFamiliarity[]
    BatteryPairFamiliarity[]
}
```

Key는 `PlayerPersonId` Pair를 Stable Sort해 사용한다.

- Edition/시즌 카드가 바뀌어도 같은 Person이면 팀 내 익숙함이 이어질 수 있다.
- 다른 TeamSeason의 Chemistry와 공유하지 않는다.
- 팀 이적 시 새 팀의 Familiarity는 별도다.

Save 크기를 막기 위해:

- 실제 함께 출전한 Pair만 저장
- Cap 도달 후 더 이상 증가시키지 않음
- 오래된 0 또는 최소 값 Pair 정리 가능

정확한 정책은 Persistence Agent가 프로파일링 후 확정한다.

## 7. AI 라인업/교체 연결

AI는 Chemistry를 절대 우선하지 않는다.

개념 평가:

```text
ExpectedLineupValue
 = PlayerAbilityValue
 + ConditionValue
 + MatchupValue
 + TeamColorValue
 + ChemistryValue
 - PositionPenalty
```

`ChemistryValue`에는 상한을 둔다.

목표:

- 능력치가 훨씬 좋은 선수를 궁합 때문에 벤치에 고정하지 않음.
- 비슷한 후보 사이에서는 궁합/Condition이 실제 tie-breaker 역할.

벤치 교체 후 수비 포지션과 Chemistry를 재평가할 수 있지만, 경기 중 매 타석마다 비싼 전체 Graph를 재계산하지 않도록 캐시/증분 계산을 검토한다.

---

## 8. 경기 중 배터리 변경

투수 교체 또는 포수 교체가 발생하면 Battery Chemistry를 재계산한다.

```text
Pitcher Change
→ new Pitcher-Catcher Battery Modifier

Catcher Change
→ current Pitcher-new Catcher Modifier
```

이미 진행된 타석 결과를 소급 변경하지 않는다.

## 9. 09/11 시스템 연결

### RecoveryCenter

Stored Base Condition의 회복 Resolver에 Modifier.

### ConditioningCoach

같은 회복 Resolver에 Modifier.

합성 순서와 Cap은 하나의 `ConditionRecoveryContext`에서 처리한다.

```text
BaseRecovery
× FacilityModifier
× StaffModifier
→ Clamp
```

시설/스태프가 각각 별도 Update를 호출해 두 번 회복시키지 않는다.

## 10. UI/UX

### 10.1 선수 카드/미니 카드

기존 작은 선수 카드에 Condition Level을 읽기 쉽게 표시한다.

- 10단계 아이콘/게이지
- Hover/상세에서 실제 원인 표시

```text
기본 컨디션: 좋음
비주포지션: -1
타선 궁합: +1
예상 경기 컨디션: 좋음
```

내부 수치 전체를 항상 노출할 필요는 없다.

### 10.2 라인업 화면

타순 사이에 Chemistry Edge를 표시한다.

```text
1 [선수] ─ 좋음 ─ 2 [선수] ─ 보통 ─ 3 [선수]
```

색상만으로 구분하지 않고 아이콘/텍스트/선 형태도 함께 사용해 접근성을 확보한다.

### 10.3 배터리

선발/현재 투수와 포수 사이에:

```text
배터리 궁합: 좋음
함께 소화한 이닝: 충분
예상 영향: 컨디션 +1단계
```

정도로 표시한다.

### 10.4 ImageGen

기능 UI는 UI Toolkit으로 구현한다.

ImageGen은 다음에만 사용:

- 컨디션 10단계용 비기능성 심볼/배지 컨셉
- 라인업/배터리 그래프 주변 장식
- 기존 UI와 어울리는 야구 매니지먼트 풍 패널 아트

수치/텍스트/Graph 자체를 이미지로 굽지 않는다.

## 11. Save / Determinism

Save 대상:

- 기존 Condition State
- 필요한 Familiarity Pair State

파생 대상:

- Lineup Chemistry 현재 점수
- Battery Chemistry 현재 점수
- EffectiveMatchCondition

같은 Save + 같은 Lineup + 같은 상태면 같은 Chemistry 결과가 나와야 한다.

궁합 계산에 매 경기 랜덤을 넣지 않는다.

## 12. 구현 단계

### Stage 0 — Condition Audit (최우선, 다른 구현보다 먼저)

Agent A:
- Condition 관련 타입/범위/Save/업데이트 경로 전수 조사.

Agent B:
- EffectiveRating의 ConditionBonus 연결 조사.

Agent C:
- OffPosition/PitcherRole/피로/연투/부상과 Condition 연결 조사.

산출물:

```text
Condition Source of Truth Map
Condition Update Lifecycle
Condition → Match Rating Contract
```

Gate:
- 중복 Condition 타입 생성 금지.

### Stage 1 — Presentation Mapping

- `ConditionPresentationTable`
- Level 1..10 mapping
- UI용 label/icon key

Simulation 상태를 변조하지 않는다.

### Stage 2 — Familiarity State

Agent State:
- Pair key
- Shared starts/innings update
- Save/Load
- Cap/Prune

Agent Test:
- TeamSeason 격리
- PersonId continuity

### Stage 3 — Chemistry Resolver

병렬:

Agent Lineup:
- Hitter archetype derivation
- Adjacent graph
- Familiarity + StyleComplement

Agent Battery:
- Pitcher/Catcher
- Familiarity + existing attributes

Agent Test:
- Delta 상한
- 결정론

### Stage 4 — Match Condition Integration

- Base Condition + Assignment + Chemistry를 한 Context에서 합성.
- EffectiveRating이 기존 ConditionBonus를 한 번만 적용.
- 중복 적용 테스트.

### Stage 5 — AI Integration

- lineup selection tie-break
- catcher/pitcher choice
- bench substitution recompute

Chemistry Weight를 데이터화하고 상한 검증.

### Stage 6 — Facility/Staff Integration

- RecoveryCenter
- ConditioningCoach

둘 다 동일 Recovery Resolver Modifier 입력으로 통합.

### Stage 7 — UI

- mini card condition
- lineup graph
- battery panel
- tooltip/explanation
- 필요 시 ImageGen

### Stage 8 — Statistical Validation

수천~수만 경기:

- Condition 분포
- Chemistry 평균 Delta
- 강한/약한 Chemistry의 승률 영향
- lineup 다양성
- AI가 고능력 선수를 지나치게 벤치에 두지 않는지
- Recovery 시설/코치가 항상 MAX Condition을 만들지 않는지

### Stage 9 — Final Gate

```text
라인업 편성
→ Condition/Chemistry Preview
→ 경기 시작
→ EffectiveMatchCondition 적용
→ 투수/포수 교체 시 Battery 재계산
→ 경기 종료 Familiarity/Condition 갱신
→ Recovery
→ Save/Load
```

E2E 통과.

## 14. 완료 기준

- Condition Source of Truth가 하나다.
- EffectiveRating에서 ConditionBonus가 한 번만 적용된다.
- 10단계 UI는 기존 Condition의 표현층이다.
- 타선/배터리 궁합은 BaseStat을 수정하지 않는다.
- Chemistry는 Match Condition에 제한된 작은 효과만 준다.
- Familiarity는 TeamSeason별로 분리된다.
- PlayerPersonId 기준 연속성이 유지된다.
- 투수/포수 교체 시 Battery Modifier가 즉시 갱신된다.
- AI가 Chemistry를 고려하지만 능력치 판단을 압도하지 않는다.
- RecoveryCenter/ConditioningCoach가 동일 Recovery Context를 통해 한 번만 적용된다.
- Save/Load 및 동일 상태 결정론이 보장된다.
- 장기 Simulation에서 Condition/Chemistry 승률 영향이 과도하지 않다.

## 15. 2026-09-05 구현·검증 상태

### Condition 원본 / Simulation

- Audit 결과 선수 커리어의 두 Condition 복제본을 구단주 모드로 재사용하지 않고,
  `TeamSeasonPlayerStatusState`를 구단주 모드의 유일한 저장 원본으로 확정했다. 연속 0~100 값은
  유지하고 1~10단계는 데이터화한 `ConditionPresentationTable`의 표현 결과로만 만든다.
- 표시 경계, Familiarity 성장/Cap, Chemistry 가중치·상한, 주간 회복과 경기 소모는
  `OwnerExpansionBalance.json`의 `conditionChemistry` 표에서 저작하며 코드 기본값을 Production
  fallback으로 사용하지 않는다.
- `EffectiveMatchCondition`은 Base, Assignment, Lineup, Battery, Temporary modifier breakdown을
  보존한다. Chemistry는 기존 능력치에서 Style/Handling을 파생하고 BaseStat을 수정하지 않으며 최대
  ±1 Condition 단계로 제한한다.
- `DetailedMatchEngine`은 경기 전 Snapshot의 Condition을 능력 변환 경로에 한 번만 적용한다.
  비주포지션 Assignment와 Lineup/Battery는 같은 `EffectiveMatchCondition`에서 합성되어 Rating에
  중복 적용되지 않는다. Battery는 현재 투수·포수 pair를 조회하므로 교체 시 재계산되고 누적되지
  않는다.

### Runtime / Persistence / UI

- 경기 후 `BatteryUsageReport`가 기록한 실제 투수-포수 pair의 수비 아웃만 TeamSeason별 stable
  sorted Person pair Familiarity에 적립한다. 실제 참가자의 Condition/workload도 함께 갱신한다.
  주간 회복은 RecoveryCenter와 ConditioningCoach를 하나의
  `ConditionRecoveryContext`에서 합성해 한 번 실행한다.
- Save schema 4는 선수 상태와 Familiarity 원본만 저장하고 Effective Condition/Chemistry 점수는
  저장하지 않는다.
- `UI_Scene_OwnerConditionChemistry`와 경기 준비 화면은 Base, 배치, 타선, 배터리, 예상 Match
  Condition을 공용 uGUI Shell에서 표시한다. 화면의 중심 표기는 연속 0~100 원값이 아니라 데이터화된
  1~10단계와 한글 상태이며, 기존 에셋으로 충분해 ImageGen은 사용하지 않았다.

### Test / Balance
