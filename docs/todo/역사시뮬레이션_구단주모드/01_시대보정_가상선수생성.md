# 01. Source Player 정규화와 Canonical Bake

## 0. 목적

정규화된 실제 선수 데이터를 Source와 1:1인 Runtime-safe Canonical Content로 변환한다. 이 단계는
여러 선수의 기록을 섞어 새로운 선수를 만드는 Synthetic Generation이 아니다.

```text
SourcePlayerPerson
  └─ SourcePlayerSeason
          ↓ 시대·포지션·역할 정규화
          ↓ Reliability Shrinkage
          ↓ 결정론적 Rating 변환
PlayerPersonDefinition
  └─ PlayerSeasonDefinition
```

한 Source PlayerSeason의 능력치 직접 입력은 그 시즌 자신의 기록뿐이다. 같은 연도·포지션·역할
집단의 평균, 표준편차, 백분위, Z-Score, 리그 환경은 Source 값을 평가하는 비교 모집단으로만 쓴다.

## 1. Offline과 Runtime 경계

### 1.1 Offline / Editor

Offline Pipeline이 담당한다.

- 원본 Snapshot 검증과 Normalized JSON 생성
- Source Person/Season Stable Key 생성 및 1:1 provenance 검증
- Era/Position/Role Normalization과 Reliability Shrinkage
- `BaseAttributes`, `Cost`, `TrainingCeiling` 결정
- Position, PitcherRole, RegistrationType, Origin 결정
- Source TeamSeason 연결 및 Canonical Archive Bake
- 실제 선수명·구단명 blacklist와 충분한 가상 이름 후보 데이터 생성
- Manifest, Content Hash, Validation Report 생성

### 1.2 Runtime

Runtime은 Baked 값을 소비한다. World Seed로 Ability, Cost, TrainingCeiling 또는 Origin을 다시 만들지
않는다. 실제 이름도 Canonical Definition에서 읽지 않는다.

```text
Canonical Content
→ WorldIdentityRegistry
→ Historical Match Simulation
→ Statistics / Standings / Awards
```

## 2. Stable Person / Season 1:1 Mapping

개념적 provenance는 다음 관계를 보존한다.

```text
SourcePlayerKey
→ Stable PlayerPersonId

SourcePlayerKey + SourceSeasonYear
→ Stable PlayerSeasonId
```

- 같은 Source Person의 2009~2012 시즌은 같은 `PlayerPersonId` 아래 연결한다.
- 다른 Source Person은 반드시 다른 `PlayerPersonId`를 가진다.
- `PlayerSeasonId`는 한 Source PlayerSeason에만 대응한다.
- 서로 다른 Person의 시즌을 이어 CareerSpan을 만들지 않는다.
- 원본 ID는 Editor provenance에 보존할 수 있지만 Runtime에는 Runtime-safe Stable ID만 배포한다.

`CareerSpan`은 연결된 동일 Source Person 시즌의 최소·최대 연도로 계산한다. 누락 시즌을 다른 선수
기록으로 메우거나 연속인 것처럼 위장하지 않는다.

## 3. Source 기록에서 BaseAttributes로

기존 Rating Converter의 구체식은 유지하되 입력 경계를 강제한다.

```text
Source Season Statistics
→ Era Normalization
→ Position / Role Normalization
→ Reliability Shrinkage
→ Deterministic Rating Conversion
→ BaseAttributes
```

타자는 AVG/OBP/SLG, HR/PA, BB%, K%, SB, 출장량, Position 및 신뢰 가능한 수비 기록을 사용한다.
투수는 IP, GS, ERA 계열, K/9, BB/9, HR/9, 출장 형태와 PitcherRole을 사용한다.

시대·역할 보정 모집단은 다음에만 영향을 준다.

- 해당 Source 수치가 같은 환경에서 어느 수준인지
- 작은 표본을 어느 기준값 쪽으로 얼마나 축소할지
- 서로 다른 연도의 Rating 스케일을 어떻게 맞출지

다른 Player B/C의 개별 기록을 Player A의 Contact/Power/Speed/Stuff/Control로 직접 복사하거나
벡터로 섞지 않는다. covariance sampling, 3~7 Reference mixing, 능력치별 Source 교체, Similarity
Reject용 Synthetic Player 재생성은 Production Player Bake에서 금지한다.

## 4. Reliability Shrinkage

작은 표본을 그대로 극단 Rating으로 바꾸지 않기 위해 같은 모집단의 안정적인 baseline으로 축소할 수
있다. Shrinkage는 Source 자신의 관측치를 얼마나 신뢰할지 결정하는 과정이며 다른 선수의 개별 시즌을
합성하는 과정이 아니다.

개념식:

```text
Reliability = Sample / (Sample + StabilizationPoint)
AdjustedRate = Reliability × SourceRate + (1 - Reliability) × PopulationMean
```

`StabilizationPoint`, Rating slope/cap, Position/Role baseline은 `BalanceTable` 또는 Versioned Offline
Config에서 관리한다. 변경 시 Rating 상관 및 Historical Simulation 분포를 다시 검증한다.

## 5. 고정 Baked 값

각 `PlayerSeasonDefinition`에는 다음 Canonical 값이 확정된다.

```text
PlayerPersonId
PlayerSeasonId
BaseAttributes
Position
PitcherRole
RegistrationType
OriginYear
OriginFranchiseId
OriginTeamSeasonKey
Cost
TrainingCeiling
```

같은 Source Data Version, Normalization Version, Balance Version은 항상 같은 결과를 만든다. World
Seed, 표시 이름, Historical 성적, Award, 현재 시즌 성적은 이 값을 바꾸지 않는다. 특수 Edition도
같은 PlayerSeason의 Cost와 Origin을 공유한다.

Cost는 Source-backed Baked Rating 모집단의 결정론적 percentile 등 현행 합리적 방식을 사용할 수
있다. World MVP 수상이나 Simulation 성적을 Cost에 환류시키지 않는다.

## 6. Canonical Person에는 표시 이름이 없다

`PlayerPersonDefinition`은 Canonical 정체성과 야구 데이터만 가진다.

```text
PlayerPersonDefinition
{
    PlayerPersonId
    BirthYear
    Bats
    Throws
    PrimaryPosition
    RegistrationType
    CareerSpan
}
```

World-independent `FictionalName`을 Baked Player에 고정하지 않는다. 실제 Source 이름은 Editor 검수와
blacklist 생성에만 쓰고 Runtime Archive에는 노출하지 않는다.

새 World의 표시 이름은 03절의 `WorldPlayerIdentity`가 소유한다. Name Mapping Key는
`PlayerSeasonId`가 아니라 `PlayerPersonId`이므로 동일 Person의 모든 시즌은 한 World에서 같은 이름을
사용한다.

## 7. Historical Statistics는 Simulation 결과다

Source 기록은 Ability Bake의 원본이지 게임 기록실의 결과가 아니다.

```text
Baked PlayerSeason
→ Detailed Match Simulation
→ PlateAppearance / Pitching / Fielding / Baserunning
→ Game Statistics
→ Season Statistics
```

Source에서 30 HR였던 선수가 World A에서는 24 HR, World B에서는 33 HR을 기록할 수 있다. Source
30 HR을 목표로 Runtime 결과를 강제하거나 별도의 `Ability → 예상 성적` 합성기로 과거 기록을 만들지
않는다. Historical World와 실제 플레이 시즌은 같은 야구 판정 모델을 사용하고, Historical 실행은
표현/UI만 생략한다.

## 8. Award와 OriginalHistory

정식 경로는 World Statistics를 만든 뒤 수상을 결정한다.

```text
Historical Match Simulation
→ Season Statistics
→ AllStarSelectionResolver / GoldenGloveAwardResolver / RegularSeasonMvpResolver
→ All-Star Game / Postseason
→ AllStarGameMvpResolver / PostseasonMvpResolver
→ WorldAwardRecord
```

Source Award는 정식 World Award로 복사하지 않는다. BaseAttributes 순위만으로 All-Star/GG/MVP를
뽑지도 않는다.

`OriginalHistory` enum이나 Reader가 회귀 비교를 위해 남아 있다면 Legacy/Debug/Validation 전용으로
격리한다. Production New Game UI와 설정에서는 노출하지 않고, 정식 Runtime Source of Truth로
사용하지 않는다.

## 9. World Identity 이름 데이터

Offline Pipeline은 실제 Source 선수 이름 전체를 blacklist로 만들고, 충분한 이름 공간의 후보를
Runtime-safe 콘텐츠로 제공한다.

- Domestic: 성씨 빈도와 자연스러운 한국 이름 음절/세대 경향을 데이터화한다.
- Foreign: RegistrationType이 Foreign일 때만 현재 데이터가 표현하는 범위 안에서 별도 후보를 쓴다.
- 생성 이름이 Source 이름과 exact match하면 Reject한다.
- 작은 50~100개 목록 순환이나 닉네임식 조합을 사용하지 않는다.
- null/empty, 숫자, 제어문자, 과도한 길이, 금칙어를 거부한다.

이 단계는 후보 공간과 blacklist를 준비할 뿐 Person별 최종 이름은 World 생성 시 결정한다.

## 10. 필수 자동 검증

### Mapping / Determinism

- Source PlayerSeason 수와 Canonical PlayerSeason 1:1 대응
- Runtime PlayerSeason마다 정확히 하나의 Source provenance
- 동일 Source Person 다년도 `PlayerPersonId` 일치, 다른 Person ID 불일치
- 같은 Source+Version의 BaseAttributes/Cost/TrainingCeiling 완전 일치
- World Seed를 바꿔도 모든 Canonical 값 동일
- 다른 선수 개별 기록 Mixing, SourceSeason 복제, 타연도 위장 0건

### Rating 변환

- HR Rate↔Power, K%↔Contact, SB↔Speed
- K/9↔Stuff, BB/9↔Control, IP/G↔Stamina
- 시대·역할·Reliability 보정 뒤 방향성과 합리적인 상관 확인

### World 결과

- 같은 Seed의 Event/Statistics/Standings/Award hash 일치
- 다른 Seed에서는 고정 Ability를 유지하면서 시즌 기록이 달라질 수 있음
- 다수 Seed의 AVG/OBP/SLG, HR, BB/K, ERA, WHIP, R/G 분포가 목표 범위
- Award Resolver가 `SeasonStatistics` 없이 실행되지 않음

### Identity

- Source 선수명 exact match 0건과 World 내부 중복 0건
- 동일 Person 다년도 이름 일치
- 이름 샘플 200~500개를 Validation Report로 출력해 사람이 자연스러움을 검수
- DisplayName만 바꾼 두 입력의 Match 결과 완전 일치

## 11. Bake Gate

다음 중 하나라도 발생하면 Runtime Archive를 배포하지 않는다.

- 1:N 또는 N:1 Person/Season provenance
- 선수 A의 Ability에 선수 B/C의 개별 기록 혼입
- Baked Person별 World-independent 표시 이름 저장
- 실제 Source 이름의 Runtime 노출 또는 generated exact match
- World Seed에 따른 BaseAttributes/Cost 변화
- Source 기록·Award를 정식 World 결과로 복사하는 Production 경로

과거 3~7 Reference 혼합, covariance Replacement, 고정 `FictionalName` 기반 Archive의 Hash/Count는
새 정본 계약의 완료 근거로 재사용하지 않는다.
