# 16. 구단주 모드 새 게임, 스타터 로스터와 첫 배정 튜토리얼

## 0. 문서 목적과 상태

이 문서는 구단주 모드에서 `새 구단 시작`을 누른 뒤 구단 선택, 메인 선수 카드 10장 선택,
프런트 매니저 선택, 구단주 닉네임 입력, 저가치 선수 자동 충원, 25인 로스터 확정, 선택한 프런트
매니저의 첫 선수 배정 가이드까지 이어지는 Production 플로우를 정의한다.

현재 Production은 `OwnerModeManager.StartNewGame()`이 설정된 연도의 첫 유효 정규구단과 그 구단의
Canonical `Core25`를 즉시 선택한다. 따라서 이 문서의 전체 기능은 **미구현**이다. 기존 World,
`WorldCardCatalog`, `ActiveRosterValidator`, `ManagerModeRuntimeState`, `FrontManagerGuide`를 재사용하되,
선택 화면만 만든 뒤 기존 즉시 생성 경로를 남겨 두지 않는다.

이 기능의 게임적 목표는 “처음부터 강한 선수 열 명을 받는다”가 아니다.

> 제한된 Cost 안에서 구단의 어느 시대와 어떤 포지션을 중심축으로 삼을지 선택하고, 부족한 자리를
> 저가치 선수로 메운 뒤 첫 라인업 배정에서 선택의 결과를 이해하게 한다.

완료 시 플레이어는 왜 자신의 초기 전력이 그렇게 구성됐는지, 어느 포지션이 강하고 약한지,
다음 스카우트에서 무엇을 보강해야 하는지를 설명할 수 있어야 한다.

---

## 대상 모드

- 대상: **구단주 모드 전용**
- 선수 커리어 모드의 캐릭터 생성, 계약, 감독 AI 소유 라인업에는 적용하지 않는다.
- Canonical Content, World Identity, Match Simulation은 공용 계약을 그대로 사용한다.
- 구단주 모드의 카드 소유 상태, 초기 로스터, 닉네임, Onboarding 진행도는 선수 커리어 Save와
  공유하지 않는다.

## 1. 최종 사용자 플로우

```text
타이틀 — 구단주 모드 / 새 구단 시작
  ↓
World 준비 Loading
  ↓
1. 구단 선택
  ↓
2. 메인 선수 카드 10장 선택
  ↓
3. 프런트 매니저 선택
  ↓
4. 구단주 닉네임 입력
  ↓
5. 창단 명단 확인
   - 선택한 메인 카드 10장
   - 결정론적으로 충원한 저가치 카드 15장
   - 저가치 카드 전체 목록 확인 및 최대 30회 리롤
   - 프런트 매니저 추천 배정
  ↓
6. 최종 확인
   - 이 시점에만 Runtime과 Save를 생성
  ↓
Owner Home 첫 진입
  ↓
7. 선택한 프런트 매니저의 선수 배정 가이드
  ↓
정상 구단주 플레이
```

순서는 `구단 → 카드 → 프런트 매니저 → 닉네임 → 명단 확인`으로 고정한다. 구단을 먼저 골라야 해당
Franchise의 카드 후보를 만들 수 있고, 프런트 매니저와 닉네임은 전력 선택에 영향을 주지 않는
개인화 단계이므로 카드 선택 뒤에 연달아 둔다.

이전 단계로 돌아갈 수 있다. 다만 다음 규칙을 지킨다.

- 닉네임 수정이나 화면 재진입만으로 자동 충원 결과가 다시 굴러가지 않는다.
- 구단을 바꾸면 카드 선택과 충원 Preview를 비운다.
- 첫 충원 목록은 무료로 생성하고, 이후 새 충원 목록 생성은 사유와 관계없이 리롤 횟수 한 번을
  소비한다. 카드 선택이나 구단을 바꾼 뒤 새 목록을 만드는 경우도 포함한다.
- 명시적인 리롤 없이 같은 Draft 단계로 돌아오면 마지막으로 확인한 목록을 그대로 복원한다.
- 최종 확인 전에는 `ManagerHistoricalRuntimeState`와 정식 구단주 Save를 만들지 않는다. 리롤 제한을
  보존하는 Draft Checkpoint만 별도 저장한다.
- 최종 확인은 두 번 실행돼도 Save와 지급 카드가 중복 생성되지 않는 단일 Commit이어야 한다.

## 2. 단계별 UX 명세

### 2.1 World 준비 Loading

구단명과 선수명은 `WorldIdentityRegistry`, 카드 후보는 `WorldCardCatalog`가 있어야 표시할 수 있다.
따라서 구단주 모드 버튼을 누른 직후 기존 `PrewarmNewGameWorld()`를 Loading 화면에서 실행한다.

- Bake 적중 여부와 준비 진행 상태를 표시한다.
- 취소하면 타이틀로 돌아가며 Runtime과 Save는 만들지 않는다.
- 실제 Source 선수명, Source 구단명, Source ID를 Loading 또는 오류 문구에 표시하지 않는다.
- World 준비가 끝나면 `UI_Scene_OwnerNewGame`을 열고 Draft를 시작한다.

### 2.2 구단 선택

선택 후보는 `OriginYear`의 정규 `TeamSeasonDefinition`만 사용한다. 특수 합성팀은 선택할 수 없다.
화면에는 World의 가상 구단명과 다음 정보만 표시한다.

| 표시 | 목적 |
|---|---|
| 가상 구단명·색상 | 구단 정체성 |
| 기본 전력 | 출발 난이도 참고. `RosterStrengthResolver` 결과를 재사용 |
| Franchise 역사 연도 범위 | 카드 후보 폭 설명 |
| 타자/투수 카드 후보 수 | 선택 가능성 확인 |
| 대표 성향 | 장타, 수비, 선발 등 데이터 기반 요약 |

구단을 선택하면 해당 `FranchiseId`를 Origin으로 가진 Normal 카드 후보를 전 연도에서 구성한다.
`TeamSeasonKey` 하나의 `Core25`만 후보로 쓰지 않는다. 그래야 플레이어가 같은 구단의 서로 다른 시대를
조합하는 구단주 모드의 수집 재미가 첫 선택부터 드러난다.

구단 카드는 다음 검사를 통과한 구단만 선택 가능 상태로 표시한다.

- Normal 카드 중 서로 다른 `PlayerPersonId`로 야수 6장, 투수 4장을 선택할 수 있다.
- §3의 Cost 제한을 만족하는 10장 조합이 하나 이상 존재한다.
- 선택 후 저가치 충원으로 유효한 25인 로스터를 만들 수 있다.

불가능한 구단을 다른 구단 선수나 생성 선수로 조용히 보충해 활성화하지 않는다. 잠금 사유와 부족한
포지션을 표시하고 콘텐츠 감사 오류로 남긴다.

### 2.3 메인 선수 카드 10장 선택

화면은 카드 Browser와 우측 `선택 명단 / Cost / 포지션 구성` Inspector로 나눈다.

- 기본 정렬: Cost 내림차순 → `OriginYear` 내림차순 → `PlayerSeasonId` 오름차순
- Filter: 연도, 야수/투수, 포지션/`PitcherRole`, Cost
- 카드 표시: World 선수명, `OriginYear`, 포지션/역할, Cost, 핵심 능력치, 예상 배정
- 선택 카드: 정확히 10장. 야수 6장 + 투수 4장
- 이미 선택한 `PlayerPersonId`의 다른 연도 카드는 선택 불가
- 특수 Edition은 초기 무료 지급 대상에서 제외하고 Normal만 허용
- 선택할 때마다 남은 Cost와 “현재 선택으로 완성 가능한가”를 즉시 표시

`Next`는 단순히 현재 합계만 검사하지 않는다. 남은 선택 수로 야수/투수 수량, Cost, 고Cost 카드 수,
Person 중복 규칙을 만족할 수 있는지 `OwnerStarterSelectionValidator`가 판정한다. 더 이상 완성 가능한
조합이 없으면 해당 선택을 적용하지 않고 이유를 표시한다.

### 2.4 프런트 매니저 선택

새 게임은 정확히 두 명의 프런트 매니저 타입을 제공한다. 선택은 외형과 초상화만 바꾸는
**Cosmetic 선택**이며 경기, 카드, 경제, 스카우트, 훈련, 시설, 튜토리얼 내용과 확률에 어떤
특수효과도 주지 않는다.

| 순번 | Stable ID | 선택 화면 기준 이미지 | 제작 상태 |
|---:|---|---|---|
| 1 | `FRONT_MANAGER_DEFAULT_01` | `FrontManager_Default_01_Analysis.png` | 8개 표정 Production Asset 존재 |
| 2 | `FRONT_MANAGER_DEFAULT_02` | `FrontManager_Default_02_Test.png` | 단일 시안만 존재. 이를 기준으로 8개 표정 제작 필요 |

두 선택 카드는 같은 크기와 정보량을 사용한다. 화면에는 `Analysis` 초상화, 임시 표시명, 한 줄 소개만
보여 주며 “능력”, “보너스”, “추천 구단” 같은 오해를 만드는 항목은 표시하지 않는다. 표시명이 별도로
확정되지 않은 동안에는 `프런트 매니저 1`, `프런트 매니저 2` Localization Key를 사용한다.

- 한 명을 반드시 선택해야 다음 단계로 갈 수 있다.
- 기본 자동 선택은 하지 않는다. 사용자가 두 외형을 직접 비교하고 선택한다.
- 선택 변경은 최종 확인 전까지 자유롭고 리롤 횟수나 선수 명단을 바꾸지 않는다.
- 선택한 `FrontManagerId`는 Draft Checkpoint와 구단주 Save에 저장한다.
- 최종 확정 뒤 매니저 변경 기능은 이번 범위에 포함하지 않는다.
- 2번은 8개 표정과 Runtime Mapping이 모두 검증되기 전에는 Production에서 선택 가능 상태로
  노출하지 않는다. 완성 시점에는 두 타입 모두 같은 조건으로 활성화해야 한다.

### 2.5 구단주 닉네임 입력

- 입력 길이: 공백 제거 후 2~12자
- 허용: 한글, 영문, 숫자, 내부 한 칸 공백
- 금지: 앞뒤 공백, 연속 공백, 제어문자, Rich Text 표식, 데이터셋 금칙어
- 저장값: `OwnerProfileState.Nickname`
- 표시 예: `김구단 구단주님`
- 닉네임은 Seed, 후보 정렬, 충원 결과, 경기 결과에 영향을 주지 않는다.

닉네임은 World Identity의 일부가 아니다. 선수·구단 가상 이름 Registry에 넣지 않고 구단주 Save의
프로필 값으로만 보관한다.

### 2.6 창단 명단 확인

이 화면에 진입할 때 선택 카드 10장에 저가치 카드 15장을 Preview로 충원한다. 좌측은 25인 역할표,
우측은 메인/충원 구분과 다음 정보를 표시한다.

- 25/25, 야수 14/14, 투수 11/11, 외국인 0~3/3
- 선택한 프런트 매니저의 `Analysis` 초상화와 표시명
- 메인 10장 Cost 합계와 제한
- 주전 야수 9, 벤치 야수 5, 선발 5, 중간계투 4, Setup 1, Closer 1
- 비주포지션과 투수 역할 불일치 예상 비용
- 가장 강한 포지션 2개와 가장 약한 포지션 2개
- `다음 보강 추천`: 약점 Resolver가 고른 포지션 한 개

랜덤 충원 15장은 요약 숫자로 숨기지 않고 모두 공개한다. 각 카드에서 World 선수명, `OriginYear`,
Origin 구단, Position/`PitcherRole`, Cost, 핵심 능력치, 추천 배정을 확인할 수 있어야 한다. 카드 선택
시 기존 `UI_Popup_OwnerPlayerCard`와 같은 상세 정보 Provider를 사용한다.

화면 하단에는 `현재 15장을 버리고 리롤` 버튼과 `남은 리롤 30/30`을 표시한다.

- 첫 자동 충원 목록은 리롤 횟수에 포함하지 않는다. 플레이어는 최초 목록 + 최대 30개 새 목록,
  총 31개 목록을 확인할 수 있다.
- 한 번의 리롤은 저가치 15장 **전체**를 교체한다. 개별 카드 잠금·부분 리롤은 지원하지 않는다.
- 리롤 후 이전 목록으로 되돌릴 수 없다. 첫 실행 시 교체 사실을 안내하고 이후에는 버튼 문구와
  잔여 횟수로 결과 소멸을 명확히 한다.
- 리롤 처리 중에는 버튼과 최종 확인을 잠가 중복 입력을 막는다.
- 결과가 성공적으로 생성·Checkpoint 저장된 뒤에만 `RerollsUsed`를 증가시킨다.
- 남은 횟수가 0이면 현재 목록 확정만 가능하고 버튼을 비활성화한다.
- 리롤 최대 횟수는 코드 상수가 아니라 §6.1의 `MaximumFillerRerolls`로 제어한다.

30회의 리롤은 플레이어가 단순히 더 높은 Cost 총합을 찾는 노동이 되어서는 안 된다. 모든 목록은
동일한 데이터 기반 Cost 구성(첫 구현값 Cost 1/2/3 각 5장)을 사용하고 25인 역할 조건도 동일하게
통과한다. 따라서 리롤의 주된 선택은 선수 정체성, 세부 능력치, Origin과 포지션 적합도다.

최종 확인 문구는 “메인 카드 10장과 자동 충원 15장으로 시작하며, 미선택 카드는 보유하지 않습니다”를
명시한다. 리롤을 한 경우 `확인 목록 31개 · 리롤 30/30 사용`처럼 실제 설정값을 함께 표시한다. 확정 뒤
타이틀로 돌아가 새 게임을 다시 만드는 작업은 기존 Save 교체 확인 정책을 따른다.

## 3. 초기 카드 선택 Balance 계약

아래 값은 첫 구현값이다. 코드 상수가 아니라 `OwnerExpansionBalance.json`의 `starterRoster` 섹션에서
저작하고 Game 레이어가 순수 `OwnerStarterRosterBalance`로 변환해 주입한다.

| 항목 | 첫 구현값 | 설계 이유 |
|---|---:|---|
| 메인 카드 수 | 10 | 직접 선택의 만족감과 25인 전체 수동 선택 피로 사이 절충 |
| 야수 / 투수 | 6 / 4 | 타선과 마운드 중 한쪽만 고Cost로 채우는 시작 해법 방지 |
| 총 Cost 상한 | 50 | 평균 Cost 5.0. Cost 8~10 중심의 올스타 명단 차단 |
| Cost 9~10 | 최대 2장 | 최고급 핵심 선수에 명확한 기회비용 부여 |
| Cost 7~10 | 최대 4장 | 한 시즌의 중요 선수만 대량 선점하는 시작 방지 |
| 동일 `OriginYear`의 Cost 7~10 | 최대 2장 | 특정 연도의 핵심 카드 독점 방지 |
| 동일 Person | 최대 1장 | 같은 선수의 다년도 카드 동시 선발 방지 |
| Edition | Normal만 | 특수 Edition 무료 지급과 Cost 대비 실전 능력 왜곡 방지 |

Cost 제한은 **메인 10장에만** 적용한다. 자동 충원 15장은 별도 저가치 규칙으로 생성되므로 메인
선택 예산에 합산하지 않는다. UI에는 `메인 선택 Cost 43/50`처럼 범위를 분명히 표시한다.

“특정 연도의 중요 선수 카드를 모두 획득할 수 없어야 한다”는 다음 두 규칙으로 보장한다.

1. Cost 총합 50으로 열 장 전체를 고Cost로 구성할 수 없다.
2. Cost 7 이상은 네 장, Cost 9 이상은 두 장까지만 허용한다.
3. 같은 `OriginYear`의 Cost 7 이상은 두 장까지만 허용한다.

같은 연도의 중저Cost 카드를 함께 쓰는 테마 선택은 허용하되, 그 연도의 고Cost 핵심을 모두 가져가는
것만 막는다. 특정 선수·구단·연도 예외 규칙은 만들지 않는다.

이 값은 경제/전력 Balance 변경이다. 최종 확정 전 §11.5.5의 조합 전수 검사와 대량 시즌 시뮬레이션을
통해 조정하며, 수치를 바꾸면 보고서에 이전/이후 분포를 남긴다.

## 4. 저가치 15장 자동 충원 규칙

### 4.1 후보 Pool

충원 후보는 `WorldCardCatalog`의 Normal 카드 중 다음 조건을 모두 만족해야 한다.

- Cost 1~3
- 선택한 메인 10장의 `PlayerPersonId`와 다름
- 이미 충원한 카드와 `PlayerPersonId`가 다름
- 유효한 Position/`PitcherRole`과 `RegistrationType` 보유
- 활성 World의 Canonical Content에 존재

충원 카드는 선택 Franchise로 제한하지 않는다. 이 15장은 창단 시 저가 계약으로 합류한 선수라는
역할이며, 다른 Origin이 섞여도 Canonical `Core25`를 수정하거나 Source 선수를 합성하는 것이 아니다.
선택 구단의 정체성은 플레이어가 직접 고른 10장과 이후 TeamColor 구성으로 만든다.

### 4.2 구성 목표

메인 6야수/4투수에 아래 인원을 추가해 표준 25인을 만든다.

```text
저가치 야수 8명  → 전체 야수 14명
저가치 투수 7명  → 전체 투수 11명
```

단순 무작위 8+7 추출이 아니라, 먼저 결손 역할을 채운 뒤 남은 자리를 뽑는다.

1. 포수 포함 주전 수비 8자리와 DH 후보 확보
2. 백업 포수와 벤치 수비 Coverage 확보
3. 선발투수 5명 확보
4. 중간계투 4명, Setup 1명, Closer 1명 확보
5. 외국인 선수 최대 3명 검사
6. `ActiveRosterValidator` 최종 통과

비주포지션 배치가 허용되는 기존 계약은 유지하되, 자연 포지션 후보가 있는데도 무작위로
비주포지션을 선택하지 않는다. 첫 구현의 목록별 Cost 구성은 Cost 1/2/3 각 5장으로 고정한다.
역할별 후보 부족으로 이 구성을 만족할 수 없으면 목록 생성을 실패시키며 Cost 구성 자체를 조용히
바꾸지 않는다. 같은 Cost 안에서 역할 적합도와 약점 보완 점수를 계산한 뒤 RNG로 동률을 해소한다.

### 4.3 결정론과 실패 처리

`StarterRosterSeed`는 Draft 시작 시 확정하고 닉네임과 무관하게 저장한다. 각 목록의 Seed는 RNG
호출 횟수에 의존하지 않고 `StarterRosterSeed + SelectionFingerprint + RerollIndex`의 Stable Hash로
파생한다. 최초 목록의 `RerollIndex`는 0, 첫 리롤은 1, 마지막 허용 Index는 Draft가 보관한
`RerollLimitSnapshot`이다(첫 구현값 30). Resolver는 주입받은 결정론적 RNG만 사용하며 후보는
`PlayerSeasonId` 오름차순으로 정렬한 뒤 평가한다.

```text
같은 ContentHash
+ 같은 WorldSeed
+ 같은 StarterRosterSeed
+ 같은 TeamSeasonKey
+ 같은 선택 CardId 10장
+ 같은 RerollIndex
+ 같은 BalanceVersion
= 같은 충원 15장 + 같은 역할 배정 + 같은 Preview Hash
```

이전에 본 목록과 완전히 같은 15장 조합이 나오면 `RerollResultHashHistory`를 기준으로 최대
`DuplicateRerollRetryCount`만큼 파생 Seed를 다시 만든다. 중복을 피하지 못하면 현재 목록을 유지하고
리롤 횟수를 소비하지 않은 채 오류를 표시한다. 무제한 재시도 루프는 금지한다.

후보가 부족하면 실패한다. Cost 4 이상, Cost 구성 변경, 타 구단의 Canonical `Core25` 직접 복사,
생성 선수, Person 중복으로 조용히 메우지 않는다. 오류에는 부족한 역할과 필요한 수량을 포함하고
현재 유효한 목록이 있으면 그 목록은 보존한다.

### 4.4 Canonical `Core25`와의 경계

- `TeamSeasonDefinition.Core25CardIds`는 Offline Canonical Definition이므로 수정하지 않는다.
- AI 구단의 `CurrentRosterState`는 기존 해당 연도 `Core25`를 유지한다.
- 선택한 플레이어 구단의 새 `CurrentRosterState`만 메인 10장 + 충원 15장으로 만든다.
- `OwnedPlayerCardState`에는 이 25장만 한 번씩 지급한다.
- 선택하지 않은 원본 `Core25`, 후보 Browser의 미선택 카드, 특수 Edition은 보유 목록에 넣지 않는다.
- 지급 출처는 카드 상태에 Boolean을 추가하지 않고 `OwnerNewGameReceipt`의 Selected/Filler CardId로
  기록한다.

## 5. 프런트 매니저 선수 배정 튜토리얼

### 5.1 용어와 범위

여기서 “매니저”는 감독 AI가 아니라 안내 NPC **프런트 매니저**다. 튜토리얼의 “선수 배정”은
25인 보유 선수를 새로 뽑거나 등록/말소하는 기능이 아니라, 확정된 25인 안에서 다음 경기용 역할과
라인업을 확인·변경하는 과정이다.

- 타자: 주전 수비 위치, DH, 벤치, 타순
- 투수: 선발 1~5, 중간계투 1~4, Setup, Closer
- 적용 Command: `UpsertLineupPreset`
- 최종 판정: `ValidateLineupPreset`과 `ActiveRosterValidator`

임의의 Collection 카드를 25인 ActiveRoster에 넣고 빼는 등록 변경 Command는 이 튜토리얼 범위가
아니다. 해당 기능이 생기기 전까지 “1군 등록 변경”으로 오해하게 하는 문구를 쓰지 않는다.

### 5.2 튜토리얼 진행

첫 Owner Home이 실제로 표시된 뒤 아래 순서로 진행한다.

| 단계 | 프런트 매니저 행동 | 완료 조건 |
|---:|---|---|
| 1 | 닉네임으로 환영하고 선택한 구단·메인 10장을 요약 | 대화 확인 |
| 2 | `선수단` CTA로 이동 | Roster Route 실제 진입 |
| 3 | 25인 구성과 메인/충원 구분, 14/11 규칙 설명 | 구성 영역 확인 |
| 4 | 약점 포지션과 추천 배정 한 건을 강조 | 대상 카드 Inspector 열기 |
| 5 | 추천 배정 Preview의 전/후 적합도와 페널티 설명 | `추천 배정 적용` 또는 `현재 배정 유지` 명시 선택 |
| 6 | 현재 Preset 재검증 결과 설명 | 유효한 `ValidateLineupPreset` 결과 확인 |
| 7 | 다음 보강 추천과 Home 복귀 CTA 제공 | Home 복귀 또는 `나중에` 선택 |

자동 충원 Resolver가 이미 가장 적합한 배정을 만들었다면 억지로 나쁜 Swap을 요구하지 않는다.
`현재 배정 유지`도 유효한 판단으로 인정하되, Preview와 검증 결과를 실제로 확인한 뒤에만 단계를
완료한다.

### 5.3 건너뛰기·재개·반복

- 첫 대화에서 `튜토리얼 진행`과 `나중에`를 제공한다.
- `나중에`는 영구 Skip이 아니다. Home의 도움말에서 이어서 시작할 수 있다.
- 도움말의 `첫 선수 배정 다시 보기`로 완료 후에도 재생할 수 있으나 보상은 없다.
- 단계 진행은 `OwnerOnboardingState`에 저장한다. 앱 종료 후 마지막 미완료 단계부터 재개한다.
- 기존 `GuideRepeatState`는 Cue 중복 억제를 담당하고, Onboarding 단계 원본으로 사용하지 않는다.
- 기존 `TUTORIAL_OWNER_FIRST_ENTRY` Cue와 `OpenRoster` CTA는 재사용한다.
- 단계 3~7에는 새 Fact/Cue가 필요하며, Presentation이 튜토리얼 완료를 임의 판정하지 않는다.

### 5.4 필요한 신규 Guide Fact/Cue

| Fact | Cue | 발생 위치 |
|---|---|---|
| `OwnerStarterRosterOverviewOpened` | `TUTORIAL_OWNER_ROSTER_OVERVIEW` | Roster Route + Overview 표시 완료 |
| `OwnerStarterPlayerInspected` | `TUTORIAL_OWNER_ASSIGNMENT_TARGET` | 지정 카드 Inspector 열림 |
| `OwnerStarterAssignmentReviewed` | `TUTORIAL_OWNER_ASSIGNMENT_REVIEWED` | 추천 적용/유지 Command 성공 |
| `OwnerStarterLineupValidated` | `TUTORIAL_OWNER_LINEUP_VALID` | Game 검증 성공 결과 |
| `OwnerStarterOnboardingCompleted` | `TUTORIAL_OWNER_COMPLETE` | Onboarding 완료 Commit |

각 Cue는 최소 3개 Variation과 한국어 대사를 가진다. 단, 튜토리얼 단계의 순서는 무작위 Variation이
아니라 `OwnerOnboardingState.Step`이 소유한다. Cue는 상태를 설명할 뿐 다음 단계로 넘기는 권한을
가지지 않는다.

### 5.5 두 프런트 매니저의 공통 동작 계약

`FrontManagerId`는 어떤 Guide Fact와 Cue를 선택할지 결정하지 않는다. 두 타입은 같은
`front_manager_guide_dataset_v1.json`의 Fact/Cue/Variation, 같은 `FrontManagerGuide` 반복 정책,
같은 CTA와 같은 판단 결과를 소비한다. 차이는 최종 `ExpressionAssetKey`를 어느 캐릭터 세트에서
해결하는가뿐이다.

```text
Guide Fact + Cue Expression(예: Analysis)
+ OwnerProfileState.FrontManagerId
→ FrontManagerCharacterCatalog.ResolveExpressionAssetKey
→ FM_01_ANALYSIS 또는 FM_02_ANALYSIS
```

금지 사항:

- 매니저 타입별 선수 능력치·Cost·Condition·Chemistry 보정
- 매니저 타입별 리롤 횟수·Scout 확률·재정·시설 효과
- 같은 Fact에서 타입별로 유리하거나 불리한 조언 제공
- 캐릭터별 전용 Cue 때문에 한 타입만 정보를 더 받는 구조
- 이름이나 표시 문자열로 타입을 판정하는 분기

현재 Guide JSON은 단일 `character`와 `FM_ANALYSIS` 같은 공용 Asset Key만 가진다. 이를 다음처럼
복수 캐릭터 Catalog로 확장한다.

```text
FrontManagerCharacterDefinition
  FrontManagerId
  DisplayNameKey
  SelectionDescriptionKey
  PreviewExpression = Analysis
  ExpressionAssetKeys[8]

FrontManagerCharacterCatalog
  Characters[2]
  Get(FrontManagerId)
  ResolveExpressionAssetKey(FrontManagerId, Expression)
```

Cue의 `expressionKey`는 `Analysis`, `Warning` 같은 의미 Key로 유지한다. Dataset Factory 또는 Game
Resolver가 선택한 캐릭터의 Runtime Asset Key로 한 번 변환하고, Presentation은 전달받은 Key를
`Resources.Load<Sprite>`로 표시할 뿐 캐릭터 선택이나 폴백 대상을 계산하지 않는다.

선택한 캐릭터의 특정 표정이 누락되면 같은 캐릭터의 `Neutral`을 임시 폴백으로 사용할 수 있으나
콘텐츠 오류를 기록한다. 다른 캐릭터의 이미지를 대신 표시하지 않는다. `Neutral` 자체가 없거나
Production Build 검증에서 8개 표정 중 하나라도 누락되면 빌드를 실패시킨다.

### 5.6 2번 매니저 ImageGen 제작 계약

2번의 기준 원본은 다음 파일이며 덮어쓰거나 삭제하지 않는다.

```text
Assets/10.Datas/FrontManager/Art/FrontManager_Default_02_Test.png
```

현재 시안은 1024×1536 ARGB 이미지이며 배경이 포함되어 있다. 이 파일을 Identity Reference로 사용해
`Neutral / Welcome / Analysis / Concerned / Warning / Celebrate / Surprised / Calm` 8개 Production
이미지를 만든다. 기존 Test를 곧바로 `Analysis` Runtime Asset으로 참조하지 않고, 배경을 제거하고
공통 구도에 맞춘 최종 `FrontManager_Default_02_Analysis.png`를 별도로 만든다. 즉, 나머지 표정 7장과
정리된 Analysis 1장까지 총 8장을 납품한다.

ImageGen 실행은 `imagegen` 스킬의 기본 내장 도구 모드를 사용하며, 서로 다른 표정은 각각 별도 호출로
생성/편집한다. 2번 시안은 매 호출의 `identity-preserve` Edit Target이다. 생성 뒤 결과를 대화 임시
경로에만 두지 않고 아래 프로젝트 경로로 옮겨 검수한다.

```text
원본/제작본
Assets/10.Datas/FrontManager/Art/FrontManager_Default_02_<Expression>.png

Runtime
Assets/10.Datas/Resources/FrontManager/FM_02_<EXPRESSION>.png
```

공통 Prompt 불변조건:

- 2번 시안의 동일 인물 정체성, 얼굴 비율, 짧은 머리, 남색·흰색 재킷, 내부 셔츠와 바지 유지
- 태블릿과 펜, 전신 세로 구도, 카메라 각도, 인물 크기를 가능한 한 유지
- 1024×1536, 실제 Alpha가 있는 투명 배경, 외곽 Halo 없음
- 이미지 안 문자, Logo, Watermark, 추가 인물, 추가 소품 없음
- 표정별로 요청한 얼굴 표정만 우선 변경하고 복장·체형·피부색·헤어스타일을 재해석하지 않음

표정별 연출 목표:

| Expression | 목표 |
|---|---|
| `Neutral` | 감정이 과하지 않은 기본 응대 표정 |
| `Welcome` | 처음 만나는 플레이어를 맞는 부드러운 미소 |
| `Analysis` | 태블릿 자료를 설명하는 집중된 표정. Test 시안과 가장 가까움 |
| `Concerned` | 걱정스럽지만 공포스럽지 않은 표정 |
| `Warning` | 문제를 분명히 알리는 단호한 표정 |
| `Celebrate` | 승리와 좋은 소식을 축하하는 밝은 표정 |
| `Surprised` | 예상 밖 결과에 놀란 표정. 과장된 Cartoon 표정 금지 |
| `Calm` | 안정시키는 차분한 표정 |

첫 결과는 `Analysis` 정리본으로 만들고 얼굴·복장·Silhouette 기준을 확정한 뒤 나머지 7장을 만든다.
Variant 간 정체성이 흔들리면 전부 다시 생성하지 않고 한 표정씩 단일 변경으로 반복한다. 결과물마다
원본 대비 얼굴, 손가락, 태블릿, 펜, 옷 경계, 투명 Alpha를 육안 검수한다.

1번 Runtime Asset도 새 복수 캐릭터 Naming에 맞춰 `FM_01_<EXPRESSION>` Key를 제공한다. 기존
`FM_ANALYSIS` 등은 Legacy Alias로 유지할 수 있지만 신규 Save와 Dataset은 번호가 포함된 Key를
사용한다.

## 6. 데이터와 상태 계약

### 6.1 정적 Balance

```text
OwnerStarterRosterBalance

  MainCostLimit = 50
  MaxCostNineOrHigher = 2
  MaxCostSevenOrHigher = 4

  FillerCount = 15
  FillerMaximumCost = 3

```

`MaximumFillerRerolls`의 유효 범위는 0~30이며 기본값은 30이다. 0이면 최초 목록만 확인할 수 있다.
세 Cost 수량의 합은 항상 `FillerCount`와 같아야 하고 각 값은 0 이상이어야 한다. Config 파서는 범위를
벗어난 리롤 횟수와 잘못된 Cost 수량 합계를 Production 진입 전에 거부한다.

저작 위치:

```text
Assets/10.Datas/Resources/NewGame/OwnerExpansionBalance.json
  starterRoster
```

`OwnerExpansionBalanceConfig`가 필수값과 범위를 검증한 뒤 `NewGameDefinition.LoadOwnerModeBalanceTable()`
경로에서 구단주 전용 Balance에만 합성한다. 선수 커리어 Balance Hash에는 포함하지 않는다.

최종 Runtime Save와 별도로 `OwnerNewGameDraftCheckpointStore`가 Draft 진행을 로컬에 저장한다.

## 선행 설계 결정

아래 항목은 이 문서에서 확정한다.

1. **카드 후보 범위:** 선택 Franchise의 전 연도 Normal 카드다.
2. **메인 구성:** 정확히 10장, 야수 6/투수 4다.
3. **초기 Cost:** 총 50, Cost 9+ 최대 2, Cost 7+ 최대 4, 동일 연도 Cost 7+ 최대 2다.
4. **동일 선수:** `PlayerPersonId` 기준 한 장만 허용한다.
5. **특수 Edition:** 초기 무료 선택에서 제외한다.
6. **충원 범위:** 전체 Normal Catalog의 Cost 1~3이며 Origin Franchise 혼합을 허용한다.
7. **충원 리롤:** 최초 목록은 무료이며, 전체 15장 리롤을 기본 최대 30회 제공한다.
8. **리롤 Balance:** 최대 횟수와 Cost 1/2/3 구성은 `OwnerExpansionBalance.json`에서 제어한다.
9. **리롤 지속성:** 성공한 리롤 횟수·현재 목록·결과 Hash 이력을 Draft Checkpoint에 즉시 저장한다.
10. **목록 교체:** 이전 목록 복원과 개별 카드 잠금·부분 리롤은 지원하지 않는다.
11. **Runtime 생성 시점:** 최종 확인 한 번에서만 생성·저장한다.
12. **첫 진입 정의:** 새 게임 Receipt가 있고 Onboarding이 미완료인 Save의 Owner Home 첫 표시다.
13. **선수 배정 의미:** 확정 25인 내부의 라인업/역할 배정이며 ActiveRoster 등록 변경이 아니다.
14. **튜토리얼 Skip:** 임시 연기와 도움말 재개를 지원하고 영구 강제 Skip은 두지 않는다.
15. **기존 Save:** 새 튜토리얼을 소급 강제하지 않는다.
16. **매니저 수:** `FRONT_MANAGER_DEFAULT_01/02` 정확히 두 타입을 지원한다.
17. **매니저 효과:** 외형 선택일 뿐 Gameplay·Guide 정보·확률·Balance 차이가 없다.
18. **2번 Asset:** `FrontManager_Default_02_Test.png`를 보존한 채 ImageGen으로 8표정 Production 세트를
    별도 제작한다.
19. **선택 수명:** 새 게임에서 반드시 선택하고 Save에 고정한다. 게임 중 변경은 이번 범위가 아니다.

Cost와 고Cost 장수는 첫 구현 Balance다. 이 수치를 확정 설계로 코드에 박는다는 뜻은 아니며,
대량 검증 결과에 따라 데이터만 조정한다.

## 8. Save/Load와 Migration

현행 `ManagerHistoricalSaveAdapter.CurrentSaveVersion`은 5다. 구현 시 Owner Profile, New Game Receipt,
Onboarding State를 추가하며 SaveVersion을 6으로 올린다.

### v5 → v6

- `OwnerProfileState.Nickname = "구단주"`
- `OwnerProfileState.FrontManagerId = "FRONT_MANAGER_DEFAULT_01"`
- `OwnerNewGameReceipt = null`과 `IsLegacySetup = true`
- `OwnerOnboardingState.IsCompleted = true`
- 기존 `GuideRepeatState`는 그대로 복원
- 기존 25인 로스터와 Owned Cards를 새 Resolver로 재생성하지 않음

기존 Save에 새 튜토리얼을 자동으로 띄우지 않는다. 도움말에서 수동 재생은 허용한다.

신규 v6 Save는 다음 불변조건을 검사한다.

- Receipt의 선택 10장 + 충원 15장 = 서로 다른 Person 25명
- Receipt CardId 집합 = 초기 Owned Card 집합 = 플레이어 구단 초기 Roster 집합
- 저장된 `MainCostTotal` = 현재 Canonical Cost 합계
- `RerollsUsed <= RerollLimitSnapshot`, 채택 Index와 Filler Result Hash 일치
- `OwnerProfileState.FrontManagerId`가 Character Catalog의 두 Stable ID 중 하나
- 저장된 Content/Balance Version이 Receipt와 호환
- Save/Load 전후 Nickname, Receipt, Onboarding Step, Roster, Owned Cards 일치
- Load 중 자동 충원 Resolver와 World 생성기 재실행 0회

## 9. 오류·취소·재진입 정책

- World 준비 실패: 오류 요약과 `다시 시도 / 타이틀` 제공, 빈 Runtime 생성 금지
- 후보 부족: 해당 구단 잠금과 역할별 부족 수 표시
- 10장 미만/초과: 다음 단계 진입 불가
- Cost 초과: 초과량과 제거 가능한 고Cost 카드 강조
- 완성 불가능 선택: 선택 적용 전 거부하고 이유 표시
- 닉네임 오류: 입력 유지, 정규화 결과와 제한 표시
- 프런트 매니저 미선택: 다음 단계와 최종 확인 비활성
- 선택한 매니저의 표정 Asset 누락: Production 콘텐츠 검증 실패, 다른 매니저 이미지로 대체 금지
- Preview 실패: 최종 확인 비활성, 부족 역할 표시
- 리롤 횟수 소진: 현재 목록 유지, 리롤 버튼 비활성, 최종 확인은 허용
- 리롤 생성/Checkpoint 저장 실패: 현재 목록과 횟수 유지, 재시도 가능 오류 표시
- Save 쓰기 실패: Runtime Commit을 사용자에게 성공으로 표시하지 않고 재시도 가능 상태 유지
- Loading/마지막 Commit 중 중복 클릭: 입력 잠금과 idempotency key 적용
- 앱 종료: Draft Checkpoint에서 현재 목록·잔여 리롤·Wizard 단계를 복원

- `OriginYear`의 모든 정규구단이 유효 조합을 제공하거나 잠금 사유가 데이터 감사 결과로 명시된다.
- 프런트 매니저 2종이 각각 8개 표정과 Runtime Key를 빠짐없이 제공한다.

- §선행 설계 결정 19개를 구현과 테스트가 그대로 따른다.

### 표현 계층 게이트

- Presentation은 후보 자격, Cost 합계, 충원, 역할 적합도, 약점, 튜토리얼 완료를 계산하지 않는다.
- UI는 Game/Simulation의 immutable Preview와 Validation reason code를 표시한다.
- UI는 저장된 `FrontManagerId`에 해당하는 Character Catalog의 초상화만 표시한다.
- Source 실명/구단명/ID 노출이 0건이다.

### 가이드 Fact 게이트

- 기존 `OwnerModeFirstEntry`와 신규 5 Fact의 Production 생산자가 있다.
- Fact는 실제 사용자 행동과 Game Commit 뒤에만 발행한다.
- Save/Load, 화면 재진입, `RuntimeChanged` 반복으로 Cue가 중복되지 않는다.

## 검증 근거

### 11.1 Rule

- 정확히 10장, 야수 6/투수 4만 통과
- Cost 50 통과, 51 거부
- Cost 9+ 3장 거부, Cost 7+ 5장 거부
- 같은 `OriginYear`의 Cost 7+ 3장 거부
- 같은 Person 다른 연도 카드 동시 선택 거부
- 특수 Edition 선택 거부
- 메인 카드와 충원 Person 중복 0건
- 모든 목록이 Cost 1/2/3 각 5장
- `MaximumFillerRerolls` 0과 30 허용, -1과 31 거부
- 세 Cost 수량의 합이 15가 아니면 Config 거부
- 프런트 매니저 미선택·알 수 없는 ID 거부, 두 정식 ID 허용
- 각 매니저의 8개 의미 표정이 고유한 Runtime Asset Key로 해석됨
- 최종 25명, 야수 14/투수 11, 외국인 최대 3
- 포수, 선발 5, 중간계투 4, Setup, Closer 역할 충족
- 선택하지 않은 카드가 Owned Collection에 들어가지 않음

### 11.2 Determinism

- 같은 입력 두 번의 충원 CardId 순서, 역할, Preview Hash 완전 일치
- 후보 원본 컬렉션 순서를 섞어도 결과 일치
- 닉네임만 바꿔도 충원·배정 결과 불변
- 다른 `StarterRosterSeed`에서는 통계적으로 둘 이상의 충원 결과 발생
- 같은 `RerollIndex` 재실행 결과 일치, 다른 Index에서 목록 다양성 확보
- 닉네임·화면 재진입·앱 재시작이 현재 목록과 잔여 횟수를 바꾸지 않음
- `FrontManagerId`만 바꿔도 카드·로스터·리롤·경제·첫 경기 Event Stream이 동일
- 같은 Cue/Expression에서 타입별 Asset Key만 `FM_01_*`/`FM_02_*`로 달라짐
- Save/Load 전후 경기 입력과 첫 경기 Event Stream 일치

### 11.3 Persistence

- v6 Round-trip에서 Profile/Receipt/Onboarding/Roster/Owned Cards 일치
- v5 Migration이 기존 로스터를 변경하지 않고 Tutorial 완료 상태로 복원
- 미완료 Tutorial 단계 저장 후 정확한 단계 재개
- Draft Checkpoint Round-trip에서 현재 15장, 사용 횟수, Hash 이력 일치
- Draft와 v6 Save Round-trip에서 선택한 `FrontManagerId` 일치
- v5 Migration은 1번 매니저를 사용하고 기존 진행 상태를 변경하지 않음
- 30회 성공 후 31번째 리롤 거부, 실패한 리롤은 횟수 미소비
- 최종 확인 중복 호출로 카드·Save 중복 없음
- Load 중 Resolver 재실행 0회

### 11.4 Production E2E

- 새 Save 없음 → 구단주 버튼 → Wizard → 최종 확인 → Home → 배정 Tutorial 완료
- 뒤로가기 후 카드 선택 변경 → 같은 Seed 기반 새 Preview → 정상 Commit
- 최초 목록과 최대 30회 리롤의 15장 전체 확인, 교체, 잔여 횟수 표시
- 두 매니저 Preview 비교, 필수 선택, 최종 확인, Home/Tutorial 초상화 일치
- 앱 재시작 후 마지막 목록과 잔여 리롤 횟수 복원
- 후보 부족/Cost 초과/닉네임 오류에서 정확한 UI 피드백
- `OpenRoster`, Inspector, 추천 적용/유지, Home 복귀 CTA 실제 동작
- 기존 Save 있음 → `계속하기`에서 Wizard와 첫 Tutorial을 재실행하지 않음

### 11.4.1 ImageGen Asset QA

- 2번 8장 모두 1024×1536이며 실제 투명 Alpha 보유
- 얼굴·헤어·복장·체형·태블릿·펜의 캐릭터 동일성 유지
- 손가락·눈·치아·태블릿 외곽과 투명 경계의 생성 결함 0건
- 각 표정을 Thumbnail 크기에서도 서로 구분 가능
- 문자·Logo·Watermark·불필요한 배경·추가 인물 0건
- 1번과 2번의 Canvas, 발 위치, 얼굴 높이, 화면 점유율이 UI 교체 시 튀지 않는 허용 범위
- `UI_System_FrontManagerGuide`의 FullDialogue/Briefing/Toast/ContextBubble에서 두 타입 모두 Crop 없음

### 11.5 Balance·대량 검증

#### 11.5.1 전체 Catalog 조합 감사

1982~2025의 모든 정규 Franchise/`OriginYear` 조합에서 다음을 집계한다.

- 선택 가능한 야수/투수/Cost 구간별 카드 수
- Cost 50 이내 6야수/4투수 조합 존재 여부
- 메인 선택 뒤 Cost 1~3 충원 성공률
- 역할별 후보 부족 건수
- Replacement Canonical 사용 건수와 그 사유

완료 기준은 Production에서 선택 가능한 구단의 충원 실패 0건이다.

#### 11.5.2 생성 분포

최소 10,000개 Draft Seed × 대표 구단군을 실행한다.

- 충원 Cost 1/2/3 비율
- 최초 목록과 리롤 목록의 Cost 1/2/3 각 5장 준수율
- 31개 목록 내 완전 중복률과 중복 회피 재시도 횟수
- 자연 포지션/역할 배정률
- 비주포지션·투수 역할 불일치 수
- 외국인 선수 수
- 같은 Person/Card 중복
- 약점 포지션 분포

특정 포지션 또는 Cost 3 카드가 Seed와 무관하게 고착되면 후보 점수와 동률 해소를 재검토한다.

#### 11.5.3 초기 전력 비교

최소 1,000개 스타터 로스터를 생성해 다음을 보고한다.

- 25인 기본 전력 평균/표준편차/P10/P50/P90
- 메인 10장 Cost 합계별 기본 전력
- 타자/투수 전력 격차
- 선택 구단별 시작 전력 편차
- 기존 Canonical `Core25` 대비 전력 차이
- 최초 목록 확정과 30회 중 최고 전력 목록 선택 사이의 전력 상승폭
- 전력 대신 포지션 적합도를 최대로 고른 경우의 상승폭

#### 11.5.4 시즌 결과

`DetailedMatchEngine` 공개 경로로 최소 10,000경기를 실행한다.

- 리그 AVG/OBP/SLG, HR/G, BB%, K%, R/G, ERA, WHIP
- 스타터 로스터 Cost/기본 전력과 승률 상관
- Cost 50 상한 조합과 저Cost 조합의 승률 분포
- 한쪽이 80% 이상 승률로 고착되는 조합 존재 여부
- 같은 Seed/입력 반복 결과 일치

Cost 50을 바꾸기 전에는 “높은 Cost가 강한가”뿐 아니라 “어떤 선택도 사실상 정답 하나로 수렴하지
않는가”를 본다. 목표는 완전한 전력 평준화가 아니라 강한 선수와 포지션 Coverage 사이의 선택이다.

#### 11.5.5 Cost 제한 전수 검사

각 구단 후보에서 현실적으로 노출할 상위 카드 조합을 전수 또는 Branch-and-Bound로 검사한다.

- 동일 `OriginYear`의 Cost 7+ 3장 이상 조합 0건
- Cost 9+ 3장 이상 조합 0건
- 최소 3개 이상의 성격이 다른 유효 조합 존재
  - 타선 중심
  - 선발 중심
  - 수비/균형 중심
- 선택 불가능 카드가 지나치게 많아 Browser가 사실상 함정 목록이 되지 않는지 확인

## 제거/정리 대상

- `UI_Scene_NewGame.Title.cs`에서 Save가 없을 때 `OwnerModeManager.StartNewGame()`을 즉시 호출하는 경로
- `OwnerModeManager.StartNewGame()`의 “첫 유효 정규구단 자동 선택” Production 책임
- `OwnerModeNewGameConfiguration.PlayerTeamSeasonKey`를 사용자 선택 대신 쓰는 Production 의미
- 플레이어 구단이 Canonical `Core25` 25장을 자동으로 전부 소유하게 하는 초기화 경로
- 첫 진입 Tutorial을 `RuntimeChanged`만으로 시작해 Shell 표시 시점을 보장하지 못하는 경로
- Guide Dataset의 단일 `character`만 가정하는 Factory/Validator 계약
- `UI_Scene_OwnerClubInformation`의 `FM_WELCOME` 하드코딩과 선택 매니저를 우회하는 직접 Resource Load

테스트 Fixture와 Legacy Save Migration에 필요한 overload는 이름과 접근 범위로 Production 경로와
구분한다. 제거 뒤에도 AI 구단 Canonical `Core25` 생성과 `TeamSeasonDefinition.Core25CardIds`는 유지한다.
