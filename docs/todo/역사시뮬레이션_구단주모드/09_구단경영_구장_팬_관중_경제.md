# 09. 구단 경영 — 구장·팬·관중·시설·홈경기 경제

> 상태: 신규 정본 기획안 / Codex 구현 기준
>
> 적용 범위: 현재 문서에서 `구단주 모드`라 부르는 Manager Mode의 플레이어 구단. Presentation 표시명이 프로젝트에서 `구단주 모드`로 변경되어 있다면 UI 문구만 그 기준을 따르고, 기존 코드/문서 타입명은 무리하게 일괄 개명하지 않는다.

## 0. 목적

현재 05절은 `Money`의 사용처에 계약·연봉·시설·코치를, 획득처에 경기 수익을 두고 있으며 SP/DP를 시설에서 생산하도록 정의한다. 하지만 **실제 홈경기 수익, 팬/인기도, 구장 수용력, 시설 성장, 주간 운영 루프**는 정식 계약이 없다.

이 문서는 이 공백을 메워 다음 순환을 완성한다.

```text
경기 결과/구단 성과
    ↓
팬 기반·인기도 변화
    ↓
홈경기 관중
    ↓
Money 수익
    ↓
구장·시설·스태프 투자
    ↓
SP/DP/회복/분석/전술 연구 효율
    ↓
선수단 운영 선택
    ↓
다음 경기/시즌
```

핵심 원칙:

1. `Money / SP / DP` 3자원 구조를 유지한다. 새 범용 재화를 만들지 않는다.
2. 시설은 BaseStat을 직접 올리지 않는다.
3. 시설 효과는 기존 시스템의 **생산량·회복·정보 품질·연구 효율**을 바꾼다.
4. 플레이어 구단의 소유 경제와 AI 구단의 시뮬레이션 경계를 섞지 않는다.
5. 모든 밸런스 수치는 데이터화한다.
6. Core/Simulation은 Unity를 참조하지 않는다.
7. 동일 Seed와 동일 상태에서는 관중·수익 계산이 재현 가능해야 한다.

## 1. 기존 문서와의 연결

### 1.1 05절과의 연결

기존 계약을 변경하지 않는다.

```text
Money — 계약/연봉/FA/트레이드/시설/코치
SP    — 스카우트 전용
DP    — 카드 훈련 전용
```

이 문서는 다음을 추가한다.

```text
ManagerEconomyState
  + ClubOperationState
  + StadiumState
  + FacilityState[]
  + HomeGameFinanceRecord[] / SeasonFinanceSummary
```

SP/DP를 Money로 직접 구매하는 통로는 만들지 않는다.

### 1.2 02절 Club DNA와의 연결

`FranchiseIdentityProfile` / `TeamSeasonClubState`는 경기 스타일과 장기 구단 성향이다.

`FanBase`, `Popularity`, `Stadium`, `Facility`는 **운영/경제 상태**다.

둘을 같은 타입으로 합치지 않는다.

Club DNA는 관중 계산의 작은 설명 변수로 사용할 수 있으나 능력치나 수익을 직접 보장하지 않는다.

### 1.3 12절 Condition 시스템과의 연결

`RecoveryCenter`는 Condition 회복 Resolver에 **회복 효율 Modifier**만 전달한다.

시설 자체가 `Condition = 100`처럼 값을 직접 덮어쓰지 않는다.

### 1.4 10절 경기 전 분석과의 연결

`DataAnalysisCenter`는 상대 분석 리포트의 정보 신뢰도/노출 범위에 Modifier를 제공할 수 있다.

### 1.5 06절 전술과의 연결

`TacticLab`은 전술 연구 비용/연구 후보/Signature 진행 보조에만 관여한다. 경기 중 Tactic Bonus를 시설이 직접 추가하지 않는다.

## 3. 관중 산정

정확한 Money 규모는 현재 프로젝트의 연봉/계약/Scout 경제 단위를 먼저 감사한 뒤 `ClubOperationBalanceTable`에 맞춘다. 기획 문서에서 임의의 절대 금액을 하드코딩하지 않는다.

개념식:

```text
ExpectedDemand
 = BaseDemand(FanBase)
 × PopularityFactor
 × RecentPerformanceFactor
 × OpponentAttractionFactor
 × LeagueGradeFactor
 × SeasonImportanceFactor
 × TicketPriceFactor
 × AttendanceMomentumFactor
```

```text
Attendance
 = Clamp(
     DeterministicVariance(ExpectedDemand, GameSeed),
     min: 0,
     max: Stadium.Capacity)
```

원칙:

- 승리만으로 항상 만원이 되지 않는다.
- 낮은 티켓 가격은 관중에 유리하지만 경기당 수익은 낮아질 수 있다.
- 높은 티켓 가격은 단기 수익을 높일 수 있으나 수요를 감소시킨다.
- 상위 리그 진입은 수요 잠재력을 높이지만 운영비/시설 비용도 함께 상승한다.
- 특정 카드 보유 자체로 관중이 무한히 오르는 보너스는 만들지 않는다.
- MVP/우승/연승 등의 월드 기록은 `Popularity` 이벤트로 간접 반영할 수 있다.

## 4. 팬 기반과 인기도

### 4.1 FanBase

장기적인 구단 지지 기반.

변화 요인:

- 시즌 성적
- 승격/강등
- 포스트시즌 진출/우승
- 장기 연속 부진
- 시즌 누적 홈 관중

한 경기 결과로 크게 출렁이지 않는다.

### 4.2 Popularity

단기 화제성.

변화 요인:

- 연승/연패
- 순위 경쟁
- 대형 수상/뉴스
- 시즌 주요 경기
- 팬 이벤트/홍보 시설

FanBase보다 빠르게 오르고 빠르게 감소한다.

### 4.3 AttendanceMomentum

최근 홈 관중의 단기 관성.

별도 영구 능력치가 아니라 최근 N경기 상태에서 파생해도 된다. Save 크기를 줄일 수 있다면 파생값을 우선한다.

## 5. 홈경기 경제

```text
TicketRevenue  = Attendance × RevenuePerAttendee(TicketPolicy)
FanShopRevenue = Attendance × FanShopRate(FacilityLevel)
OperatingCost  = StadiumOperatingCost + FacilityOperatingCost + GameDayCost
NetGameIncome  = TicketRevenue + FanShopRevenue + OtherRevenue - OperatingCost
```

경제 목표:

- 홈경기만 반복해 Money가 무한히 눈덩이처럼 쌓이지 않게 한다.
- 상위 리그에서 수익 잠재력과 비용 부담이 함께 증가한다.
- 시설을 전부 최고 레벨로 빠르게 올리는 것이 항상 정답이 되지 않도록 유지비/기회비용을 둔다.
- 티켓 가격 정책은 최소 2개 이상의 유효 전략이 존재하도록 대량 시뮬레이션으로 검증한다.

## 6. 시설

### 6.1 ScoutingCenter

```text
효과
- SP 주간 생산량
- SP 저장 한도
```

Scout 확률 자체는 임의로 올리지 않는다. Scout Pool 확률 계약은 05절을 유지한다.

### 6.2 TrainingCenter

```text
효과
- DP 주간 생산량
- 필요하면 DP 저장 한도
```

CardTraining의 TrainingCeiling 계약을 우회하지 않는다.

### 6.3 RecoveryCenter

```text
효과
- 경기 후/휴식일 Condition 회복 Resolver 효율
```

부상 제거, 즉시 완전 회복 같은 하드 치트 효과 금지.

### 6.4 DataAnalysisCenter

```text
효과
- OpponentScoutingReport의 Confidence 개선
- Unknown → Estimated 전환 범위 일부 확대
```

상대의 실제 미공개 전술카드/숨은 RNG를 그대로 노출하지 않는다.

### 6.5 TacticLab

기존 06절 `전술 연구소`를 별도 중복 시스템으로 만들지 않는다.

```text
효과
- 안정/승부/전문 연구 비용 효율
- 연구 후보 접근성
- Signature 업적 추적 UI 보조
```

### 6.6 FanShop

```text
효과
- 관중 1인당 부대수익
- 소폭의 Popularity 유지 보조
```

능력치/경기 확률에는 직접 관여하지 않는다.

## 7. 구장 성장

구장 레벨은 단순 Money만으로 바로 최대치까지 올리는 구조를 피한다.

업그레이드 조건은 데이터 기반으로 구성한다.

```text
StadiumUpgradeRequirement
{
    RequiredLeagueGrade?
    MinimumFanBase?
    MinimumSeasonAttendance?
    MoneyCost
}
```

추천 원칙:

- 낮은 리그에서 무제한 증축 금지.
- 관중 수요가 없는 상태에서 과도하게 큰 구장은 유지비 부담이 된다.
- 승격과 팬 성장에 따라 자연스럽게 증축 목표가 열린다.

## 8. 주간/시즌 운영 플로우

```text
주 시작
→ 시설 생산(SP/DP)
→ 스태프/시설 유지비 반영
→ 일정 진행
→ 홈경기마다 Attendance/Revenue 계산
→ 경기 결과로 Popularity/Momentum 갱신
→ 주 종료 재무 요약
```

시즌 종료:

```text
정규시즌/포스트시즌 결과
→ FanBase 장기 변화
→ 승격/강등 반영
→ 다음 시즌 시설 상한/구장 조건 갱신
→ SeasonFinanceSummary 확정
```

## 9. UI/UX

UI는 기존 프로젝트 UI 공통 셸/네비게이션/폰트/카드 문법이 있으면 반드시 재사용한다.

### 9.1 구단 경영 메인

한 화면에서 다음을 읽을 수 있어야 한다.

```text
상단
  Money / SP / DP
  현재 리그

좌측
  구장 레벨/수용인원
  최근 평균 관중
  평균 점유율

중앙
  시설 6종 카드/타일
  레벨 / 다음 효과 / 업그레이드 비용

우측
  FanBase
  Popularity
  최근 관중 추세

하단
  이번 주 수입/지출
  시즌 누계
```

### 9.2 홈경기 결과 요약

경기 종료 화면 또는 구단 경영 화면에서:

```text
관중 12,345 / 15,000
점유율 82.3%
티켓 수익
부대 수익
운영비
순수익
팬/인기도 변화 이유
```

수치는 예시이며 실제 포맷은 프로젝트 Money 스케일에 맞춘다.

### 9.3 ImageGen 사용 조건

UI Toolkit으로 레이아웃을 먼저 만든다.

ImageGen은 다음 경우에만 사용한다.

- 구장/시설 화면의 배경 일러스트가 필요할 때
- 시설 타입별 비주얼 아이콘/패널 장식이 기존 에셋으로 부족할 때
- 프야매 감성의 2D 야구 경영 UI 분위기를 맞추기 위한 비기능성 아트가 필요할 때

금지:

- 버튼 텍스트/수치가 이미지에 구워진 UI
- 엔트리브 원본 UI/일러스트의 직접 복제
- 기능 로직을 이미지로 대체

## 10. Save / Persistence

플레이어 구단 Save에 포함:

```text
ClubOperationState
StadiumState
FacilityState[]
TicketPolicy
CurrentSeasonFinanceSummary
필요한 최근 관중 히스토리
```

Definition/Balance 데이터는 Save에 복제하지 않고 Stable ID/버전으로 참조한다.

AI 구단에 플레이어용 `ClubOperationState`를 강제로 만들지 않는다. AI 경제가 필요해지는 후속 기능 전까지는 별도 단순 AI 운영 Profile을 사용할 수 있다.

## 11. 구현 단계

### Stage 0 — Repository Audit

Agent A:
- 기존 `ManagerEconomyState`, Money 처리, 주간 Tick, 경기 종료 보상 경로 조사.

Agent B:
- 시설/코치/구장/팬 관련 기존 타입과 TODO 검색.

Agent C:
- Save Adapter/RuntimeState/Manager Mode Scene 경로 조사.

산출물:
- 재사용 타입 목록
- 새 타입이 정말 필요한 목록
- Money 단위/평균 수입·지출 기준

Gate:
- 중복 모델을 만들지 않는 계약 확정.

### Stage 1 — Core Contract

Agent Core:
- `ClubOperationState`, Stadium/Facility/Balance Definition.
- Unity 비의존.

Agent Test:
- 생성/검증/불변성 테스트.

### Stage 2 — Simulation Economy

Agent Economy:
- Attendance Resolver
- HomeGameFinance Resolver
- Fan/Popularity Resolver
- Weekly Facility Production

Agent Test:
- 결정론/경계값/수익 보존 테스트.

### Stage 3 — Existing System Integration

병렬 가능:

Agent ScoutFacility:
- ScoutingCenter → 기존 SP 생산 경로.

Agent TrainingFacility:
- TrainingCenter → DP 생산 경로.

Agent RecoveryFacility:
- 12절 Condition API 확정 후 RecoveryCenter 연결.

Agent AnalysisFacility:
- 10절 ScoutingReport API 확정 후 DataAnalysisCenter 연결.

Agent TacticFacility:
- 기존 전술 연구소와 TacticLab 통합.

### Stage 4 — Runtime/Persistence

- Manager Mode 주간 진행에 연결.
- 홈경기 종료 시 수익 반영.
- Save/Load.
- 재로드 시 중복 수익 지급 금지.

### Stage 5 — UI

- UI Toolkit ViewModel → View 순서.
- 필요한 경우 ImageGen을 비기능성 에셋 생성에 사용.
- 게임 진행을 막지 않는 빈 상태/최대 레벨/자금 부족 상태 제공.

### Stage 6 — Balance Validation

대량 시즌 시뮬레이션:

- Rookie~Galaxy 리그별 수익/비용 분포
- 시설 투자 회수 기간
- 티켓 정책별 기대값
- Money 인플레이션
- SP/DP 생산량이 Scout/CardTraining 루프를 붕괴시키지 않는지

### Stage 7 — Final Gate

- 실제 Manager Mode 진입 → 주간 진행 → 홈경기 → 수익 → 시설 업그레이드 → Save → Load E2E 통과.
- AI/Career에 Owned Economy 유출 없음.
- Core/Simulation Unity 참조 없음.
- 문서/테스트/코드가 동일한 Balance Definition을 소비.

## 12. 멀티 에이전트 분할

```text
Agent A  Repository/Economy Audit
Agent B  Core State + Balance Definitions
Agent C  Attendance/Fan/Finance Simulation
Agent D  Facilities + 05/10/12/06 Integration
Agent E  Persistence + Runtime Flow
Agent F  UI Toolkit + ImageGen Assets(optional)
Agent G  Rule/Determinism/Statistical/E2E Tests
Agent H  Independent Review / Cross-document Audit
```

A가 계약을 확정한 뒤 B/C는 병렬 가능.
D는 대상 API 계약이 확정된 뒤 부분 병렬.
UI는 ViewModel 계약 이후 시작.
G는 Stage 1부터 각 Lane과 병행한다.

## 13. 완료 기준

- 홈경기 관중/수익이 실제 Manager Mode Money에 반영된다.
- FanBase/Popularity가 경기·시즌 결과에 따라 변화한다.
- Stadium Capacity가 관중 상한으로 작동한다.
- 티켓 정책에 실제 trade-off가 존재한다.
- 시설 6종의 효과가 기존 시스템 API를 통해서만 적용된다.
