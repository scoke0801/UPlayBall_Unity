# 11. 코칭 스태프와 프런트 전문 인력

> 상태: 신규 정본 기획안 / Codex 구현 기준

## 0. 목적

05절은 Money의 사용처로 `코치`를, DP 획득처로 `코치`를 언급하지만 코칭 스태프의 Definition, 계약, 배치, 효과, AI 대응, UI가 없다.

이 문서는 코칭 스태프를 **능력치 직접 버프 카드가 아닌, 기존 운영 시스템의 효율과 정보 품질을 조정하는 영속 인력**으로 정의한다.

핵심 목표:

```text
Money
→ 스태프 영입/계약/급여
→ 훈련·회복·분석 운영 효율
→ 장기적인 구단 운영 선택
```

핵심 원칙:

1. 선수 BaseStat 직접 +N 금지.
2. TeamColor/Edition/Tactic과 중복되는 능력치 버프 시스템으로 만들지 않는다.
3. 플레이어 구단은 Money로 스태프를 관리한다.
4. AI 구단/선수 커리어 모드 구단도 동일한 Simulation 효과 Profile을 가져 공정성을 유지하되, 플레이어용 Owned Economy를 복제하지 않는다.
5. 스태프 이름/정체성은 가상 데이터만 사용한다.
6. 밸런스는 Definition/Table로 데이터화한다.

---

## 1. 역할

초기 정식 역할은 5종으로 제한한다.

```text
StaffRole
  HittingCoach
  PitchingCoach
  DevelopmentCoach
  ConditioningCoach
  ScoutingDirector
```

기능이 명확하지 않은 수석코치/단장/트레이너 등은 최초 구현에서 추가하지 않는다.

후속 확장은 역할 슬롯을 늘리는 것이 아니라 `SpecialtyTag`로 우선 해결한다.

---

## 2. 데이터 모델

기존 Staff/Coach 타입이 존재하면 우선 재사용한다.

```text
StaffDefinition
{
    StaffId
    FictionalName
    StaffRole Role

    int QualityTier
    StaffSpecialtyTag[] Specialties
    StaffPhilosophyTag[] PhilosophyTags

    SalaryBand
    ContractPreference
}
```

```text
StaffContractState
{
    StaffId
    TeamSeasonKey
    RemainingSeasons
    Salary
    MoraleOrSatisfaction?   // 기존 동등 시스템이 있을 때만
}
```

```text
TeamStaffAssignmentState
{
    HittingCoachId?
    PitchingCoachId?
    DevelopmentCoachId?
    ConditioningCoachId?
    ScoutingDirectorId?
}
```

Simulation은 계약 객체를 직접 읽지 않고 아래 Profile로 수렴시키는 것을 권장한다.

```text
TeamStaffEffectProfile
{
    HittingTrainingEfficiency
    PitchingTrainingEfficiency
    DevelopmentPointEfficiency
    ConditionRecoveryEfficiency
    ScoutingConfidenceModifier
}
```

이 Profile은 플레이어/AI 모두 동일한 Consumer API가 읽는다.

## 3. 스태프 효과

### 3.1 HittingCoach

허용:

- 타자 CardTraining에서 특정 프로그램의 DP 효율 보조
- 타자 훈련 프로그램 추천/Preview 품질

금지:

- 경기 중 Contact/Power 직접 +N
- TeamColor처럼 로스터 전체 능력치 버프

### 3.2 PitchingCoach

허용:

- 투수 CardTraining의 DP 효율 보조
- 투구 훈련 프로그램 추천/Preview 품질

금지:

- 경기 중 Velocity/Control 직접 +N

### 3.3 DevelopmentCoach

허용:

- 09절 TrainingCenter 생산 DP의 사용 효율 또는 CardTraining 비용 효율
- TrainingCeiling까지 남은 성장 여지 분석

절대 TrainingCeiling을 초과시키지 않는다.

### 3.4 ConditioningCoach

허용:

- 12절 Base Condition 회복 Resolver의 회복 효율 Modifier
- 연투/연속 출장 후 회복 보조

금지:

- 부상 자동 제거
- 경기 직전 Condition 강제 MAX

### 3.5 ScoutingDirector

허용:

- 10절 OpponentScoutingReport Confidence 보조
- 스카우트 UI의 후보 풀 정보 설명 품질

주의:

05절 ScoutRoller의 Cost/Edition 확률을 몰래 바꾸지 않는다.
확률 가중이 필요해지는 후속 기획이 없다면 Scout 결과 확률에 관여하지 않는다.

## 4. Specialty / Philosophy

스태프를 단순 Quality 숫자 하나로만 만들지 않되 시스템 폭증을 피한다.

예:

```text
StaffSpecialtyTag
  PowerTraining
  ContactTraining
  SpeedTraining
  ControlTraining
  BreakingTraining
  StarterCare
  BullpenRecovery
  VeteranManagement
  YoungPlayerDevelopment
  DataAnalysis
```

Specialty는 **효율의 방향**을 바꾸며 새로운 Stat Layer를 만들지 않는다.

예:

```text
DevelopmentCoach(Quality 4, YoungPlayerDevelopment)
→ 저Cost/성장 여지 큰 카드 훈련 DP 효율 소폭 우대
```

정확 수치는 Balance Table.

---

## 5. 스태프 시장과 계약

### 5.1 시장

초기 구현은 다음 구조로 제한한다.

```text
Offseason Staff Market
Midseason Replacement Pool
```

오프시즌에 주 후보 풀이 갱신된다.
중도 교체는 가능하지만 잔여 급여/위약금 등의 기회비용을 데이터화할 수 있다.

### 5.2 계약

```text
StaffOffer
{
    StaffId
    Salary
    ContractYears
}
```

계약 기간은 기존 시즌/계약 인프라가 있으면 재사용한다.

선수 계약과 스태프 계약은 별도 타입으로 유지한다.

### 5.3 급여

Money의 지속 지출처.

- 시즌/주간 급여 지급 시점은 기존 경제 Tick에 맞춘다.
- Save/Load 재실행 시 중복 급여 차감 금지.
- 스태프 최고 등급을 전부 고용하는 것이 모든 리그에서 최적이 되지 않도록 비용 곡선을 둔다.

---

## 6. AI 구단 / 선수 커리어 모드 경계

AI 구단에 플레이어와 동일한 Staff Market/계약 경제를 반드시 시뮬레이션할 필요는 없다.

대신 공정한 Simulation 입력을 위해:

```text
AiStaffProfileResolver
input:
  LeagueGrade
  ManagerQuality
  TeamSeasonClubState
  DeterministicSeed

output:
  TeamStaffEffectProfile
```

을 사용할 수 있다.

원칙:

- AI에 `StaffContractState`/Money 소비를 강제로 만들지 않는다.
- 선수 커리어 모드 플레이어는 스태프를 직접 관리하지 않는다.
- 선수 커리어 모드의 소속 구단은 AI Staff Effect Profile을 통해 동일한 Condition/분석/훈련 경로를 사용할 수 있다.
- 구단주 모드 플레이어 구단만 실제 고용/급여/교체를 관리한다.

---

## 7. Club DNA와의 관계

Club DNA와 Staff는 서로 다른 소유 단위다.

```text
Club DNA = 구단의 장기 운영/경기 성향
Staff    = 현재 계약된 인력
```

Staff Philosophy가 `TeamSeasonClubState`의 시즌 변화에 작은 가중을 줄 수는 있으나 즉시 DNA를 덮어쓰지 않는다.

초기 구현에서는 DNA 직접 변화 연결을 선택 기능으로 두고, 핵심 Gate에서 제외해도 된다.

## 8. UI/UX

### 8.1 스태프 화면

```text
상단
  구단 Money / 시즌 인건비

좌측
  현재 5개 역할 슬롯

중앙
  선택 스태프 상세
  Quality / Specialty / Philosophy
  현재 효과
  계약 기간 / 급여

우측
  후보 시장
  필터: 역할 / Quality / 급여
```

### 8.2 효과 표현

`타격 +5`처럼 오해되는 표현을 피한다.

좋은 예:

```text
타자 훈련 DP 효율 +8%
회복 효율 +6%
상대 분석 신뢰도 소폭 상승
```

정확한 수치는 실제 Balance에 맞춘다.

### 8.3 계약 팝업

```text
스태프 이름
역할/등급/특기
계약 기간
급여
예상 시즌 총비용
현재 스태프와 비교
[계약]
```

### 8.4 ImageGen

필요 시:

- 가상 코치/스태프 초상화
- 역할별 실루엣/오피스 배경
- 기존 UI 카드 프레임과 어울리는 비기능성 장식

스태프 초상화를 생성할 경우 팀 로고/실제 인물과 유사한 요소를 넣지 않는다.

텍스트/수치는 UI Toolkit으로 렌더링한다.

## 9. Save / Content

Definition:

```text

StaffBalanceTable
```

Save:

```text
StaffContractState[]
TeamStaffAssignmentState
```

AI/Career는 필요하면 파생 `TeamStaffEffectProfile`만 Runtime에 유지하고 플레이어 소유 계약을 저장하지 않는다.

## 10. 콘텐츠 생성

실제 인물 이름을 사용하지 않는다.

Codex는 먼저 다음을 조사한다.

- 기존 가상 이름 생성기/Name Pool
- Staff/Manager 이름 시스템
- Stable ID 생성 정책

재사용 가능하면 같은 이름 정책을 사용한다.

새 카탈로그가 필요하면 Offline/Editor에서 Stable ID를 가진 가상 StaffDefinition을 Bake하는 방식을 우선한다.

Runtime에서 매 Load마다 랜덤 StaffId를 재생성하지 않는다.

## 11. 구현 단계

### Stage 0 — Audit

Agent A:
- Coach/Staff/Manager/Contract 타입 전수 조사.

Agent B:
- CardTraining/Condition/Scouting API 조사.

Agent C:
- Manager Economy weekly/season payment 경로 조사.

Gate:
- Staff 효과의 Consumer API 확정.

### Stage 1 — Core Definition

Agent Core:
- StaffDefinition
- StaffContractState
- Assignment
- EffectProfile
- BalanceTable

Agent Content:
- Stable Staff Catalog 전략.

### Stage 2 — Effect Resolver

Agent Effect:
- `StaffEffectProfileResolver`
- Specialty/Quality 합성
- Clamp

Agent Test:
- BaseStat 직접 수정 경로가 없는지 테스트.

### Stage 3 — Market / Contract / Economy

Agent Market:
- Staff Market
- Offer/Contract/Replacement
- Salary Tick

Agent Persistence:
- Save/Load
- 중복 차감 방지

Stage 2와 3은 Core 계약 후 병렬 가능.

### Stage 4 — Consumer Integration

병렬 Lane:

```text
Hitting/Pitching/Development → CardTraining
Conditioning                 → 12 Condition Recovery
ScoutingDirector             → 10 OpponentScoutingReport
```

각 Lane은 기존 Resolver에 Modifier를 전달할 뿐 자체 Stat 계산을 만들지 않는다.

### Stage 5 — AI/Career Parity

- AiStaffProfileResolver
- 선수 커리어 구단에 Owner Economy 유출 없이 EffectProfile 적용
- 동일 입력 결정론

### Stage 6 — UI

- Staff Office 화면
- Market/Compare/Contract Popup
- 필요 시 ImageGen 초상화/배경

### Stage 7 — Balance

대량 시즌 검증:

- Staff 비용 대비 DP/Condition/Intel 가치
- 최고 Quality 독점이 필수 전략이 되지 않는지
- AI vs Player 평균 효과 격차
- Money 인플레이션/적자율

### Stage 8 — Final Gate

```text
오프시즌 시장
→ 스태프 계약
→ 급여 반영
→ 해당 시스템 효율 변화
→ 시즌 진행
→ 교체/재계약
→ Save/Load
```

E2E 통과.

## 13. 완료 기준

- 5개 역할의 Definition/계약/배치가 존재한다.
- 플레이어 구단에서 Money로 계약/급여가 실제 처리된다.
- Staff가 BaseStat을 직접 수정하지 않는다.
- TrainingCeiling을 우회하지 않는다.
- ScoutRoller 확률을 몰래 수정하지 않는다.
- Conditioning 효과가 공통 Condition API를 통해서만 적용된다.
- Opponent Intel 효과가 Confidence API를 통해서만 적용된다.
- AI/Career에 Owned Staff Economy가 유출되지 않는다.
- Save/Load 후 계약 기간/급여/배치가 정확히 복원된다.
- 장기 경제/효율 검증에서 단일 최고 조합만 강제되지 않는다.

## 14. 2026-09-05 구현·검증 상태

### Core / Simulation

- 역할을 HittingCoach, PitchingCoach, DevelopmentCoach, ConditioningCoach,
  ScoutingDirector 5개로 고정하고 `StaffDefinition`, 계약·배치 State, 효과 Profile, 결정론적 Market과
  AI Profile Resolver를 구현했다.
- 급여·역할별 효과·Quality curve·Market/AI profile 계수는 `OwnerExpansionBalance.json`의 Staff
  표에서 저작하고 구단주 전용 Balance에만 합성한다.
- Hitting/Pitching/Development 효과는 CardTraining 효율과 TrainingCeiling 경계에서만 소비한다.
  Conditioning과 Scouting은 각각 공통 Recovery/Intel Context modifier만 제공한다. BaseStat과
  ScoutRoller Edition 확률은 변경하지 않는다.

### Runtime / Persistence / UI

- 플레이어 구단은 `OwnerModeManager`의 Staff Market에서 Money로 계약하며 연간 급여 settlement는
  season receipt로 한 번만 차감된다. AI와 선수 커리어에는 계약 경제·Owned Staff State를 넣지 않고
  결정론적 Effect Profile만 허용한다.
- 시즌 종료 transaction은 남은 연봉을 한 번 정산한 뒤 계약의 RemainingSeason을 감소시키고 만료
  슬롯을 해제한다. Save/Load 뒤 같은 시즌 정산이 반복되지 않으며 다음 시즌에 새 receipt 경계를 쓴다.
- `ManagerModeCoordinator.TrainOwnedCard`와 `OwnerModeManager`의 기존 CardTraining command가
  Hitting/Pitching Coach와 DevelopmentCoach의 `StaffTrainingEfficiency`를 한 번만 적용한다.
  Production E2E는 실제 소유 카드의 DP 비용 감소와 TrainingCeiling 준수를 함께 검증한다.
- Save schema 4는 Stable Staff/Contract ID, 역할 배치, 기간, 급여, 마지막 지급 시즌을 복원한다.
- `UI_Scene_OwnerStaffOffice`는 공용 uGUI Shell에서 5개 역할, Quality, Specialty, Philosophy,
  효율 설명, 급여·기간과 Market 계약 Action을 표시한다. 능력치 직접 버프로 오해되는 문구는 쓰지
  않는다. 가상 인물 이름을 사용하며 별도 초상화 ImageGen은 사용하지 않았다.

### Test / Balance

- 중복 배치, 역할 불일치, 계약 비용·급여 중복, 만료, TrainingCeiling, Scout 확률 불변과 Save
  round-trip을 headless test로 검증했다. Production E2E에는 Staff 계약 뒤 기존 CardTraining
  경로의 효율 적용 회귀가 포함된다.
- 장기 급여/홈 매출 비율은 평균 Market 5인 6.41%, 최고 Quality 5인 25.74%로 측정됐다. 비용 차이는
  유의미하지만 최고 인력 일변도 여부는 실제 여러 시즌의 선수 육성 선택까지 포함해 계속 관찰한다.
- 시즌 전환 Runtime/Persistence는 구현했고 관련 Owner E2E 5/0, Persistence 6/0, Staff 16/0을
  통과했다. 최신 통합 전 Unity 대상 실행은 39/39 통과했으나 최신 통합본의 시즌 전환 전체 UI 흐름,
  Unity Test Runner와 Player Build는 사용자 지시에 따라 생략했으므로 **부분 완료**다.
